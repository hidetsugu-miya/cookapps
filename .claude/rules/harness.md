# The Claude Code harness

## Where things are

### Look in `.claude/` for what guards a change

Hooks are in `.claude/hooks/`, which is tracked, and they are wired in `.claude/settings.local.json`, which is not; worktrees use the main checkout's settings, so the hooks that run are the main checkout's.
`guard-public.sh` stops forbidden public words (`file` looks at the checkout the file belongs to, so a file of the worktree is checked there, and passes a file of another repository; `tree` and `log` look at the checkout of the directory they run in), `post-edit.sh` checks an edited file for forbidden public words (`guard-public.sh file`), runs rustfmt on an edited `src-tauri/**/*.rs`, and runs `tsc --noEmit` on the project (`ts` or `e2e`) of an edited `.ts` file under `ts/` or `e2e/`, or `wdio.conf.ts`, all in the checkout the edited file belongs to, not in `CLAUDE_PROJECT_DIR` (skipped when `node_modules` has no `tsc`, and for a file of another repository), `guard-e2e.sh` (the CI and E2E records) and `guard-review.sh` protect the records (`guard-review.sh` stops every command that names `record-review` or `.claude/reviews` unless it is release-verifier's; `range-check.sh` is the one other writer of the pass record, and its command names neither, #932), and `pre-git.sh` checks the records of CI, E2E and review before a push (`run-ci.sh` and `run-e2e.sh` write the first two) for the HEAD of the checkout the command runs in (the `cwd` of the hook input, moved by a leading `cd DIR &&` or `cd DIR;` and by the place of `git -C`), not of `CLAUDE_PROJECT_DIR`, while the records are read from the main checkout, and runs `check-guard-e2e.sh` when the pushed range touches `guard-e2e.sh`, `hook-log.sh` or that script, `check-pre-git.sh` when it touches `pre-git.sh`, `hook-log.sh`, that script, `check-ci.sh`, `check-e2e.sh` or `release-only-diff.sh`, `check-range-check.sh` when it touches `range-check.sh`, `record-review.sh`, that script, `check-ci.sh` or `check-e2e.sh`, and `plan-release-test.py` when it touches `plan-release*.py`, `nightly-limit.sh`, `use-worktree.sh`, `handover.sh` or `post-gh.sh` (`testing.md`). Every hook that `settings.local.json` wires (`guard-e2e.sh`, `guard-review.sh`, `post-edit.sh`, `post-gh.sh`, `pre-git.sh`, `session-start.sh`) sources `hook-log.sh` and, once it knows the run is its business (a call that ends early with exit 0 is not logged, and reads no clock), appends at its exit its name, start time, duration and exit code to `logs/hooks-{YYYY-MM-DD}.log` of the main checkout (`logs/` is gitignored; #260), and `pre-git.sh` adds one line for each `gate` with its name, duration and exit code, so that a slow hook can be traced afterwards. The log holds no command, path or file content, and a log that cannot be written changes neither the hook's decision nor its exit code. `TSUNAGIAI_HOOK_LOG_DIR` replaces the directory, and the self-tests set it to a temporary one. `session-start.sh` runs `npm ci` when `node_modules` is missing, and `post-gh.sh` tells the session to go on with `issue-plan` after `gh issue create` and the removal of `needs:owner`, and after `gh pr merge` runs `plan-release.py release` and, when it succeeds, tells the session to see through the release of a `follow_up` (watch its `release` run, then comment on the issues), to look at the runs of a `tag_due` and tag by hand only when the workflow left no run, and to prepare the Release PR when changes wait (`issues.md`).
`.claude/skills/` holds `improvement-proposal` (a session only: file refactoring and harness improvements, and UI/UX ones, as issues), `issue-plan` (an issue, its place in the order, and the parent issue of a feature), `ship` (in a night run, file one improvement of its own first; implement the issues in the order of the plan, up to 10 points a night, on one branch with one pull request, and prepare the Release PR; in a night run, post the new releases to X; `/ship` and 「次を進めて」) and `readme-product` (the README as a product page, and its photos).
`.claude/agents/` holds the reviewers (`code-reviewer`, `performance-reviewer`, `security-reviewer`), `release-verifier`, `release-planner`, and the three scouts of `improvement-proposal`, `ux-scout`, `refactor-scout` and `harness-scout` (`refactor-scout` and `harness-scout` also run in the night run of `ship`).
The nightly run (`issues.md`) is `.claude/tools/nightly.sh ship` at 00:30, with its own lock (`.claude/nightly/ship.lock`) and log (`.claude/nightly/ship-{date}.log`, deleted after 30 days). The job at 22:00 that ran `improvement-proposal` is retired (#485).
In that run, `ship` launches `refactor-scout` and `harness-scout` before its reorder, keeps at most one candidate that the AI may decide, of `point:3` or less, as an issue (`proposal`, with a section `AI が決めたこと`), and implements it first on the run's branch, in the run's pull request (`issues.md`). A session does not take that step.
Around the run it uses four more tools. `nightly-limit.sh` answers whether a run may start a new issue (`issue {n} --taken {numbers}`: the 10 points of a night, the deadline, the unit rule of a point:8 issue or of the `solo` parts of one, and the label `session`, whose issue a night run does not start; the four only in a night run, which has `NIGHTLY_DEADLINE_EPOCH`), `handover.sh` reads and writes the hand-over Discussion (`read` the last hand-over and the owner's replies since, `history {n}` the last n hand-overs and the `<!-- ai -->` writes since the oldest of them, which `harness-scout` reads), `dependabot-issues.sh` makes an issue for each open Dependabot pull request that has none (`issues.md`; `DEPENDABOT_ISSUES_DRY_RUN=1` prints without making), and `use-worktree.sh` takes the one worktree for a branch and gives it back (`worktree.md`).
`range-check.sh {passed HEAD} {list file}` checks a fix of non-blocking findings made after a pass, in a session or a night run, with no release-verifier launch (#932): the tree is clean, the passed commit has a pass record or is `origin/main` or its ancestor (a commit of main passed this gate when it entered main), and is an ancestor of HEAD, HEAD has passing CI and E2E records, and every changed path appears in the list of the fixed findings (each line holds a `path` or `path:line`); when all hold it writes HEAD's pass record through `record-review.sh`, otherwise it prints the reason or the paths outside the list and exits 1 (`review.md`). `check-range-check.sh` is its self-test, on a temporary repository and temporary records.
`x-post.sh` (its logic is in `x-post.py`) posts to X, and `ship` runs it once a day in the night run only, in step 2 after the release has been watched (`issues.md`). `auth` is the one authorization that the owner runs at the screen, once: it reads the Client ID and the Client Secret from the secret item, prints the URL of the consent page (and opens it), and writes the refresh token into the keychain. `check {file}` checks a text and writes the reason to stderr when it fails: at most 280 characters by X's weighting, no word that `guard-public.sh text` forbids, one URL that is the Releases page, no `@` mention (exit 0 passes, exit 1 fails). `send {file} {tag}` takes the last version of the text as `{tag}` (`v0.{minor}.{patch}`) and refuses it, before any network, when it is not newer than the tag in `.claude/x-posted`, or when a night run (`NIGHTLY_DEADLINE_EPOCH` set) finds that file missing. Then it runs the same check, takes a new access token with the refresh token in the keychain service `jp.mysis.tsunagiai.x` (account `refresh_token`), writes the new refresh token back there (and reads it again to check it), and only then posts (when it cannot write it, it does not post, and exits 2), and writes `{tag}` into `.claude/x-posted` itself (exit 0 prints the URL of the post, exit 1 is a refused tag or a failed check, exit 2 is a failed read of the secret item or the keychain, a failed token or post, or a post that was made while `.claude/x-posted` could not be written, which the run does not retry; exit 3 is a post that got no answer, so it may have been made: `{tag}` is written, the post is not sent again, and the owner checks X). The first post, while the file is missing, is the owner's, run by hand in a terminal; a session never sends. The text is written from `git show {last kept tag}:CHANGELOG.md`, because the night run only fetches and the `CHANGELOG.md` of the main checkout lacks the new versions. The script holds no secret: the Client ID and the Client Secret are only in the secret item, which `op` reads with a service account (read only is enough: the service account cannot write the vault, and the refresh token, which X replaces at every use, is therefore not kept there), and the refresh token is only in the keychain, never in a file, a log or the output. `.claude/x-post.json` of the main checkout (gitignored, with the rest of `.claude/`) names the keychain service that holds the service account token, the vault and the item, as `op_token_keychain_service`, `op_vault` and `op_item`; their values are private (`publishing.md`), so no tracked file holds them, and without that file `auth` and `send` exit 2 before any network. The item holds the Client ID in the field labelled `クライアントID` and the Client Secret in the field labelled `クライアントシークレット`. The service account token is read from the keychain, from the item whose account is the login user (`getpass.getuser()`), and goes to `op` in its environment only. `.claude/x-posted` of the main checkout (gitignored, with the rest of `.claude/`) holds the tag last posted, one line `v0.{minor}.{patch}`; only `send` writes it, after a post or a post that got no answer.
`plan-release.py` prints `next --mine` (`start` is the queue in the order of the plan, `waits_for_session` lists the issues with the label `session`, which the night run leaves out of `start`, and `stop` says when nothing may start; `waits_for_session` and `stop` are for the night run, which has `NIGHTLY_DEADLINE_EPOCH`), `release` (what waits for the owner's merge, the Release PR, the version it writes in `CHANGELOG.md`, `urgent`, and `tag_due`, the tag of a merged Release PR that does not exist yet: `release.yml` makes it at the merge, so `tag_due` shows only until it has, or when the workflow did not, and `follow_up`, the merged Release PR whose tag exists and whose issues are not yet commented, until the agent that did so marks it, `issues.md`) and `close` (closes the parents whose sub-issues are all released), and `split {file}` (the split of `issue-plan` step 3: it checks everything, the `solo` of the parts of a `point:8` issue and the `session` of the parts of an issue with `session` included, then makes the parts as sub-issues of the large issue, with their comments, with `gh` as an argument list, and comments their numbers on the large issue, which stays open as their parent; with no parts it only labels the issue `whole`; `issues.md`).
`plan-release.py snapshot` closes the open issues of other authors as not planned, before it prints the order (`issues.md`, "Trust only the owner's issues and comments").
`plan-release.py apply` leaves out the closed and the fixed issues of a plan, and saves the plan it accepted, as `.claude/plan.json` of the main checkout (gitignored, written through a temporary file), which `next` reads.
`clean-target.sh` keeps `src-tauri/target` from growing with the old output of the app itself.
It runs every day at 21:00 and needs no argument.
In the main checkout and in every worktree, it deletes what has nothing modified in the last 24 hours, or nothing newer than the `src-tauri/Cargo.toml` of that checkout, and nothing while cargo or rustc runs: the entries of `incremental/` in each profile, and the entries of the app itself (`tsunagiai-*`, `tsunagiai_lib-*`, `libtsunagiai_lib-*`, `tsunagiai_mcp-*`, and the same names with `cookapps` for the output built before the rename) in `deps/`, `build/` and `.fingerprint/`.
The second condition removes the output built before the last change of `Cargo.toml` without waiting 24 hours, because the version is fixed at `0.0.0` and `Cargo.toml` changes only with the dependencies or features, which change the hash of the app's own output, and nothing uses the old one again.
The output of dependency crates stays.
It also deletes the files of `.claude/ci/` and `.claude/e2e/` (the records and logs of `run-ci.sh` and `run-e2e.sh`) in the main checkout that are older than 30 days; `check-ci.sh` and `check-e2e.sh` read only the record of HEAD.
It deletes the `logs/hooks-*.log` of the main checkout that are older than 30 days.
It prints the size of each target before and after, and appends it to `.claude/nightly/clean-target-{date}.log` (deleted after 30 days).
The launchd plists are `~/Library/LaunchAgents/jp.mysis.tsunagiai.ship.plist` (00:30, running `nightly.sh ship`, label `jp.mysis.tsunagiai.ship`) and `jp.mysis.tsunagiai.clean-target.plist` (21:00, running `clean-target.sh`), outside the repository. After a change to a plist, `launchctl bootout gui/$(id -u)/{label}` and `launchctl bootstrap gui/$(id -u) {plist}` load it again.
A gate that stops a command is a finding about the change, not an obstacle to route around.

```text
Good: pre-git.sh refuses the push -> read its message, and fix what it names
Bad:  pre-git.sh refuses the push -> write the record by hand
```

### Build graphify only in the main checkout, after the merge

`graphify-out/` is gitignored, so a graph built in a worktree is lost with it, and a branch's graph does not describe main.

```text
Good: merge -> fast-forward the main checkout -> update the graph there
Bad:  build the graph in a worktree and delete the worktree
```

### Write the agents and the rules in their own language

`.claude/rules/` is written in English. `.claude/agents/`, `.claude/hooks/`, `.claude/rules/`, `.claude/skills/` and `.claude/tools/` are tracked and edited on a worktree branch, and the rest of `.claude/`, with the two gitignored rules and `.claude/hooks/public-words`, is edited in the main checkout (`worktree.md`).
The hooks and the gates run the main checkout's copy of `.claude/hooks/` and `.claude/tools/`, so a change to either takes effect after the merge and the fast-forward of the main checkout.

```text
Good: change .claude/rules/review.md on the branch, and .claude/rules/machines.md in the main checkout
Bad:  change .claude/rules/machines.md in the worktree
```
