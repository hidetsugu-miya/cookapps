# The Claude Code harness

## Where things are

### Look in `.claude/` for what guards a change

Hooks are in `.claude/hooks/`, which is tracked, and they are wired in `.claude/settings.local.json`, which is not; worktrees use the main checkout's settings, so the hooks that run are the main checkout's.
`guard-public.sh` stops forbidden public words (`file` looks at the checkout the file belongs to, so a file of the worktree is checked there, and passes a file of another repository; `tree` and `log` look at the checkout of the directory they run in), `post-edit.sh` checks an edited file for forbidden public words (`guard-public.sh file`), runs rustfmt on an edited `src-tauri/**/*.rs`, and runs `tsc --noEmit` on the project (`ts` or `e2e`) of an edited `.ts` file under `ts/` or `e2e/`, or `wdio.conf.ts`, all in the checkout the edited file belongs to, not in `CLAUDE_PROJECT_DIR` (skipped when `node_modules` has no `tsc`, and for a file of another repository), `guard-e2e.sh` (the CI and E2E records) and `guard-review.sh` protect the records (`guard-review.sh` stops every command that names `record-review` or `.claude/reviews` unless it is release-verifier's; `range-check.sh` is the one other writer of the pass record, and its command names neither, #932), and `pre-git.sh` checks the records of CI, E2E and review before a push (`run-ci.sh` and `run-e2e.sh` write the first two) for the HEAD of the checkout the command runs in (the `cwd` of the hook input, moved by a leading `cd DIR &&` or `cd DIR;` and by the place of `git -C`), not of `CLAUDE_PROJECT_DIR`, while the records are read from the main checkout, and runs `check-guard-e2e.sh` when the pushed range touches `guard-e2e.sh`, `hook-log.sh` or that script, `check-pre-git.sh` when it touches `pre-git.sh`, `hook-log.sh`, that script, `check-ci.sh`, `check-e2e.sh` or `release-only-diff.sh`, `check-range-check.sh` when it touches `range-check.sh`, `record-review.sh`, that script, `check-ci.sh` or `check-e2e.sh`, and `plan-release-test.py` when it touches `plan-release*.py`, `nightly-limit.sh`, `use-worktree.sh`, `handover.sh` or `post-gh.sh` (`testing.md`). Every hook that `settings.local.json` wires (`guard-e2e.sh`, `guard-review.sh`, `post-edit.sh`, `post-gh.sh`, `pre-git.sh`, `session-start.sh`) sources `hook-log.sh` and, once it knows the run is its business (a call that ends early with exit 0 is not logged, and reads no clock), appends at its exit its name, start time, duration and exit code to `logs/hooks-{YYYY-MM-DD}.log` of the main checkout (`logs/` is gitignored; #260), and `pre-git.sh` adds one line for each `gate` with its name, duration and exit code, so that a slow hook can be traced afterwards. The log holds no command, path or file content, and a log that cannot be written changes neither the hook's decision nor its exit code. `TSUNAGIAI_HOOK_LOG_DIR` replaces the directory, and the self-tests set it to a temporary one. `session-start.sh` runs `npm ci` when `node_modules` is missing, and `post-gh.sh` tells the session to go on with steps 1 to 4 of `issue-plan` after `gh issue create` and the removal of `needs:owner` (the reorder is left to the start of `ship` and to the owner's request), and after `gh pr merge` runs `plan-release.py release` and, when it succeeds, tells the session to see through the release of a `follow_up` (watch its `release` run, then comment on the issues), to look at the runs of a `tag_due` and tag by hand only when the workflow left no run, and to prepare the Release PR when changes wait (`.claude/skills/release/SKILL.md`).
`.claude/skills/` holds `improvement-proposal` (a session only: file refactoring and harness improvements, and UI/UX ones, as issues), `issue-plan` (an issue, its place in the order, and the parent issue of a feature), `ship` (in a night run, file one improvement of its own first; implement the issues in the order of the plan, up to 10 points a night, on one branch with one pull request, and prepare the Release PR (in a night run, also merge it and see the release through, and then post the new releases to X; at the owner's instruction, 2026-11-19); `/ship` and 「次を進めて」), `release` (prepare the Release PR, merge it in a night run, and see a merged one through: the tag, the release run and the comments on the issues; steps 2 and 8 of `ship`, and the session that `post-gh.sh` tells) and `readme-product` (the README as a product page, and its photos).
`.claude/agents/` holds the reviewers (`code-reviewer`, `performance-reviewer`, `security-reviewer`), `release-verifier`, `release-planner`, and the three scouts of `improvement-proposal`, `ux-scout`, `refactor-scout` and `harness-scout` (`harness-scout` also runs in the night run of `ship`, and `refactor-scout` does not (at the owner's instruction, 2026-11-18; #934: in four nights the four improvements filed were all `harness-scout`'s, and none of `refactor-scout`'s was taken)).
The nightly run (`ship` skill, "Rules") is `.claude/tools/nightly.sh ship` at 00:30, with its own lock (`.claude/nightly/ship.lock`) and log (`.claude/nightly/ship-{date}.log`, deleted after 30 days). The job at 22:00 that ran `improvement-proposal` is retired (#485).
In that run, `ship` launches `harness-scout` before its reorder, keeps at most one candidate that the AI may decide, of `point:3` or less, as an issue (`proposal`, with a section `AI が決めたこと`), and implements it first on the run's branch, in the run's pull request (`ship` skill, "Rules"). A session does not take that step.
Around the run it uses four more tools. `nightly-limit.sh` answers whether a run may start a new issue (`issue {n} --taken {numbers}`: the 10 points of a night, the deadline, the unit rule of a point:8 issue or of the `solo` parts of one, and the label `session`, whose issue a night run does not start; the four only in a night run, which has `NIGHTLY_DEADLINE_EPOCH`), `handover.sh` reads and writes the hand-over Discussion (`read` the last hand-over and the owner's replies since, `history {n}` the last n hand-overs and the `<!-- ai -->` writes since the oldest of them, which `harness-scout` reads), `dependabot-issues.sh` makes an issue for each open Dependabot pull request that has none (`ship` skill, "Rules"; `DEPENDABOT_ISSUES_DRY_RUN=1` prints without making), and `use-worktree.sh` makes the worktree of a branch and, with `--park`, removes it (`worktree.md`).
`range-check.sh {passed HEAD} {list file}` checks a fix of non-blocking findings made after a pass, in a session or a night run, with no release-verifier launch (#932): the tree is clean, the passed commit has a pass record or is `origin/main` or its ancestor (a commit of main passed this gate when it entered main), and is an ancestor of HEAD, HEAD has passing CI and E2E records, and every changed path appears in the list of the fixed findings (each line holds a `path` or `path:line`); when all hold it writes HEAD's pass record through `record-review.sh`, otherwise it prints the reason or the paths outside the list and exits 1 (`review.md`). `check-range-check.sh` is its self-test, on a temporary repository and temporary records.
`x-post.sh` (its logic is in `x-post.py`) posts the new releases to X, and only the night run of `ship` uses it (`.claude/skills/ship/SKILL.md`, "Rules", "Post the releases to X with `x-post.sh`").
`plan-release.py` prints `next --mine` (`start` is the queue in the order of the plan, `waits_for_session` lists the issues with the label `session`, which the night run leaves out of `start`, and `stop` says when nothing may start; `waits_for_session` and `stop` are for the night run, which has `NIGHTLY_DEADLINE_EPOCH`), `release` (what waits for the merge of the Release PR, the Release PR, the version it writes in `CHANGELOG.md`, `urgent`, and `tag_due`, the tag of a merged Release PR that does not exist yet: `release.yml` makes it at the merge, so `tag_due` shows only until it has, or when the workflow did not, and `follow_up`, the merged Release PR whose tag exists and whose issues are not yet commented, until the agent that did so marks it, `.claude/skills/release/SKILL.md`) and `close` (closes the parents whose sub-issues are all released), and `split {file}` (the split of `issue-plan` step 3: it checks everything, the `solo` of the parts of a `point:8` issue and the `session` of the parts of an issue with `session` included, then makes the parts as sub-issues of the large issue, with their comments, with `gh` as an argument list, and comments their numbers on the large issue, which stays open as their parent; with no parts it only labels the issue `whole`; `issue-plan` skill, "Rules").
`plan-release.py snapshot` closes the open issues of other authors as not planned, before it prints the order (`issues.md`, "Trust only the owner's issues and comments").
`plan-release.py apply` leaves out the closed and the fixed issues of a plan, and saves the plan it accepted, as `.claude/plan.json` of the main checkout (gitignored, written through a temporary file with a name of its own, so that two sessions applying at once do not share one), which `next` reads.
`plan-release.py claim --worktree {path} {n}...` claims issues for a worktree (`.claude/claims/{n}/owner` of the main checkout, gitignored with the rest of `.claude/`), and `next` lists the issues that a worktree which still exists has claimed in `claimed`, outside `start` (`worktree.md`, "Claim an issue before you start it"; #1008).
`clean-target.sh` keeps `src-tauri/target` from growing with the old output of the app itself, and runs every day at 21:00 with no argument; what it deletes is in the comment at the top of the script.
The launchd plists are `~/Library/LaunchAgents/jp.mysis.tsunagiai.ship.plist` (00:30, running `nightly.sh ship`, label `jp.mysis.tsunagiai.ship`) and `jp.mysis.tsunagiai.clean-target.plist` (21:00, running `clean-target.sh`), outside the repository. After a change to a plist, `launchctl bootout gui/$(id -u)/{label}` and `launchctl bootstrap gui/$(id -u) {plist}` load it again.
A gate that stops a command is a finding about the change, not an obstacle to route around.

```text
Good: pre-git.sh refuses the push -> read its message, and fix what it names
Bad:  pre-git.sh refuses the push -> write the record by hand
```

### Build graphify only in the main checkout, after the merge

`graphify-out/` is gitignored, so a graph built in a worktree is lost with it, and a branch's graph does not describe main.

```text
Good: merge -> fast-forward the main checkout -> update the graph there
Bad:  build the graph in a worktree and delete the worktree
```

### Write the agents and the rules in English

`.claude/agents/` and `.claude/rules/` are written in English (at the owner's instruction, 2026-11-18; #953). `.claude/agents/`, `.claude/hooks/`, `.claude/rules/`, `.claude/skills/` and `.claude/tools/` are tracked and edited on a worktree branch, and the rest of `.claude/`, with the two gitignored rules and `.claude/hooks/public-words`, is edited in the main checkout (`worktree.md`).
The hooks and the gates run the main checkout's copy of `.claude/hooks/` and `.claude/tools/`, so a change to either takes effect after the merge and the fast-forward of the main checkout.

```text
Good: change .claude/rules/review.md on the branch, and .claude/rules/machines.md in the main checkout
Bad:  change .claude/rules/machines.md in the worktree
```
