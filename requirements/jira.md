# Jira requirements

## J-1 Jira connection

The settings screen has a card 「Jira 接続」 in the tab 「開発」 (the tab `orca`, A-3), the last of its five cards, under the card of the PCs with the server (A-37). The card holds the connection to Jira Cloud: the site's URL, the email address and the API token, a save, and a test of the connection. Rust is `src-tauri/src/jira.rs` (the commands `jira_settings`, `jira_save` and `jira_test`, #868), built like the Todoist connection of T-1 (the token in the keychain, the commands in the service's module); the frontend is `ts/jira-settings.ts`. The site's URL, the authentication, what is saved and where, and what is sent are in `requirements/constraints.md`, "Jira". Only Atlassian Cloud is supported: there is no switch for a self-hosted Jira.

The card is in the shape of the other integrations' cards: the header row (the logo `.logo.orca`, the name 「Jira 接続」 and the `?` hint `#jira-help`, `aria-label` 「Jira 接続の説明」), under it one row (`#jira-items`, the common row of the settings, `itemRow`) with the name 「Jira」, a line and a state label, and the form (`#jira-form`, `.card-add`) with the three fields, 「保存」 (`.text-btn.primary`) and 「接続を試す」 (`#jira-test`, `.text-btn`). The fields are `#jira-site` (`aria-label` and placeholder 「サイトの URL」), `#jira-email` (「メールアドレス」) and `#jira-token` (`type="password"`, 「API トークン」); a placeholder only names its field. The card shows no text about what to type besides the `?` hint (`.claude/rules/frontend.md`).

The row. The line under 「Jira」 is the saved site's URL, and the state label is 「保存済み」 (green) when a site and a token are saved, and 「未設定」 (gray) otherwise. After a test it is 「接続できました」 (green) with the user that Jira answered (the display name and the email address joined by 「 ・ 」, the part Jira did not give is left out) in the line, or 「接続できません」 (orange) after a failed one. A read or a save puts the saved state back.

Reading. `jira_settings` is called each time the tab is shown, and the site and the email address go into the fields; it asks Jira nothing (it reads the file and the keychain) and never returns the token, only `hasToken`. The token field is emptied. Only the latest read draws, and a read that began before a save does not. A failed read writes its message to the log (A-28) and leaves the card as it was.

Saving. 「保存」 (and Enter in a field) calls `jira_save` with `site`, `email` and `token` as typed, and the token field is emptied at once. Rust refuses a site that is not an Atlassian Cloud one, an email address that cannot be a credential and a token with characters a header cannot hold, and a save with no token typed when none is stored; each refusal is a Japanese message shown on a card (A-28), and the form is kept as it was. An empty token keeps the stored one; an empty email address saves a connection that uses a Bearer token. The answer (`site` as Rust normalized it, `email`, `hasToken`) is drawn.

Trying. 「接続を試す」 calls `jira_test` with the same three values, with an empty token meaning the stored one, and saves nothing. Rust sends the credential where Atlassian takes it: with an email address, to the site; with none, through `api.atlassian.com` (the Cloud ID of the site is read first, with no credential), because a scoped token is refused on the site's own URL (`requirements/constraints.md`, "Jira"). The button is disabled until the call ends. A success draws the state and the user; a failure shows its message on a card (A-28), draws 「接続できません」 and enables the button again.

The `?` hint says that only Atlassian Cloud sites (`https://{名前}.atlassian.net`) can be connected, that an email address means Basic authentication with the account's API token and none means Bearer authentication with a scoped token (sent through `api.atlassian.com`), that an empty token in 「保存」 keeps the saved one, that 「接続を試す」 asks Jira who the credential belongs to with the values of the form and saves nothing, and, in its foot, that the token is kept in the keychain and never shown.

Unit tests (`cargo test`, `jira.rs`) cover the site's URL (the accepted forms and their origin, and the refused ones: other hosts, a host that only ends or contains `atlassian.net`, user info, a port, `http`, a dotted or empty name), the email address and the token, the header (Bearer without an email address, Basic with one), the reading of Jira's answer (the user, no email address, an answer that is not JSON, 401 and 403, other statuses with the body cut short), the file (no file, a round trip, a broken file, no token in it), the Cloud ID (the accepted form and what cannot go into a URL), the choice of the base URL (the site for Basic, the gateway with the Cloud ID for Bearer, a site that gives no Cloud ID), and, against local `TcpListener`s that stand for the site and the gateway, the request that is sent for each of the two ways (the path and the Basic or Bearer header, and that the request for the Cloud ID has no credential), a rejected credential, a redirect that is not followed in either call and a host that cannot be reached.
The E2E spec `settings.e2e.ts` ("settings: Jira connection (the 開発 tab, J-1)") covers the tab's name, that the settings are read only when the tab is shown, the card's header, row and form, the states 「未設定」 and 「保存済み」, the arguments of `jira_save` (with an email address and without), a refused save (a card, the form kept), the arguments of `jira_test` (the form's values, an empty token), the button kept off while it waits, the state and the user after a success, a failed test (a card and 「接続できません」), a failed read (the log, no card) and the hint; `settings: tabs` covers the tab's label among the eleven, and the spec of the 開発 tab's cards covers the card's place, last of the five.

Why. The Jira integration (#867) needs a connection that the later parts read the tickets through, so the owner wants to put the site and the credential in once, on a card of their own, and know that they work before anything draws Jira (the owner's decision of 2026-11-19, #868: the card goes in the tab 「開発」, which is the tab 「Orca」 renamed so that it matches the sidebar's button; Atlassian Cloud only; the email address optional, for a scoped token).
