# Technical constraints

The constraints of one integration or one requirement, by area.
The constraints of the whole app (the OAuth flow, the scopes, the tokens and `accounts.json`) are in `AGENTS.md`, under "Technical constraints".
Read an area's section before you change a behavior it covers, and when a change makes a constraint different, change the section in the same pull request.

## Mail

- A mail is sent with `users.messages.send` (`mail_send.rs`; a new mail and a reply), which `gmail.modify` is enough for: Google's reference for the method lists `https://mail.google.com/`, `gmail.modify`, `gmail.compose` and `gmail.send` as the scopes it accepts (https://developers.google.com/workspace/gmail/api/reference/rest/v1/users.messages/send, read 2026-11-14), so no new scope is asked for and no account must log in again. The request is `{raw, threadId}`, with `raw` the RFC 5322 message in base64url (https://developers.google.com/workspace/gmail/api/guides/sending). A reply is put in its thread only when `threadId` is given, `In-Reply-To` and `References` are set as RFC 2822 says and the subject matches (https://developers.google.com/workspace/gmail/api/guides/threads), so Rust reads the Message-ID and References of the thread's last message that is not a draft (`threads.get`, `format=metadata`) and refuses a Message-ID that is not one well-formed `<id>`. Before anything is sent Rust checks each recipient as one plain ASCII `addr` or `Name <addr>`, and refuses a CR, LF or other control character in a recipient, the subject or the sender, so that no header can be injected. A subject or a name that is not ASCII is sent as RFC 2047 encoded-words, and the plain-text body as UTF-8 base64 with CRLF line ends. A reply written in the rich editor (M-10, `markdown` true) goes as `multipart/alternative`, its Markdown as the `text/plain` part and the HTML that `markdown_to_html` makes from it as the `text/html` part: that HTML is made from the parsed Markdown, a raw HTML tag in the text is written out as text, except that the empty paragraph the editor writes as `<br />` (also `<br/>` and `<br>`) alone in its block is the fixed `<p><br></p>` in the HTML and is left out of the `text/plain` part (the text/plain part is the Markdown as it is otherwise), so that no other tag and no script comes out of it, and only `http`, `https` and `mailto` links keep their anchor, so the editor's text cannot put a tag, a script or a `javascript:` link into the mail. A rate-limited or 401 send is sent again (Gmail did not process it), and an answer that is lost is not, so a mail is never sent twice by the app. A mail with files (M-12) goes as `multipart/mixed` through the same `raw` of the same call: the files are base64 in MIME lines, never saved, and their total is limited to 25 MB (`MAX_ATTACHMENTS`, Gmail's own limit), which is about 33.4 MB of message before the `raw` encoding. The file names go into `filename` and `filename*` (RFC 2231) only after the encoding that leaves no control or non-ASCII character in a header line, and the files are read only from the open dialog (`mail_attach_pick`), never from a path the page gives. Gmail's documentation gives 35 MB (36,700,160 bytes, the discovery document's `maxSize` of `messages.send`) for a message sent as a media upload, and says nothing of the size of the JSON `raw` request, which is what this app sends: a send of files near 25 MB is not measured. Nothing of the mail (recipients, subject, body, files) is kept or logged.
- The threads the mail screen has opened (M-2) are held in memory only (`HeldThreads`, `gmail/held.rs`), by account and thread ID, as `thread` last answered them, and are in no file and no log of the app. They take at most 64 MB of text (`HELD_THREAD_BYTES`), the oldest dropped first: a body carries its inlined images as data: URIs, up to 27 MB a thread, so the cap holds at least two threads of the largest size and several hundred of ordinary mail, and it is the cap of the two image caches (`INLINE_CACHE_BYTES`, `IMAGE_CACHE_BYTES`). The 64 MB is on top of those caches: an inlined image is held both in the held body and in `InlineCache`. `tsunagiai-mcp` holds none.

## Calendar

- An event is created (C-5) with `events.insert` of the Calendar API on a calendar whose `accessRole` is `owner`, with the scope `calendar.events.owned`, which `SCOPE` of `auth.rs` asks for with `calendar.readonly`. `calendar.events` is not asked for, because it reaches the calendars that others shared with the account too, and `calendar.app.created` is not, because it can write only to a calendar that the app made.
- An event is rewritten (C-7) with `events.patch` and deleted with `events.delete`, with the same scope, on an event that the user organized (`organizer.self`) on a calendar whose `accessRole` is `owner`. The event is read first with `events.get` (`fields` `organizer(self),hangoutLink,recurrence,attendees`: the entries of the guests, so that a guest who stays is sent back as Google holds it, and `recurrence`, which only the series of a repeating event has), because the screen's mark is not trusted. The ID is that of one occurrence of a repeating event (the week is read with `singleEvents`), so the series is never touched: an event that has `recurrence` is refused. The tools of Claude (C-6) send nothing that invites an address the event does not have: they read the same `events.get` and hand the form of the screen the values instead, and the owner's 「保存」 sends it. `sendUpdates` is `all` when the event has guests (for a patch also when it has them after the change), else `none`; Google then sends the update or the cancellation to the guests. `events.delete` answers 204 with no body, which `send_json` of `gmail.rs` reads as `null`.
- An account that logged in before the scope was added keeps its old grant: its events are read as before, and the new scope is asked for at its next login. A create with the old grant is refused by Google with a 403 (`ACCESS_TOKEN_SCOPE_INSUFFICIENT`), which the screen shows as a request to log in again.

## Slack

- The Slack compose screen (S-1) sends its things to do one by one with `chat.postMessage` (`chat:write`, under the owner's own name), each only on the press of "投稿" (which Claude Code may ask the screen to press with the tool `slack_compose_post`, S-23: the owner allows each call in the terminal, and the screen sends them the same way), and a card that continues the thread of an earlier one is a reply with `thread_ts` set to the `ts` that the earlier call answered: no other method and no new scope. The calls are not one transaction, so a failure leaves the earlier posts in Slack; the screen marks them posted and never sends them again. `@here`, `@channel` and `@everyone` become broadcast mentions (`<!here>`, `<!channel>`, `<!everyone>`) only in a text written in a card: one posted with "投稿" (`slack_post` with `written` true), where a text that Claude Code wrote in a card has had them made full-width (`slack::without_new_broadcasts`, S-4) unless the owner typed that text; the mail's content, also when Claude Code changed it, is sent escaped, as text, because it is untrusted. The destinations that Claude Code is offered (S-4) are those of the picker (the recent ones and the joined channels): no new method and no new scope.
- A Slack workspace may also have an App-Level Token (`xapp-`, scope `connections:write`, S-16), kept in the OS keychain (service `jp.mysis.tsunagiai.slack-app`, user name the workspace's `team_id`) and never shown or logged. With it the app keeps a WebSocket open to Slack's Socket Mode (`apps.connections.open`, then the `wss` address of slack.com it answers) for as long as the app runs, and reads the channels whose message events arrive; the list is still read on a timer (every 5 minutes while every workspace is connected, else every 2 minutes).
- The custom emoji of a Slack workspace (S-26) are read with `emoji.list` (`emoji:read`, an optional scope) when a thread or a channel's history has a reaction, or when the emoji picker of S-25 opens, kept in memory only for an hour (`TimelineCache`) and never saved; their images are fetched by `fetch_images` as the users' icons are, only from the hosts of `icon_host_ok`.
- A reaction of a Slack message is added or taken off (S-25) with `reactions.add` and `reactions.remove` (`reactions:write`, an optional scope) by the workspace's token, only when the user presses it, or chooses an emoji in the picker, in the thread or in a channel's history; the people who gave a reaction (`users`) are read for `mine` and kept in memory only.

- The app's identifier is `jp.mysis.tsunagiai` (`identifier` in `tauri.conf.json`, and `IDENTIFIER` in `identity.rs`, which a unit test keeps equal). It names the app config directory (`jp.mysis.tsunagiai`, from Tauri's `app_config_dir`) and the keychain services: `jp.mysis.tsunagiai` (the refresh tokens of the Gmail accounts, user name the account's address) and `jp.mysis.tsunagiai.claude`, `.database`, `.formation` (the app's secret key for the servers on the saved environments' PCs, user `client-key`, A-37), `.jira` (the Jira API token, user `api-token`, J-1), `.notion`, `.slack`, `.slack-app` and `.todoist`. The E2E build's identifier is `jp.mysis.tsunagiai.e2e`. The identifier before the rename was `jp.mysis.cookapps`, and the move from it is done by the app itself (#750):
  - The config directory: at each start, before anything reads the settings (the `setup` of the app, and `identity::config_dir` for `tsunagiai-mcp`, which builds the path itself), when `jp.mysis.tsunagiai` does not exist (not even empty) and `jp.mysis.cookapps` beside it does, the contents of the old folder are copied into it, folders and files, with their modes; an entry that is neither (a link to nothing, a socket) is skipped, so one of them does not stop the move of the rest. The copy is made in a folder beside the new one and renamed into place, so a failure leaves no half-filled new folder (the next start tries again; the failure is logged to the standard error and the app starts with an empty folder otherwise). The old folder is not deleted or changed. A folder of another identifier (the E2E build's) never takes the old one. Whichever of the app and `tsunagiai-mcp` starts first does the copy.
  - The keychain (`keychain.rs`, the one place every module reads, writes and deletes its secrets through): a read that finds no item under the new service reads the item with the same user name under the old service (`jp.mysis.cookapps`, `jp.mysis.cookapps.claude` and so on: the same name with the old identifier in place of the new), and when it finds one it writes the value under the new service and uses it. The old item is not deleted by a read. The old service is asked once for each item in a process (the answer "nothing there" is remembered), and one read of it at a time, so a permission prompt of the OS is not asked twice for the same item; the async callers of `auth.rs` read and delete off the async workers. A write goes to the new service only. A delete removes the item under the old service first and then under the new one (both run even when the first fails), because a delete that left the old item would let the next read copy it back, and a logout or a disconnect would not take effect. The app and `tsunagiai-mcp` are two processes, so a read that has copied the old item reads it once more, and when a delete took it meanwhile, deletes its copy and finds nothing. A secret is in no log, error text or `Debug`.
  - The tests: the read, the copy, the remembered answer, a delete that lands in the middle of a copy and the delete on a map instead of the keychain (`keychain.rs`), and the copy of the folder on temporary folders (`identity.rs`). No test touches the real keychain or the real config folder.

## Orca

- The connection to Orca's runtime (A-7; the history it was made for is retired) is made from Orca's own files, `orca-runtime.json` (this machine, over its unix socket) and `orca-environments.json` (a paired server, over a WebSocket with end-to-end encryption), in Orca's settings folder; they are read at each connect and never written, and no token or key from them is kept, logged or shown. It was written against Orca 1.4.248 and an Orca update can change it.
- A file pasted or dropped on an Orca terminal or in the pane of A-9 (A-10) is put in `.orca/drops/` of the worktree, under its own name (a name taken gets `name copy.ext`, `name copy 2.ext`, as Orca 1.4.253 does; a name with a path separator, a control or bidirectional formatting character, or over 255 bytes, is refused), through `files.stat`, `files.readDir`, `files.writeBase64Chunk`, `files.commitUpload` and `files.delete` of Orca's runtime (this machine's unix socket, a paired server's WebSocket), which are not a public interface. It was written against Orca 1.4.248 (the names and the typed text follow Orca 1.4.253), and an Orca update can change it. The file is held in memory only, and the window's own file drop is off (`dragDropEnabled` false) so that the page gets the dropped files.
- A plain terminal started from the plus of the Orca work pane (A-16) is made by Orca's CLI, `orca terminal create --worktree path:<path> --json` (`--environment=<name>` for a saved environment), run once, in a worktree of the list read just before, with an argument list and a timeout; its reply `result.terminal.handle` names the terminal. It was checked on Orca 1.4.250 (its help and its CLI source), and an Orca update can change it.
- A new worktree for the hand-over of A-9 is made by Orca's CLI, `orca worktree create --repo=id:<repository id> --name=<name> [--branch=<branch>] [--base-branch=<ref>] --no-parent --json` (`--environment=<name>` for a saved environment; `--branch` and `--base-branch` only when `orca_worktree_create` was given a branch or a base), run once, in the temporary folder, with an argument list and a timeout of 60 seconds; its reply `result.worktree.path` is the new worktree's absolute path. Just before, Rust checks that the environment is a saved one, that the repository id is a project of the list read just now (an `ssh:` host and an archived-only repository are not), and that the name, trimmed, is not empty, does not start with `-`, is not `.` or `..` and has no control character, `/` or `\`, and that the branch and the base, when given, are, trimmed (a blank one is none), a name git accepts as a ref (`git check-ref-format`: they do not start with `-`, hold no space, control character, zero-width, bidirectional or tag character (the ones `orca_handoff` takes out of a card) or `~ ^ : ? * [ \`, no `..` or `@{`, are not `@`, and have no component that is empty, starts with `.` or ends with `.lock`, nor a `/` or `.` at the end); nothing is made otherwise. The repository id is `OrcaProject.key` (`repoId` of `orca worktree ps`), so `--repo=id:` is used and not `--project`, which takes a project id or a display name. `--no-parent` is passed because the CLI otherwise records the context it can infer (`ORCA_TERMINAL_HANDLE` of the environment) as the parent. It was checked on Orca 1.4.255 by its help and its CLI source in `app.asar` (`handlers/worktree.js`, `worktree-project-target.js`) and by the shape of `orca worktree show --json`; the command itself was never run, so the exact reply of `worktree create` (`result.worktree.path`), its behavior on a saved environment, what it does with `--branch` when the branch already exists (reading the `app.asar` of Orca 1.4.256 suggests that it checks that branch out and makes no numbered new one; it was never run) and with `--base-branch`, the time it takes on a large repository and the answer of a repository whose setup policy is undecided (the CLI asks for `--setup`) were not checked, and an Orca update can change them.

A file saved before the rename has `cookapps-display-name` and `cookapps-screens` instead: they are read as the new keys are (the new key wins when both are there), and a save writes the new keys only. The folder `claude-plugin/` is a folder of its own, so that the config directory, which holds `client_secret.json` and the settings, is never the root Claude Code reads hooks, `.mcp.json` and agents from; it is never given to a call either (see the call of a skill below), and no `plugin.json` is written in it. The name is the folder's and is limited to a to z, 0 to 9 and `-` (at most 64 characters, no `--`, not starting or ending with `-`) before any path is made of it, so a name never points outside `claude-plugin/skills/`; a save goes through `write_atomic`. They are read, saved and deleted by `skill_list`, `skill_get`, `skill_save` and `skill_delete` (`skills.rs`, the commands of the app). That Claude Code ignores the two keys of つなぎAI's own was not checked. The tab 「スキル」 of the settings screen (A-32) reads the list each time it is shown and keeps a saved skill's name fixed (the folder); a new skill whose name is taken is stopped by the screen before `skill_save`, and `skill_save` takes `create` (true for a new skill) and refuses, in Japanese, a new skill whose `SKILL.md` exists, so that a list that was not read cannot make a new skill replace a saved one; without `create` it replaces the skill of that name.
  The tools of `tsunagiai-mcp` `skill_list`, `skill_get` and `skill_save` (A-32, #345) are the way Claude Code in the pane of the 「スキル」 tab reads and saves the skills: they call `skills::list_skills`, `skills::read_skill` and `skills::save_skill`, the functions of the commands above, so every check above holds for them, and `skill_save` takes `create` as the command does (false when left out). `skill_save` is `destructive_hint`, so the pane asks the owner each time, and it sends `changed` `skills` to the app (the screen bridge's `RULES.changes`, A-36), which makes the tab read the list and fill its form again. There is no tool that deletes. They are not offered with `--formation` or `--calendar`, and the texts they answer are quoted as data. A skill is also given to a pane of Claude Code (A-36): `claude_code_start` takes a `skill` (`{name, screen}`), and `skills::plugin_for` adds `--plugin-dir {a folder made for the call}` to the arguments of the launch script, for a name that it let through (valid, saved, and listing the screen of the pane in `tsunagiai-screens`); no screen passes one today (the pane of S-7 gives none, and `claude -p` is no longer called with a skill: `skill_call` and the prefix `/tsunagiai:{name} ` are gone), so this is the way back for a later issue. The call of S-4 is gone too. Claude Code reads everything in a plugin folder (the other skills, the `allowed-tools` or `hooks` of a `SKILL.md` placed by hand, `hooks/hooks.json` and `.mcp.json` of the plugin), which `--setting-sources user` does not stop, so the folder of the call is made new in the system's temporary directory (mode 0700, a random name), holds only `.claude-plugin/plugin.json` and `skills/{name}/SKILL.md`, the saved skill read (`parse`) and written again (`render`) so that only `name`, `description` and the keys `tsunagiai-*` remain, and is deleted when the process ends (`CallPlugin` is dropped with the pane's session), failed or not. A skill whose text has a shell command in it (`!` and a command in backquotes) is not refused: tried on 2026-11-15 with `claude -p` (the call that was) with Claude Code 2.1.325 and Haiku, with one skill whose body held such a command that would make a file, under `--tools ""` the command was not run (no file was made), and `claude -p` printed "Shell command permission check failed … Permission to use Bash has been denied." as its answer, exit code 0. Tried on 2026-11-15 with `claude -p` and Haiku, with a plugin of one skill: the command was run as a skill under those flags, with the rest of a multi-line input as its arguments, and the model followed the skill's instruction. The pane has not been tried with a skill. What Claude Code does goes to Anthropic with the skill's text, and the owner wrote it.
- The Claude Code panes (A-36) run `claude` in a pseudo terminal that the app opens (`portable-pty` 0.9.0: MIT, the crate of the WezTerm repository, 29.5k stars on that repository, 29M downloads, its `pty` folder committed to in 2026-09; checked on 2026-11-16). The child is started as an argument array (`/bin/sh {script}`, never a shell line built by the app) in `claude-code/` of the app config directory, as the leader of a session of its own, and nothing is written to its input but the keys typed in the pane. The script (`start.sh`, `start-with-tools.sh`, `start-auto.sh`) and `mcp.json` (`mcp-calendar.json` for `start-auto.sh`) in that folder are written by the app at each start in a fixed form from paths the app decided, and are replaced through `write_atomic`: no text of a mail, a message, a Todo or a summary is put in either file or in an argument (the one text an argument holds is the first instruction of a pane, after a `--` as one element of the list and never read by a shell: the orchestrator's, which Rust builds from the names of its projects, and the one that a screen gives, 1 to 20,000 characters with the hidden and control characters taken out, #976; the language server part of the Orca file pane gives the names of an environment, a project, a worktree, an ssh Host and a language, which are lines of a quote that the text calls data), and the one MCP server of `mcp.json` is `tsunagiai-mcp` next to the app's own executable (a development build has none unless `cargo build --bin tsunagiai-mcp` was run: the pane then says so). `--tools ''` takes the built-in tools off and `--strict-mcp-config` leaves the servers of every other file out, so Claude Code in the pane can use only the tools of `tsunagiai-mcp` (and the built-in tools of a screen that asks for them, the database screen), and the permission to use a tool of `tsunagiai-mcp` is asked in the terminal, except in the pane of the calendar screen (C-6, #1074): it runs with `--permission-mode auto` (Rust takes the mode as "manual" or "auto" only, and refuses "auto" with the built-in tools and for the orchestrator), so `mcp-calendar.json` starts `tsunagiai-mcp --calendar`, which offers the seven tools of the calendar screen only (`CALENDAR_TOOLS`, C-6), and no other tool that writes can run with no question. That the flags give exactly this in the interactive mode was not checked beyond what `claude --help` says; the pane was not run against a real `claude` in the tests, which use short commands. The child gets the environment of the app with the changes of A-4 (the key of the API key method is in its environment, in no argument, file, log line or error text), `TERM=xterm-256color` and `COLORTERM=truecolor`. What the terminal prints and the keys typed are not kept or logged by Rust and cross only the channel of the pane. A session is ended with its whole process group (SIGTERM, then SIGKILL after 2 seconds) when its pane is closed, when a pane of the same id starts, when the screen no longer takes its output, and when the app ends; a session whose process ended by itself is forgotten at once. At most the processes of the open panes run: no pool, no restart, and no process is kept for a pane that has been closed.

## The app's log and fonts

- The log of the app (A-28) is `app-log.jsonl` in the app config directory: a line of JSON for each entry (time, `error` / `warn` / `info`, the place, a text of at most 500 characters), written from Rust (`app_log::write`) and from the screen (`log_write`) and read by `log_read`; the 「ログ」 tab of the settings (A-3) shows it and opens its folder with `log_open_folder`, which Rust gives to the opener plugin as the config directory (the page gives no path, and no capability is added). Lines older than 30 days are dropped and the file is kept at 1 MiB or under, the newest lines staying. It holds no token, mail, message, terminal output or typed key: the callers do not pass them, and the module cuts the text, collapses line breaks and masks words shaped like a token. The screens write every failure to it (`ts/error-card.ts`, A-28) with the text that Rust answered for the failed command (or the page made for a refusal of its own, as 「スキル「…」はもうあります」), which may name the account or the file it was about but holds none of the above; a failure of a sync or a read is written and shows no card.
- The font (the family and the size) of each screen, of the editor, of the Orca work pane and of the whole app, and the family of the monospace text (A-20), is in `font-settings.json` in the app config directory; the family names to choose from are read from this Mac's fonts with CoreText (`CTFontManagerCopyAvailableFontFamilyNames`, through the `objc2-core-text` crate) at each start and kept in no file, and no font is loaded from outside.

## Notion

- Notion is read through Notion's MCP server (`https://mcp.notion.com/mcp`, `notion.rs`), not the REST API, because only the MCP lists the teamspaces and the favorites; only the settings tab (N-1) uses it yet. It is an interface for AI clients, not a public API for apps, and whether an app that is no AI client may use it is not documented (not checked). It was checked on 2026-11-10 against server version 1.2.0 (the prototype of #365), and its tools, arguments and replies can change; a reply is JSON wrapped in a string.
  - The app registers one public client by dynamic client registration (`/register`, `token_endpoint_auth_method` `none`, no client secret, redirect `http://127.0.0.1/`) the first time, and keeps its `client_id` in `notion-accounts.json` in the app config directory, because registering again leaves the earlier connections hanging. The same file lists the connected workspaces (id, name, and the user's name and email address from `notion-get-self`); it holds no token.
  - The login is PKCE S256 with a loopback redirect, served by the listener that Google's login uses (`auth.rs`). Notion takes any port on `127.0.0.1` for the registered redirect and the path must be the registered one (tried on 2026-11-14 by `GET /authorize`); the code is exchanged at `/token`, which also revokes (RFC 7009; a revoke of a made-up token answered 200).
  - The tokens are in the OS keychain, service `jp.mysis.tsunagiai.notion`, user name the workspace's id, as one JSON entry (access token, refresh token, expiry) so that a new pair replaces the old in one write. They are never shown, logged or kept in a file, and `tsunagiai-mcp` does not read them, so nothing else refreshes them. One token is one workspace, so each workspace is connected on its own.
  - The access token lasts 8 hours; it is refreshed 5 minutes before its end and when a call is refused with 401. The refresh token changes at every refresh and an old one used again ends the connection, so a workspace refreshes one at a time and the new pair is written to the keychain before the access token is used. A refresh answered `invalid_grant` (180 days after the first consent at the latest, or 30 days unused) deletes the keychain entry and leaves the workspace in the list with `reconnect` true; any other failure keeps the tokens.
  - A call is Streamable HTTP: `initialize`, the `notifications/initialized` notice, then `tools/call`; the reply is JSON or a server-sent event stream. The token holds the user's full rights (77 tools, deletion included), so `ALLOWED_TOOLS` in `notion.rs` is the only list of tools the app calls, and it holds `notion-get-self`, `notion-list-favorite-pages`, `notion-get-teams` and `notion-search` (a call of any other name is refused before anything is sent, and none of them writes). Notion's limit is 180 requests a minute (600 on Business and above); one call is three requests (`initialize`, the notice, the call), so at most 3 calls run at once (`MAX_PARALLEL_CALLS`). A rate limit (HTTP 429 with `Retry-After`, or an error with `rate_limited` and `retry_after_seconds` in the reply) is an error whose text names the seconds to wait (a minute when none are given).
  - The lists (`notion_favorites`, `notion_teamspaces`, `notion_teamspace_pages`; the replies are read by the pure functions of `notion/pages.rs`) answer `null` when the workspace needs a new connection, as the other commands do. The favorites are `notion-list-favorite-pages` (type, url, title, icon), read with `nextCursor` up to 20 replies; the teamspaces are `notion-get-teams` (id and name, 10 at most, no icon); the pages of a teamspace are `notion-search` with an empty query, `teamspace_id` and 50 results at most, with no way to read on, and `path` (the titles of the parents, joined by ` / `) is what builds the tree: a page hangs under the result whose own parents and title are its `path`, and one whose parent is not among the results is a root. The order is the search's, not the sidebar's. Notion gives no teamspace icon.
  - Not tried against a real login by this code, so a Notion update or the first real connection can show a difference: the `workspace_id` and `workspace_name` of the token reply, the shape of the text of `notion-get-self` (`user_of` reads `name` and `email` or `person.email`, at the top or under `user`), and the session id header of the reply to `initialize`. The lists were written from what #365 records of the replies of 2026-11-10, not from a reply itself: the wrapper of the list (a bare array, or an object whose list is under `results`, `favorites`, `pages`, `teams`), the name of the cursor argument (`cursor`) and of the page size (`page_size`), whether `path` holds the parents only (taken so) or the page's own title too, and where `rate_limited` sits in the error.

## Jira

- Only Jira Cloud is spoken to (J-1, #868; `jira.rs`): the site is `https://{name}.atlassian.net`, and `site_url` is the one place that accepts it. It takes a `https` URL whose host is one label of letters, digits and hyphens (not starting with a hyphen) plus `.atlassian.net`, with no user info and no port (443 is the default), keeps the origin and drops the path, query and fragment, and refuses everything else, so the token cannot be sent to another host whatever is typed. Self-hosted Jira (Server and Data Center) is out of scope.
- The communication goes to two hosts only, the site (`*.atlassian.net`, validated as above) and Atlassian's gateway `https://api.atlassian.com`, all with a timeout of 15 seconds and no redirect followed, so the credential never goes to another host; the `Authorization` header is marked sensitive. `api_base` (`jira.rs`) is the one function that chooses the base URL that a Jira REST path is put after, and the later parts of the Jira integration (#869 and on) call it, so a call of theirs goes where the credential is taken. The test of the connection is `GET {base}/rest/api/3/myself` (who the credential belongs to; it reads and changes nothing).
  - With an email address (Basic), the base is the site's origin.
  - With none (Bearer, a scoped token), the base is `https://api.atlassian.com/ex/jira/{cloudId}`. Atlassian refuses a scoped token on the site's own URL with 401 and says to use the gateway (checked on 2026-11-20 in "401 Unauthorized error when service account accesses Jira or Confluence API", `support.atlassian.com/atlassian-cloud/kb/401-unauthorized-error-when-service-account-accesses-jira-or-confluence-api/`, which gives `https://api.atlassian.com/ex/jira/<cloudId>/{api}` and `/rest/api/3/myself` as the check; and "Manage API tokens for service accounts", `support.atlassian.com/user-management/docs/manage-api-tokens-for-service-accounts/`, which says that Bearer or Basic authentication is used with the `api.atlassian.com` gateway, with the Bearer example `https://api.atlassian.com/ex/jira/{cloudId}/rest/api/3/project`). The Cloud ID is read from `GET {site}/_edge/tenant_info`, which answers `{"cloudId": "{uuid}"}` with no credential (tried on 2026-11-20 against a real Cloud site: 200 and that JSON; against a site that does not exist: 404 with HTML; the endpoint is not in Atlassian's two documents above, so it can change). That call is sent no `Authorization` header. The Cloud ID goes into the URL only when it is 1 to 64 letters, digits and hyphens (`cloud_id_of`).
- The authentication follows the email address: with one, `Authorization: Basic base64(email:token)` (an API token of an account); with none, `Authorization: Bearer {token}` (a scoped token). The email address is refused when it has no `@`, or holds a colon, a space or a control character; the token is refused when it holds anything but printable ASCII.
- The API token is in the OS keychain, service `jp.mysis.tsunagiai.jira`, user `api-token` (`keychain.rs`). It is written by `jira_save` only, never returned to the screen (`jira_settings` answers `hasToken`), never written to a file, and in no log or error text. A save with an empty token keeps the stored one and is refused when none is stored; `jira_test` takes the token of the form, else the stored one, and saves nothing.
- Not checked: a call with a real credential. The two documents above were read and the tenant endpoint was tried without a credential, but no token was sent to Jira by the tests or by this change, so the answer of `/rest/api/3/myself` for a scoped token through the gateway, and for a Basic token on the site, is from the documents only (#868).
- The tests are the pure functions (the site's URL, the email address, the token, the header, the reading of an answer, the Cloud ID) and the calls against local `TcpListener`s that stand for the site and the gateway (`jira.rs`). No test calls Jira, touches the keychain or the real config folder.

## Database

- The script of a connection (#717, #718; `database/script.rs`; D-1) opens the way to the database, for instance a port forward through AWS Systems Manager that the owner writes with the `aws` command. The app starts no AWS tool itself and depends on no AWS crate (`aws-config` and `aws-sdk-ssm` were removed with `database/ssm.rs`). The script is the owner's own text, saved in `database-profiles.json` (a profile's `script`); it is run, never built from input of anyone else.
  - It is run as a child process with no shell: its body is written to a file of its own (mode 0700, in a folder of its own, `tsunagiai-script-{16 hex}`, made in the system's temporary folder and deleted when the script has ended) and that file is run, so the interpreter is the one of its first line (`#!/bin/sh` is put first when there is none). The folder is created with `create_dir` (never reused) and the file with `create_new`, and the file is closed before it is run; a run that fails with `ETXTBSY` (the file still open for writing in another thread that forked meanwhile) is tried again up to 5 times.
  - A GUI app does not have the PATH of a shell, so the script is run with the app's own PATH: a script that needs `aws` names its path (for instance `/opt/homebrew/bin/aws`). Not tried against a real AWS account by this code.
  - The port is the connection's own (its host and its port, D-1; the owner chooses it, the app picks none, #745). Before the script is run, the app tries a TCP connection to `{host}:{port}`; when something answers, the connection fails with 「{host}:{port} は、スクリプトを実行する前から使われています。…」 and the script is not run (no file is made), so a script never runs against a port that another process holds. The check and the script's own listening are not one step: another process may take the port between them, and the script then fails to listen, which shows as a script that is not ready (or ends) with its standard error. The port is the connection's own, so it is known before the check (the app no longer picks a free one): any other process on this machine can listen there first, as it could take a free port in the gap before. No code is added for it: a process that listens first makes the script fail to listen, which shows as above, and one that listens after the check and answers is the known limit below.
  - The script is ready when a TCP connection to `{host}:{TSUNAGIAI_PORT}` succeeds (a try every 100 ms, 500 ms each; `TSUNAGIAI_PORT` is the connection's port, the host is the connection's host; the same port is given as `COOKAPPS_PORT` too, the name before the rename, for a saved script that reads it). The probe connects and closes at once, so a port forward sees one connection that carries nothing. The wait is 2 minutes (`script::TIMING`).
  - Being ready proves only that something listens on `{host}:{TSUNAGIAI_PORT}`, not that it is the script's process: another process that starts listening there between the check of the port and the script's own listening is taken for the script, and MySQL is logged in to it with the password. The app does not check which process listens (no `lsof`, no pid of the listener); this is a known limit, like the gap between the check and the listening above.
  - The standard input is `/dev/null`. The standard output and the standard error are read to the end, line by line (text that is not UTF-8 with replacement characters; a line keeps its first 4,096 bytes and the rest of it is dropped up to its line feed), by one task; the standard error keeps the last 5 non-empty lines, each cut to 300 characters; the wait for the end of the two is 1 second after the script has ended, because a process that the script left behind may hold them open. While the script is awaited, each line of both, with its control characters and hidden characters (zero-width, bidirectional formatting and tag ones) taken out (a tab becomes a space) and cut to 300 characters, is given to the caller (`script::OnLine`; `database_connect` tells the screen with the event `database-script-output`, #1027, D-3); after the script is ready nothing is given, and the output is read and dropped, so that a script that stays up never waits for a pipe. The lines are shown on the screen only and go to no log and no file (a script may echo a secret).
  - The script runs in a process group of its own (`process_group(0)`, unix). Ending it sends SIGTERM to the group (`kill(-pgid)`, the crate `libc` 0.2, which tokio and the other dependencies already use; added as a direct dependency only for `kill`), waits 5 seconds for the first process, and sends SIGKILL to the group when it is still there; after the first process has gone, the group is sent SIGTERM again for what it left behind and SIGKILL after 5 seconds. The app's exit ends every script that is open, all together (`RunEvent::Exit` in `lib.rs`: the sessions, then the scripts). A kill of the app itself leaves the script running until it ends by itself. `tsunagiai-mcp` starts a script for `db_test` with a `Scripts` of its own: when it ends while a test waits, the runtime drops `supervise` before it ends the group, and `kill_on_drop` reaches the first process only, so a `Script` that is dropped while its group may still run (`done` not set) sends SIGKILL to the group (`Drop for Script`; it sends nothing after `supervise` has ended the group, because the group's id may be another process's by then).
  - A script that ended after it was ready closes the session on its next look (`Sessions::reap`, D-3): nothing is read at an interval for it. The monitoring task of a script (`supervise`) ends with the script, and a script that is gone from `Scripts` (a close, a delete of the connection) is ended with it.
- The MySQL session (#625, #631; `database/mysql.rs`) is opened with `sqlx` 0.9 (features `mysql`, `runtime-tokio` and `tls-rustls-aws-lc-rs`, no default features: no macros, no migrations, no other database), whose TLS is the rustls with `aws_lc_rs` that the app already has (`cargo tree -i native-tls`, `-i openssl` and `-i rsa` find nothing). The target is MySQL 5.7, 8.0 and 8.4 with `mysql_native_password` and `caching_sha2_password`.
  - The SSL mode is `Preferred` for a host that is the machine itself (`localhost`, a loopback address), with a script or without one: TLS when the server offers it, a plain connection otherwise. For every other host (over a network, with a script or without one) it is `Required` (with `Preferred` an attacker on the way could make the server look as if it had no TLS, and the password would go in plain text). In both modes the certificate is not verified (sqlx accepts any certificate; the owner's decision stays: it needs a CA bundle for each server, such as the one of RDS), so `Required` stops the downgrade and not a server that presents a certificate of its own. The time zone and the `sql_mode` are the server's: the defaults of sqlx (`time_zone='+00:00'`, `PIPES_AS_CONCAT`, `NO_ENGINE_SUBSTITUTION`) are turned off. The password of `caching_sha2_password` is sent through TLS, and the RSA path of sqlx (the feature `mysql-rsa` and the crate `rsa`) is not built in, so a server with no TLS that asks for that password is the error of D-2. Not tried against a real server by this code (only against a local fake of the protocol, `cargo test`): the TLS handshake and `caching_sha2_password` on MySQL 8.0 and 8.4.
  - No session is made read only (at the owner's decision, #861: every connection can be written to at any time): what the SQL tab runs is run with the rights of the connection's user and committed at once by the server's own autocommit, so a write is stopped only by those rights. The password never goes into a URL (the options are set field by field), a log or an error. The connection test (`database_test`) reads the saved password of the connection from the keychain only when the field is empty and the connection still has the user, the script, the host and the port of the saved one (otherwise it is refused, so that the saved password is never sent to another place), and the password goes to no screen. The keychain has no way to ask whether a password is saved without reading it (`keyring` 4 and its macOS store: `get_attributes` and `get_credential` both go through `find_generic_password`), so the list reads each saved password to show "保存済み".
  - A connection has 15 seconds from the first byte to the answer of the first query; it is not retried.
- The open connections (#632; `database/session.rs`) are kept in the app's memory, one session for each connection (`tauri::State`, `Sessions`), and reused until they are closed: by the menu's "切断", by a save or a delete of the connection, by a query that shows the stream broken or past 30 seconds, and by the app's exit (`RunEvent::Exit` in `lib.rs`: the sessions, then the scripts). Nothing is read at an interval: a session is read only by a press, so a connection that is gone from the list has no process left (a delete closes it first). Closing a session also closes its tunnel (`ssm::Tunnels::close`).
  - The databases are read from `information_schema.SCHEMATA` and the tables from `information_schema.TABLES`; the name of the database is a bound value (`?`), and every value of a query that comes from the screen is bound, never put in the SQL text. The columns are cast in the SQL (`CAST … AS CHAR` for names, `AS UNSIGNED` for the row estimate and the lengths) so that they decode on MySQL 5.7, 8.0 and 8.4 alike; not tried against a real server by this code.
  - The records of a table (#633, D-4; `database/records.rs`) are read on the same session as one page of ``SELECT * FROM `db`.`table` LIMIT ? OFFSET ?`` (a page is 100 rows, 101 are asked for). The names are the only part put in the SQL text, between backticks with a backtick inside doubled, and the limit and the offset are bound, which makes the statement a prepared one: its rows come in the binary protocol, which `sqlx` gives as the bytes of each value (read without a typed decoder, so that the types that need the crates `chrono`, `bigdecimal` or the `json` feature are not added) and `cell_of` turns into text. Every value of a page is held in memory for the page only, a text is cut to 200 characters, a binary value is kept as its length, and a read past 30 seconds closes the session (as every query there). The estimate of the rows is `information_schema.TABLES.TABLE_ROWS`, bound by the schema and the table, and is shown as an estimate; it is read with the page 0 only, and a later page is given the one the screen holds. The rows are turned into cells one by one as they come, borrowed from the row's buffer, and the 101st is only counted.
  - The structure of a table (#634, D-5; `database/structure.rs`) is read on the same session from `information_schema.COLUMNS` (the name, the type, whether NULL is allowed, the key, the default and the comment) and `information_schema.TABLES` (the engine and the collation), with the schema and the table as bound values (`?`), never put in the SQL text, and every column cast as above. Two small queries at every press of the tab, each under the 30 seconds of every query there; the indexes, the foreign keys and the triggers are not read. Not tried against a real server by this code.
  - The SQL tab (#635, D-6; `database/sql.rs`) runs the text of the user on the same session as one prepared statement, as it is (only the whitespace and the semicolons at its ends are cut), on a session that is not read only (D-2), so a statement that writes is run and committed at once, and its footer tells the rows MySQL says it affected. The database of the tree is chosen by a `USE` of its own with a quoted name (`records::quote_identifier`), never put in the user's text. The rows are limited to 1,000 and read as a stream that stops after the 1,001st, so the rest is never held; the time is limited by `max_execution_time` of 30 seconds (MySQL stops a SELECT itself) and by 35 seconds for the whole run, past which the connection and its script are ended (`KILL QUERY` is not used: it needs a second connection and the password kept in memory). Before each run `max_execution_time` and `sql_select_limit` are set, with the `USE`, in one round trip; after it, whatever the result (a `USE` that failed too), the two are put back and autocommit is turned on again (a `SET autocommit = 0` of the user's text does not outlive its run). Not tried against a real server by this code.
  - The write of the records tab (#863, D-4; `database/write.rs`, the command `database_apply`) runs the inserts, updates and deletes that the screen has gathered in one transaction on the same session (`BEGIN`, `COMMIT` when every statement has run, `ROLLBACK` for any failure or refusal), on a session that is not read only (D-2), so it is stopped only by the rights of the connection's user. The screen is not trusted for the shape of the table: Rust reads `information_schema.COLUMNS` and the unique indexes of `information_schema.STATISTICS` (`records::read_key`, the schema and the table bound, every column cast) in the same call and plans against them. The names are the only part put in the SQL text (between backticks, `records::quote_identifier`); every value, the key's too, is bound, as a number for an integer or BIT column and as text for the rest, with NULL (`None`) told from the empty text. An update and a delete find their row by the whole key (the primary key, else a unique key none of whose columns may be NULL) and end with `LIMIT 1`; the matched rows (`CLIENT_FOUND_ROWS`, set by sqlx) must be 1, or everything is rolled back, and a table with no key is refused for both. Binary columns are never written. The statements are not kept in sqlx's cache of prepared statements (`persistent(false)`). The time is the 30 seconds of every query, after which the connection is closed (the server ends the transaction) and the words say that a commit in flight may have gone through. The input is limited (64 characters for a name, 1,000,000 for a value, 1,000 changes, no control character but the line feed, the carriage return and the tab in a value). Not tried against a real server by this code; the statements, the plan and the refusals are pure functions under `cargo test`, and the run's stop and rollback rule is tested with a runner that answers by a list.
  - The row count of `information_schema.TABLES` is an estimate for InnoDB (and MySQL 8 may serve statistics up to a day old, `information_schema_stats_expiry`), so the screen names the column 行数（概算）.

## Updates

- Updates use `tauri-plugin-updater`. Pushing the annotated tag `v{version}`, or merging the Release PR (which makes that tag, `release.yml`), starts the `release` job, which makes `tsunagiai.app.tar.gz`, its `.sig` and `latest.json` (`scripts/make-latest-json.sh`) and puts them in a GitHub Release.
  The app reads `releases/latest/download/latest.json` (`plugins.updater.endpoints` in `tauri.conf.json`) and verifies the download with the public key `plugins.updater.pubkey`.
  `bundle.createUpdaterArtifacts` is not in `tauri.conf.json`; the `release` job passes it with `--config`, so a local build needs no signing key.
  The version is the tag's alone (at the owner's instruction, 2026-11-09; Discussion #293): `version` in `src-tauri/Cargo.toml` and `Cargo.lock` is fixed at `0.0.0` and `tauri.conf.json` has none, and the `release` job passes the version of the tag with `--config` too, which Info.plist, `app.package_info()` (U-2) and the updater's comparison take. A build without it (`tauri dev`, E2E) reports `0.0.0`, and `scripts/install-app.sh` passes the latest tag.
