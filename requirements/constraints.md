# Technical constraints

The constraints of one integration or one requirement, by area.
The constraints of the whole app (the OAuth flow, the scopes, the tokens and `accounts.json`) are in `AGENTS.md`, under "Technical constraints".
Read an area's section before you change a behavior it covers, and when a change makes a constraint different, change the section in the same pull request.

## Mail

- A mail is sent with `users.messages.send` (`mail_send.rs`; a new mail and a reply), which `gmail.modify` is enough for: Google's reference for the method lists `https://mail.google.com/`, `gmail.modify`, `gmail.compose` and `gmail.send` as the scopes it accepts (https://developers.google.com/workspace/gmail/api/reference/rest/v1/users.messages/send, read 2026-11-14), so no new scope is asked for and no account must log in again. The request is `{raw, threadId}`, with `raw` the RFC 5322 message in base64url (https://developers.google.com/workspace/gmail/api/guides/sending). A reply is put in its thread only when `threadId` is given, `In-Reply-To` and `References` are set as RFC 2822 says and the subject matches (https://developers.google.com/workspace/gmail/api/guides/threads), so Rust reads the Message-ID and References of the thread's last message that is not a draft (`threads.get`, `format=metadata`) and refuses a Message-ID that is not one well-formed `<id>`. Before anything is sent Rust checks each recipient as one plain ASCII `addr` or `Name <addr>`, and refuses a CR, LF or other control character in a recipient, the subject or the sender, so that no header can be injected. A subject or a name that is not ASCII is sent as RFC 2047 encoded-words, and the plain-text body as UTF-8 base64 with CRLF line ends. A reply written in the rich editor (M-10, `markdown` true) goes as `multipart/alternative`, its Markdown as the `text/plain` part and the HTML that `markdown_to_html` makes from it as the `text/html` part: that HTML is made from the parsed Markdown, a raw HTML tag in the text is written out as text, and only `http`, `https` and `mailto` links keep their anchor, so the editor's text cannot put a tag, a script or a `javascript:` link into the mail. A rate-limited or 401 send is sent again (Gmail did not process it), and an answer that is lost is not, so a mail is never sent twice by the app. Nothing of the mail (recipients, subject, body) is kept or logged.
- The threads the mail screen has opened (M-2) are held in memory only (`HeldThreads`, `gmail/held.rs`), by account and thread ID, as `thread` last answered them, and are in no file and no log of the app. They take at most 64 MB of text (`HELD_THREAD_BYTES`), the oldest dropped first: a body carries its inlined images as data: URIs, up to 27 MB a thread, so the cap holds at least two threads of the largest size and several hundred of ordinary mail, and it is the cap of the two image caches (`INLINE_CACHE_BYTES`, `IMAGE_CACHE_BYTES`). The 64 MB is on top of those caches: an inlined image is held both in the held body and in `InlineCache`. `cookapps-mcp` holds none.

## Slack

- The Slack compose screen (S-1) sends its things to do one by one with `chat.postMessage` (`chat:write`, under the owner's own name), each only on the press of "投稿" (or by the request of S-23, which sends them the same way from Rust, `slack::post_planned`), and a card that continues the thread of an earlier one is a reply with `thread_ts` set to the `ts` that the earlier call answered: no other method and no new scope. The calls are not one transaction, so a failure leaves the earlier posts in Slack; the screen marks them posted and never sends them again. `@here`, `@channel` and `@everyone` become broadcast mentions (`<!here>`, `<!channel>`, `<!everyone>`) only in a text written in a card: one the owner posts with "投稿" (`slack_post` with `written` true), or one posted by a request to Claude whose own words hold every such word of the text (`slack::post_decision`, S-23); the mail's content, also when Claude changed it, is sent escaped, as text, because it is untrusted. A Slack link in a request to Claude (S-23) is read as the link of the picker is, with `conversations.info` for the channel's name: no new method and no new scope.
- A Slack workspace may also have an App-Level Token (`xapp-`, scope `connections:write`, S-16), kept in the OS keychain (service `jp.mysis.cookapps.slack-app`, user name the workspace's `team_id`) and never shown or logged. With it the app keeps a WebSocket open to Slack's Socket Mode (`apps.connections.open`, then the `wss` address of slack.com it answers) for as long as the app runs, and reads the channels whose message events arrive; the list is still read on a timer (every 5 minutes while every workspace is connected, else every 2 minutes).
- The custom emoji of a Slack workspace (S-26) are read with `emoji.list` (`emoji:read`, an optional scope) when a thread or a channel's history has a reaction, or when the emoji picker of S-25 opens, kept in memory only for an hour (`TimelineCache`) and never saved; their images are fetched by `fetch_images` as the users' icons are, only from the hosts of `icon_host_ok`.
- A reaction of a Slack message is added or taken off (S-25) with `reactions.add` and `reactions.remove` (`reactions:write`, an optional scope) by the workspace's token, only when the user presses it, or chooses an emoji in the picker, in the thread or in a channel's history; the people who gave a reaction (`users`) are read for `mine` and kept in memory only.

The remote branches picked in the list of branches of the Orca screen (A-25, and A-9's ref and existing branch) are in `orca-branch-recent.json` there: for each pair of an Orca (`null` is this machine, else a saved environment's name) and a repository (`OrcaProject.key`), the last 5 branch names as Orca names them, the newest first, for at most 50 pairs (the pair picked from longest ago is dropped), written through a temporary file and a rename and read again at each write; a file that is missing, cannot be read or is not that shape remembers nothing. It holds names only, no time and no path. The method the Claude calls sign in with is in `claude-auth.json` there, and the Anthropic API key is in the OS keychain (service `jp.mysis.cookapps.claude`). The connection profiles of the database screen (#625; `database.rs`) are in `database-profiles.json` there: for each, an id made at the first save (16 random bytes in hex, never changed), the name, the user name, whether it goes through AWS Systems Manager, the AWS profile name, the region, the bastion's `Name` tag, the DB host and the DB port, written through `write_atomic`; a file that cannot be read is an error and a save never replaces it. The password of a profile is in the OS keychain (service `jp.mysis.cookapps.database`, user the profile's id), never in the file and never in the answer of a command (the screen is told only whether one is saved); an edit that leaves the password empty leaves the keychain as it is, and deleting a profile deletes its password first.

## Orca

- The connection to Orca's runtime (A-7; the history it was made for is retired) is made from Orca's own files, `orca-runtime.json` (this machine, over its unix socket) and `orca-environments.json` (a paired server, over a WebSocket with end-to-end encryption), in Orca's settings folder; they are read at each connect and never written, and no token or key from them is kept, logged or shown. - The SSH hosts come from `ssh.listEditableTargets` of Orca's runtime (the socket of A-7), which is not a public interface.
- A file pasted or dropped on an Orca terminal or in the pane of A-9 (A-10) is put in `.orca/drops/` of the worktree, under its own name (a name taken gets `name copy.ext`, `name copy 2.ext`, as Orca 1.4.253 does; a name with a path separator, a control or bidirectional formatting character, or over 255 bytes, is refused), through `files.stat`, `files.readDir`, `files.writeBase64Chunk`, `files.commitUpload` and `files.delete` of Orca's runtime (this machine's unix socket, a paired server's WebSocket), which are not a public interface. It was written against Orca 1.4.248 (the names and the typed text follow Orca 1.4.253), and an Orca update can change it. The file is held in memory only, and the window's own file drop is off (`dragDropEnabled` false) so that the page gets the dropped files.
- A plain terminal started from the plus of the Orca work pane (A-16) is made by Orca's CLI, `orca terminal create --worktree path:<path> --json` (`--environment=<name>` for a saved environment), run once, in a worktree of the list read just before, with an argument list and a timeout; its reply `result.terminal.handle` names the terminal. It was checked on Orca 1.4.250 (its help and its CLI source), and an Orca update can change it.
- A new worktree for the hand-over of A-9 is made by Orca's CLI, `orca worktree create --repo=id:<repository id> --name=<name> [--branch=<branch>] [--base-branch=<ref>] --no-parent --json` (`--environment=<name>` for a saved environment; `--branch` and `--base-branch` only when `orca_worktree_create` was given a branch or a base), run once, in the temporary folder, with an argument list and a timeout of 60 seconds; its reply `result.worktree.path` is the new worktree's absolute path. Just before, Rust checks that the environment is a saved one, that the repository id is a project of the list read just now (an `ssh:` host and an archived-only repository are not), and that the name, trimmed, is not empty, does not start with `-`, is not `.` or `..` and has no control character, `/` or `\`, and that the branch and the base, when given, are, trimmed (a blank one is none), a name git accepts as a ref (`git check-ref-format`: they do not start with `-`, hold no space, control character, zero-width, bidirectional or tag character (the ones `orca_handoff` takes out of a card) or `~ ^ : ? * [ \`, no `..` or `@{`, are not `@`, and have no component that is empty, starts with `.` or ends with `.lock`, nor a `/` or `.` at the end); nothing is made otherwise. The repository id is `OrcaProject.key` (`repoId` of `orca worktree ps`), so `--repo=id:` is used and not `--project`, which takes a project id or a display name. `--no-parent` is passed because the CLI otherwise records the context it can infer (`ORCA_TERMINAL_HANDLE` of the environment) as the parent. It was checked on Orca 1.4.255 by its help and its CLI source in `app.asar` (`handlers/worktree.js`, `worktree-project-target.js`) and by the shape of `orca worktree show --json`; the command itself was never run, so the exact reply of `worktree create` (`result.worktree.path`), its behavior on a saved environment, what it does with `--branch` when the branch already exists (reading the `app.asar` of Orca 1.4.256 suggests that it checks that branch out and makes no numbered new one; it was never run) and with `--base-branch`, the time it takes on a large repository and the answer of a repository whose setup policy is undecided (the CLI asks for `--setup`) were not checked, and an Orca update can change them.
- How the Orca work pane is split into panes (A-17) is saved for each project, under the place of its row (this machine, or a saved environment), in `orca-panes.json` in the app config directory: a tree of panes and splits that holds only tab ids (`claude:{pane key}`, `orca:{handle}`, `file:{n}` for a file open in the editor of A-18), the share of its size that each node of a split takes, and project keys of Orca, mended against the tabs Orca lists at each read, never holding what a terminal printed or was typed.
- The files of a worktree on the Orca screen (A-18) are read and saved through `files.readDir`, `files.read`, `files.writeIfUnchanged`, `files.createFile`, `files.createDir`, `files.delete`, `files.rename` and `git.checkIgnored` of Orca's runtime (this machine's unix socket, a paired server's WebSocket, the connection of A-10), which are not a public interface. They were read in the `app.asar` of Orca 1.4.253 and tried on this machine's Orca (a saved environment was not tried), and an Orca update can change them; `files.createFile` and `files.createDir`, which make a new file or folder of the tree (a name that is one name, never overwriting one that exists), were read in the `app.asar` of Orca 1.4.258 and never run on a real Orca, and `files.createFile` also makes the scratchpad file of A-29 in `.orca/scratchpad/` of a worktree (`orca_scratchpad_create`: a taken name is answered as the existing file); `files.delete` deletes a file, or a folder with what is in it (`recursive`), for good (`rm` with `force`: no Trash, and a path that is not there is no error), and was read there too and never run on a real Orca; `files.rename` (`{worktree, oldRelativePath, newRelativePath}`) moves or renames a file or a folder inside the worktree (`orca_file_move`), never onto a path that exists, and makes no folder, so Rust makes the missing folders of the target with `files.createDir` when it answers `ENOENT` and calls it once more; it was read there too and never run on a real Orca. A file is written only when the disk still holds the text that was read, by Orca's own signature of it, so a file changed elsewhere is never overwritten; only text of at most 384 KiB that is UTF-8 and has one kind of line end is opened. The text of a file is held in memory only and is in no log or file of the app. The reads of a folder, of its ignore marks (`git.checkIgnored`, asked after the list is drawn) and of a file believe a worktree that was confirmed against `orca worktree ps` for 60 seconds, in memory only and for the exact path of one target, so a folder read starts no CLI; a save, a create, a delete, a move and a download ask the list each time. The time of the automatic save is in `editor-settings.json` in the app config directory.
- The scratchpad of an SSH host (A-30) is the folder `~/.local/share/cookapps/scratchpad/` on that host, read and written by this Mac's `/usr/bin/ssh`, run with an argument list (no local shell): `-o BatchMode=yes -o ConnectTimeout=10 -o ControlMaster=auto -o ControlPath=~/.cache/cookapps/ssh/%C -o ControlPersist=60 -T [-l {username}] [-p {port}] -- {configHost} {command}`, killed after 30 seconds. The host is the `configHost` of a target of `ssh.listEditableTargets`, read at each call and refused when it is empty, starts with `-` or holds a whitespace or control character. `BatchMode` means that ssh never asks, so a key with a passphrase must be in ssh-agent; the key is that of `~/.ssh/config`, and so are the user and the port, except for a target added by hand in Orca (`source` `manual`, or no `source` and `configHost` equal to `host`), whose `username` (when not empty; checked as the host is) and `port` (when not 22; 1 to 65535) are passed as `-l` and `-p`, a shape read in the `app.asar` of Orca 1.4.258 and not tried on a real Orca; cookapps holds no secret. The folder of the sockets is made 0700, and the `Control` options are left out when a socket's path there would be over 103 bytes. The command the host runs is one of six constant `sh -c '...'` POSIX scripts; the names (checked in Rust first) and the text go to its standard input, never into the command. A save writes a temporary file in the same folder and moves it over the file, only when the file still has the `cksum` that was read. Nothing of a file, a name or ssh's output is kept or logged. The plus of the Orca work pane makes such a file for an SSH host's row and opens it in the editor of A-18, which reads and saves it by `ssh_scratch_read` and `ssh_scratch_write` in place of Orca's `files.*`; its tab is a `file:{n}` of `orca-panes.json` as any file's, and the text is held in memory only. The file pane of A-18 lists that folder (`ssh_scratch_list`) while an SSH host's row is selected with no tab, or the tab of one of its scratchpad files is, and makes, renames and deletes its files there (`ssh_scratch_create`, `ssh_scratch_rename`, `ssh_scratch_delete`); the list is read when it is first shown, at the return of the window's focus and after the app's own changes, never at an interval, and the names are held in memory only. It was never run against a real host (the scripts ran under this Mac's `sh` and `dash` only), and the Mac that runs cookapps must have the Host in its own `~/.ssh/config` unless the target was added by hand in Orca; only a host that this machine's Orca lists has a scratchpad (the row of a host of a saved environment alone has none).
- The difference of a file from HEAD on the Orca screen (A-24) is read through `git.diff` of Orca's runtime (this machine's unix socket, a paired server's WebSocket, the connection of A-10), with `staged` false and `compareAgainstHead` true, which is not a public interface. It was read in the `app.asar` of Orca 1.4.255 (`git-params.js`, the handler of `git.diff`) and not yet tried on a saved environment, and an Orca update can change it. Rust compares the two texts by lines (`orca_diff.rs`, Myers' algorithm of the `similar` crate, with a deadline of 2 seconds), only for text of at most 384 KiB a side that is UTF-8; a binary file, a diff Orca marks as too large, and over a paired server a diff over about 4 MiB (`diff_too_large`) are refused with a reason. The texts are held in memory only and are in no log and no file of the app.
- The branches of a worktree on the Orca screen are read through `git.localBranches` (`{worktree}`, answered `{current, branches, committedAt, worktreePaths}`) and `repo.searchRefs` (`{repo, query, limit: 50, namespace: "remote"}`, answered `{refDetails: [{refName, localBranchName}], refs, truncated}`) of Orca's runtime (this machine's unix socket, a paired server's WebSocket, the connection of A-10), which are not a public interface. They are the calls of the branch picker of Orca 1.4.255's renderer, were read again in the `app.asar` of Orca 1.4.256 and tried on this machine's Orca 1.4.256 over its unix socket (a saved environment was not tried, and the old shape of `repo.searchRefs` with `refs` alone was not seen on a real Orca), and an Orca update can change them. The worktree is believed as for the files above (`orca worktree ps`, 60 seconds, an SSH host refused), `repo` is the `OrcaProject.key` of the worktree and is sent as `id:{key}`, and the branch names are held in memory only and are in no log and no file of the app. The branch of a worktree is switched through `git.switchBranch` (`{worktree, target: {kind, name}, expectedExecutionHostId}`, `kind` `local` or `remote` only, never `new`, which makes a branch; answered `{ok, branch, head}` with `warning` when the switch worked but a later step failed, as a success; a refusal comes as an error whose message is Orca's own words and is shown as it is, cut at 200 characters). Its handler was read in the `app.asar` of Orca 1.4.256 (`out/main/index.js`, `agent-session-operation-ledger-*.js` of `app.asar.unpacked`) and the call was never run on a real Orca, because it changes a worktree. - The history of a worktree on the Orca screen (A-27) is read through `git.history` (`{worktree, refs: "head", limit, skip, historyToken}`, `limit` 1 to 200, answered `{items: [{id, displayId, subject, message, author, timestamp, parentIds}], hasMore, historyToken, historyChanged}`, the commits reachable from HEAD, the newest first; the first read has no `historyToken` and Orca answers one, a UUID it keeps for 15 minutes of idleness, and the next reads send it back with `skip`, so that they read the history the first page began even if HEAD moved (`historyChanged` true and no item when Orca no longer holds it, then the list is read again from the start); Orca still walks `skip` commits for each page, as the token is no cursor; read in the `shared/git/history/` and `rpc-contract/git-params.js` of Orca 1.4.258's `app.asar`, and the token was not tried on a real Orca), `git.commitCompare` (`{worktree, commitId}`, answered `{summary: {status, parentOid, changedFiles, errorMessage}, entries: [{path, status, oldPath, added, removed}]}`, the files a commit changed against its first parent) and `git.commitDiff` (`{worktree, commitOid, filePath, parentOid, oldPath}`, answered in the shape of `git.diff`: the text at the parent and at the commit) of Orca's runtime (this machine's unix socket, a paired server's WebSocket, the connection of A-10), which are not a public interface. The three reads were called on this machine's Orca 1.4.258 over its unix socket and the shape of each answer was checked there; a saved environment was not tried, and an Orca update can change them. `git.commitDiff` can answer a failure of git on Orca's side with empty texts and no error, so Rust cannot tell a commit Orca could not read from an empty file. The worktree is believed as for the files above (`orca worktree ps`, 60 seconds, an SSH host refused), and the commit ids sent are full object ids that Rust checked. The subjects, authors, paths and texts are held in memory only and are in no log and no file of the app, and nothing here writes to the worktree. The choice between the files and the history is held in memory only (no file).
- A file of a worktree on the Orca screen is copied to this PC (A-22) through `files.stat`, `files.readChunk` (and, on a host that lacks either, `files.readPreview`, by which a text file comes back as a UTF-8 string, so a text that is not UTF-8 is not the same bytes) of Orca's runtime (this machine's unix socket, a paired server's WebSocket, the connection of A-10), which are not a public interface. - An HTML file of a worktree on the Orca screen is opened in the default browser (A-31) from an HTTP server of the app (`orca_preview.rs`), which listens on `127.0.0.1` alone, on a port the OS gives, from the first open until the app ends (it is not started before, and nothing stops it earlier). An address is `http://127.0.0.1:{port}/{token}/{path from the worktree}`: the token is 16 random bytes of the OS in hex, one for each worktree (a target and a path), held in memory only, so it changes at every start of the app; a request with a token no worktree has is answered 404. Only GET and HEAD are answered (405 otherwise), and only with a `Host` header that is exactly `127.0.0.1:{port}` (403 otherwise, looked at first, so a name rebound to this address reads nothing). The path has its percent escapes taken out and is then held to the path check of A-18, a path with a part that starts with `.` (`.env`, `.git/config`, `.npmrc`, `a/.b/c`) is answered 404 without asking Orca (and the command refuses to open one), a folder has no list, and the server answers any file of a worktree that has a token, so that a page gets its images, styles and scripts; the command opens only a path that ends with `.html`. A file is read as the download of A-22 reads it (`files.stat`, `files.readChunk`, never past the size, or `files.readPreview`; the same limits and the same unchecked points; a HEAD asks `files.stat` alone, unless the host lacks it) and is sent as it is read, with a `Content-Type` decided from the extension and `Cache-Control: no-store`, `X-Content-Type-Options: nosniff` and `Referrer-Policy: no-referrer`. The command asks the target's list each time, as a download does; a request to the server believes a worktree as a read of A-18 does (`orca worktree ps`, 60 seconds), so a worktree that left the list, and an SSH host, are answered 404; a failed connection to Orca and a 502 drop that belief, and a 404 for a file that is not there keeps it. The page that is opened is the worktree's own file and runs in the browser as any page of `127.0.0.1` does: the server gives it no way to reach the app (it has no other route, and takes no body). No CSP `sandbox` is set (a `type="module"` script and the page's own `fetch` would stop working), so the danger that is left is that the script of an opened page reads the files of the same worktree that have no part starting with `.`; whether Orca's `files.stat` and `files.readChunk` follow a symbolic link inside the worktree was not checked. The bytes of a file, a path and a token are in no log and no file of the app, and the address is not returned to the page of the app. The server was run only against a fake Orca in the unit tests: no real browser and no real Orca was tried.

- A program in an Orca terminal can write the clipboard with OSC 52 (A-12): the page decodes the request and calls `navigator.clipboard.writeText` (no Tauri command, no file; a refused write leaves the text held in memory for the next copy event), only for a request the terminal prints live (not a snapshot or a mirror frame), for the target `c` or none, with base64 of at most 128 KiB; a read (`?`) is never answered. The limits follow Orca 1.4.250's `osc52-clipboard.js`.
- Ghostty's settings for the Orca terminals (A-13) are read from Ghostty's config files (`~/.config/ghostty/` and `~/Library/Application Support/com.mitchellh.ghostty/`, `config.ghostty` and `config`) and theme files only when the owner presses the import button, and are never written. What the terminals take from them is saved in `ghostty-settings.json` in the app config directory, with the entries imported and left. The places and the format follow Orca 1.4.250's own Ghostty import and Ghostty 1.4.0, and an update of either can change them.
- The colors of the Orca terminals (A-14) are the built-in themes of Orca 1.4.250, a table that the app holds (`src-tauri/src/orca_themes.json`, taken from Orca's `app.asar`), and the theme chosen for the light and for the dark appearance, with which of them the terminals draw (the system's appearance, or always the light or the dark one, A-15), is saved in `terminal-theme.json` in the app config directory. The first time the settings of the Orca on this Mac can be read, they give the choice: `terminalThemeLight` and `terminalThemeDark` of the `settings` row in `profiles/local-default/profile-state.db` (SQLite) in Orca's settings folder, which is not a public interface and was read on Orca 1.4.250. That file is opened read-only with `rusqlite` and never written, and its content is not kept or logged. An Orca update can change it (then the defaults are used).

## Claude and skills

- The skills (a text of instructions the owner writes for the Claude calls of the screens that talk to it, #127) are saved one for each folder, `claude-plugin/skills/{name}/SKILL.md` in the app config directory, in the shape of Claude Code's own: a front matter with `name` and `description` (the keys Claude Code reads) and `cookapps-display-name` and `cookapps-screens` (the screens that may use it, `slack-paste` and `slack-thread`; cookapps's own keys), and the instructions as the body. The folder `claude-plugin/` is a folder of its own, so that the config directory, which holds `client_secret.json` and the settings, is never the root Claude Code reads hooks, `.mcp.json` and agents from; it is never given to a call either (see the call of a skill below), and no `plugin.json` is written in it. The name is the folder's and is limited to a to z, 0 to 9 and `-` (at most 64 characters, no `--`, not starting or ending with `-`) before any path is made of it, so a name never points outside `claude-plugin/skills/`; a save goes through `write_atomic`. They are read, saved and deleted by `skill_list`, `skill_get`, `skill_save` and `skill_delete` (`skills.rs`). That Claude Code ignores the two keys of cookapps's own was not checked. The tab 「スキル」 of the settings screen (A-32) reads the list each time it is shown and keeps a saved skill's name fixed (the folder); a new skill whose name is taken is stopped by the screen before `skill_save`, and `skill_save` takes `create` (true for a new skill) and refuses, in Japanese, a new skill whose `SKILL.md` exists, so that a list that was not read cannot make a new skill replace a saved one; without `create` it replaces the skill of that name.
  A call of a skill (S-4 and S-7, #346) adds `--plugin-dir {a folder made for the call}` to the arguments of the call and puts `/cookapps:{name} ` before its input (`skill_call`), for a name that `skills::plugin_for` let through (valid, saved, and listing the screen of the call in `cookapps-screens`); the tools, the MCP servers and the settings stay off (`--tools ""`, `--strict-mcp-config`, `--setting-sources ""`). Claude Code reads everything in a plugin folder (the other skills, the `allowed-tools` or `hooks` of a `SKILL.md` placed by hand, `hooks/hooks.json` and `.mcp.json` of the plugin), which `--setting-sources ""` does not stop, so the folder of the call is made new in the system's temporary directory (mode 0700, a random name), holds only `.claude-plugin/plugin.json` and `skills/{name}/SKILL.md`, the saved skill read (`parse`) and written again (`render`) so that only `name`, `description` and the keys `cookapps-*` remain, and is deleted when the call is over (`CallPlugin` is dropped), failed or not. A skill whose text has a shell command in it (`!` and a command in backquotes) is not refused: tried on 2026-11-15 with Claude Code 2.1.325 and Haiku, with one skill whose body held such a command that would make a file, under `--tools ""` the command was not run (no file was made), and `claude -p` printed "Shell command permission check failed … Permission to use Bash has been denied." as its answer, exit code 0. Tried on 2026-11-15 with Claude Code and Haiku, with a plugin of one skill: the command was run as a skill under those flags, with the rest of a multi-line input as its arguments, and the model followed the skill's instruction. The call goes to Anthropic with the skill's text, and the owner wrote it.

## The app's log and fonts

- The log of the app (A-28) is `app-log.jsonl` in the app config directory: a line of JSON for each entry (time, `error` / `warn` / `info`, the place, a text of at most 500 characters), written from Rust (`app_log::write`) and from the screen (`log_write`) and read by `log_read`; the 「ログ」 tab of the settings (A-3) shows it and opens its folder with `log_open_folder`, which Rust gives to the opener plugin as the config directory (the page gives no path, and no capability is added). Lines older than 30 days are dropped and the file is kept at 1 MiB or under, the newest lines staying. It holds no token, mail, message, terminal output or typed key: the callers do not pass them, and the module cuts the text, collapses line breaks and masks words shaped like a token.
- The font (the family and the size) of each screen, of the editor, of the Orca work pane and of the whole app, and the family of the monospace text (A-20), is in `font-settings.json` in the app config directory; the family names to choose from are read from this Mac's fonts with CoreText (`CTFontManagerCopyAvailableFontFamilyNames`, through the `objc2-core-text` crate) at each start and kept in no file, and no font is loaded from outside.

## Notion

- Notion is read through Notion's MCP server (`https://mcp.notion.com/mcp`, `notion.rs`), not the REST API, because only the MCP lists the teamspaces and the favorites; no screen uses it yet. It is an interface for AI clients, not a public API for apps, and whether an app that is no AI client may use it is not documented (not checked). It was checked on 2026-11-10 against server version 1.2.0 (the prototype of #365), and its tools, arguments and replies can change; a reply is JSON wrapped in a string.
  - The app registers one public client by dynamic client registration (`/register`, `token_endpoint_auth_method` `none`, no client secret, redirect `http://127.0.0.1/`) the first time, and keeps its `client_id` in `notion-accounts.json` in the app config directory, because registering again leaves the earlier connections hanging. The same file lists the connected workspaces (id, name, and the user's name and email address from `notion-get-self`); it holds no token.
  - The login is PKCE S256 with a loopback redirect, served by the listener that Google's login uses (`auth.rs`). Notion takes any port on `127.0.0.1` for the registered redirect and the path must be the registered one (tried on 2026-11-14 by `GET /authorize`); the code is exchanged at `/token`, which also revokes (RFC 7009; a revoke of a made-up token answered 200).
  - The tokens are in the OS keychain, service `jp.mysis.cookapps.notion`, user name the workspace's id, as one JSON entry (access token, refresh token, expiry) so that a new pair replaces the old in one write. They are never shown, logged or kept in a file, and `cookapps-mcp` does not read them, so nothing else refreshes them. One token is one workspace, so each workspace is connected on its own.
  - The access token lasts 8 hours; it is refreshed 5 minutes before its end and when a call is refused with 401. The refresh token changes at every refresh and an old one used again ends the connection, so a workspace refreshes one at a time and the new pair is written to the keychain before the access token is used. A refresh answered `invalid_grant` (180 days after the first consent at the latest, or 30 days unused) deletes the keychain entry and leaves the workspace in the list with `reconnect` true; any other failure keeps the tokens.
  - A call is Streamable HTTP: `initialize`, the `notifications/initialized` notice, then `tools/call`; the reply is JSON or a server-sent event stream. The token holds the user's full rights (77 tools, deletion included), so `ALLOWED_TOOLS` in `notion.rs` is the only list of tools the app calls, and it holds `notion-get-self` alone for now. Notion's limit is 180 requests a minute (600 on Business and above).
  - Not tried against a real login by this code, so a Notion update or the first real connection can show a difference: the `workspace_id` and `workspace_name` of the token reply, the shape of the text of `notion-get-self` (`user_of` reads `name` and `email` or `person.email`, at the top or under `user`), and the session id header of the reply to `initialize`.

## Database

- The port forward of a connection that goes through AWS Systems Manager (#625, #630; `database/ssm.rs`) is opened with `aws-sdk-ssm` and `aws-config` (features `credentials-login` and `sso`, so that the login of `aws login` is read) and `session-manager-plugin` as a child process, never with the `aws` command, which is not in the PATH of a GUI app. The SDK's TLS is rustls with `aws_lc_rs`, the one the app already has (`cargo tree` shows no `native-tls` or `openssl`). The app never starts a login: an expired one is the error 「AWS の認証が切れています」, and the owner runs `aws login` by hand.
  - The bastion is found by its `Name` tag among the managed nodes (`DescribeInstanceInformation`, the one filter `tag:Name`; the SDK's documentation lists `tag:{keyname}` as a filter key). A tag filter cannot be combined with a filter of another type (the reference of `Filters`), so `PingStatus` is not a filter: it is read from each node that comes back (#661, where the two filters together were the error `ValidationException`). The first node whose `PingStatus` is Online is used; one that is not found is the error 「踏み台「{name}」が見つかりません」. The instance must be one that the DB's security group lets reach the port (#625: with one that is not, the tunnel opens and MySQL never answers).
  - `StartSession` is called with the document `AWS-StartPortForwardingSessionToRemoteHost` and the parameters `host` and `portNumber`; the local port is not given. The plugin takes the arguments of `ValidateInputAndStartSession` in its `session.go`: the response, the region, `StartSession`, the AWS profile, the parameters as JSON (`Target` is required) and `https://ssm.{region}.amazonaws.com`. The response holds the token of the data channel, so it goes in the environment variable `AWS_SSM_START_SESSION_RESPONSE`, which the plugin reads when its first argument is that name (`session.go`; tried on 2026-11-15 with plugin 1.2.835.0), and not in the argument list that `ps` shows. Nothing goes through a shell.
  - The plugin chooses a free port and writes `Port N opened for sessionId …` on its standard output (`muxportforwarding.go`; it has no line break of its own, the next write starts with one). The app reads that line (30 seconds at most; it took 2 seconds on 2026-11-14), and goes on reading the output to its end so that the plugin never waits on a full pipe. Its other output, errors included (`Cannot perform start session: …`), is on the same stream; the last line is the reason shown when it ends without a port.
  - The plugin is looked for in the folders of the installers (`/opt/homebrew/bin`, `/usr/local/bin`, `/usr/local/sessionmanagerplugin/bin`) and then in the PATH, by running it with `--version`; none is the error 「session-manager-plugin が見つかりません」, before any call to AWS.
  - A tunnel is closed by stopping the plugin and calling `TerminateSession`, because stopping the parent alone leaves the plugin and a Connected session (#625). A plugin that gave no port is stopped and its session is ended too. The app's exit closes the tunnels that are open (`RunEvent::Exit` in `lib.rs`; the sessions are closed together, and the `TerminateSession` of each tunnel has 5 seconds there and not 20, because the exit waits for it); a kill of the app itself leaves the session to SSM's own idle limit.
  - Each AWS call has 20 seconds, the credentials' loading included; a call past it is the error 「AWS への接続が時間内に終わりませんでした」.
- The MySQL session (#625, #631; `database/mysql.rs`) is opened with `sqlx` 0.9 (features `mysql`, `runtime-tokio` and `tls-rustls-aws-lc-rs`, no default features: no macros, no migrations, no other database), whose TLS is the rustls with `aws_lc_rs` that the app already has (`cargo tree -i native-tls`, `-i openssl` and `-i rsa` find nothing). The target is MySQL 5.7, 8.0 and 8.4 with `mysql_native_password` and `caching_sha2_password`.
  - The SSL mode is `Preferred` for a connection through the tunnel and for a host that is the machine itself (`localhost`, a loopback address): TLS when the server offers it, a plain connection otherwise. For every other host (no SSM, over a network) it is `Required` (with `Preferred` an attacker on the way could make the server look as if it had no TLS, and the password would go in plain text). In both modes the certificate is not verified (sqlx accepts any certificate; the owner's decision stays: it needs a CA bundle for each server, such as the one of RDS), so `Required` stops the downgrade and not a server that presents a certificate of its own. The time zone and the `sql_mode` are the server's: the defaults of sqlx (`time_zone='+00:00'`, `PIPES_AS_CONCAT`, `NO_ENGINE_SUBSTITUTION`) are turned off. The password of `caching_sha2_password` is sent through TLS, and the RSA path of sqlx (the feature `mysql-rsa` and the crate `rsa`) is not built in, so a server with no TLS that asks for that password is the error of D-2. Not tried against a real server by this code (only against a local fake of the protocol, `cargo test`): the TLS handshake and `caching_sha2_password` on MySQL 8.0 and 8.4.
  - Every session is made read only at its start (`SET SESSION TRANSACTION READ ONLY`), so a write is refused by MySQL. The password never goes into a URL (the options are set field by field), a log or an error. The connection test (`database_test`) reads the saved password of the connection from the keychain only when the field is empty and the connection still has the user, the host, the port and the SSM fields of the saved one (otherwise it is refused, so that the saved password is never sent to another place), and the password goes to no screen. The keychain has no way to ask whether a password is saved without reading it (`keyring` 4 and its macOS store: `get_attributes` and `get_credential` both go through `find_generic_password`), so the list reads each saved password to show "保存済み".
  - A connection has 15 seconds from the first byte to the answer of the first query; it is not retried.
- The open connections (#632; `database/session.rs`) are kept in the app's memory, one session for each connection (`tauri::State`, `Sessions`), and reused until they are closed: by the menu's "切断", by a save or a delete of the connection, by a query that shows the stream broken or past 30 seconds, and by the app's exit (`RunEvent::Exit` in `lib.rs`: the sessions, then the tunnels). Nothing is read at an interval: a session is read only by a press, so a connection that is gone from the list has no process left (a delete closes it first). Closing a session also closes its tunnel (`ssm::Tunnels::close`).
  - The databases are read from `information_schema.SCHEMATA` and the tables from `information_schema.TABLES`; the name of the database is a bound value (`?`), and every value of a query that comes from the screen is bound, never put in the SQL text. The columns are cast in the SQL (`CAST … AS CHAR` for names, `AS UNSIGNED` for the row estimate and the lengths) so that they decode on MySQL 5.7, 8.0 and 8.4 alike; not tried against a real server by this code.
  - The records of a table (#633, D-4; `database/records.rs`) are read on the same session as one page of ``SELECT * FROM `db`.`table` LIMIT ? OFFSET ?`` (a page is 100 rows, 101 are asked for). The names are the only part put in the SQL text, between backticks with a backtick inside doubled, and the limit and the offset are bound, which makes the statement a prepared one: its rows come in the binary protocol, which `sqlx` gives as the bytes of each value (read without a typed decoder, so that the types that need the crates `chrono`, `bigdecimal` or the `json` feature are not added) and `cell_of` turns into text. Every value of a page is held in memory for the page only, a text is cut to 200 characters, a binary value is kept as its length, and a read past 30 seconds closes the session (as every query there). The estimate of the rows is `information_schema.TABLES.TABLE_ROWS`, bound by the schema and the table, and is shown as an estimate; it is read with the page 0 only, and a later page is given the one the screen holds. The rows are turned into cells one by one as they come, borrowed from the row's buffer, and the 101st is only counted.
  - The structure of a table (#634, D-5; `database/structure.rs`) is read on the same session from `information_schema.COLUMNS` (the name, the type, whether NULL is allowed, the key, the default and the comment) and `information_schema.TABLES` (the engine and the collation), with the schema and the table as bound values (`?`), never put in the SQL text, and every column cast as above. Two small queries at every press of the tab, each under the 30 seconds of every query there; the indexes, the foreign keys and the triggers are not read. Not tried against a real server by this code.
  - The SQL tab (#635, D-6; `database/sql.rs`) runs the text of the user on the same session as one prepared statement, as it is (only the whitespace and the semicolons at its ends are cut), under the read only session (D-2) that makes MySQL refuse a write. The database of the tree is chosen by a `USE` of its own with a quoted name (`records::quote_identifier`), never put in the user's text. The rows are limited to 1,000 and read as a stream that stops after the 1,001st, so the rest is never held; the time is limited by `max_execution_time` of 30 seconds (MySQL stops a SELECT itself) and by 35 seconds for the whole run, past which the connection and its tunnel are closed (`KILL QUERY` is not used: it needs a second connection and the password kept in memory). Before each run the session is made read only again (the text of the user may have set it to read write) and `max_execution_time` and `sql_select_limit` are set, with the `USE`, in one round trip; after it, whatever the result (a `USE` that failed too), the read only is set again and the two are put back. Not tried against a real server by this code.
  - The row count of `information_schema.TABLES` is an estimate for InnoDB (and MySQL 8 may serve statistics up to a day old, `information_schema_stats_expiry`), so the screen names the column 行数（概算）.

## Updates

- Updates use `tauri-plugin-updater`. Pushing the annotated tag `v{version}`, or merging the Release PR (which makes that tag, `release.yml`), starts the `release` job, which makes `cookapps.app.tar.gz`, its `.sig` and `latest.json` (`scripts/make-latest-json.sh`) and puts them in a GitHub Release.
  The app reads `releases/latest/download/latest.json` (`plugins.updater.endpoints` in `tauri.conf.json`) and verifies the download with the public key `plugins.updater.pubkey`.
  `bundle.createUpdaterArtifacts` is not in `tauri.conf.json`; the `release` job passes it with `--config`, so a local build needs no signing key.
  The version is the tag's alone (at the owner's instruction, 2026-11-09; Discussion #293): `version` in `src-tauri/Cargo.toml` and `Cargo.lock` is fixed at `0.0.0` and `tauri.conf.json` has none, and the `release` job passes the version of the tag with `--config` too, which Info.plist, `app.package_info()` (U-2) and the updater's comparison take. A build without it (`tauri dev`, E2E) reports `0.0.0`, and `scripts/install-app.sh` passes the latest tag.
