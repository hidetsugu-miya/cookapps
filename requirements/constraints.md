# Technical constraints

The constraints of one integration or one requirement, by area.
The constraints of the whole app (the OAuth flow, the scopes, the tokens and `accounts.json`) are in `AGENTS.md`, under "Technical constraints".
Read an area's section before you change a behavior it covers, and when a change makes a constraint different, change the section in the same pull request.

## Mail

- A mail is sent with `users.messages.send` (`mail_send.rs`; a new mail and a reply), which `gmail.modify` is enough for: Google's reference for the method lists `https://mail.google.com/`, `gmail.modify`, `gmail.compose` and `gmail.send` as the scopes it accepts (https://developers.google.com/workspace/gmail/api/reference/rest/v1/users.messages/send, read 2026-11-14), so no new scope is asked for and no account must log in again. The request is `{raw, threadId}`, with `raw` the RFC 5322 message in base64url (https://developers.google.com/workspace/gmail/api/guides/sending). A reply is put in its thread only when `threadId` is given, `In-Reply-To` and `References` are set as RFC 2822 says and the subject matches (https://developers.google.com/workspace/gmail/api/guides/threads), so Rust reads the Message-ID and References of the thread's last message that is not a draft (`threads.get`, `format=metadata`) and refuses a Message-ID that is not one well-formed `<id>`. Before anything is sent Rust checks each recipient as one plain ASCII `addr` or `Name <addr>`, and refuses a CR, LF or other control character in a recipient, the subject or the sender, so that no header can be injected. A subject or a name that is not ASCII is sent as RFC 2047 encoded-words, and the plain-text body as UTF-8 base64 with CRLF line ends. A rate-limited or 401 send is sent again (Gmail did not process it), and an answer that is lost is not, so a mail is never sent twice by the app. Nothing of the mail (recipients, subject, body) is kept or logged.
- The threads the mail screen has opened (M-2) are held in memory only (`HeldThreads`, `gmail/held.rs`), by account and thread ID, as `thread` last answered them, and are in no file and no log of the app. They take at most 64 MB of text (`HELD_THREAD_BYTES`), the oldest dropped first: a body carries its inlined images as data: URIs, up to 27 MB a thread, so the cap holds at least two threads of the largest size and several hundred of ordinary mail, and it is the cap of the two image caches (`INLINE_CACHE_BYTES`, `IMAGE_CACHE_BYTES`). The 64 MB is on top of those caches: an inlined image is held both in the held body and in `InlineCache`. `cookapps-mcp` holds none.

## Slack

- The Slack compose screen (S-1) sends its things to do one by one with `chat.postMessage` (`chat:write`, under the owner's own name), each only on the press of "投稿" (or by the request of S-23, which sends them the same way from Rust, `slack::post_planned`), and a card that continues the thread of an earlier one is a reply with `thread_ts` set to the `ts` that the earlier call answered: no other method and no new scope. The calls are not one transaction, so a failure leaves the earlier posts in Slack; the screen marks them posted and never sends them again. `@here`, `@channel` and `@everyone` become broadcast mentions (`<!here>`, `<!channel>`, `<!everyone>`) only in a text written in a card: one the owner posts with "投稿" (`slack_post` with `written` true), or one posted by a request to Claude whose own words hold every such word of the text (`slack::post_decision`, S-23); the mail's content, also when Claude changed it, is sent escaped, as text, because it is untrusted. A Slack link in a request to Claude (S-23) is read as the link of the picker is, with `conversations.info` for the channel's name: no new method and no new scope.
- A Slack workspace may also have an App-Level Token (`xapp-`, scope `connections:write`, S-16), kept in the OS keychain (service `jp.mysis.cookapps.slack-app`, user name the workspace's `team_id`) and never shown or logged. With it the app keeps a WebSocket open to Slack's Socket Mode (`apps.connections.open`, then the `wss` address of slack.com it answers) for as long as the app runs, and reads the channels whose message events arrive; the list is still read on a timer (every 5 minutes while every workspace is connected, else every 2 minutes).
- The custom emoji of a Slack workspace (S-26) are read with `emoji.list` (`emoji:read`, an optional scope) when a thread or a channel's history has a reaction, or when the emoji picker of S-25 opens, kept in memory only for an hour (`TimelineCache`) and never saved; their images are fetched by `fetch_images` as the users' icons are, only from the hosts of `icon_host_ok`.
- A reaction of a Slack message is added or taken off (S-25) with `reactions.add` and `reactions.remove` (`reactions:write`, an optional scope) by the workspace's token, only when the user presses it, or chooses an emoji in the picker, in the thread or in a channel's history; the people who gave a reaction (`users`) are read for `mine` and kept in memory only.

- A new worktree for the hand-over of A-9 is made by Orca's CLI, `orca worktree create --repo=id:<repository id> --name=<name> [--branch=<branch>] [--base-branch=<ref>] --no-parent --json` (`--environment=<name>` for a saved environment; `--branch` and `--base-branch` only when `orca_worktree_create` was given a branch or a base), run once, in the temporary folder, with an argument list and a timeout of 60 seconds; its reply `result.worktree.path` is the new worktree's absolute path. Just before, Rust checks that the environment is a saved one, that the repository id is a project of the list read just now (an `ssh:` host and an archived-only repository are not), and that the name, trimmed, is not empty, does not start with `-`, is not `.` or `..` and has no control character, `/` or `\`, and that the branch and the base, when given, are, trimmed (a blank one is none), a name git accepts as a ref (`git check-ref-format`: they do not start with `-`, hold no space, control character, zero-width, bidirectional or tag character (the ones `orca_handoff` takes out of a card) or `~ ^ : ? * [ \`, no `..` or `@{`, are not `@`, and have no component that is empty, starts with `.` or ends with `.lock`, nor a `/` or `.` at the end); nothing is made otherwise. The repository id is `OrcaProject.key` (`repoId` of `orca worktree ps`), so `--repo=id:` is used and not `--project`, which takes a project id or a display name. `--no-parent` is passed because the CLI otherwise records the context it can infer (`ORCA_TERMINAL_HANDLE` of the environment) as the parent. It was checked on Orca 1.4.255 by its help and its CLI source in `app.asar` (`handlers/worktree.js`, `worktree-project-target.js`) and by the shape of `orca worktree show --json`; the command itself was never run, so the exact reply of `worktree create` (`result.worktree.path`), its behavior on a saved environment, what it does with `--branch` when the branch already exists (reading the `app.asar` of Orca 1.4.256 suggests that it checks that branch out and makes no numbered new one; it was never run) and with `--base-branch`, the time it takes on a large repository and the answer of a repository whose setup policy is undecided (the CLI asks for `--setup`) were not checked, and an Orca update can change them.
- How the Orca work pane is split into panes (A-17) is saved for each project of each target in `orca-panes.json` in the app config directory: a tree of panes and splits that holds only tab ids (`claude:{pane key}`, `orca:{handle}`, `file:{n}` for a file open in the editor of A-18), the share of its size that each node of a split takes, and project keys of Orca, mended against the tabs Orca lists at each read, never holding what a terminal printed or was typed.

- The scratchpad of an SSH host (A-30) is the folder `~/.local/share/cookapps/scratchpad/` on that host, read and written by this Mac's `/usr/bin/ssh`, run with an argument list (no local shell): `-o BatchMode=yes -o ConnectTimeout=10 -o ControlMaster=auto -o ControlPath=~/.cache/cookapps/ssh/%C -o ControlPersist=60 -T [-l {username}] [-p {port}] -- {configHost} {command}`, killed after 30 seconds. A save writes a temporary file in the same folder and moves it over the file, only when the file still has the `cksum` that was read. Nothing of a file, a name or ssh's output is kept or logged. The plus of the Orca work pane makes such a file for an SSH host's row and opens it in the editor of A-18, which reads and saves it by `ssh_scratch_read` and `ssh_scratch_write` in place of Orca's `files.*`; its tab is a `file:{n}` of `orca-panes.json` as any file's, and the text is held in memory only. It was never run against a real host (the scripts ran under this Mac's `sh` and `dash` only), and the Mac that runs cookapps must have the Host in its own `~/.ssh/config` unless the target was added by hand in Orca; only a host that this machine's Orca lists has a scratchpad (the row of a host of a saved environment alone has none).

## The app's log and fonts

- The log of the app (A-28) is `app-log.jsonl` in the app config directory: a line of JSON for each entry (time, `error` / `warn` / `info`, the place, a text of at most 500 characters), written from Rust (`app_log::write`) and from the screen (`log_write`) and read by `log_read`. Lines older than 30 days are dropped and the file is kept at 1 MiB or under, the newest lines staying. It holds no token, mail, message, terminal output or typed key: the callers do not pass them, and the module cuts the text, collapses line breaks and masks words shaped like a token.
- The font (the family and the size) of each screen, of the editor, of the Orca work pane and of the whole app, and the family of the monospace text (A-20), is in `font-settings.json` in the app config directory; the family names to choose from are read from this Mac's fonts with CoreText (`CTFontManagerCopyAvailableFontFamilyNames`, through the `objc2-core-text` crate) at each start and kept in no file, and no font is loaded from outside.

## Notion

- Notion is read through Notion's MCP server (`https://mcp.notion.com/mcp`, `notion.rs`), not the REST API, because only the MCP lists the teamspaces and the favorites; no screen uses it yet. It is an interface for AI clients, not a public API for apps, and whether an app that is no AI client may use it is not documented (not checked). It was checked on 2026-11-10 against server version 1.2.0 (the prototype of #365), and its tools, arguments and replies can change; a reply is JSON wrapped in a string.
  - The app registers one public client by dynamic client registration (`/register`, `token_endpoint_auth_method` `none`, no client secret, redirect `http://127.0.0.1/`) the first time, and keeps its `client_id` in `notion-accounts.json` in the app config directory, because registering again leaves the earlier connections hanging. The same file lists the connected workspaces (id, name, and the user's name and email address from `notion-get-self`); it holds no token.
  - The login is PKCE S256 with a loopback redirect, served by the listener that Google's login uses (`auth.rs`). Notion takes any port on `127.0.0.1` for the registered redirect and the path must be the registered one (tried on 2026-11-14 by `GET /authorize`); the code is exchanged at `/token`, which also revokes (RFC 7009; a revoke of a made-up token answered 200).
  - The tokens are in the OS keychain, service `jp.mysis.cookapps.notion`, user name the workspace's id, as one JSON entry (access token, refresh token, expiry) so that a new pair replaces the old in one write. They are never shown, logged or kept in a file, and `cookapps-mcp` does not read them, so nothing else refreshes them. One token is one workspace, so each workspace is connected on its own.
  - The access token lasts 8 hours; it is refreshed 5 minutes before its end and when a call is refused with 401. The refresh token changes at every refresh and an old one used again ends the connection, so a workspace refreshes one at a time and the new pair is written to the keychain before the access token is used. A refresh answered `invalid_grant` (180 days after the first consent at the latest, or 30 days unused) deletes the keychain entry and leaves the workspace in the list with `reconnect` true; any other failure keeps the tokens.
  - A call is Streamable HTTP: `initialize`, the `notifications/initialized` notice, then `tools/call`; the reply is JSON or a server-sent event stream. The token holds the user's full rights (77 tools, deletion included), so `ALLOWED_TOOLS` in `notion.rs` is the only list of tools the app calls, and it holds `notion-get-self` alone for now. Notion's limit is 180 requests a minute (600 on Business and above).
  - Not tried against a real login by this code, so a Notion update or the first real connection can show a difference: the `workspace_id` and `workspace_name` of the token reply, the shape of the text of `notion-get-self` (`user_of` reads `name` and `email` or `person.email`, at the top or under `user`), and the session id header of the reply to `initialize`.

## Updates

- Updates use `tauri-plugin-updater`. Pushing the annotated tag `v{version}`, or merging the Release PR (which makes that tag, `release.yml`), starts the `release` job, which makes `cookapps.app.tar.gz`, its `.sig` and `latest.json` (`scripts/make-latest-json.sh`) and puts them in a GitHub Release.
  The app reads `releases/latest/download/latest.json` (`plugins.updater.endpoints` in `tauri.conf.json`) and verifies the download with the public key `plugins.updater.pubkey`.
  `bundle.createUpdaterArtifacts` is not in `tauri.conf.json`; the `release` job passes it with `--config`, so a local build needs no signing key.
  The version is the tag's alone (at the owner's instruction, 2026-11-09; Discussion #293): `version` in `src-tauri/Cargo.toml` and `Cargo.lock` is fixed at `0.0.0` and `tauri.conf.json` has none, and the `release` job passes the version of the tag with `--config` too, which Info.plist, `app.package_info()` (U-2) and the updater's comparison take. A build without it (`tauri dev`, E2E) reports `0.0.0`, and `scripts/install-app.sh` passes the latest tag.
