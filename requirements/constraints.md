## Mail

- A mail is sent with `users.messages.send` (`mail_send.rs`; a new mail and a reply), which `gmail.modify` is enough for: Google's reference for the method lists `https://mail.google.com/`, `gmail.modify`, `gmail.compose` and `gmail.send` as the scopes it accepts (https://developers.google.com/workspace/gmail/api/reference/rest/v1/users.messages/send, read 2026-11-14), so no new scope is asked for and no account must log in again. The request is `{raw, threadId}`, with `raw` the RFC 5322 message in base64url (https://developers.google.com/workspace/gmail/api/guides/sending). A reply is put in its thread only when `threadId` is given, `In-Reply-To` and `References` are set as RFC 2822 says and the subject matches (https://developers.google.com/workspace/gmail/api/guides/threads), so Rust reads the Message-ID and References of the thread's last message that is not a draft (`threads.get`, `format=metadata`) and refuses a Message-ID that is not one well-formed `<id>`. Before anything is sent Rust checks each recipient as one plain ASCII `addr` or `Name <addr>`, and refuses a CR, LF or other control character in a recipient, the subject or the sender, so that no header can be injected. A subject or a name that is not ASCII is sent as RFC 2047 encoded-words, and the plain-text body as UTF-8 base64 with CRLF line ends. A reply written in the rich editor (M-10, `markdown` true) goes as `multipart/alternative`, its Markdown as the `text/plain` part and the HTML that `markdown_to_html` makes from it as the `text/html` part: that HTML is made from the parsed Markdown, a raw HTML tag in the text is written out as text, except that the empty paragraph the editor writes as `<br />` (also `<br/>` and `<br>`) alone in its block is the fixed `<p><br></p>` in the HTML and is left out of the `text/plain` part (the text/plain part is the Markdown as it is otherwise), so that no other tag and no script comes out of it, and only `http`, `https` and `mailto` links keep their anchor, so the editor's text cannot put a tag, a script or a `javascript:` link into the mail. A rate-limited or 401 send is sent again (Gmail did not process it), and an answer that is lost is not, so a mail is never sent twice by the app. Nothing of the mail (recipients, subject, body) is kept or logged.
- The threads the mail screen has opened (M-2) are held in memory only (`HeldThreads`, `gmail/held.rs`), by account and thread ID, as `thread` last answered them, and are in no file and no log of the app. They take at most 64 MB of text (`HELD_THREAD_BYTES`), the oldest dropped first: a body carries its inlined images as data: URIs, up to 27 MB a thread, so the cap holds at least two threads of the largest size and several hundred of ordinary mail, and it is the cap of the two image caches (`INLINE_CACHE_BYTES`, `IMAGE_CACHE_BYTES`). The 64 MB is on top of those caches: an inlined image is held both in the held body and in `InlineCache`. `tsunagiai-mcp` holds none.

## Slack

- The Slack compose screen (S-1) sends its things to do one by one with `chat.postMessage` (`chat:write`, under the owner's own name), each only on the press of "投稿" (or by the request of S-23, which sends them the same way from Rust, `slack::post_planned`), and a card that continues the thread of an earlier one is a reply with `thread_ts` set to the `ts` that the earlier call answered: no other method and no new scope. The calls are not one transaction, so a failure leaves the earlier posts in Slack; the screen marks them posted and never sends them again. `@here`, `@channel` and `@everyone` become broadcast mentions (`<!here>`, `<!channel>`, `<!everyone>`) only in a text written in a card: one the owner posts with "投稿" (`slack_post` with `written` true), or one posted by a request to Claude whose own words hold every such word of the text (`slack::post_decision`, S-23); the mail's content, also when Claude changed it, is sent escaped, as text, because it is untrusted. A Slack link in a request to Claude (S-23) is read as the link of the picker is, with `conversations.info` for the channel's name: no new method and no new scope.
- A Slack workspace may also have an App-Level Token (`xapp-`, scope `connections:write`, S-16), kept in the OS keychain (service `jp.mysis.tsunagiai.slack-app`, user name the workspace's `team_id`) and never shown or logged. With it the app keeps a WebSocket open to Slack's Socket Mode (`apps.connections.open`, then the `wss` address of slack.com it answers) for as long as the app runs, and reads the channels whose message events arrive; the list is still read on a timer (every 5 minutes while every workspace is connected, else every 2 minutes).
- The custom emoji of a Slack workspace (S-26) are read with `emoji.list` (`emoji:read`, an optional scope) when a thread or a channel's history has a reaction, or when the emoji picker of S-25 opens, kept in memory only for an hour (`TimelineCache`) and never saved; their images are fetched by `fetch_images` as the users' icons are, only from the hosts of `icon_host_ok`.
- A reaction of a Slack message is added or taken off (S-25) with `reactions.add` and `reactions.remove` (`reactions:write`, an optional scope) by the workspace's token, only when the user presses it, or chooses an emoji in the picker, in the thread or in a channel's history; the people who gave a reaction (`users`) are read for `mine` and kept in memory only.

## Settings files

- The app's identifier is `jp.mysis.tsunagiai` (`identifier` in `tauri.conf.json`, and `IDENTIFIER` in `identity.rs`, which a unit test keeps equal). It names the app config directory (`jp.mysis.tsunagiai`, from Tauri's `app_config_dir`) and the keychain services: `jp.mysis.tsunagiai` (the refresh tokens of the Gmail accounts, user name the account's address) and `jp.mysis.tsunagiai.claude`, `.database`, `.notion`, `.slack`, `.slack-app` and `.todoist`. The E2E build's identifier is `jp.mysis.tsunagiai.e2e`. The identifier before the rename was `jp.mysis.cookapps`, and the move from it is done by the app itself (#750):
  - The config directory: at each start, before anything reads the settings (the `setup` of the app, and `identity::config_dir` for `tsunagiai-mcp`, which builds the path itself), when `jp.mysis.tsunagiai` does not exist (not even empty) and `jp.mysis.cookapps` beside it does, the contents of the old folder are copied into it, folders and files, with their modes; an entry that is neither (a link to nothing, a socket) is skipped, so one of them does not stop the move of the rest. The copy is made in a folder beside the new one and renamed into place, so a failure leaves no half-filled new folder (the next start tries again; the failure is logged to the standard error and the app starts with an empty folder otherwise). The old folder is not deleted or changed. A folder of another identifier (the E2E build's) never takes the old one. Whichever of the app and `tsunagiai-mcp` starts first does the copy.
  - The keychain (`keychain.rs`, the one place every module reads, writes and deletes its secrets through): a read that finds no item under the new service reads the item with the same user name under the old service (`jp.mysis.cookapps`, `jp.mysis.cookapps.claude` and so on: the same name with the old identifier in place of the new), and when it finds one it writes the value under the new service and uses it. The old item is not deleted by a read. The old service is asked once for each item in a process (the answer "nothing there" is remembered), and one read of it at a time, so a permission prompt of the OS is not asked twice for the same item; the async callers of `auth.rs` read and delete off the async workers. A write goes to the new service only. A delete removes the item under the old service first and then under the new one (both run even when the first fails), because a delete that left the old item would let the next read copy it back, and a logout or a disconnect would not take effect. The app and `tsunagiai-mcp` are two processes, so a read that has copied the old item reads it once more, and when a delete took it meanwhile, deletes its copy and finds nothing. A secret is in no log, error text or `Debug`.
  - The tests: the read, the copy, the remembered answer, a delete that lands in the middle of a copy and the delete on a map instead of the keychain (`keychain.rs`), and the copy of the folder on temporary folders (`identity.rs`). No test touches the real keychain or the real config folder.

The connection profiles of the database screen (#625; `database.rs`) are in `database-profiles.json` there: for each, an id made at the first save (16 random bytes in hex, never changed), the name, the user name, the script (the body of the script that opens the way to the database, empty for none; a file of before #718 has none, and the fields of SSM that it holds are ignored), the DB host and the DB port, written through `write_atomic`; a file that cannot be read is an error and a save never replaces it. ## Database

- The script of a connection (#717, #718; `database/script.rs`; D-1) opens the way to the database, for instance a port forward through AWS Systems Manager that the owner writes with the `aws` command. The app starts no AWS tool itself and depends on no AWS crate (`aws-config` and `aws-sdk-ssm` were removed with `database/ssm.rs`). The script is the owner's own text, saved in `database-profiles.json` (a profile's `script`); it is run, never built from input of anyone else.
  - It is run as a child process with no shell: its body is written to a file of its own (mode 0700, in a folder of its own, `tsunagiai-script-{16 hex}`, made in the system's temporary folder and deleted when the script has ended) and that file is run, so the interpreter is the one of its first line (`#!/bin/sh` is put first when there is none). The folder is created with `create_dir` (never reused) and the file with `create_new`, and the file is closed before it is run; a run that fails with `ETXTBSY` (the file still open for writing in another thread that forked meanwhile) is tried again up to 5 times.
  - A GUI app does not have the PATH of a shell, so the script is run with the app's own PATH: a script that needs `aws` names its path (for instance `/opt/homebrew/bin/aws`). Not tried against a real AWS account by this code.
  - The port is the connection's own (its host and its port, D-1; the owner chooses it, the app picks none, #745). Before the script is run, the app tries a TCP connection to `{host}:{port}`; when something answers, the connection fails with 「{host}:{port} は、スクリプトを実行する前から使われています。…」 and the script is not run (no file is made), so a script never runs against a port that another process holds. The check and the script's own listening are not one step: another process may take the port between them, and the script then fails to listen, which shows as a script that is not ready (or ends) with its standard error. The port is the connection's own, so it is known before the check (the app no longer picks a free one): any other process on this machine can listen there first, as it could take a free port in the gap before. No code is added for it: a process that listens first makes the script fail to listen, which shows as above, and one that listens after the check and answers is the known limit below.
  - The script is ready when a TCP connection to `{host}:{TSUNAGIAI_PORT}` succeeds (a try every 100 ms, 500 ms each; `TSUNAGIAI_PORT` is the connection's port, the host is the connection's host; the same port is given as `COOKAPPS_PORT` too, the name before the rename, for a saved script that reads it). The probe connects and closes at once, so a port forward sees one connection that carries nothing. The wait is 2 minutes (`script::TIMING`).
  - Being ready proves only that something listens on `{host}:{TSUNAGIAI_PORT}`, not that it is the script's process: another process that starts listening there between the check of the port and the script's own listening is taken for the script, and MySQL is logged in to it with the password. The app does not check which process listens (no `lsof`, no pid of the listener); this is a known limit, like the gap between the check and the listening above.
  - The standard input and output are `/dev/null` and the standard error is read to the end, line by line (text that is not UTF-8 with replacement characters), keeping the last 5 non-empty lines, each cut to 300 characters; the wait for the end of the standard error is 1 second after the script has ended, because a process that the script left behind may hold it open.
  - The script runs in a process group of its own (`process_group(0)`, unix). Ending it sends SIGTERM to the group (`kill(-pgid)`, the crate `libc` 0.2, which tokio and the other dependencies already use; added as a direct dependency only for `kill`), waits 5 seconds for the first process, and sends SIGKILL to the group when it is still there; after the first process has gone, the group is sent SIGTERM again for what it left behind and SIGKILL after 5 seconds. The app's exit ends every script that is open, all together (`RunEvent::Exit` in `lib.rs`: the sessions, then the scripts). A kill of the app itself leaves the script running until it ends by itself. `tsunagiai-mcp` starts a script for `db_test` with a `Scripts` of its own: when it ends while a test waits, the runtime drops `supervise` before it ends the group, and `kill_on_drop` reaches the first process only, so a `Script` that is dropped while its group may still run (`done` not set) sends SIGKILL to the group (`Drop for Script`; it sends nothing after `supervise` has ended the group, because the group's id may be another process's by then).
  - A script that ended after it was ready closes the session on its next look (`Sessions::reap`, D-3): nothing is read at an interval for it. The monitoring task of a script (`supervise`) ends with the script, and a script that is gone from `Scripts` (a close, a delete of the connection) is ended with it.
- The MySQL session (#625, #631; `database/mysql.rs`) is opened with `sqlx` 0.9 (features `mysql`, `runtime-tokio` and `tls-rustls-aws-lc-rs`, no default features: no macros, no migrations, no other database), whose TLS is the rustls with `aws_lc_rs` that the app already has (`cargo tree -i native-tls`, `-i openssl` and `-i rsa` find nothing). The target is MySQL 5.7, 8.0 and 8.4 with `mysql_native_password` and `caching_sha2_password`.
  - The SSL mode is `Preferred` for a host that is the machine itself (`localhost`, a loopback address), with a script or without one: TLS when the server offers it, a plain connection otherwise. For every other host (over a network, with a script or without one) it is `Required` (with `Preferred` an attacker on the way could make the server look as if it had no TLS, and the password would go in plain text). In both modes the certificate is not verified (sqlx accepts any certificate; the owner's decision stays: it needs a CA bundle for each server, such as the one of RDS), so `Required` stops the downgrade and not a server that presents a certificate of its own. The time zone and the `sql_mode` are the server's: the defaults of sqlx (`time_zone='+00:00'`, `PIPES_AS_CONCAT`, `NO_ENGINE_SUBSTITUTION`) are turned off. The password of `caching_sha2_password` is sent through TLS, and the RSA path of sqlx (the feature `mysql-rsa` and the crate `rsa`) is not built in, so a server with no TLS that asks for that password is the error of D-2. Not tried against a real server by this code (only against a local fake of the protocol, `cargo test`): the TLS handshake and `caching_sha2_password` on MySQL 8.0 and 8.4.
  - Every session is made read only at its start (`SET SESSION TRANSACTION READ ONLY`), so a write is refused by MySQL. The password never goes into a URL (the options are set field by field), a log or an error. The connection test (`database_test`) reads the saved password of the connection from the keychain only when the field is empty and the connection still has the user, the script, the host and the port of the saved one (otherwise it is refused, so that the saved password is never sent to another place), and the password goes to no screen. The keychain has no way to ask whether a password is saved without reading it (`keyring` 4 and its macOS store: `get_attributes` and `get_credential` both go through `find_generic_password`), so the list reads each saved password to show "保存済み".
  - A connection has 15 seconds from the first byte to the answer of the first query; it is not retried.
- The open connections (#632; `database/session.rs`) are kept in the app's memory, one session for each connection (`tauri::State`, `Sessions`), and reused until they are closed: by the menu's "切断", by a save or a delete of the connection, by a query that shows the stream broken or past 30 seconds, and by the app's exit (`RunEvent::Exit` in `lib.rs`: the sessions, then the scripts). Nothing is read at an interval: a session is read only by a press, so a connection that is gone from the list has no process left (a delete closes it first). Closing a session also closes its tunnel (`ssm::Tunnels::close`).
  - The databases are read from `information_schema.SCHEMATA` and the tables from `information_schema.TABLES`; the name of the database is a bound value (`?`), and every value of a query that comes from the screen is bound, never put in the SQL text. The columns are cast in the SQL (`CAST … AS CHAR` for names, `AS UNSIGNED` for the row estimate and the lengths) so that they decode on MySQL 5.7, 8.0 and 8.4 alike; not tried against a real server by this code.
  - The records of a table (#633, D-4; `database/records.rs`) are read on the same session as one page of ``SELECT * FROM `db`.`table` LIMIT ? OFFSET ?`` (a page is 100 rows, 101 are asked for). The names are the only part put in the SQL text, between backticks with a backtick inside doubled, and the limit and the offset are bound, which makes the statement a prepared one: its rows come in the binary protocol, which `sqlx` gives as the bytes of each value (read without a typed decoder, so that the types that need the crates `chrono`, `bigdecimal` or the `json` feature are not added) and `cell_of` turns into text. Every value of a page is held in memory for the page only, a text is cut to 200 characters, a binary value is kept as its length, and a read past 30 seconds closes the session (as every query there). The estimate of the rows is `information_schema.TABLES.TABLE_ROWS`, bound by the schema and the table, and is shown as an estimate; it is read with the page 0 only, and a later page is given the one the screen holds. The rows are turned into cells one by one as they come, borrowed from the row's buffer, and the 101st is only counted.
  - The structure of a table (#634, D-5; `database/structure.rs`) is read on the same session from `information_schema.COLUMNS` (the name, the type, whether NULL is allowed, the key, the default and the comment) and `information_schema.TABLES` (the engine and the collation), with the schema and the table as bound values (`?`), never put in the SQL text, and every column cast as above. Two small queries at every press of the tab, each under the 30 seconds of every query there; the indexes, the foreign keys and the triggers are not read. Not tried against a real server by this code.
  - The SQL tab (#635, D-6; `database/sql.rs`) runs the text of the user on the same session as one prepared statement, as it is (only the whitespace and the semicolons at its ends are cut), under the read only session (D-2) that makes MySQL refuse a write. The database of the tree is chosen by a `USE` of its own with a quoted name (`records::quote_identifier`), never put in the user's text. The rows are limited to 1,000 and read as a stream that stops after the 1,001st, so the rest is never held; the time is limited by `max_execution_time` of 30 seconds (MySQL stops a SELECT itself) and by 35 seconds for the whole run, past which the connection and its script are ended (`KILL QUERY` is not used: it needs a second connection and the password kept in memory). Before each run the session is made read only again (the text of the user may have set it to read write) and `max_execution_time` and `sql_select_limit` are set, with the `USE`, in one round trip; after it, whatever the result (a `USE` that failed too), the read only is set again and the two are put back. Not tried against a real server by this code.
  - The row count of `information_schema.TABLES` is an estimate for InnoDB (and MySQL 8 may serve statistics up to a day old, `information_schema_stats_expiry`), so the screen names the column 行数（概算）.

## Updates

- Updates use `tauri-plugin-updater`. Pushing the annotated tag `v{version}`, or merging the Release PR (which makes that tag, `release.yml`), starts the `release` job, which makes `tsunagiai.app.tar.gz`, its `.sig` and `latest.json` (`scripts/make-latest-json.sh`) and puts them in a GitHub Release.
  The app reads `releases/latest/download/latest.json` (`plugins.updater.endpoints` in `tauri.conf.json`) and verifies the download with the public key `plugins.updater.pubkey`.
  `bundle.createUpdaterArtifacts` is not in `tauri.conf.json`; the `release` job passes it with `--config`, so a local build needs no signing key.
  The version is the tag's alone (at the owner's instruction, 2026-11-09; Discussion #293): `version` in `src-tauri/Cargo.toml` and `Cargo.lock` is fixed at `0.0.0` and `tauri.conf.json` has none, and the `release` job passes the version of the tag with `--config` too, which Info.plist, `app.package_info()` (U-2) and the updater's comparison take. A build without it (`tauri dev`, E2E) reports `0.0.0`, and `scripts/install-app.sh` passes the latest tag.
