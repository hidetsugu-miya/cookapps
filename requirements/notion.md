# Notion requirements

## N-1 Notion accounts

The settings screen has a tab 「Notion」 (between Slack and Claude, A-3) with one card, in the shape of the other integrations' cards: the header row (the logo `.logo.notion`, the name and the `?` hint `#notion-help`), under it one row for each connected workspace (`#notion-accounts`), and the add row (`.card-add`) with the button 「追加」 (`#notion-add`, `.text-btn.primary`). Rust is `src-tauri/src/notion.rs` (the commands `notion_accounts`, `notion_connect` and `notion_disconnect`, #367); the frontend is `ts/notion-settings.ts`. The OAuth connection, the tokens and the file of the workspaces are in `requirements/constraints.md`, "Notion".

The rows. A row is the common row of the settings (`itemRow`): an avatar with the initials of the workspace's name on the color that the name gives, the workspace's name (`.item-name`), under it the user's name and email address from `notion-get-self`, joined by 「 ・ 」 (the part that Notion did not give is left out; nothing when neither is), the state label and the button that unlinks (`.icon-btn`, `aria-label` 「{workspace} の接続を解除」). The state is 「使える」 (green) when a token is kept and 「再連携が要る」 (orange) when `reconnect` of `NotionAccount` is true, that is, when no token is kept. With no workspace the card says 「ワークスペースはまだありません」. A workspace is a row of its own: more than one can be connected, in the order that `notion_accounts` answers.

Reading. `notion_accounts` is called each time the Notion tab is shown, and draws the answer; it asks Notion nothing (it reads the file and the keychain). Only the latest read draws, and a read that began before an unlink does not. A failed read writes its message to the log (A-28) and leaves the card as it was.

Adding. 「追加」 calls `notion_connect` with no argument, which opens the default browser on Notion's consent; the button is disabled until the call ends, so that a second consent does not start. When it ends, with a success or a failure, the list is read again. A failure shows its message on a card (A-28). Connecting a workspace that is connected already replaces its token, so a workspace that shows 「再連携が要る」 is mended by 「追加」 and the consent of that workspace.

Unlinking. The unlink button opens the confirmation of the other integrations (「{workspace} の接続を解除しますか？」, 「キャンセル」 and 「解除」). 「解除」 calls `notion_disconnect` with the `workspaceId`, which revokes the grant at Notion and drops the token and the entry, and the row goes. A failure shows its message on a card (A-28) and keeps the row.

The `?` hint says how to add a workspace (the browser opens, the workspace is chosen and allowed, one workspace at a time, how to mend one that needs a new connection), and that the token is kept in the keychain and never shown. The card shows no text about what to do besides that (`.claude/rules/frontend.md`).

Unit tests (`cargo test`, `notion.rs`) are those of #367. The E2E spec `settings.e2e.ts` ("settings: Notion") covers that the workspaces are read only when the tab is shown, the rows (the name, the user, the two states and their colors, the initials, the unlink button of each), the header row and the add row, the empty card, the call of `notion_connect` (no argument, the button off while it waits, the list read again, a second workspace beside the first), a failed connection (a card, the list as it was, the button on again), the confirmation of an unlink (「キャンセル」 sends nothing, 「解除」 calls `notion_disconnect` with the `workspaceId` and draws the rest), a failed unlink (a card, the row kept), a failed read (the log, no row) and the hint; and `settings: tabs` covers the tab's place among the eleven.

Why. Notion is read through its MCP server, which needs a login of its own for each workspace, so the owner wants to see which workspaces are connected, under whose account, and whether each still works, before any screen shows Notion's pages (the owner's decision of 2026-11-10, #365: it is unclear whose account a screen shows unless the account is on it; this is the connection's part of it, #368).
