# Claude requirements

## A-1 Claude integration

A local MCP server (`cookapps-mcp`, stdio) lets Claude list, read, archive, mark read and trash inbox threads, and list events

## A-2 Claude model and effort

The Claude tab of the settings screen has a card "モデルと effort" (shown whether or not Claude can be used; the columns are headed "用途", "モデル" and "effort", and a note says the next call uses the choice and the default is Sonnet and medium, Sonnet and high for the Slack thread conversation, so the options carry no "(デフォルト)") with, for each of eight purposes, a name, where it is used, and two narrow selects that choose its model and its effort: the Slack summary (S-2, "Slack の要約", used when a Todo is made from a Slack message), the mail summary (M-8, "メールの要約", the AI summary of the mail detail), the prompt conversation (S-3, "プロンプトの会話", editing the Todo summary prompt with Claude) the Slack text proofreading (S-4, "Slack に貼る文章の校正", the Claude pane of the Slack compose screen) the Slack thread conversation (S-7, "Slack のスレッドの相談", the Claude pane of the thread detail) and the summary of a handoff (A-9, "Orca に渡す要約", "Orca に渡すペインで、渡す内容を要約するとき", the Claude call `claude_summarize_handoff` that returns the points of a summary of the content, quoted as data; the instruction the user wrote is not sent to it; the pane of A-9 calls it when the hand-over is pressed, and shows the selects of `orcaHandoff` in the frame of its field before a hand-over, as S-7 shows those of `slackReply`) and the Todo conversation ("Todo の相談", "Todo の Claude ペインで、タスクを頼むとき", the Claude call `claude_chat_todo` that returns a short reply and the proposed tasks, each a name, a date and a project, from the conversation so far, the new request, today's date and the Todoist projects of the last load; no tools and no MCP servers, as S-7, and the conversation and the request are enclosed as untrusted data; a request of more than 2000 characters is refused, a task is returned only with a name of 1 to 500 characters and a date of `YYYY-MM-DD` or `YYYY-MM-DD HH:MM` or none, a project that was not given is none, and an answer of more than 50 tasks is refused; the Claude pane of the Todo screen (T-7) calls it and shows the selects of `todoChat` in the frame of its request field, as S-7 shows those of `slackReply`) and the Slack conversation ("Slack の相談", "Slack の一覧とチャンネルの Claude ペイン", the Claude call `claude_chat_slack` of S-24 that returns a short reply and, when the request asks for one, the draft of a post, from the conversation so far, the new request and, when a channel is open, its recent messages; no tools and no MCP servers, as S-7; the Slack pane of S-24 shows the selects of `slackChat` in the frame of its request field, as S-7 shows those of `slackReply`). Each `claude -p` call uses the model and effort of its own purpose. The model is Haiku, Sonnet (the default) or Opus (Fable is not offered; a saved `"fable"` is an invalid value and gives Sonnet). The effort is low, medium (the default), high, xhigh or max, and `--effort` is always passed. Changing the model also switches the effort to the one the documentation recommends for it, saved in the same write: Haiku medium, Sonnet high, Opus medium (Rust `recommended_effort`, from https://platform.claude.com/docs/en/build-with-claude/effort, "Recommended effort levels"); the screen sends the model alone, and `claude_model_settings_save` takes an optional `effort` that defaults to the recommended one, while changing the effort sends both. The first default (nothing saved) stays Sonnet and medium, and Sonnet and high for `slackReply`. An effort select is colored by its value (`data-effort`, variables in `:root`): low gray, medium green, high yellow, xhigh orange, max red, following a change, a save and a failed save; the settings card colors the background and the text, and the frameless select of S-3 the text only. A change is saved at once, for that purpose only, in `claude-settings.json` in the app config directory (an object keyed by `slackSummary`, `mailSummary`, `promptChat`, `proofread`, `slackReply`, `orcaHandoff`, `todoChat` and `slackChat`, each `{model, effort}`; one save reads the file again, changes one purpose and writes all eight through a temporary file and a rename), and the next call uses it. Rust checks the purpose, the model and the effort against their lists when saving (a refusal is a Japanese message), and a missing file, an unreadable file or an invalid value gives the default for that purpose, so only a listed value reaches `--model` and `--effort`. A file in the old form, one `{model, effort}` pair for every call, gives that pair to all eight purposes until a purpose is saved, and a file without `slackReply` gives that purpose its default (and one without `orcaHandoff`, `todoChat` or `slackChat` gives it Sonnet and medium). From high up (high, xhigh, max) a call may run 300 seconds (`--effort max` took 61 seconds on a small input); below that it is 60 seconds for the summaries and 120 seconds for the prompt conversation, the proofreading, the summary of a handoff, the Todo conversation and the Slack conversation. The `?` hint of the Claude card says that each of the eight calls has its own model and effort. The thread detail of S-6 shows the selects of `slackReply` in the frame of its request field, as S-3 shows those of the prompt conversation. The screen of S-3 shows the selects of the prompt conversation too, and the Slack compose screen of S-4 those of the proofreading

## A-4 Claude connection

The `claude -p` calls of M-8, S-2, S-3, S-4 and S-7 go through the Claude Code CLI, which signs in either with the Claude subscription (the default) or with an Anthropic API key. The first card of the Claude tab ("Claude", with ↻ and `?`) has two rows with radios, "サブスクリプション" (email, plan, Claude Code version and state: ログイン中, 未ログイン with the `claude auth login` guidance, 未導入, 確認できません) and "API キー" (the workspace ID when Anthropic says it, the note that every call is billed, the state 未登録, 確認済み, 確認できません or 使えません, "貼り直す" and the disconnect button), so the state of the one not in use shows too. Pressing the radio of the API key row with no key stored, or with a key Anthropic refuses, only opens the key field ("確認して保存"); nothing is switched or logged out. If the keychain cannot be read, only the key row says 確認できません with the error; if asking for the connection itself fails, the card shows one failed row with the error and no radio, so nothing can be pressed, and Claude is in its failed state. At start only `claude_status` is called (so a start without the settings never asks Anthropic about a key); `claude_connection`, which answers the three parts of the card and the usable state `claude` with each state read once, is called when the Claude tab is first shown, by ↻ and after a change of the connection, and only the latest answer of the reads is used. While a change is on its way ↻ and the radios wait, and so does the button of the key field (also while the states are being read); sending the field while a change is on its way does nothing and does not empty it. A change of the connection redraws the connection card only, so the model selects and the prompt row keep their place and focus. Only the radio of a row switches the method (the radios are not grouped by name, so the arrow keys move none of them, and are disabled while a change is on its way); clicking or double-clicking the text of a row does nothing. The key is never shown, and the field is emptied as soon as it is read. The method is saved in `claude-auth.json` in the app config directory (`{"method":"subscription"|"apiKey"}`, written through a temporary file and a rename; a missing file, an unreadable one or an invalid value gives the subscription), and the key is in the OS keychain (service `jp.mysis.cookapps.claude`). Rust does not call the API for the work: the `claude -p` child process gets the key as `ANTHROPIC_API_KEY`, and `ANTHROPIC_AUTH_TOKEN` is taken out (the CLI prefers it) together with `ANTHROPIC_BASE_URL`, `CLAUDE_CODE_USE_BEDROCK`, `CLAUDE_CODE_USE_VERTEX` and `CLAUDE_CODE_USE_FOUNDRY` (they would send the key to another host or provider than the one it was checked against), while the subscription takes `ANTHROPIC_API_KEY`, `ANTHROPIC_AUTH_TOKEN` and `CLAUDE_CODE_OAUTH_TOKEN` out. The key is in no command-line argument, log line or error text. `claude auth status` answers `loggedIn: true` for a made-up key (measured), so it does not check a key. A pasted key is trimmed, must start with `sk-ant-` and must not be an Admin key (`sk-ant-admin`) (a refusal is a Japanese message), then `GET https://api.anthropic.com/v1/models?limit=1` with `Authorization: Bearer` and `anthropic-version: 2026-10-21` (a short timeout) asks Anthropic, and the response header `anthropic-workspace-id` is shown on the key row. 401 and 403 mean the key cannot be used; any other failure means it cannot be checked. At registration neither is saved. When `claude_status` asks again later, a key that cannot be checked stays usable (only the state says 確認できません), and a key Anthropic refuses is not usable. A key registered from the field that the radio of the API key row opened (`claude_key_save` with `switch`: after the check, the keychain write and the `claude-auth.json` write), and pressing the radio of a stored key (`claude_method_set` asks Anthropic first and refuses a rejected key; one that cannot be asked about is let through), switch to the API key and run `claude auth logout` for Claude Code, unless the API key is the method already (then nothing is logged out, so a login made again by hand is kept). The logout is checked by reading `claude auth status` again (that alone, no `--version`): only logged out or no Claude Code counts, and a login that remains, or a status that cannot be read, means the logout is not confirmed (the switch stays). `claude_method_set` then answers an error; `claude_key_save` answers that the key is stored, with `logoutError`, and the screen closes the field and shows that text as the error. A key pasted again with "貼り直す" (`switch` false) only replaces the key: the method does not change and nothing is logged out. Going back to the subscription only changes the method (the key is kept, and a logged-out row says 未ログイン with the `claude auth login` guidance). Deleting the key asks for confirmation, and when the key was in use the method goes back to the subscription (the logout is not undone). The usable state the whole screen follows (`Claude`: the sidebar, Todo, M-8, S-4, S-7, S-3) is `ready` for a logged-in subscription, or for an API key that is not refused (then email and plan are empty, the sidebar popup and the button's `aria-label` say "API キー" instead of the email); it is not `ready` while the key is refused or missing. The `?` hint explains the key (made in the Console, limited to a workspace, kept in the keychain, switching logs Claude Code out on this device). No cost is shown. Unit tests and E2E never run a real logout

## A-32 Skills tab

The settings screen has a tab 「スキル」, right of 「Claude」 (A-3), with one card of the same name. It makes, changes and deletes the skills of #127: the instructions the owner writes once for the Claude calls of the screens that talk to it (S-4, S-7). The files and the four commands (`skill_list`, `skill_get`, `skill_save`, `skill_delete`) are in `src-tauri/src/skills.rs` and `requirements/constraints.md` ("Claude and skills"); the frontend is `ts/skill-settings.ts`, which draws what Rust answers and sends what the form holds. Rust checks every text and answers a refusal in Japanese (`skills::check`). No help text is on the card (`frontend.md`).

Why. The owner asked for a place in the settings to make, change and delete skills, with the list at the left and the edit field at the right (2026-11, issue #340, from #127; Discussion #123). Changing the instructions through a talk with Claude is a later issue (#345) and is not here.

The list. `skill_list` is called each time the tab is shown (never at the start of the app or when the settings open on another tab), and only the latest answer draws. The left column (`#skill-list`) has a button (`.skill-row`) for each skill, in the order Rust answers, with the display name (`.item-name`) and under it the name (`.item-meta`); the one the form shows has `aria-current="true"`. With none, the column says 「スキルはまだありません」. Under the list is 「新しいスキル」 (`#skill-new`, `aria-pressed` while the form is for a new skill). A failed read shows its message in `#error`.

The form. It is hidden until a skill is pressed or 「新しいスキル」 is pressed. Pressing a skill fills it from the list's answer (no other call); pressing 「新しいスキル」 empties it and gives the focus to 「名前」. Its fields are 「名前」 (the name of the skill, the folder of `SKILL.md`), 「表示名」, 「使う画面」 (a check box for each screen that can use skills: 「Slack に貼る文章の校正」, `slack-paste`, and 「Slack のスレッドの相談」, `slack-thread`), 「説明」 and 「指示」 (the body of `SKILL.md`), then 「削除」 (only for a saved skill) and 「保存」. The name of a saved skill is read-only, because it is the folder: another name would make a second skill. A field has no placeholder.

Saving. 「保存」 (or Enter in a one-line field) calls `skill_save(skill, create)` with the fields as typed (the name is not trimmed here: Rust checks it), the checked screens (in the order of the check boxes on the screen, not of the presses), and `create`, which is true for a new skill (the form opened by 「新しいスキル」) and false for a saved one, and takes the answer as the skill as saved (texts trimmed, the screens in a fixed order), which fills the form again, and the list is read again. A new skill whose name is a saved skill's is not sent: `#error` says 「スキル「{name}」はもうあります」, because a save of a taken name replaces that skill. The list the screen holds may not have been read (it is still on its way, or its read failed), so Rust refuses it too: with `create`, `skill_save` answers the same 「スキル「{name}」はもうあります」 when `SKILL.md` of that name exists, and saves nothing; without `create` it replaces the skill as before. The check of the screen stays, so that the usual case sends nothing. A failed save shows its message in `#error` and keeps the form as typed. While a save or a delete is on its way, another press of 「保存」, 「削除」, a skill or 「新しいスキル」 does nothing.

Deleting. 「削除」 opens the confirmation of A-18 (`confirmDelete`, `role="alertdialog"`, 「{display name} を完全に削除します。元に戻せません。」) under the button; 「キャンセル」 closes it and changes nothing. 「削除」 in it calls `skill_delete(name)`, hides the form and reads the list again. A failed delete shows its message in `#error` and keeps the form.

Not here. A change that is not saved is lost when another skill or 「新しいスキル」 is pressed (there is no warning). Renaming a saved skill, and a skill for a screen other than the two, are not offered.

No new command, no new saved file, no new call to an outside service.

Unit tests (`cargo test`) of the commands are those of #339 (`skills.rs`), and the ones of `create` (a new skill never replaces a saved one, a folder with no `SKILL.md` is a free name, a save without `create` replaces). The E2E spec `settings.e2e.ts` ("settings: skills") covers that the list is read only when the tab is shown, the list and its empty note, the form of a saved skill (its fields, the read-only name, the delete button) and of a new one (pressed by the page's own click, because the driver's click focuses the button after the handler), a save of a new skill and of a changed one (the arguments of `skill_save` with `create`, the screens in the order of the check boxes, the form taking the saved answer, the list read again), a new skill sent with `create` when the list was not read and the refusal of Rust shown, a taken name not being sent, a failed save, the delete with its confirmation and its cancel, a failed delete and a failed read, and no placeholder. The tab's place and its panel are in "settings: tabs".
