# Claude requirements

## A-1 Claude integration

A local MCP server (`tsunagiai-mcp`, stdio) lets Claude list, read, archive, mark read and trash inbox threads, and list events

The language servers of a project of the Orca screen (A-34, #960) are read and written by four tools, so that Claude Code can set them up (the owner's decision of 2026-11-18, #957). They go through the functions of `src-tauri/src/lsp.rs` that the app's own save uses (`read_settings`, `save_server`, `delete_server`, `set_ssh_host`), so every check of a save applies, the file `lsp-settings.json` keeps its shape, and a change is read and written under one lock. Each takes `environment` (`local` is this Mac, which the app saves as no environment; any other text is the name of a saved environment) and `project` (the id of the repository in Orca, the key of A-34) and answers the settings of that project as saved (`environment`, `project`, `sshHost` and `servers`, in the names of `lsp_settings` of A-34).
- `lsp_settings` (`read_only_hint`): reads them, `servers` being `[{language, name, autoStart, command, mount, service}]` with one server for each language, the unset ones (ruby-lsp, of the language `ruby`, which starts by itself) for a project with nothing saved. A key that a save would refuse (empty, a control character) is refused.
- `lsp_server_save` (`destructive_hint`): takes `server`, `{language, name, autoStart, command, mount, service}` (`language` and `autoStart` always, the rest left out for what the app decides: a `name` left out is the name that the app's table gives the language, and a `command` left out is the server that the app finds for the language in the place the worktree runs in, #974). The server of the same language is replaced as a whole and keeps its place, else this one is put after the others. The result is checked as a whole: the language one of A-21 and taken by one server, a name of at most 64 characters, an absolute `mount`. A project with nothing saved has ruby-lsp, so a server of `ruby` replaces ruby-lsp.
- `lsp_server_delete` (`destructive_hint`): takes `language` and deletes the server of that language; a language the project has no server of is an error. A project with no server is kept as one with none (not as the unset ones).
- `lsp_repo_ssh_host_set` (`destructive_hint`): takes `ssh_host`, a Host of `~/.ssh/config` that `ssh::check_host` accepts, or an empty text to take it off; the servers are kept.

The descriptions say that `language` is a language name of A-21 and that `command` is a statement that `/bin/sh -c` runs in the worktree. A write asks the client for a check each time (the same decision as D-8's `db_profile_save`), and none of the four is offered with `--formation`: the orchestrator runs in auto mode, and `FORMATION_KEPT_TOOLS` keeps only the reads of mail, calendar and `db_profiles`. The command of a server is run by the app, in the worktree, when a file of its language is opened, so it is the owner's own text as written (A-34). The pane of A-36 that the ✦ of the language server part opens (A-34, #976) is the client of `lsp_settings` and `lsp_server_save`: its first instruction names the environment and the project as the values these tools take, and every write of the pane asks the owner in the terminal, as above.
Unit tests (`cargo test`): the functions of `lsp.rs` (add, replace in place by the language, refuse and write nothing, delete by the language, the ssh host set and taken off, the key checked) and, in `tsunagiai-mcp.rs`, the annotations of the four tools, the words their descriptions must hold, the arguments (what is required and what is left to the app) and the list of the tools with and without `--formation`. No E2E: no screen.

## A-4 Claude connection

The `claude -p` calls of M-8, S-2 and A-9 go through the Claude Code CLI, which signs in either with the Claude subscription (the default) or with an Anthropic API key. The first card of the Claude tab ("Claude", with ↻ and `?`) has two rows with radios, "サブスクリプション" (email, plan, Claude Code version and state: ログイン中, 未ログイン with the `claude auth login` guidance, 未導入, 確認できません) and "API キー" (the workspace ID when Anthropic says it, the note that every call is billed, the state 未登録, 確認済み, 確認できません or 使えません, "貼り直す" and the disconnect button), so the state of the one not in use shows too. Pressing the radio of the API key row with no key stored, or with a key Anthropic refuses, only opens the key field ("確認して保存"); nothing is switched or logged out. If the keychain cannot be read, only the key row says 確認できません with the error; if asking for the connection itself fails, the card shows one failed row with the error and no radio, so nothing can be pressed, and Claude is in its failed state. At start only `claude_status` is called (so a start without the settings never asks Anthropic about a key); `claude_connection`, which answers the three parts of the card and the usable state `claude` with each state read once, is called when the Claude tab is first shown, by ↻ and after a change of the connection, and only the latest answer of the reads is used. While a change is on its way ↻ and the radios wait, and so does the button of the key field (also while the states are being read); sending the field while a change is on its way does nothing and does not empty it. A change of the connection redraws the connection card only, so the model selects and the prompt row keep their place and focus. Only the radio of a row switches the method (the radios are not grouped by name, so the arrow keys move none of them, and are disabled while a change is on its way); clicking or double-clicking the text of a row does nothing. The key is never shown, and the field is emptied as soon as it is read. The method is saved in `claude-auth.json` in the app config directory (`{"method":"subscription"|"apiKey"}`, written through a temporary file and a rename; a missing file, an unreadable one or an invalid value gives the subscription), and the key is in the OS keychain (service `jp.mysis.tsunagiai.claude`). Rust does not call the API for the work: the `claude -p` child process gets the key as `ANTHROPIC_API_KEY`, and `ANTHROPIC_AUTH_TOKEN` is taken out (the CLI prefers it) together with `ANTHROPIC_BASE_URL`, `CLAUDE_CODE_USE_BEDROCK`, `CLAUDE_CODE_USE_VERTEX` and `CLAUDE_CODE_USE_FOUNDRY` (they would send the key to another host or provider than the one it was checked against), while the subscription takes `ANTHROPIC_API_KEY`, `ANTHROPIC_AUTH_TOKEN` and `CLAUDE_CODE_OAUTH_TOKEN` out. The key is in no command-line argument, log line or error text. `claude auth status` answers `loggedIn: true` for a made-up key (measured), so it does not check a key. A pasted key is trimmed, must start with `sk-ant-` and must not be an Admin key (`sk-ant-admin`) (a refusal is a Japanese message), then `GET https://api.anthropic.com/v1/models?limit=1` with `Authorization: Bearer` and `anthropic-version: 2026-10-21` (a short timeout) asks Anthropic, and the response header `anthropic-workspace-id` is shown on the key row. 401 and 403 mean the key cannot be used; any other failure means it cannot be checked. At registration neither is saved. When `claude_status` asks again later, a key that cannot be checked stays usable (only the state says 確認できません), and a key Anthropic refuses is not usable. A key registered from the field that the radio of the API key row opened (`claude_key_save` with `switch`: after the check, the keychain write and the `claude-auth.json` write), and pressing the radio of a stored key (`claude_method_set` asks Anthropic first and refuses a rejected key; one that cannot be asked about is let through), switch to the API key and run `claude auth logout` for Claude Code, unless the API key is the method already (then nothing is logged out, so a login made again by hand is kept). The logout is checked by reading `claude auth status` again (that alone, no `--version`): only logged out or no Claude Code counts, and a login that remains, or a status that cannot be read, means the logout is not confirmed (the switch stays). `claude_method_set` then answers an error; `claude_key_save` answers that the key is stored, with `logoutError`, and the screen closes the field and shows that text as the error. A key pasted again with "貼り直す" (`switch` false) only replaces the key: the method does not change and nothing is logged out. Going back to the subscription only changes the method (the key is kept, and a logged-out row says 未ログイン with the `claude auth login` guidance). Deleting the key asks for confirmation, and when the key was in use the method goes back to the subscription (the logout is not undone). The usable state the whole screen follows (`Claude`: the sidebar, Todo, M-8, S-4, S-7) is `ready` for a logged-in subscription, or for an API key that is not refused (then email and plan are empty, the sidebar popup and the button's `aria-label` say "API キー" instead of the email); it is not `ready` while the key is refused or missing. The `?` hint explains the key (made in the Console, limited to a workspace, kept in the keychain, switching logs Claude Code out on this device). No cost is shown. Unit tests and E2E never run a real logout

## A-32 Skills tab

The settings screen has a tab 「スキル」, right of 「Claude」 (A-3), with one card of the same name. It makes, changes and deletes the skills of #127: the instructions the owner writes once for the Claude of the screens that talk to it (S-4, S-7). The files and the four commands (`skill_list`, `skill_get`, `skill_save`, `skill_delete`) are in `src-tauri/src/skills.rs` and `requirements/constraints.md` ("Claude and skills"); the frontend is `ts/skill-settings.ts`, which draws what Rust answers and sends what the form holds. Rust checks every text and answers a refusal in Japanese (`skills::check`). No help text is on the card (`frontend.md`).

Why. The owner asked for a place in the settings to make, change and delete skills, with the list at the left and the edit field at the right (2026-11, issue #340, from #127; Discussion #123). Changing the instructions through a talk with Claude is a later issue (#345) and is not here.

The list. `skill_list` is called each time the tab is shown (never at the start of the app or when the settings open on another tab), and only the latest answer draws. The left column (`#skill-list`) has a button (`.skill-row`) for each skill, in the order Rust answers, with the display name (`.item-name`) and under it the name (`.item-meta`); the one the form shows has `aria-current="true"`. With none, the column says 「スキルはまだありません」. Under the list is 「新しいスキル」 (`#skill-new`, `aria-pressed` while the form is for a new skill). A failed read writes its message to the log (A-28) and shows no card.

The form. It is hidden until a skill is pressed or 「新しいスキル」 is pressed. Pressing a skill fills it from the list's answer (no other call); pressing 「新しいスキル」 empties it and gives the focus to 「名前」. Its fields are 「名前」 (the name of the skill, the folder of `SKILL.md`), 「表示名」, 「使う画面」 (a check box for each screen that can use skills: 「Slack に貼る文章の校正」, `slack-paste`, and 「Slack のスレッドの相談」, `slack-thread`), 「説明」 and 「指示」 (the body of `SKILL.md`), then 「削除」 (only for a saved skill) and 「保存」. The name of a saved skill is read-only, because it is the folder: another name would make a second skill. A field has no placeholder.

Saving. 「保存」 (or Enter in a one-line field) calls `skill_save(skill, create)` with the fields as typed (the name is not trimmed here: Rust checks it), the checked screens (in the order of the check boxes on the screen, not of the presses), and `create`, which is true for a new skill (the form opened by 「新しいスキル」) and false for a saved one, and takes the answer as the skill as saved (texts trimmed, the screens in a fixed order), which fills the form again, and the list is read again. A new skill whose name is a saved skill's is not sent: a card (A-28) says 「スキル「{name}」はもうあります」, because a save of a taken name replaces that skill. The list the screen holds may not have been read (it is still on its way, or its read failed), so Rust refuses it too: with `create`, `skill_save` answers the same 「スキル「{name}」はもうあります」 when `SKILL.md` of that name exists, and saves nothing; without `create` it replaces the skill as before. The check of the screen stays, so that the usual case sends nothing. A failed save shows its message on a card (A-28) and keeps the form as typed. While a save or a delete is on its way, another press of 「保存」, 「削除」, a skill or 「新しいスキル」 does nothing.

Deleting. 「削除」 opens the confirmation of A-18 (`confirmDelete`, `role="alertdialog"`, 「{display name} を完全に削除します。元に戻せません。」) under the button; 「キャンセル」 closes it and changes nothing. 「削除」 in it calls `skill_delete(name)`, hides the form and reads the list again. A failed delete shows its message on a card (A-28) and keeps the form.

Not here. A change that is not saved is lost when another skill or 「新しいスキル」 is pressed (there is no warning). Renaming a saved skill, and a skill for a screen other than the two, are not offered.

No new command, no new saved file, no new call to an outside service.

Unit tests (`cargo test`) of the commands are those of #339 (`skills.rs`), and the ones of `create` (a new skill never replaces a saved one, a folder with no `SKILL.md` is a free name, a save without `create` replaces). The E2E spec `settings.e2e.ts` ("settings: skills") covers that the list is read only when the tab is shown, the list and its empty note, the form of a saved skill (its fields, the read-only name, the delete button) and of a new one (pressed by the page's own click, because the driver's click focuses the button after the handler), a save of a new skill and of a changed one (the arguments of `skill_save` with `create`, the screens in the order of the check boxes, the form taking the saved answer, the list read again), a new skill sent with `create` when the list was not read and the refusal of Rust shown, a taken name not being sent, a failed save, the delete with its confirmation and its cancel, a failed delete and a failed read, and no placeholder. The tab's place and its panel are in "settings: tabs".

## A-36 Claude Code pane

The shared part of the panes in which Claude Code runs as a terminal, with the tools of `tsunagiai-mcp` (the owner's decision of 2026-11-16, issues #722 and #730). The screens that hold such a pane are the database screen (D-7, #720 and #773: the Claude tab, the first tab of the pane at the right, with the built-in tools), the orchestration mode of the development screen (A-37, #793 and #795: the pane `formation:{name}`, `kind: "formation"`), the language server part of the Orca file pane (A-34, #976: the pane `lsp-claude`, owner `orca-lsp`, with the built-in tools and a first instruction), the right side of the Todo screen (T-7, #732: the pane `todo-claude`, owner `todo-claude`, with no built-in tools and a first instruction), the left column of Claude mode of the Slack compose screen (S-4, #734: the pane `slack-compose`, owner `slack-compose`, with no built-in tools and a first instruction), the right of the calendar screen (C-6, #1062 and #1074: the pane `calendar-claude`, owner `calendar-claude`, with no built-in tools, the `auto` permission mode and a first instruction), the right pane of the Todo prompt screen (S-3, #733: the pane `todo-prompt`, owner `todo-prompt`, with no built-in tools and a first instruction), the right pane of the page of a Todo draft (S-18, #736: the pane `todo-draft`, owner `todo-draft`, with no built-in tools and a first instruction) the right of the Slack thread (S-7, #735: the pane `slack-thread`, owner `slack-thread`, with no built-in tools and a first instruction), the right of the Slack screen's unread list, watch and channel history (S-24, #737: the pane `slack-claude`, owner `slack-claude`, with no built-in tools and a first instruction) and later issues; this requirement is the part they share.

Where it runs. つなぎAI opens a pseudo terminal itself (Rust, `src-tauri/src/claude_code.rs`, the crate `portable-pty`), with no Orca in between, and the screen draws it with the xterm.js of `ts/orca-terminal.ts` (a terminal of the kind `pty`), so the font, the colors and the keys of A-13 to A-15 and A-20 are the Orca terminals'. `ts/claude-code.ts` is what a screen calls: `showClaudeCode(host, {id, builtinTools, permissionMode, skill, prompt, onEnd}, owner)`, `isClaudeCodeShowing(host, id, owner)`, `hideClaudeCode(owner)` and `closeClaudeCode(id, owner)`. A screen gives each pane an `id` (Rust names the process by it) and an `owner`, and a host element that the terminal fills (`.claude-code-pane`).

The folder. Claude Code runs in `claude-code/` of the app config directory, which holds two files that the app writes at each start: `mcp.json`, the config of `--mcp-config`, which names `tsunagiai-mcp` at the place next to the app's own executable (`Contents/MacOS/tsunagiai-mcp` in the bundle) and no other server, and a launch script (`start.sh`, or `start-with-tools.sh` for a screen that keeps the built-in tools). The pseudo terminal runs `/bin/sh {script}` with the folder as its working folder, with an argument array and no other shell. The script is written in a fixed form from three paths that the app decides (the `claude` found, `mcp.json`, and the fixed flags) and nothing from a mail, a message, a Todo or a summary: it adds `/usr/local/bin` and `/opt/homebrew/bin` to the PATH and runs `exec claude --tools '' --permission-mode manual --setting-sources user --strict-mcp-config --mcp-config {mcp.json} "$@"`. `--permission-mode manual` makes Claude Code ask the owner for every tool that writes, whatever `defaultMode` the owner's user settings hold (a write of `tsunagiai-mcp` such as `trash`, `archive`, `db_profile_save` and `db_test`, and Bash on the screen that keeps the built-in tools: the owner's decision of 2026-11-16, #722), and `--setting-sources user` reads only the user settings, not the `.claude/settings.json` and `.claude/settings.local.json` of `claude-code/`, which every pane shares, so that an "always allow" chosen in one pane is not kept for the others (it holds for that session only). `--tools ''` is left out when the screen asks for the built-in tools (the database screen does, #720: its pane has the id and the owner `database-claude`, it is shown and hidden with `showClaudeCode` and `hideClaudeCode` as the pane at the right is opened and closed or the screen is shown and left, and `closeClaudeCode` ends it only when its tab is closed or its process has ended by itself, D-7), and `"$@"` is `--plugin-dir {folder}` when the pane has a skill of A-32 (the plugin folder is the one `skills::plugin_for` makes for the call, and goes when the process ends), then `-- {prompt}` when the pane has a first instruction (below). `claude` is the installer's file (`~/.local/bin/claude`), else the first one found in the PATH of the app, `/usr/local/bin` and `/opt/homebrew/bin`. The sign-in is the one of A-4: the child gets the same environment changes as a `claude -p` call (the API key as `ANTHROPIC_API_KEY`, or the subscription with the credential variables taken out). Every pane's child process also has no variable that starts with `ORCA_` (Orca's own, which its state hooks read) or `CLAUDE_CODE_MESSAGING_` (those of its orchestration), so that a Claude Code of ours does not take its pane for one of Orca's when the app was started from an Orca terminal. The orchestrator of A-37 is the pane with the id `formation:{name}` (`kind: "formation"`), which runs in `formations/{name}/` (the folder of the formation of that name, A-37) with a script of its own. `claude_code_start` takes no projects and ignores the `prompt` of the screen for this pane: Rust reads the projects saved with the formation (`formations/{name}/formation.json`, A-37) in `prepare`, and adds their first instruction as the last argument of the script, at each start and so at a restart too.

The permission mode (#1074; the owner's decision of 2026-11-19, #1070).
A screen may give a pane `permissionMode`, "manual" or "auto", and `claude_code_start` takes it as an argument (`permissionMode`, `ClaudeCodePermissionMode` in `ts/bindings/`); `ts/claude-code.ts` passes "manual" when the screen gives none.
Rust reads it as one of the two words and refuses any other text, so a screen cannot pass another mode to `--permission-mode`.
"manual" is the script above, as it was.
"auto" starts the pane with `start-auto.sh` and `mcp-calendar.json`, which `claude-code/` holds beside the others and the app writes at each start of such a pane: the script runs `exec claude --tools '' --permission-mode auto --setting-sources user --strict-mcp-config --mcp-config {mcp-calendar.json} "$@"`, and the config names `tsunagiai-mcp` with the argument `--calendar`.
Claude Code then asks the owner for no tool, so `--calendar` makes `tsunagiai-mcp` offer the seven tools of the calendar screen only (`CALENDAR_TOOLS`: `list_events`, `list_calendars`, `calendar_set_shown`, `calendar_create_event`, `calendar_update_event`, `calendar_delete_event` and `calendar_show_slots`, C-6), and no other tool that writes can run unasked.
"auto" with the built-in tools, and "auto" for the orchestrator (A-37, which has its own script and mode), are refused with a Japanese message before any file is written or process started (`claude_code::check_permission_mode`).
Only the calendar pane (C-6) takes "auto"; what an unasked tool does, a notice to a guest included, is sent with no check (the owner's decision, #1070).

The first instruction (#976). A screen may give a pane `prompt`, the text that Claude Code starts with: `claude_code_start` takes it as an optional argument (none or null for none) and the launch script gets it after `--`, as one element of the argument list (the same shape as the orchestrator's, which the script passes on as `"$@"`; the `--` is needed because the script ends with `--mcp-config`, which takes several values, and it keeps a text from being read as an option). The shell is not asked to read it. It is checked before any file is written or process started (`claude_code::pane_prompt`, with `formation::check_prompt`): 1 to 20,000 characters (counted as characters), not only blanks, no NUL (an argument cannot hold one), and the characters that are hidden or act as controls in a terminal (C0 and C1 controls other than the line break and the tab, DEL, zero-width, bidi and tag characters) are taken out first, as A-9 does for a card; a text that fails is refused with a Japanese message and nothing starts. A screen that builds the text from values that come from outside (a name, a path, a message) puts them inside a quote that the text calls data, and never loose in it. The pane `formation:{name}` takes none from the screen.

The process. The terminal starts with the size of the host (`cols` and `rows`, 1 to 1000 each; the screen fits it to the host and sends each change), the keys typed go to it one send at a time (at most 100,000 characters in a send, counted as characters and not as bytes, in order, and after the start has answered), and its output goes to the screen through one channel of events, `output` and `ended` (`ended` carries `clean`, true only when the process ended by itself with the exit code 0, which Rust decides from the status and the screen does not read from the message). A multi-byte character cut between two reads is held for the next. The first show starts the process, and `claude_code_start` answers the number of that start; hiding the pane leaves a running process running and drawing into the hidden terminal, and showing it again starts nothing. A pane whose process has ended (it printed `Claude Code が終わりました`) or could not start is begun anew when it is shown again after a hide: its screen is cleared and a process is started. The process ends, with everything it started (its process group: SIGTERM, and SIGKILL after 2 seconds), when the pane is closed (`closeClaudeCode`, which sends `claude_code_close` with the id and the number of the start, after the start has answered, and Rust ends the process only when that number is the one it holds for the id, so a close that comes late cannot end a process of a pane that started the same id again), when a pane of the same `id` starts, when the screen no longer takes its output (the page was reloaded), and when the app ends. When it ends by itself, the terminal draws `Claude Code が終わりました`, with the exit code when it is not 0, the keys typed after that are dropped, and `onEnd` of the options, when the screen gave one, is called only when the exit code is 0 (not for a start that failed, and not for an end with an exit code or a signal: the message stays drawn, and the screen decides what to do with the pane).

Errors. A failure to start is a Japanese message drawn in the terminal in the place of the output: `claude` is missing (「Claude Code が見つかりません。入れてから、もう一度試してください」), `tsunagiai-mcp` is missing at its place (「tsunagiai-mcp が見つかりません（{path}）。開発ビルドでは cargo build --bin tsunagiai-mcp で作ってください」: a development build has it only when it was built), the pseudo terminal or the process cannot be opened, the sign-in cannot be read, or the skill is not usable on the screen. The pane shows no help text (`frontend.md`).

Not here. The pane's screen, the header of its tabs, the choice of the skill, the text that a screen puts into Claude Code, and what Claude Code's answer is used for are those of the screens that hold a pane. Claude Code may ask whether to trust the folder `claude-code/` (not checked); nothing here answers it. A permission to use a tool of `tsunagiai-mcp` is asked by Claude Code in the terminal, as it always does.

The fields of a screen (#731; `src-tauri/src/screen_bridge.rs`, `ts/screen-bridge.ts`; the owner's decision of 2026-11-16, #722 decision 2: what Claude Code writes goes into the field as it is, the owner can take it back, and nothing is sent or saved). `tsunagiai-mcp` is another process than the app, so the app opens one Unix domain socket, `screen-bridge.sock` in the app config folder, at each start (mode 0600; a stale socket file of an earlier start is removed first, and a file there that is not a socket is never removed, only logged; a path over 100 bytes is refused). A tool call connects once, sends one line of JSON and reads one line: `{"op":"read","target"}`, `{"op":"write","target","fields":{name: text}}`, `{"op":"post","target"}` or `{"op":"changed","what"}`, answered `{"ok":true,"fields"?}` or `{"ok":false,"error"}` (a line holds at most 1 MiB). The call ends in a Japanese error, which is the tool's result, when the app is not running or the socket has no listener (「つなぎAIが動いていません…」), when the app does not answer within 8 seconds, and when the app answers with an error. Every request is checked in Rust before a screen is asked, by the client and again by the app: the name of a target (and of a field, and of a change) is 1 to 32 characters of `a-z`, `0-9`, `-` and `_`, a target must be in the list `RULES.targets` (a read, a write and a post), a write has 1 to 8 fields of at most 10,000 characters each (counted as characters), and a change is one of `RULES.changes` (`todo`, `calendar` and `calendar-shown`). The list of targets holds `slack-compose` (the Slack compose screen, S-4, #734, the first), `calendar-form` (the form of an event that Claude Code fills in instead of inviting a new guest, C-6, #1073: the fields `form` and `description`, a write only, open while the Claude pane of the calendar screen is open and the calendar screen is shown) and `calendar-slots` (the candidates of free time on the calendar screen, C-6, #1063: the fields `slot1` to `slot8`, each `start/end` in the form `YYYY-MM-DDTHH:MM/YYYY-MM-DDTHH:MM`, a read and a write and no post, open while the Claude pane of the calendar screen is open) and `todo-prompt` (the instructions of the Todo summary, S-3, #733: the one field `body`, a read and a write and no post, open while the Todo prompt screen is shown and its instructions are loaded) and `todo-draft` (the draft of a Todo made from a Slack message, S-18, #736: the fields `name` and `description`, a read and a write and no post, open while a draft page is open and the Todo screen is shown); and `slack-thread` (the open Slack thread and its reply field, S-7, #735: the fields `thread`, only read, and `reply`, a read and a write and no post, open while a thread is shown) and `slack-channel` (the history of the open Slack channel and its post field, S-24, #737: the fields `channel`, only read, and `post`, a read and a write and no post, open while the Slack screen is shown and no thread is); a screen adds its own name when its issue registers the screen's fields. `changed` is what `todoist_add_task` (below) uses to tell the app that the Todo changed (#732); the Todo screen registers `onScreenChanged("todo", …)` and reads its list again as after any change of a task.
The app passes a read, a write and a post to the screen as the event `screen-bridge-ask` (`ScreenAsk`: `id`, `op` `read`, `write` or `post`, `target`, `fields`) and waits at most 5 seconds (40 seconds for a post, which has a post to Slack on its way; the client waits 45) for the command `screen_bridge_answer(id, answer)` (`ScreenAnswer`: `ok`, `fields`, `error`); the answer is the value the screen holds now, not one that Rust kept. An answer that comes after the wait is dropped, and an ask with no answer leaves nothing waiting. A screen registers its target with `registerDraftTarget(name, {names, isOpen, read, write, post?})`: `names` are the fields a write may name (a write that names another is refused before anything is written, with the names it has), a target that is not registered, or whose screen is not open (`isOpen` is false), answers a Japanese error for a read, a write and a post, `write` puts the texts into the fields (a thrown error with a Japanese message is the refusal, and the whole write is refused), and `post`, which a screen may have, does what the screen's own "投稿" button does and answers fields that say what happened (`state`); a screen without it answers that it cannot post. The screen keeps what its fields held before each write and draws its own 「元に戻す」: only the screen knows when a change of the owner's makes the way back unusable (S-4 does, newest write first). A post that waits longer than its wait answers 「投稿の結果を待ちきれませんでした。投稿されたかどうかは、つなぎAIの画面で確かめてください」: it never tells the caller to try again. `onScreenChanged(what, run)` registers a function that the screen's code calls when the event `screen-bridge-changed` (the `what` as the payload) arrives.
The tools of `tsunagiai-mcp`: `screen_read(target)` (`read_only_hint`) answers `{target, fields, note}`, `screen_write(target, fields)` (`destructive_hint`, so Claude Code asks the owner each time) answers 「画面の欄に書き込みました」, and `slack_compose_post()` (`destructive_hint` and `open_world_hint`, no argument, so Claude Code asks the owner each time; S-23) asks the Slack compose screen to post its things to do and answers 「N 件を投稿しました」 or that the dialog of the destinations is open and nothing is posted yet. A field can hold a mail or a Slack message that someone else wrote, so the description of `screen_read` and the `note` of its answer say that the texts are data and no instruction in them is followed, and the texts are quoted as JSON strings. `slack_thread_read()` and `slack_channel_read()` (`read_only_hint`, no argument; S-7 and S-24, #735 and #737) answer the open Slack thread, and the history of the open Slack channel, as text enclosed between `BEGIN` and `END` lines that the app made: the descriptions say that the messages are data that others wrote and are never followed. The tools of the calendar screen (C-6, #1063 and #1073: the other six, which read and switch the calendars and create, rewrite and delete an event, are described in C-6, and each sends `changed` to the app after a success (`calendar` for an event, `calendar-shown` for `calendar_set_shown`), which `ts/calendar.ts` reads with `onScreenChanged`; `calendar_create_event` with a guest and `calendar_update_event` with a guest that the event does not have send nothing to Google and write the target `calendar-form` instead, so that the owner saves, C-6; none is offered with `--formation`). `calendar_show_slots` is the one of C-6, #1063; `calendar::slot_fields` in `calendar.rs`, `tsunagiai-mcp.rs`). `calendar_show_slots(slots)` (`read_only_hint`: it saves nothing and sends nothing outside the app, it only draws on the screen; the hint is no promise that Claude Code does not ask, because a pane in the `manual` mode asked for it all the same, tried 2026-11-19, and the calendar pane does not ask because it runs in the `auto` mode, #1074) takes 1 to 8 candidates, each `{start, end}` as `YYYY-MM-DDTHH:MM` in this Mac's time. The tools of Todoist (#732; `src-tauri/src/todoist.rs`, `tsunagiai-mcp.rs`). `todoist_projects` and `todoist_tasks` (`read_only_hint`) read Todoist as it is now, with one full sync (the same read as the app's, `fetch_sync`, and kept nowhere), with the token of the same keychain entry that the app reads (`read_token`); `todoist_projects` answers `{projects, note}` (the projects in tree order: `id`, `name`, `color`, `inbox`, `parentId`, `depth`) and `todoist_tasks` answers `{tasks, note}` (the active tasks by due date: `id`, `content`, `description`, `projectId`, `parentId` (a subtask is a row of its own), `priority` (as the Todoist apps number it: 1 is the most urgent), `due`, `labels`).
