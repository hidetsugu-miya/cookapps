# Orca requirements

## A-6 Orca

A screen of its own (`nav-orca`, `#orca`; the button is 「開発」 and this screen is its Orca mode, A-5 and A-37) shows which Claude agents run in Orca, a desktop agent orchestrator with a CLI (`orca`), shows their terminals (A-8, A-12) and starts new ones. It stores nothing about a session: every read asks the CLI again. Only agents of type `claude` are listed and started; an agent of another type (Codex) has no row, and a launch always starts Claude.

The screen is two panes side by side (`#orca` is a `.split-main`): the list pane `#orca-list` on the left, the divider `#orca-split` (a `.split-bar` with `role="separator"`, `aria-orientation="vertical"`, `aria-label` "一覧の幅", `aria-valuemin` 20, `aria-valuemax` 50 and `tabindex` 0), and the work pane `#orca-work`. The list is 25% of the screen at first and the user sets it between 20% and 50% by dragging the divider, or with the arrow keys (Right widens, Left narrows, 2% a step); the ratio is kept in memory (as the divider of S-1 and S-6, `ts/split.ts` serves both). The list pane has a header bar (`#orca-header`) as high as every header (44 px at least, A-23), level with the tab strip of the work pane, and no heading: it holds only the button of the list (A-23), 28 px high. It has no reload button (the list is read by the clock and when the screen is shown; at the owner's instruction, 2026-11-14) and no new button: a session is started from the plus of the work pane (A-16). The pane has no footer, no status label of the target and no menu of it, and a read that failed or a missing `orca` shows in the notice above the list (removed at the owner's instruction, 2026-11-16; #712). The list shows the projects (A-8) and nothing else: there is no working view that groups the agents by state (入力待ち, 作業中, 完了), and no button that switches to one (removed at the owner's instruction, 2026-11-14; #577). The agents are seen as the sessions under their projects (A-8) and in the count of the Orca button. `nav-count` of the Orca button shows the number of sessions that need the user: the rows that wait (入力待ち) plus the notices below, with the label "Orca（確認待ち n 件）"; 作業中 is not counted. The count is added to the Dock badge (`set_badge`, T-1), so the Dock shows a number when only Orca has a session that needs the user, and it goes when the sum is 0.

The work pane is split into panes (A-17); each has the tab bar (A-8, A-16: the tab strip of the selected project, shown also when it is empty, and the plus right after its last tab), and under it the terminal of the tab it shows (A-8, A-12), or a line (`.orca-empty`) that says why there is none: 「プロジェクトを選んでください」 when no project is selected, 「セッションはありません」 for a project with no session, and 「このセッションのターミナルはありません」 for a Claude session with no terminal handle. The screen has no composer and no history: the user types into the terminal. The pane of A-9 shows the terminal of the session it handed to (A-9).

New session. A session is started from the plus of the work pane (A-16), which calls `orca_start(path, environment)` with the place of that worktree (its `environment`: the saved environment's name, null for this machine): it starts Claude in that worktree with no first prompt (the user types it in the terminal). The dialog of the worktrees (`openWorktreeDialog`, `showMenu`, `role="dialog"`, shared with the chip of A-9) has a filter field (`aria-label` "worktree を絞り込む", case-insensitive on "{repo} ・ {branch}") and two-line rows (the repository, then the branch) of the worktrees it is given; picking one closes it. A launch is never tried again, because after a lost reply a second one would start twice (the CLI forbids a fresh retry of a launch); a failure shows the CLI's message (`error.message`) in `#error`. The side pane of A-9 launches and sends through the same checks (`orca_handoff` composes the prompt and then runs the same launch or send once); a send whose answer says `result.send.accepted` is false is a failure too (Japanese message).

After a launch. A launch that works follows the session it started (`orca_start` answers `{paneKey, handle}`, and A-9 uses the same answer): the project and the tab that were selected stay meanwhile, and once a read holds the row of that `paneKey` or of that `handle` (the one that is not `null`; the read after the launch, a later one or a list of the stream of A-12, for at most 30 seconds), the screen selects its project and its tab, so its terminal shows. Until the row is in the list the work pane shows a note (`#orca-started`, `role="status"`: 「セッションを始めました。一覧に現れるのを待っています…」), and the plus is disabled, so a second session cannot be started meanwhile. Selecting a project, a tab or a row, or a read after the 30 seconds (one that failed too) drops the wait; the launch is never followed after the user selected another project or tab while it was on its way. When Orca's reply had neither a `paneKey` nor a `handle` (both `null`), nothing can be waited for: the note says 「セッションを始めました。Orca の画面で開けます。」, the plus stays enabled, and the note goes at the next selection.

The CLI is found among the absolute places `/usr/local/bin/orca` and `/Applications/Orca.app/Contents/Resources/bin/orca` (a GUI app has no shell PATH), and run with an argument list, never through a shell, in the temporary folder, with stderr dropped and a timeout (15 seconds for a read, 60 seconds for a launch and a send) after which the child is killed, off the UI thread. The commands are `orca worktree ps --limit 200 --json` and `orca terminal list --json` (the list), `orca terminal send --terminal <handle> --text=<text> --enter --json` (send), `orca terminal create --worktree path:<path> --json` (a new terminal, A-16), `orca worktree create --repo=id:<repository id> --name=<name> [--branch=<branch>] [--base-branch=<ref>] --no-parent --json` (a new worktree, A-9; `--branch` and `--base-branch` only when given; `orca_worktree_create` answers `result.worktree.path`), `orca agent launch --agent claude --worktree path:<path> --surface terminal --prompt=<text> --json` (launch; `orca_start` gives no `--prompt`, and only the handoff of A-9 gives one; its reply holds `result.outcome` `{kind: "terminal", handle, paneKey}`, which `orca_start` and `orca_handoff` return as `{paneKey, handle}`, each `null` when the reply lacks it or holds it in a shape that is not a pane key (at most 256 characters of `[A-Za-z0-9:_-]`) or a terminal handle), and `orca environment list --json`; the text of the user is joined to its flag (`--text=--json` is accepted, while `--text --json` is refused as "requires a value"), and `--environment=<name>` is added to every one of them but the list of environments when a target is chosen. The output is JSON, `{ok, result, error: {code, message}}`, also on failure, so stdout is read whatever the exit code and `error.message` is shown (the code when there is no message); an empty output or one that is no JSON gives a Japanese message. The prompt text is in no log line.

Rows are built by a pure function from the two documents (`result.worktrees[].agents[]` and `result.terminals[]`), tolerant of absent fields. An agent is kept when its `agentType` is `claude`, it is top-level (`parentPaneKey` null) and `hasLivePty` is true. Its group follows `state`: `waiting`, `blocked` and `permission` are 入力待ち, `done` is 完了, and every other state (`working`, and a state not known yet) is 作業中. The line (the title of the row and of its tab) is the first line of `conversationName`, else of `prompt` and `taskTitle`, in this order (each read as A-8 says: only what the owner or Claude wrote, never a message of the harness, data or the output of a process), else the first line of the `title` of the terminal of the same pane (`result.terminals[]`, joined as below) without the status mark Claude Code puts in front of it (a first character that is no letter or digit, followed by a space; taken off once, with the spaces after it), whatever the state. Every one of these texts is read as A-8 says ("Sessions under a project"): the line is the first line that has text left, and a text with none gives the turn to the next one. The branch is the worktree's `displayName`, the repository its `repo` and the path its `path`. A row also carries the agent's last answer (`reply`: the first line of `lastAssistantMessage`, read as A-8 says (so a JSON object, the output of a process and a message of the harness are no reply) and cut to 200 characters; null when it has none), which the list draws after the line (A-8) and the tab does not, the number of its subagents at work (`subagents`: the items of its `subagents[]` whose `state` is `working`; 0 when the field is absent or is not an array, and an item that is not an object counts for none; Orca lists them only while they run), which the list draws at the right end of the row (A-8) and the tab does not, and the agent's `paneKey` (null when it has none), which names its tab (A-12), and its `status` and `projectKey` (A-8). The time is `stateStartedAt` for an agent that runs or waits ("2 分", the time since) and `updatedAt` for a done one ("18 分前"), sent as epoch milliseconds and formatted by the screen. The terminal handle is found by joining the agent's `paneKey` with the terminals' `"{tabId}:{leafId}"` (an orphaned terminal by its `recordedPaneKey`, as below). Rows are sorted by `updatedAt`, newest first. The launch targets are all worktrees, with their path, repository and `displayName`.

Just before it acts, Rust reads the list again (with the environment): a send goes only to a handle that belongs to a row of that list (a top-level agent of a live terminal; `writable` is not used, because a plain shell terminal is writable too; an orphaned terminal, one that lost its tab and still runs, belongs to the agent whose pane is its `recordedPaneKey` when its `agentIdentity` is `claude` and no other orphaned terminal recorded that pane, and a live terminal of that pane comes first), and a launch or a new terminal (A-16) only into a worktree of it; otherwise the answer is a Japanese error and nothing is sent. Rust validates before it runs anything and answers in Japanese: the text is not blank and at most 100,000 characters; the handle begins with `term_` and holds only `[A-Za-z0-9_-]`; the path is absolute; the environment is one listed by `orca environment list --json` (`result.environments`, each a name or an object with a `name`, else an `id`).

The target is "このマシン" or a saved environment (a paired server): the one place the screen is connected to besides this machine, so at most one saved environment is read at a time. While a saved environment is the target, this machine is read too and its items are in the same list (A-33). The target is read from `orca-settings.json` in the app config directory (`{"kind":"local"}` or `{"kind":"environment","name":"..."}`), and only when the file does not exist yet the first saved environment is used, else this machine. The app never writes the file and has no place to choose the target: no screen, menu or card changes it (the label and the menu of the list pane were removed at the owner's instruction, 2026-11-16, #712, and the card of the Orca tab of the settings at the owner's instruction, 2026-11-16, #714); the target is the saved value, and a change to the file is taken at the next read. A saved environment that is no longer listed, or a file that cannot be used while an environment is saved, never switches the target by itself: the read is a failed one with 「保存した接続先が見つかりません」 (shown in the notice above the list), and the owner corrects the file (with no environment saved there is nothing else to choose, so a file that cannot be used gives this machine). The list pane shows no label of the target and no menu of it, and the pane has no footer (removed at the owner's instruction, 2026-11-16; #712). What a read says is in the notice above the list: 「読み込めませんでした: {message}」 in the failed style when it failed (the rows of the last good read stay while the target is the same; the notice is the target's alone, and what the read of this machine says is not shown yet, A-33), and 「orca コマンドが見つかりません。…」 when no `orca` was found. When a read names a target other than the one held (the file was changed), the notices and the base of the old target are dropped, and the rows are those of the new target. When `orca environment list` itself fails, the screen keeps the target, the environments and the rows it had, and shows the failure. While the target is a saved environment that is listed, its list is streamed (A-12) and not read by the clock; this machine's list beside it is read by the clock (A-33).

The list is read at startup (for the count), every 10 seconds while the Orca screen is shown and every 60 seconds otherwise, one read at a time, and no more by the clock once the command was found missing (showing the screen looks again); a streamed list (A-12) is not read by the clock (this machine's beside it is, A-33). The count of the Orca button follows every read (the clock's read for the count alone included) through one function. It counts the sessions of this machine and of the saved environment, and no session of an SSH host: a Claude agent in a worktree whose `hostId` is not `local` makes no row, so neither the count, the badge of the Dock nor a notice has it (the owner's instruction, 2026-11-16, issues #783 and #785). A row has stopped when its group is 完了 or its status is `failed` or `interrupted` (Orca says an agent stopped with Esc as `state` `done` with `interrupted` true). A stopped row has a notice when, while the app runs, it went from not stopped to stopped between two reads, or it first appeared in a read after the first of the target and had already stopped (a pane the app has seen stopped is remembered, so it has no new notice when it leaves the list and comes back stopped, and the memory ends when it is seen running or a read names another target). The rows of the first read of a target (at startup, and after a read names another target) are only the base and have no notice, so what had finished before is not counted; a read that names another target than the one held drops every notice. A notice goes when the session is shown on the Orca screen (the screen is shown, the window is not hidden, and the row is the selected tab; the session seen only in the side pane of A-9 does not clear it), when the row runs again (it is no longer stopped), or when it leaves the list; a row that stops while it is shown has no notice. A row with no pane key cannot be opened, so it has no notice (it is still counted while it waits). A failed read, and a read that did not find the rows while the command is there, leave the notices as they are; a missing command drops them. The notices are held in memory only. While one row or more is working (its group is 作業中 and its status is `working` or `monitoring`), the icon of `#nav-orca` (the `svg` only, not `.nav-count`) is yellow (`--agent-working`) and fades slowly (`opacity` between 1 and .55 over 2 seconds, `ease-in-out`, endless), by the class `working` on the button; under `prefers-reduced-motion: reduce` it stays yellow and does not fade. The number that work is not on the button: it is in the `aria-label` (read aloud, and in the tooltip on hover), after the count of the waiting ones (「Orca（確認待ち 1 件、作業中 2 件）」, 「Orca（作業中 2 件）」, 「Orca（確認待ち 1 件）」, else 「Orca」). The class and the label follow every read the count follows, so a read for the count alone moves them too; a failed read cannot say that a session works, so it takes the mark and that part of the label away and leaves the count of the waiting ones as it is, and a missing command or a change of the target removes them all.

The environments are read (`orca environment list`, and the target resolved) only at startup, when the screen is shown and in a read after a failure (`orca worktree ps` and `orca terminal list` of this machine are read at the same time as `orca environment list` whatever the file says: they are the target's own lists when this machine is the target, and the lists beside it (`local`, below) when a saved environment is); the clock reads the agents and terminals of the target held while the screen is shown, and only `orca worktree ps` (for the count, with no terminal list) while another screen is shown. A read in the background swaps the rows in place and keeps the selection (dropped only when its session is gone), the terminal shown and the scroll position, and never calls `show()`.

Where an item is. Every row, worktree, project and plain terminal that `orca_overview` and the stream of A-12 answer has `environment`: `null` for this machine, else the name of the saved environment it was read from (the stream places each list it sends in its environment, in the sink of `orca_stream_open`). While a saved environment is the target, `orca_overview` also reads this machine's lists, side by side with the target's (every scope, with the same terminals as the scope reads: `Badge` reads no terminal), and answers them as `local` (`OrcaLocal`: its own `state` and `message`, and the rows, worktrees, projects and terminals, each with `environment` `null`); `local` is `null` when this machine is the target, whose lists are the ones of the overview itself. The two reads fail apart: a failed or missing read of this machine is `local.state` `failed` or `missing` and leaves the target's lists and state as they were read, and a failed read of the target leaves `local`. The rest of the answer (the state, the rows and the count, and the notices) is the target's alone. The screen draws both places in one list (A-33): the lists of `local` and the target's are mixed, a project and a session of a saved environment carry its name (`environment`), and the place of an operation is read from `environment` ("Where an operation goes" below). The count of the Orca button and the notices stay the target's, whatever `local` holds. Both fields may be absent in TypeScript (`optional = nullable`), so a screen that does not read them is not changed by them.

Where an operation goes. An operation on a row, a tab or a worktree is called with the `environment` of that item (the saved environment's name, null for this machine) and not with the target the screen holds: the close of a terminal, the start of Claude or of a terminal from the plus (the worktree picked, A-16), the scratchpad (the worktree's, A-29), the stream or the mirror of a terminal with its reads, its keys and the files dropped on it (the tab's, A-10 and A-12), the file pane with its files, history, branches, downloads and diffs and the files it opens (the worktree's, A-18, A-24, A-25 and A-27), and the layout of A-17 and the files and diffs open in a project (the project row's; a project that the list does not hold takes the target). The list the screen draws holds both places (A-33), so the place is read from each item and each row gets its own. The side pane of A-9 keeps its own destination. The E2E specs cover it with a list that holds the rows of a saved environment and of this machine side by side (`orca.e2e.ts`: the close, the start, the layout, the files, the mirror's reads and keys and the attached image; `orca-files.e2e.ts`: the history).

Unit tests (`cargo test`) cover row building, the argument lists (the `--flag=value` form and the environment), the validation, the parsing of the output and the environments and the target setting, the place of every item of a read of a saved environment and of this machine (`assemble`, `place_in`, and `placed_in` of the stream), and that `local` comes beside the target's lists and that a failed read of either side leaves the other (`with_local`); none of them runs the real CLI. The E2E spec `orca.e2e.ts` covers (the mix of the two places is A-33's) the header, the two panes and the divider, the selection, the start from the plus (A-16: its menu, the dialog, the arguments of a launch and the following of its session, a failed launch), the missing command, a failed read shown in the notice, no label or menu of the target in the list pane, a read in the background, and the count and its notices.

## A-7 Orca session history

Retired (#478, the owner's decision 2026-11-12). The history of a session (what the user asked, what the agent answered and the tools it ran) is no longer read or drawn, and the app has no command for it: the pane of A-9 and the Orca screen show the terminal of the session (A-9, A-12), where a question of Claude is answered as well (A-11).

What stays is the connection to Orca's runtime, which the history was the first to use and which the other requirements name as A-7's (`src-tauri/src/orca_link.rs`, with the framing of `orca_e2ee.rs`). The runtime is not a public interface. It was written against Orca 1.4.248, and an Orca update can change it. This machine is reached over the unix socket of `orca-runtime.json` in Orca's settings folder (`authToken`, and the transport of kind `unix` with its `endpoint`): one JSON line `{id, authToken, method, params}` and one line back, a connection for each call. The socket exists on macOS and Linux; on another OS a call fails with a message that says so. A saved environment (A-6) is reached over its WebSocket (`ws://` only: the frames are encrypted end to end, with the pairing's key, and TLS is not built in) with the device token and the public key of `orca-environments.json`, using Orca's own framing. Both files are read at each connect and never written. A failed call shows Orca's code (「Orca がエラーを返しました（{code}）」), never Orca's own message; when Orca is not running on this machine the message is 「Orca に接続できません。Orca が起動しているか確認してください」. A token, a key or an authentication frame is in no log, no error text and no event. A caller that keeps a connection open tries again after 1, 2, 5, 10 and then 30 seconds.

Unit tests (`cargo test`) cover the framing and encryption of the paired connection against fixed vectors, the choice of the pairing and the endpoint, the answer of a call (the result, or the code and never the message), the handshake and a refused token against a stand-in server, a call over the unix socket, and the back-off; none of them talks to a real Orca.

## A-8 Orca terminal and project list

The Orca screen (A-6) shows the terminals of Orca, one for each tab, and its list pane is a list of projects with a switch to the working agents. It was written against Orca 1.4.248.

Projects. The list pane shows the projects. A row (a button, `.orca-project` in a `.orca-proj`, `aria-pressed` for the selected one) has the status icon, the name and the number of sessions (nothing when it is 0). The number stays a number when the project is open. A pure function builds them from the two documents of A-6: one project for each `repoId` among the worktrees that are not archived (`isArchived` is not true), have a path, and whose `hostId` is `local` (a worktree with no `hostId` is this machine's); the name is the worktree's `repo`. The worktrees of an SSH host (any other `hostId`) are not projects, and the list draws no row for them (below). The sessions of a project are its Claude rows (A-6) and its plain terminals. The projects with a working session (a session of the project whose icon is the yellow ring; the icon of the project itself may be a question or a failure, which outrank working, and the project is still one of them; also a project whose own icon works when no Claude row of it does, as when another agent or a worktree's status works) come first. The stopped projects follow: those with one session or more (the number of sessions shown on the row is not 0) that are not in the working group. The projects with no session come last. The stopped projects are newest first by the latest `lastActivityAt` of the project's worktrees, as the pure function lists them, and so are the projects with no session. The working projects are not reordered by their activity, which moves with the work: the screen keeps them in the order they entered the working group, in memory only. A project that begins to work (it had no working session at the last read that worked, or it is new, or the screen has just started) goes in front of the ones that already work, and several that begin together keep the order the function lists them in (newest first); one with no working session left leaves the group and goes among the stopped projects, or those with no session. A project whose sessions only wait for the user is not in the working group and stays below it; one with a session that works and another that waits is in the group, and a question asked or answered there moves nothing. A read that failed changes none of this, and a change of the target starts it again. The list draws no SSH host: no heading "SSH" and no row `ssh:{hostId}`, and so the sessions of an SSH host's worktrees are not listed (the owner's instruction, 2026-11-16, issues #783 and #784). Rust leaves out the worktrees of an SSH host (any `hostId` but `local`) when it makes the rows, the projects and the plain terminals, and answers no `ssh` or `hosts` list in the overview, the stream or `local` (issue #785). While a saved environment is the target the list holds this machine's projects beside its own, newest first as one list, and a project of the saved environment carries its name as a chip (A-33). The search field above the list (A-19) narrows them by name.

Sessions under a project. Each project opens and closes by itself, so any number can be open at once. A project that has a tab other than a file (a Claude session with a pane, or a plain terminal) has an arrow at the left of its row (`.orca-arrow`, an `.icon-btn` of 24 px with a chevron that turns down when open, `aria-expanded`, `aria-label` "セッションを開く" and "セッションを閉じる"); a project with no session has none. Selecting a project (its row, a session row, or a session started from the plus) opens it and closes no other. The arrow opens or closes its own project whether it is selected or not; it changes only the list, and the selection, the tabs, the panes and the terminals of the work pane stay as they are. Selecting a closed project again opens it. At first every working project is open and the others are closed, and a project opens, also when the user had closed it with its arrow, when a read has a working session in it that the last read that worked did not have (a session that begins to work, or a project that begins to work, above; a project that works with no working Claude row counts as one such work); one whose working sessions are the same as at the last read stays as the user left it. The title of a session row (and of its tab) is the line of A-6, taken from the agent's `conversationName`, `prompt`, `taskTitle` or the title of its terminal, in this order, as Orca's own list names a session by the conversation first and by the prompt only when there is no name (the last answer is the reply, below, and is no title). The list shows the owner's question and Claude's answer only, and no message of the harness, no result of a tool and no output of a process (the owner's instruction, 2026-11-16, issue #760). Orca's `prompt` is the last message sent to Claude, so a message of Claude Code's harness that came after the question (an `<event kind="…" at="…">` that holds a result, a `<task-notification>`, a `<system-reminder>`) is the `prompt` whenever one came. So Rust (a pure function in `orca.rs`, `first_text_line`) reads each text of A-6 (the conversation's name, the prompt, the task's title, the title of the terminal and the last answer) in these steps. Only the first 4,000 characters are read. The elements of the harness are taken out with all they hold: `<event …>` (with its `<result>` and `<log>`), `<result>`, `<log>`, `<task-notification>`, `<system-reminder>`, `<local-command-stdout>`, `<local-command-stderr>`, `<local-command-caveat>` and `<user-prompt-submit-hook>`, each up to its closing tag; when it is never closed or its opening tag is cut (Orca cuts a prompt to 200 characters), up to the end of the text if it starts a line (only spaces before it on its line), else only its opening tag (a cut opening tag in the middle of a sentence stays as typed), so `Fix the <log> view` gives `Fix the  view`; and `<name/>` alone; what is between a pair of backticks stays as typed. The other tags are taken off every line (`<name …>`, `</name>` and `<name/>`, with a quoted value that may hold `>`; the name starts with an ASCII letter and holds only letters, digits, `-`, `_` and `.`, so `<https://…>` is not a tag; a `<` that follows an ASCII letter, a digit or `_` is a generic such as `Vec<String>`, not a tag; what is between a pair of backticks stays as typed, as in `<div>`). The first line that still has text is taken, cut to 200 characters: a line that is only tags is skipped, so the text the owner typed after an `<event …>…</event>` is the title. A text gives no line when nothing is left, when what is left opens as data nobody types (the first three lines that have text, joined by a space, start with a keyed object `{ "key" :` or one whose key has no quotes, as a REPL prints a JS value, `{ key :` (a name of ASCII letters, digits, `_` and `$` that does not begin with a digit, as in `{ a: { isAsync: true, status: 'async_launched' } }`; `{ not json`, `{ a b` and `Fix {a:1}` stay titles; issue #693), an array of objects `[ { "` or of strings `[ "key" ,`, or an XML or HTML document `<?xml ` or `<!doctype `, in any case, as Orca's `getAgentPromptLabel` decides, but for the key with no quotes, which this app adds), or when its first line opens as the output of a process (`[stderr]` or `[stdout]`). A text with no line gives the turn to the next one in the order: a `prompt` that is only a message of the harness gives it to `taskTitle` and then to the title of the terminal (which Claude Code names after the question), and the `reply` of a row whose last answer is such a text (a JSON object of a tool, an `<event>` with a result) is none. The title is never the last answer. The shapes met in a real Orca (2026-11-16) are the examples of its unit tests: `<event …>` holding a `<result>` of a JS value, of `git status` or of a script, a prompt cut inside an `<event>`, a `[stderr]` line, and a last answer that is a JSON object. A row of a saved environment is made by the same function from the tabs of the stream, whose `agentStatus` has no `conversationName` (not checked against a real stream), so its title is the `prompt` when the owner's text is in it, else the title of its terminal. The screen draws the line as text (`textContent`), so a tag that stays is shown as the characters it is. Under an open project (`.orca-sessions`, one level in from the project: its rows start right of the project's name, with the status icon and the title) is one row for each session of its tabs (`.orca-session`, a button: the status icon of the tab and its title, followed by the reply when the row has one, `data-session` the id of the tab; not `data-tab`, which marks a tab of the work pane). The reply is the row's `reply` (A-6) drawn as " - {reply}" in `.orca-session-reply` inside the title (`.orca-session-title`), as text (`textContent`) in the color `--muted`; a row with no reply shows its title alone, and the tab of the work pane shows the title alone. Why: the owner wants the exchange with Claude in the list, as Orca's own side bar shows it (2026-11-15, issue #690). A row whose `subagents` (A-6) is more than 0 ends with a badge (`.orca-session-subagents`, `role="img"`): a robot icon (an inline SVG) and the number as text, in the yellow of `--effort-high` on `--effort-high-bg`, right of the title and at the right end of the row (`margin-left: auto`, and it does not shrink, so a long title is cut with its ellipsis before the badge, never pushed past it). Its `title` and `aria-label` are 「サブエージェント {n} 件が作業中」. A row with 0 has no badge, and the tab of the work pane never has one. The list is drawn again when the number changes, and the tab strip is not. Why: the owner wants to see which session has subagents at work (2026-11-15, issue #693). A session row carries no chip of the environment (A-33), and the tab of the work pane never does. A file open in the editor (A-18) and the diff of a file (A-24) are tabs but not sessions, so they have no row. The rows are in the order of the tabs of the project as the work pane first sees them (the order of "Tabs" below, whatever the panes it is split into, A-17). The selected row (`aria-pressed`, the `--soft` background) is the row of the tab selected, which is the tab the focused pane shows (A-17), so pressing a tab in any pane moves the selection of the list to its row (only in the selected project); no row is selected while a file tab is. Pressing a row selects its project (when it is not the selected one) and its tab (it takes the focus of its pane, as pressing the tab does). Whether a project is open is kept in memory only (as the order of the working projects). The order of the working projects is kept in TypeScript with the open state, because it is a state between reads, which Rust does not keep (every read asks the CLI again); the status and the order of the rest stay in the pure function.

Status icons, the same as Orca's. A pure function maps an Orca state word to one of seven: `waiting`, `blocked` and `permission` are `question` (the `message-circle-question-mark` icon, orange); `failed` is a small red dot; `working` is a yellow ring that turns (it stops under `prefers-reduced-motion`); `monitoring` is the `activity` icon; `interrupted` and `unconfirmed` are a small gray dot; `done` and `active` are a green dot ("完了", or "起動中" on the tab of a terminal); `inactive` is a faint gray dot ("動いていない"). The colors are variables in `:root`. A word not known yet is idle for a worktree and working for an agent, as in A-6, and an agent with `interrupted` true is interrupted unless it waits or failed. The status of a row is its agent's; the status of a project is the highest rank among its top-level agents with a live pty, its worktrees' `sidebarStatus` (else `status`), and its plain terminals (a green dot), in Orca's rank: question, failed, working, monitoring, interrupted, done, idle (`unconfirmed` is drawn as interrupted and ranks with it, one place above where Orca ranks it).

Tabs. Selecting a project opens it in the list (its sessions under it, above; the other open projects stay open) and shows its sessions as tabs in the work pane, which is split into panes (A-17; a project that was never split has one pane with all its tabs), and selects the tab that the pane with the focus shows (A-17; the first of a project that has no saved layout). The tab bar of a pane (`.orca-tabbar`) is 44 px high at least (`--header-h`, A-23), level with the header of the list pane, and grows with the size chosen for the work pane (A-20; 32 px in proportion to it when that is more than 44 px, so that its text stays inside); it holds the strip (`.orca-tabs`, as wide as its tabs, which scrolls sideways when the tabs do not fit the bar) and, right after the strip, the plus of A-16 (when the tabs scroll, the plus stays in view at the right end of the bar, before the button of the file pane (A-18) in the pane that has it), and it is shown also when the strip is empty. The tabs are the project's Claude sessions (rows with a pane key), and its plain terminals, in the order they were first seen, so a read that reorders the sessions does not move them (a tab keeps its place in its pane, A-17). A project with no session says 「セッションはありません」 in the work pane, with the strip empty, and the plus of A-16 is the way to start one. The selection survives a read while its tab exists; when its session leaves Orca's list the pane shows the tab that followed it, else the one before (A-17). Nothing closes by itself, a finished session included. Every tab is a terminal (below, and A-12): a Claude session shows the terminal of its handle, and a plain terminal its own. A terminal in which `claude` starts is listed as a Claude session under the same handle (and as a plain terminal again when it ends there): its tab keeps its place in its pane, its selection and its screen (A-17).

Closing. The close button of a Claude session or a plain terminal of Orca calls `orca_close(handle, environment)`, which runs `orca terminal close --terminal <handle> --tab --json` (with `--environment=<name>` for a saved environment) with a timeout of 15 seconds; the handle is validated as in A-6, and the environment must be a saved one. The answer's `ptyKilled` is not looked at (it is false on a real machine although the process stops). `error.code` `terminal_handle_stale` is not a success, because Orca answers it for a terminal that runs too (its log shows `--tab` closes refused with it for a running terminal, which then stopped with `ptyKilled` true when closed with no `--tab`): the terminal is then closed once more by `orca terminal close --terminal <handle> --json` (the same timeout and environment), and the answer of that is read like any other, so `terminal_handle_stale` again, or any failure, is an error and the tab stays. On success the screen reads the list at once (a streamed list, A-12, says it by itself and is not read) and the tab leaves with it; on a failure (of the first close or of the second) the message is shown (`#error`) and the tab stays, and the screen reads the list again (a streamed list is not read), so that a tab Orca no longer holds leaves at once. A tab whose session is gone from Orca's list leaves at the next read. A Claude session with no terminal handle cannot be closed.

Terminals of Orca. A terminal of `orca terminal list` that no Claude row of the same read holds (A-6: the row's handle is the terminal's; a shell, or another agent), still has its tab (not `orphaned`), and is in the worktree of a project is a tab of that project, titled by its `title`, with the green dot; the floating terminal has no worktree and is left out. A Claude session's tab shows the terminal of its handle. The kind is the row's alone, and `agentIdentity` is not looked at, because Orca sets it from the process or the title before `worktree ps` has the agent (and the other way round when the agent ends): so in every read a terminal is held by a Claude row or is a plain terminal, never neither and never both. Every terminal is drawn by xterm.js (`src/vendor/xterm.js`, `xterm.css`, `addon-fit.js`, `addon-unicode11.js` and `addon-web-links.js`, kept as distributed, with their version and license in a comment, and read as classic scripts by `ts/vendor-load.ts` the first time a terminal is to be shown, not at start-up, so a terminal waits for that one read and the start of the app does not; the CSP is unchanged; scrollback 5000 lines; `ts/orca-terminal.ts`). The colors of every terminal, and of the pane around it, are those of the theme chosen in the settings for the appearance of A-15 (by default the system's, A-14); the font and the keys that send a text are Ghostty's (A-13). With a saved environment as the target the terminal is streamed (A-12). With this machine as the target the tab is a mirror, because this machine's Orca cannot stream the bytes of a terminal to this app (A-12 has the measured reason): sized to its pane when it is shown (`fit`, and a `ResizeObserver` on the host element of each pane whose fit waits until the size has rested for 50 ms), and while it is shown (in each pane, the tab it shows, A-17) the screen reads the terminal over this machine's unix socket (the socket of A-7; `terminal.read` with `{terminal, screen: true}`, which is what `orca terminal read --screen` sends, so no CLI process is started: the CLI costs about 0.1 seconds of start-up each) every second, one at a time, and takes `result.terminal.tail`, an array of lines with no colors; an answer with no `result.terminal.source` is an Orca that ignores `screen` (it answers the accumulated output), which is refused with a message to update Orca, as the CLI refuses it (`incompatible_runtime`), and draws the frame again in xterm.js when it changed. The keys typed are sent with no Enter added, so control bytes reach the terminal as typed, batched (at most 50,000 characters a send) and one send at a time, and the frame is read again soon after while the terminal is shown; the keys not sent yet go on to the terminal when it stops showing, and are dropped only when it leaves the list (A-12). What is typed can be a password, so it is kept out of the arguments of a process (`ps` shows them): the keys go to this machine's Orca over the unix socket of A-7 as `terminal.send` (`{terminal, text, enter: false, client: {id: "tsunagiai", type: "desktop"}}`, as the CLI sends them; the answer's `result.send.accepted` false is a failure). A key text is not checked for blank, but it may not be empty or hold a NUL or more than 100,000 characters. The handle must belong to a row or a plain terminal of the list read just now, for a read as for keys; it is checked the first time a read or keys go to that handle, and again after a read or a send of it failed. The mirror has no text colors (it draws the screen in the theme's foreground on its background), a full-screen program is only approximate, and a size change is not sent. A terminal's screen and keys are in no log line, error text or event of the app. A failed send shows its message (`#error`); a failed read is tried again at the next second. The reads of a terminal stop while another tab is shown in its pane, another screen is shown or the window is hidden (the terminals shown read at once when the window is shown again), and the screen of a terminal is dropped when it leaves the list. Links. A URL in the text of a terminal (this machine's mirror and a saved environment's stream alike), and a link that a program sets with OSC 8, is a link: the text `http://` or `https://` up to a space, a quote, a bracket, or a full-width punctuation mark or bracket (U+3000 to U+303F and U+FF00 to U+FFEF, so a URL in a Japanese sentence ends where the sentence goes on), found by `addon-web-links.js` (`@xterm/addon-web-links` 0.12.0, the version that goes with xterm.js 6.0.0) and, for OSC 8, by `linkHandler` of xterm.js with `allowNonHttpProtocols` (as Orca sets it; without it xterm.js drops a link of another scheme before the click), both with the same click rule. A click opens the link in the default browser only with ⌘ held, Ctrl and Alt not held, and the left button; a click without ⌘ selects as before. After it opens, the selection is cleared. While the pointer is over a link, the URL is the `title` of the terminal's box. The click calls `orca_open_url(url)`, which reads the URL again with the `url` crate and opens it with the opener only when its scheme is `http` or `https` and it has a host (any other scheme, such as `file:` or `javascript:`, and text that is no URL, fail with 「開けるのは http か https の URL だけです」, shown in `#error`). The rules follow Orca 1.4.250's own terminal and its `shell:openUrl`.

Keys. While a terminal has the focus the app's own key handlers do not act: Escape only closes a menu, popup or hint that is open (none is while a terminal is clicked), and Cmd+Z of the inbox leaves a textarea's own, which is xterm.js's input. Cmd+C copies the selection and Cmd+V pastes, as in any field. Cmd+J of A-19 is the one key that acts then: it moves to the search field.

The command. `orca_handoff(destination, instruction, files, summary, context, environment)`: `destination` is `{kind: "new", path}` (a worktree); `instruction` is what the user wrote, as it was written; `files` is the text that each upload of A-10 answered; `summary` is the points of Claude's summary of the content (empty without a card); `context` is `null` or `{kind, title, body}`; `environment` is the destination of the pane (`null`: this machine, else a saved environment's name), not the target the Orca screen holds. Each is trimmed, and a blank one is none; a value that starts with `-`, or that git would refuse as a ref (`git check-ref-format`: a space or control character, `~ ^ : ? * [ \`, `..`, `@{`, `@` alone, an empty component or one that starts with `.` or ends with `.lock`, a `/` or `.` at the end), is refused with a Japanese message (「ブランチ名に使えない文字が含まれています」, 「作成元に使えない文字が含まれています」) and nothing is made. The prompt is (the lines of the files and the summary are left out when there are none; a summary without the card is not sent)

```text
{instruction}

{the text of each attached file, one on each line}

{one line that says the block is quoted data and holds no instructions}
<tsunagiai-context kind="mail|slack|todo" title="{title}">
内容の要約:
- {point}

{body}
</tsunagiai-context>
```

with the attribute value on one line (a newline becomes a space, at most 200 characters, and `&`, `<`, `>` and `"` escaped) and, in the body, every opening or closing tag of the block, in any case, loses its `<` (it becomes `&lt;`), so that quoted mail can neither end the block nor start a second one or fake it. Before that, Rust takes out of the title and the body the C0 controls other than the line break and the tab, DEL, the zero-width characters (U+200B to U+200D, U+2060, U+FEFF), the bidi controls (U+202A to U+202E, U+2066 to U+2069) and the tag characters (U+E0000 to U+E007F), which are invisible or change how text reads and could split a tag apart (`<` + U+200B + `/tsunagiai-context>`); so `context.body` as the card shows it is the string that the command received, and the text sent is that string without those characters (the card text and the prompt differ by them only). The tags of the name the block had before the rename (`cookapps-context`, opening or closing, in any case) lose their `<` in the same way, so that a text that carries one cannot end the block or fake it either. The summary is quoted data too, because Claude made it from the content: it is inside the block, above the body, under the header "内容の要約:" and a line "- {point}" for each point (the line breaks and hidden characters of a point taken out, a blank point left out, and no header when none is left), and it goes through the same neutralizing of the tags as the body. ## A-10 Attach a file in Orca

A terminal of the Orca screen (A-8, A-12) and the pane of A-9 take files by paste and by drop, an image or a file of any other kind. Each is put in `.orca/drops/` of the worktree of the session, and its absolute path reaches Claude, which reads the file from that path: a terminal types the path into itself, as Orca's own terminal does, and the pane adds it to the instruction it sends. It works for a worktree of this machine and for one of a saved server (the target of A-6). The file is kept in memory only, in no log line and in no file of this app. Rust is `src-tauri/src/orca_attach.rs`, and the frontend is `ts/orca-attach.ts` (taking, reading and uploading the files, shared) with `ts/orca-terminal.ts` and `ts/orca-handoff.ts`. It was written against Orca 1.4.248, as A-6 to A-9, and the file names and the typed text follow Orca 1.4.253. This was first a part of the composer of the Orca screen (v0.42.0); A-12 replaced the composer by the terminal and retired it, and it is back for the terminal and the pane (#135).

Taking a file. `ts/orca-attach.ts` makes an element take files (`listenForFiles`): a paste takes the files of `clipboardData` (listened to while capturing, since the terminal's own paste handler stops the event; the event is cancelled only when there is a file, so pasting text works as before; a file copied in Finder is one), and a drop takes the files dropped, all of them. While a file is dragged over the element it has a dashed outline (`.dropping`). The elements are the terminal area of each pane of the work pane (`.orca-term`, A-17; the terminal shown in it) and the form of each pane of A-9 before a handoff (`.ho-main` in `#mail-handoff`, `#todo-handoff` and `#st-orca`; after a handoff the terminal of its session takes the files, as the terminal of the Orca screen). `dragDropEnabled` is `false` for the window (`tauri.conf.json` and `tauri.e2e.conf.json`), so a drop gives `File` objects to the page. The other choice, `onDragDropEvent` with the window's file drop on, gives the page only the paths of the files, so a command would have to read a file from a path the page names (a command that reads any file of the machine), and the page would have to find the element under the pointer by itself; the drop events of the page do both, and need no path. `initFileDrops` (called by `main.ts`) puts a document-level `dragover` and `drop` that cancel a drag that holds files, wherever it is outside those elements, so that a file dropped elsewhere does not make the webview navigate to it (a drag with no file is left alone, and the Todo list's row drag uses pointer events). A file that `FileReader` cannot read (a dropped folder is one, and one that reads as empty is refused by Rust with 「ファイルを読めません」) is refused with the message 「{name} を読めません」, and then none of the files of that paste or drop is taken. The file is read with `FileReader` into base64 and a `data:` URL, which is the thumbnail of an image in the pane (the CSP allows `data:`, not `blob:`). Whether the pane draws a file as a thumbnail is decided by its type (`image/*`); what is typed for it is decided in Rust by its bytes.

The terminal. A file taken on the terminal shown is put at once in the worktree of that terminal (`path` of its tab: the row's for a Claude session, the terminal's for a plain one, which `OrcaTerminal.path` carries) with `orca_attach_file(path, name, data, environment)`, `environment` being the place of the tab's row (null for this machine). Then the texts the command answered for the files (`AttachedFile.text`: the path as Claude reads it, with one blank after it), in order, go into the terminal: the neighbours whose `bracketed` is true are joined and pasted (`Terminal.paste`, so a program that asked for the bracketed paste gets them as one), and those whose `bracketed` is false are typed as they are (added to the keys not sent yet), by the keys of A-12 (`orca_stream_input`) or those of A-8 (`orca_terminal_input`). A message (a file that cannot be read, a failed upload or send, a file over 20 MiB, refused by the page before it is read, with the message of Rust, and no call of `orca_attach_file`) goes to `#error`, as a failed send of keys does. The paths go only to the terminal the files were put for: when another terminal is shown by the time the upload ends, nothing is typed.

The pane. The form of A-9 (before a send) has a strip `.attachments`, between the card and the field of the instruction, hidden when there is no file; after a send the pane has no strip (the files go to the terminal of the session, above). Each file is a 64 px box (`.attachment`) with a remove button (`.icon-btn`, `aria-label` "{name} を外す"): an image is a thumbnail (`img` with `alt` the file name), and any other file shows its name (`.attachment-name`, set as text, at most three lines). The files belong to the item (the mail, the thread or the task) as its draft does: they stay while another item is in view, and nothing is added or removed while a send of the item is on its way. A file that cannot be read, or that is over 20 MiB (refused by the page before it is read, so it is not added and `orca_attach_file` is not called), or that the upload refuses, gives its message in the line of the failed send (`.pending.fail`). The files are not sent to Claude, and before a hand-over they do not enable the button "Orca に渡す" (it needs the instruction; the other conditions of A-9 are unchanged). On "Orca に渡す", the files are put one by one in the worktree of the destination (the chosen worktree for a new session), to the target of the pane. `orca_handoff` gets the `text` the command answered for each file as `files` and puts each (without its trailing blank) on a line of its own after the instruction and a blank line. A failed upload shows its message, keeps the instruction and the files and sends nothing. The text for Claude of an upload is remembered for the file by worktree and target, so a press after a failed handoff does not put the file there again; a worktree or target that differs puts it again. A success clears the field and the files that were sent; a file still being read when the send began is not sent, and it stays with the item (it is not drawn while the session is shown, and the strip of the form shows it again once the session is closed). The handoff itself is that of A-9 and A-6: never tried twice, and checked against the list read just now.

`orca_attach_file` (it takes a file of any kind) checks, in Rust and in Japanese: the path is absolute; the data is base64 of a file that is not empty and at most 20 MiB (an overlong string is refused before it is decoded); the name is checked as below; then it reads the worktree list of the target just now (as a launch does), requires the path to be in it and takes the `hostId` Orca names for it (none: 「Orca が worktree のホストを答えませんでした」), and refuses a worktree of an SSH host (`hostId` of the form `ssh:{id}`, which has no file calls) with 「SSH の接続先の worktree にはファイルを添付できません」. The page names the worktree (one the list holds) and the file name only, and never a place inside the folder: the file goes in the fixed folder `.orca/drops/`, so nothing can be written outside it.

The name. The file keeps the name it was given (the page sends `File.name`, or `image` for an image and `file` for any other file when it has none), as Orca does for a file dropped on a worktree. The name comes from outside, so Rust refuses one that is empty, `.` or `..`, that holds `/`, `\`, a control character (NUL, a line end, DEL and the C1 controls among them) or a bidirectional formatting character (U+200E, U+200F, U+202A to U+202E and U+2066 to U+2069, which would make the terminal show another name than the file's), or that is over 255 bytes (`NAME_MAX`, 「ファイル名が長すぎます（255 バイトまで）」). Any other character stays as it is (blanks, quotes, `$`, non-ASCII). Whether the file is an image is read from its bytes, never from its name: PNG, JPEG, GIF and WebP by their magic bytes (SVG is not one). An image whose name has no extension (no dot after the first character) gets the one of its kind (`png`, `jpg`, `gif`, `webp`), as Orca names an image pasted with none; any other name is kept as it is, even when its extension says another kind. When the name is taken in `.orca/drops/`, the name is changed by Orca's rule (1.4.253, read in its `app.asar`; the name is split at the last dot unless that dot is the first character, so `.env` has no extension): `{stem} copy{ext}`, then `{stem} copy 2{ext}`, up to `{stem} copy 9999{ext}`; when all of them are taken, the upload is refused with 「同じ名前のファイルが多すぎます」. The stem of a name with `copy` added is cut, on a character, so that the name stays within 255 bytes; an extension too long to leave a stem is refused.

The upload is made over Orca's runtime, as A-7 reads it: this machine over its unix socket, a saved server over its WebSocket (one connection kept for the whole upload), with the pairing read from Orca's files at that moment; no token is in a return value, a log line or an error text. Every call takes `worktree` as `path:{absolute path}`, and a change also takes `expectedExecutionHostId`, the `hostId` above (without it, or with another value, Orca refuses it). The steps, in this order:
1. `files.stat` of `.orca/drops/.gitignore`; only when it answers `ENOENT`, `files.writeBase64Chunk` writes it with the content `*` and a newline, so the images do not show as changes of the repository. A failure of this write is ignored (as Orca does). Any other failure of the `stat` is the upload's.
2. One `files.readDir` of `.orca/drops` (with `limit` 5000, as A-18) gives the names the folder holds, and the first name in the order above that is not among them is free; a folder that answers `ENOENT` (the message of Orca starts with it) holds none. Step 4 refuses an existing file, so a name taken in between (or beyond the page the answer holds) fails the upload and overwrites nothing. Any other failure of the read is the upload's.
3. The bytes are written to `.orca/drops/.orca-upload-{16 hex digits}` (a short name of its own, whatever the file's name is, so it never passes 255 bytes) with `files.writeBase64Chunk` in chunks of 384 KiB (a larger frame closes the host's socket): `append` is `false` for the first chunk (the file is created, and an existing one is refused) and `true` for the others; the folders are created by the call (`files.write` does not create them and is not used).
4. `files.commitUpload` copies the temporary file to `.orca/drops/{name}`, which fails when that exists, so a file is never overwritten.
5. `files.delete` (`recursive` false) removes the temporary file, after the commit and also after a failed chunk or commit; its result is ignored.
The answer is `{ text, bracketed }` (`AttachedFile`), made from `{worktree path}/.orca/drops/{name}`: for an image `text` is the path with a backslash before a blank, a double quote, a single quote, a backtick, a backslash and each of `$ ; & | < > ( ) { } [ ] * ? ! #` (as Orca's own paste of an image path does, and Claude reads the image from such a path, a path with blanks included), and `bracketed` is true, so the screen pastes it as a bracketed paste; for any other file `text` is the path in POSIX single quotes (a `'` inside written `'\''`) and `bracketed` is false, so the screen types it as it is. Each `text` ends with one blank. A path with a control or bidirectional formatting character is refused. Nothing in `.orca/drops/` is deleted later: Orca has no clean-up of it either, and the `.gitignore` keeps it out of the repository.

Errors. The message of a failed call is Orca's code (「Orca がエラーを返しました（{code}）」), never Orca's own message, as A-7 (`LinkError::Remote` holds the message only for the caller to tell `ENOENT`). A saved server whose pairing has only the `mobile` scope answers `forbidden` to these calls; the message then says the pairing has no permission to put files there, with the code. When Orca is not running on this machine, the message of A-7 for the unix socket is shown. `files.*` is not a public interface of Orca: an update can change it, and then an upload fails with a message while the rest keeps working without files.

Unit tests (`cargo test`) cover the kind by the magic bytes, the base64 and the limit, the file name (kept as given, the names refused, the extension added to an image with none, the split at the last dot), the numbered names (Orca's rule, the limit of 255 bytes with the cut on a character, 9999 tries and then the refusal), the name chosen from the names of one read of the folder (a folder not there yet, a failed read), the escaped path of an image and the quoted path of any other file with their `bracketed`, and the refusal of a control or bidirectional formatting character, the refusal of an SSH host, the message of `forbidden`, the `hostId` lookup, the message of Orca held by an error answer, the worktree path of a plain terminal, and the upload driven by a stand-in for Orca's calls (the order of the calls and the `hostId` in them, the chunk sizes and `append`, the `.gitignore` only when missing and its failure ignored, a taken name, a failed commit and a failed chunk with the temporary file deleted and the error passed, a failed delete not failing the upload, a `stat` that fails for another reason); none of them talks to a real Orca. The E2E specs cover, in `orca.e2e.ts`, the terminal of this machine and the stream of a saved environment (the paste and the drop, a paste with no file left alone, the arguments of `orca_attach_file` for an image and for a file that is not an image, the text typed with the handle, an answer that is not bracketed typed as it is while an image is pasted as a bracketed paste, a file that cannot be read refused, a file over 20 MiB refused with the message, with no call of the command, and typing nothing, a failed upload typing nothing, a file dropped elsewhere, the worktree of a Claude session and of a plain terminal, and the tab changed while the file went), and in `orca-handoff.e2e.ts` the pane (the thumbnail of an image and the name of any other file, each with its remove button, the paste and the drop, a file over 20 MiB refused with the message, with no call of the command, a file dropped elsewhere, the button enabled by a file alone, the arguments of `orca_attach_file` and the instruction of a new session and of a running one, also with a blank instruction, a failed upload keeping the text and the images, a press after a failed handoff not uploading again, and an image pasted on the terminal of the session shown, put in its worktree with its path typed there).

## A-12 Orca terminal stream

Every tab of the Orca screen (A-8) is a terminal, drawn from what Orca streams; the work pane shows the tab selected in each of its panes (A-17), so several terminals are streamed at once. Rust is `src-tauri/src/orca_stream.rs`; the frontend is `ts/orca-terminal.ts`, with the list in `ts/orca.ts`. The methods it calls (`session.tabs.subscribeAll`, `terminal.subscribe`, `terminal.updateViewport`, `terminal.unsubscribe` and `terminal.send`) are not a public interface of Orca. They were checked on Orca 1.4.249, and an update can change them; then the list or the terminal of a saved environment says it cannot connect, while this machine keeps working.

Routes. A saved environment (the target of A-6, while it is listed) is streamed over the end-to-end encrypted WebSocket of A-7, with the pairing of `orca-environments.json`, read at each connect and never written. This machine is not streamed, and keeps the routes of A-6 and A-8: its list is read with the CLI by the clock, and its terminal is the mirror of A-8. The reason was measured on Orca 1.4.248's source and on this machine. The unix socket answers one request with one answer and refuses a streaming method with `method_not_supported` (`rpc-request-admission-prologue.ts`); the streaming methods are dispatched only over the WebSocket (`runtime-rpc-websocket-dispatch.ts`). The local WebSocket (the transport `websocket` of `orca-runtime.json`) takes only the token of a paired device, checked against the devices of `orca-devices.json` (`device-registry.ts`, `validateToken`), and the `authToken` of `orca-runtime.json` is none of them (compared on this machine). Streaming it would need this app paired as a device, which writes Orca's device registry, or another device's token; neither is done.

The list. `orca_stream_open(environment, channel)` connects, asks `worktree.ps` (`{limit: 200}`) once, and subscribes `session.tabs.subscribeAll`. Its `snapshots` replace the tabs held of every worktree, `updated` replaces the tabs of one (`removed` drops it), and `end` ends the connection, which is made again. A pure function turns the tabs into the two documents of the CLI that A-6 reads: an agent from the `agentStatus` of each terminal tab (`hasLivePty` while the tab has a terminal handle, `agentType` else the tab's `launchAgent`; Orca drops `agentStatus` for a moment while the pane keeps its terminal, so a tab that launched Claude and has a terminal handle but no `agentStatus` is an idle agent of its pane, `{parentTabId}:{leafId}`, and its row and tab do not come and go with the status), a terminal from each terminal tab with a handle (`parentTabId` and `leafId` as its pane; it is a plain terminal unless a row holds its handle, A-8), and a worktree's last activity the latest of its own and its agents'. So the rows, projects and plain terminals are built by the same functions as A-6 and A-8. `worktree.ps` is asked again when a worktree with terminals appears that it did not list (once for each), every 10 seconds while the connection lasts (the period of A-6's list while its screen is shown; the tabs do not say the git branch of a worktree, so a switch made outside the app shows only by this read), and right after the app switched a branch (A-25: `orca_switch_branch` tells the stream that runs, whatever Orca answered), one read at a time: what is asked for while a read is on its way is read when its answer comes, and a read that fails keeps the list held. Nothing else is read by a clock. The screen gets `list {rows, worktrees, projects, terminals}` only when the list changed, and takes it as a read that worked; the clock of A-6 reads nothing while the list is streamed, and showing the screen still reads it once with the CLI (with the environments). A failed or lost connection, or 60 seconds with no frame (A-7), sends `status {live: false, message}`, which the screen shows as a failed read of A-6 (the orange label and the notice, the rows kept), and is tried again after 1, 2, 5, 10 and then 30 seconds; the first list of a connection, after `status {live: true}`, makes it live again and starts the waits again. A change of the target to this machine, or a target that is not listed, ends the stream (`orca_stream_close`); one stream runs at a time, so a change to another saved environment only calls `orca_stream_open`, which ends the old stream first (a close is a call of its own, and could reach Rust after the open and end the new stream).

The terminal. Showing a tab of a streamed list (the tab selected in a pane, A-17) calls `orca_stream_terminal(handle, generation, viewport, channel)` (the generation is a number the page takes anew for each showing); each terminal shown has its own channel, and the terminals of the other panes stay subscribed. Once the list holds the handle, Rust sends `terminal.subscribe` (`{terminal, client: {id, type: "desktop"}, viewport}`, JSON frames), else the channel gets `ended` with 「このターミナルは一覧にありません」. The client id is `tsunagiai-` and 16 hex digits, new for each stream. The channel gets `snapshot {data, cols, rows}` (the screen as Orca serializes it, from `scrollback`, or the lines of `subscribed`; it replaces what is drawn), `output {data}` (the bytes printed), `size {cols, rows}` (`fit-override-changed`) and `ended {message}`. A terminal that stops being shown (another tab selected in its pane, a tab that leaves the list, a pane that closes, another screen, or a hidden window) is ended by `orca_stream_terminal_close(handle, generation)`, which sends `terminal.unsubscribe` (`{subscriptionId: "{handle}:{client}"}`), so Orca gives the terminal back its own size. A close names its terminal, so it ends no other subscription, and it cannot end one made after it for another handle, and a close of an earlier generation of the same handle changes nothing (the calls may reach Rust in the other order); the end of the stream ends them all. Showing a handle that is already subscribed subscribes it anew in place of the old subscription. After `ended`, a change of the list does not subscribe that terminal again nor send `ended` again; showing a terminal anew, or the next connection, does. A window shown again, or a connection made again, subscribes again, and a new snapshot replaces the screen.

The owners. Two kinds of screen show terminals: the work pane of the Orca screen and the pane of A-9 after a handoff (A-9), each an owner of the terminals it shows (`showTerminals(placements, focusId, owner)` and `hideTerminals(owner)` of `ts/orca-terminal.ts`, the one place that loads and draws xterm.js). An owner shows and ends only its own; a terminal wanted by two (the session shown on the Orca screen and in the pane) goes to the one that asked last, with its screen and without a new subscription. The Orca screen's pruning of the terminals that left its list (`pruneTerminals`) touches only those of its own target that it showed last: the terminal a pane of A-9 made is the pane's, so a read of the list of the Orca screen never drops it. The pane forgets its terminal (`releaseTerminal`) when its session is forgotten or it shows the session of another item, unless the Orca screen has taken the terminal since, and it asks for the terminal to be shown (`showTerminals`) only when it is not shown as asked (`isShowing`: the same handle, kind of source and host element), not at each tick. The stream of a terminal needs the stream of the list (`orca_stream_open`), which is the Orca screen's and for one saved environment at a time, so the pane streams a session only when it runs on that environment (`streamsEnvironment`); any other session, of this machine or of a saved environment, is mirrored in the pane (a saved environment's through the CLI, every 2 seconds, A-9).

Size. The terminal is always fitted to the pane (`FitAddon`), and there is no switch for it. Its size goes with the subscription, and each new size of a terminal's pane goes with `orca_stream_viewport(handle, viewport)` as `terminal.updateViewport` (`{terminal, client, viewport, claim: true}`), so Orca sizes the terminal to its pane; the keys typed claim the pane's size again (below, Keys), because Orca keeps the size of the screen that claimed last and its own screen claims at every key. The size Orca sends is drawn, from the snapshot and each `size`, so the terminal is drawn as Orca has it even when another screen of Orca took the size; the next change of the pane or the next key claims the pane's size again. A size is kept within 20 to 1000 columns and 8 to 500 rows, which both methods take. The mirror of this machine is always drawn at the pane's width. Each terminal is fitted to its own pane (a `ResizeObserver` on the host element of each pane), so a split or a drag of the divider sends the new size of every terminal whose pane changed.

The bottom row. The box of a terminal is placed absolutely inside the host element of its pane (`.orca-term`, `position: relative`), 8 px from its top, right and bottom and 12 px from its left, so the fit measures the space the box has. The fit runs again once the fonts are loaded (`document.fonts.ready`), and the last row is inside the pane, for the mirror too.

Wide characters. `@xterm/addon-unicode11` 0.9.0 (`src/vendor/addon-unicode11.js`, MIT, kept as distributed with its version and license in a comment) is loaded for every terminal, with `allowProposedApi` and `unicode.activeVersion` "11", so an emoji or a CJK character takes the cells Orca's own terminal gives it.

Keys. The keys typed go with `orca_stream_input(handle, text)`, the handle of the terminal they were typed in (validated as in A-6), as `terminal.send` (`{terminal, text, enter: false, client}`, and a stream's send also carries `viewport` (the size Rust holds for the pane, kept within the limits above) and `claimViewport: true`, as Orca's own screen sends them) on the same connection, so they are in no argument of a process. They go only to that terminal, because each send names its handle, and they go also when the terminal is no longer shown (another tab showed in its pane, another screen showed, or the window was hidden meanwhile): a terminal that is in the list of Orca held but not subscribed gets the send with no `viewport` and no `claimViewport`, as it has no pane. A terminal that is not in the list held gets nothing and the answer is 「入力したターミナルは Orca の一覧にないため、送りませんでした」. Unverified: whether Orca takes `terminal.send` for a terminal this app does not subscribe (the CLI, `orca terminal send`, sends with no subscription and works, so it is expected to). One send goes at a time, and the keys typed meanwhile go together in the next (at most 50,000 characters a send; Rust takes up to 100,000, not empty and with no NUL); the keys not sent yet are not dropped when the terminal stops showing (another tab shows in its pane, another screen shows, or the window is hidden): they go on to the terminal they were typed in. They are dropped only when the terminal leaves the list (its tab is gone). An answer whose `result.send.accepted` is false is a failure. With no connection, or no list held yet, or a terminal that is shown but not yet subscribed, the answer is 「接続先につながっていません」, and a connection lost before the answer gives 「接続が切れたため、入力を送れたか分かりません」. A failure shows its message (`#error`). An image pasted or dropped on a terminal shown is put in its worktree and its path is pasted into the terminal by these same keys (A-10).

Selection and the clipboard. A program such as Claude Code tracks the mouse (`?1003h`, `?1006h`) and draws its own selection, so xterm.js sends the drag to it as mouse reports and has no selection of its own; the program then puts what it selected in the clipboard with OSC 52 (`ESC ] 52 ; c ; {base64} BEL`). The terminal answers that request as Orca's own terminal does (`osc52-clipboard.js` of Orca 1.4.250): `term.parser.registerOscHandler(52, …)` takes the target (empty or `c`; any other is ignored), reads the text as base64 of UTF-8 (line breaks and spaces are dropped; a text that is not base64, an empty text, and a request of more than 128 KiB of base64 characters are ignored) and writes it with `navigator.clipboard.writeText`. Requests that come in one chunk of output write only the last, once the chunk is parsed (a microtask, as Orca's own terminal does). A read (the text is `?`) is never answered, so nothing of the clipboard reaches a program. Only what the terminal prints live is made: an OSC 52 request in a snapshot (the screen drawn again after `term.reset()`) or in a frame of the mirror (A-8) writes nothing, so a replay cannot overwrite a newer clipboard. A request comes by the stream and not from an action of the owner, so WKWebView may refuse the write (`NotAllowedError`; it was not checked on a real machine), and nothing is shown for a refusal. The terminal holds the latest text that the clipboard has not taken, and the next copy event of the owner (⌘C or Edit > Copy, which are both an action of the owner) puts it in the clipboard (`clipboardData.setData("text/plain", …)` and `preventDefault`) when xterm.js has no selection, and drops it; with a selection xterm.js copies its own as before. A write that was taken, a new selection in xterm.js (not the clearing of none, which xterm.js reports for a mouse mode, the alternate screen and a resize), and a snapshot also drop the held text. `macOptionClickForcesSelection` is on (as Orca sets it), so Option+drag selects in xterm.js even while a program tracks the mouse, and ⌘C copies that selection. The text is in no log line, error text or event of the app, and nothing is stored.

What a terminal prints and the keys typed are in no log line, no error text and no event but the channel of the terminal shown, and no token or key of the pairing is in any of them. Nothing is stored.

Unit tests (`cargo test`) cover the snapshots, updates and end of the tabs, the list built from the tabs and named by the worktrees, a tab with no terminal, the agent type taken from the launch, a Claude tab without a status kept as an idle row of its pane, the worktrees that make `worktree.ps` be asked again, when it is read again (`reads_ps`: an unlisted worktree, the clock or a switch of the branch, and never two reads at once) and the list sent after a switch only when it changed, odd documents, the terminal events, the params and the size limits, where keys go (`input_route`: subscribed, listed but not shown, or refused), and the shape of the events. None of them talks to a real Orca. The E2E spec `orca-handoff.e2e.ts` covers the terminal of the pane of A-9 (mirrored, streamed, and mirrored through a saved environment). ## A-13 Ghostty settings in the Orca terminal

The terminals of the Orca screen (A-8, A-12) take their font and some keys from Ghostty's config, which the owner reads in once from the settings screen. The colors of the import are read and listed as before, but the terminals draw the theme chosen in the settings (A-14) in preference to them; they use the colors of the import only while no theme has been read. Rust is `src-tauri/src/ghostty.rs`; the frontend is `ts/ghostty.ts` (the card) and `ts/orca-terminal.ts` (the terminals). The app reads Ghostty's files and never writes them.

Where the config is read. This was read from the source of Orca 1.4.250's own Ghostty import (`app.asar`, `out/main/index.js`, the functions that discover, load and map a Ghostty config) and from Ghostty 1.4.0's `ghostty.5.md`; an Orca update can change it. The files are `$XDG_CONFIG_HOME/ghostty/` (`~/.config/ghostty/` when it is not set or empty), then `~/Library/Application Support/com.mitchellh.ghostty/`, and in each folder `config.ghostty` and then `config`. Every one that exists as a regular file of at most 1,000,000 bytes is read, in that order, and their entries make one list: a later entry replaces an earlier one, as in Ghostty. With none, the import fails with 「Ghostty の設定ファイルが見つかりません」 and the places it looked in (shown with `~`). A line is `key = value` with the spaces around `=` free; a line that starts with `#` is a comment, and a `#` after a value is part of it (Ghostty has no comment after a value); a value in double quotes loses them; a line with no `=` is ignored. An empty value gives the key its default again (`font-family =` forgets the families before it). Ghostty's `config-file` is not followed.

Themes. `theme` is a name or an absolute path (a path starting with `~/` too, as Orca has it), or `light:A,dark:B` with both parts, in either order and with the spaces around a name trimmed. A name has no `/` or `\` and is not `.` or `..`. A name is looked for in `$XDG_CONFIG_HOME/ghostty/themes` (else `~/.config/ghostty/themes`), then in `$GHOSTTY_RESOURCES_DIR/themes` when that is set, else in `/Applications/Ghostty.app/Contents/Resources/ghostty/themes` and `~/Applications/Ghostty.app/Contents/Resources/ghostty/themes` (the folders Orca and Ghostty's documentation name); the first folder that holds a regular file of that name of at most 262,144 bytes gives it. A theme file is a config file: only its `palette`, `background`, `foreground`, `cursor-color`, `cursor-text`, `selection-background` and `selection-foreground` are read, and any other entry in it is ignored without a note. The colors of the config itself (the same keys) lie over those of the theme, as Ghostty says. A single theme gives its colors to the light and the dark appearance alike.

What is imported. `font-family` (every entry, in order: the first is the font and the others come after it, then the app's own `"SF Mono", Menlo, Monaco, monospace`, the start of Orca 1.4.254's own list, so that a terminal has the cells of Orca's: on a Mac without SF Mono both draw with Menlo), `font-size` (a number from 1 to 200, in pixels, as Orca takes it), `font-thicken` (`true` or `false`: `true` sets the font weight to 500, so a font without that weight draws as usual), the six colors `background`, `foreground`, `cursor-color`, `cursor-text` (the color under the cursor), `selection-background` and `selection-foreground`, `palette` (`N=color`, N from 0 to 255), `theme`, and the `keybind` entries that send a text. A color is `#rrggbb`, `rrggbb`, `#rgb` or `rgb`; a color name, or a value such as `cell-foreground`, is not imported. A key is `trigger=text:...`: the trigger is one key with its modifiers (`shift`, `ctrl` or `control`, `alt`, `opt` or `option`, `super`, `cmd` or `command`, each at most once), the key a single character or one of `enter`/`return`, `tab`, `space`, `backspace`, `delete`, `escape`/`esc`, `up`, `down`, `left`, `right` (also as `arrow_up` and so on), `home`, `end`, `page_up`, `page_down`, `insert`, `f1` to `f12`, `plus`, `equal`, `minus`, `comma`, `period`, `semicolon`, `apostrophe`, `slash`, `backslash`, `bracket_left`, `bracket_right`, `backquote`. The text is a Zig string literal: `\n`, `\r`, `\t`, `\\`, `\'`, `\"`, `\xNN` (00 to 7f) and `\u{N}`; it is not empty, has no NUL and is at most 1,000 characters. A later key with the same trigger replaces the earlier, `keybind = clear` forgets the keys before it, and a key for another action (or a text that cannot be read) with the same trigger takes the trigger away from the earlier text. In the terminal a trigger matches the key event whose `key` (a single character case folded) is the key and whose Shift, Ctrl, Alt and Meta are exactly the modifiers; Ghostty matches the unshifted character, so `shift+1` does not match. With Alt held, macOS makes another character from the key (Option+B is `∫`), so a one-character trigger with `alt` also matches the key whose `code` names that character on a US keyboard (`KeyB` is `b`, `Digit1` is `1`, and the punctuation and space codes `Minus`, `Equal`, `BracketLeft`, `BracketRight`, `Backslash`, `Semicolon`, `Quote`, `Backquote`, `Comma`, `Period`, `Slash` and `Space`), so `alt+b=text:\x1bb` works. Cmd+J (Ctrl+J outside macOS) is taken by the search of A-19 before any terminal key, so a `keybind` on that trigger never acts. The keys are made once, when the settings are applied.

What is not imported. Every other entry, and an entry of the above whose value cannot be used, is listed with the reason: 「対応していません」 for a key the terminals do not take (`window-width`, `cursor-style`, `config-file`, `font-thicken-strength` and so on, and a `keybind` for `csi:`, `esc:` or another action, with a sequence `a>b`, a prefix such as `global:` or a key such as `key_a`, each with the detail in brackets), or what is wrong with the value. A theme that is not found says which names; with `light:` and `dark:` and one of them found, the found one is imported and the other is listed. A value that is replaced by a later entry of the same key is not listed.

Saving and applying. The import is saved in `ghostty-settings.json` in the app config directory (written through a temporary file and a rename): the settings (`fontFamilies`, `fontSize`, `fontThicken`, `light` and `dark` colors with the palette as `{index, color}`, `keybinds`), the entries imported and left, and the files read. `ghostty_import` reads the files, saves and answers it; `ghostty_saved` answers the file or `null` (also when the file cannot be used). At startup the app reads the saved import and draws every terminal with it; pressing the import button draws the terminals again at once, with the font changed in place (xterm.js `options`) and the terminal shown fitted to the pane again (A-12 sends the new size); the colors of the import show only while no theme has been read (A-14), in the pane around each terminal (`.orca-term`) too, and follow the system's appearance (`prefers-color-scheme`), also when it changes. Without an import the terminals keep the app's own font (A-8). A font chosen for the terminals in the settings (A-20) takes the place of the font of the import (the family and the size; the thickening of `font-thicken` is Ghostty's own and is not drawn with it); the choice 「Ghostty の設定に従う」, which is the first one, keeps the font of the import as above. A failed import keeps the one that was saved and shows the message (`#error`).

Keys. A key of the import sends its text in place of the key: the text goes with the keys typed (A-8, A-12) to the terminal the key was pressed in, once at the keydown, and xterm.js does not see the key's events (its keypress would print the character too). A key pressed while an input method is composing is left to the input method. Shift+Enter, with no other modifier, sends ESC and a carriage return (`\x1b\r`), which is what Orca sends for it when a program has not asked for the Kitty keyboard protocol (xterm.js has none), and which Claude Code's input takes as a newline without sending; a key of the import for Shift+Enter comes first.

The card. The settings screen has the tab Orca (A-3), whose last card is 「Ghostty の設定」, in the shape of the other integrations: the header row (the logo, the name and the `?` hint `#ghostty-help` with where the files are, what is imported and the Shift+Enter note), a row `#ghostty-items` and the add row with the button 「取り込む」 (`#ghostty-import`, disabled while an import runs). The row says 「まだ取り込んでいません」 with the gray label 「未取り込み」, and after an import the green label 「取り込み済み」 with the files read (「読んだファイル: …」, each file with `~`); under it, two blocks, each a heading with the number and a list of entries: 「取り込んだ項目（n）」 (`#ghostty-imported`) with each entry as written (`key = value`), and 「取り込めなかった項目（n）」 (`#ghostty-skipped`) with each entry and its reason (`.ghostty-reason`); a block with no entry has the heading only. Nothing is read from Ghostty until the button is pressed.

Unit tests (`cargo test`) cover the file format, the places of the config and of the themes, the font entries and their limits, the colors and the palette, the theme names and the light and dark themes, a theme that is not found or not written right, the colors of the config over those of the theme, the keys (modifiers, named keys, Zig escapes, replacement, `clear`, other actions, sequences and prefixes), the report of the entries left, the files (their order, the limits, a folder, an empty file, no file) read from a temporary folder, the saved file and its case. None of them reads the real Ghostty config or the app's config folder. The E2E specs `settings.e2e.ts` (the card: nothing imported, the import with its lists, the saved import, a failed import) and `orca.e2e.ts` (the terminal's font from the saved import and from an import made in the settings, the text of a key of the import, Shift+Enter, and a key of the import for Shift+Enter) cover the screen.

## A-14 Terminal colors

The terminals of the Orca screen (A-8, A-12) are drawn in the colors of a theme that the owner chooses in the settings, one for the light appearance and one for the dark. Rust is `src-tauri/src/orca_theme.rs` (with the table `orca_themes.json`); the frontend is `ts/orca-theme.ts` (the card) and `ts/orca-terminal.ts` (the terminals).

Themes. The choice is among Orca's built-in themes, which this app holds as a table (31 themes in Orca 1.4.250): for each, the background, foreground, cursor, cursor text, selection background and foreground, and the 16 ANSI colors (the palette colors 0 to 15), all `#rrggbb`. The table was taken from the Orca 1.4.250 installed in `/Applications/Orca.app`: `app.asar` was extracted (`npx @electron/asar extract /Applications/Orca.app/Contents/Resources/app.asar DIR`) and `TERMINAL_THEME_CATALOG` of `DIR/out/shared/terminal-themes/terminal-theme-catalog.js` (the themes of `defaults.js`, `popular-dark*.js`, `popular-light.js` and `classic.js`, in that order) was written out with `node`, with `black` to `brightWhite` as the 16 colors of `ansi`. The same account is in the doc comment of `orca_theme.rs`. An Orca update can add themes or change colors; then the table is taken again. The defaults are Orca's own: `Builtin Tango Light` for the light appearance and `Ghostty Default Style Dark` for the dark. Any theme may be chosen for either appearance.

The choice. It is saved in `terminal-theme.json` in the app config directory, `{"light": "<name>", "dark": "<name>", "appearance": "system" | "light" | "dark"}` (`appearance` is A-15), written through a temporary file and a rename. A name read from the file that is not a built-in theme is replaced by the default of its slot, and a file that cannot be used is as good as none. `terminal_theme_set` takes the choice (`selection`, the two names and the `appearance` of A-15), refuses a name that is not a built-in theme with 「テーマ {name} は選べません」 (nothing is saved), saves and answers the choice. `terminal_themes` answers `{themes, selection}`: the table in its order and the choice in use. The screen asks for it once, at startup.

The first choice. While `terminal-theme.json` does not exist, the first time the settings of the Orca on this Mac can be read they give the choice, which is saved then; after that Orca's settings are not read again, and a later change in Orca is not followed. Whatever the target of the Orca screen is (this machine or a saved environment, A-6), it is this Mac's Orca that is read. The settings are in `profiles/local-default/profile-state.db` of Orca's settings folder (`~/Library/Application Support/orca`), a SQLite file: the row with `domain = 'settings'` of the table `profile_state_documents`, whose `payload` is JSON. This is not a public interface, and it was read on Orca 1.4.250; an Orca update can change it. The file is opened read-only (`SQLITE_OPEN_READ_ONLY`, with a busy timeout of 500 ms; Orca keeps it in WAL mode, so a reader does not wait for Orca's writes) and is never written, and only `terminalThemeLight` and `terminalThemeDark` of the payload are used; the payload is kept and logged nowhere. Orca's `theme` (light, dark, system) and `terminalUseSeparateLightTheme` are not looked at: the app has its own appearance rule, below. A value that is missing, empty or not text gives the default of its slot, as in Orca. A name that is not a built-in theme (a theme the owner added in Orca, which Orca writes as `custom:...` and lists in `terminalCustomThemes`, a plugin's palette `plugin:...`, or a name the table lacks) gives the default of its slot, and the other slot keeps what Orca has. When the file cannot be opened, has no such table or row, or the payload is not a JSON object, the defaults are used and nothing is saved, so that the next start tries to read Orca again. The SQLite library is `rusqlite` (with its bundled SQLite).

Appearance. The terminals take the theme of the appearance that A-15 gives: the system's (`prefers-color-scheme`), also when it changes while the app runs, unless the owner fixes it to light or dark there. Orca's own `theme`, even when it is fixed to light or dark, does not matter. The theme's colors set the terminal (xterm.js `options.theme`: background, foreground, cursor, cursor text, selection, and the palette colors 0 to 15) and the background of the pane around it (`.orca-term`); a chosen theme is drawn in every terminal at once, with no restart, and the colors that Ghostty's import (A-13) sets lie under it: the theme wins, and the import's colors show only while no theme has been read (a failed `terminal_themes`), when they follow the system's appearance. The font and the keys of the import are used as before.

The card. The Orca tab of the settings screen (A-3) holds the cards of the target (A-6), this one, the editor (A-18) and the Ghostty settings (A-13), in this order, in the shape of the other integrations: the header row (the logo, the name 「ターミナルの配色」 and the `?` hint `#terminal-theme-help`, which says that the light and the dark are chosen apart, that they follow the system's appearance unless the appearance row fixes one of them (A-15), that the themes are Orca's built-in ones, where the first choice comes from, and that the theme comes before Ghostty's colors) and the rows `#terminal-theme-items`. There are three rows (`.item`): the appearance row of A-15, then 「ライト」 (「ライトの外観で使うテーマ」) and 「ダーク」 (「ダークの外観で使うテーマ」), each with a swatch (`.theme-swatch`: the theme's background, 「Aa」 in its foreground, and its 16 colors in `.theme-dots`), the name and a select (`#terminal-theme-light` and `#terminal-theme-dark`, `aria-label` 「ライトのテーマ」 and 「ダークのテーマ」) of every theme, in the order of the table, with the chosen one selected. Choosing a theme sends both names, with the appearance as it is, to `terminal_theme_set`; the selects wait while the save is on its way, the swatch and the terminals follow the answer, and a failure shows its message (`#error`) and leaves the saved choice in the select. Before the themes are read the card has no row, and a failed read shows its message.

Unit tests (`cargo test`) cover the table (31 themes, unique names, the 22 colors of each as `#rrggbb`, the palette colors 0 to 15, the colors of `Builtin Tango Light`), the choice that Orca's settings make (both built in, values missing, empty or not text, a custom, plugin or unknown theme replaced by the default of its slot only, a payload that is not an object), the replacement of an unknown name in a choice, the read of the settings from a temporary SQLite file in WAL mode (the row, no row, no file and the file not made, a file that is not a database, a database of another shape, the file not changed by the read), the saved file and its shape, that a saved choice is not replaced and Orca is not read after it, the first choice from Orca saved once, the defaults used and not saved while Orca cannot be read, a failed save of the first choice, and `terminal_theme_set` with a built-in and an unknown name. None of them reads Orca's real settings folder or the app's config folder. The E2E specs `settings.e2e.ts` (the card above Ghostty's, the three rows, the options and the swatch, a save and its arguments, a failed save, the startup read, a failed read) and `orca.e2e.ts` (the terminal's colors for the system's appearance (the default) and when it changes, the theme over the Ghostty import, the import's colors while no theme was read, a theme chosen in the settings) cover the screen; the E2E page replaces `matchMedia` for the dark appearance (`e2e/fixtures.js`) so that a spec can change the appearance.

## A-15 Terminal appearance

The Orca terminals (A-8, A-12) draw the theme of the light appearance or the one of the dark appearance (A-14). The owner chooses in the settings which one: the system's appearance, or always the light one, or always the dark one. Rust is `src-tauri/src/orca_theme.rs` (the `appearance` of the choice); the frontend is `ts/orca-theme.ts` (the row) and `ts/orca-terminal.ts` (the terminals).

Why. The app's own screens have no dark appearance, so a system that turns dark (macOS "Auto") made the terminals dark under a light app. The owner can now keep them light, or dark, whatever the system does.

The choice. It is one of three values: `system` (the default), `light` and `dark`. With `system` the terminals take the theme of the system's appearance (`prefers-color-scheme`) and follow it when it changes, as A-14 says. With `light` or `dark` they always draw the theme chosen for that appearance, and a change of the system's appearance does not change them. The pane around the terminal (`#orca-term`) takes the same theme. The choice is drawn in every terminal at once, with no restart.

Saving. It is the `appearance` entry of `terminal-theme.json` (A-14), `"system"`, `"light"` or `"dark"`. A file without the entry (written before A-15), or with a value that is none of the three (unknown, not text, `null`), reads as `system`; the names of the themes are read as A-14 says. The first choice taken from Orca's settings (A-14) is `system`: Orca's own `theme` is not looked at. `terminal_theme_set` takes and answers the choice with the `appearance` in it, and `terminal_themes` answers it in `selection`; no new file and no new communication is added.

The row. The card of A-14 has the appearance row first (`.item`, the name 「外観」 and the note 「ターミナルが使うテーマ」, with no swatch) with a select `#terminal-theme-appearance` (`aria-label` 「ターミナルの外観」) of 「システムに合わせる」, 「ライト」 and 「ダーク」, in that order, the saved one selected. Choosing one sends the choice with the other entries as they are to `terminal_theme_set` (and choosing a theme sends the appearance as it is); the selects wait while the save is on its way, the terminals follow the answer, and a failure shows its message (`#error`) and leaves the saved choice in the select. The `?` hint of the card says what the three values do.

Unit tests (`cargo test`) cover the save and the read back of each value, the file shape, a file without the entry and one with an unknown, mistyped or `null` value (read as `system`), that the entry survives the replacement of an unknown theme name, and that the defaults and the choice taken from Orca are `system`. None of them reads Orca's real settings folder or the app's config folder. The E2E specs `settings.e2e.ts` (the row and its options, the saved value shown, a save and its arguments, the appearance kept when a theme is chosen, a failed save) and `orca.e2e.ts` (the terminal fixed to light or to dark when the system's appearance changes, the terminal drawn again at once when the appearance is chosen in the settings, and back to following the system) cover the screen.

## A-16 Start from the plus of the Orca work pane

The work pane of the Orca screen (A-6) starts a session from a plus right after the last tab of the tab bar of each of its panes (A-17), as Orca does: Claude in a worktree, or a plain terminal in it. The list pane's header has no new button. Rust is `orca_terminal_create` and `orca_start` in `src-tauri/src/orca.rs`; the frontend is `ts/orca.ts`.

Why. A session starts where the user is looking: the project selected in the list pane. The plus sits beside the tabs it adds to, and a plain terminal could not be started from the app at all.

The plus. `.orca-plus` (an `.icon-btn` of 28 px with a plus, `aria-label` 「セッションを始める」, `aria-haspopup` "menu"; one in each pane) is the last child of the tab bar `.orca-tabbar` (A-8), after the strip of tabs, which is as wide as its tabs and no wider than the room that is left: the plus follows the last tab, and when the tabs do not fit, the strip scrolls sideways and the plus stays in view at the right end of the bar, before the button of the file pane (A-18) in the pane that has it. It is disabled while no project is selected (a project row of the list pane), before the first read, when the command is missing, while a start is on its way and while its tab is waited for (A-6). Pressing it first gives its pane the focus (A-17), so the new tab joins that pane, then opens a menu (`openMenu`, `role="menu"`) of three items, in this order: 「Claude を起動」, 「ターミナルを開く」 and 「スクラッチパッド」 (A-29), each with a line icon at its left and no colored dot (`CLAUDE_SVG` for Claude, `TERMINAL_SVG` for the terminal: a rounded square with `>_` in it, `SCRATCHPAD_SVG` for the scratchpad: a sheet with two lines of text). The start is of the project selected in the list pane, whichever pane's plus was pressed. No item of the menu is ever disabled.

Where. The worktrees of the selected project are the worktrees of the list that carry its key (`OrcaWorktree.projectKey`: the project key of A-8, the `repoId`; empty when a repository has none). With exactly one, the item acts in it at once. With none or with two or more, the dialog of the worktrees of A-6 opens under the plus, with only the worktrees of that project (a project with none shows 「該当する worktree がありません」 and nothing starts), and picking one starts there (or, for the scratchpad, asks for the name there). The target is the one the screen shows, as in A-6.

Claude. 「Claude を起動」 is the start of A-6: `orca_start(path, environment)`, the same checks, the same follow (A-6, "After a launch").

Terminal. 「ターミナルを開く」 calls `orca_terminal_create(path, environment)`, which answers `{paneKey, handle}` as `orca_start` does: `paneKey` is always `null` (a plain terminal has no pane that Orca names) and `handle` is `result.terminal.handle`, `null` when the reply lacks it or holds it in a shape that is not a terminal handle (`term_` and `[A-Za-z0-9_-]`). Rust runs `orca terminal create --worktree path:<path> --json` (`--environment=<name>` when a target is chosen), with no `--focus`, no `--title` and no `--command`, in the temporary folder with an argument list, never through a shell, and a timeout of 60 seconds, once (a lost reply is never followed by a second run). Just before, it validates and reads the list again, as a launch does: the path is absolute, the environment is a saved one, and the path is a worktree of the list read just now; otherwise the answer is a Japanese error and nothing is made. The terminal that was made is a plain terminal of A-8 (no Claude row holds it, it still has its tab and it is in a listed worktree), so it is a tab of its project with no change to the list.

After it. The terminal is followed as a session is (A-6, "After a launch"): the project and the tab that were selected stay, the note and the disabled plus show while it is waited for, and once a read or a streamed list (A-12) holds a plain terminal of that `handle`, for at most 30 seconds, the screen selects its project and its tab, so its terminal shows (mirrored on this machine, streamed from a saved environment, A-8, A-12). Selecting a project or a tab or the 30 seconds drop the wait, and a start is never followed after the user selected another project or tab while it was on its way. A failure shows its message (`#error`) and the selection stays. A start made as Claude is waited for as a Claude row only, and one made as a terminal as a plain terminal only.

The CLI. `orca terminal create` was read on Orca 1.4.250 (`orca terminal create --help`, and `cli/handlers/terminal.js` and `cli/terminal-format.js` of its app: the reply is `{ok, result: {terminal: {handle, title, surface, warning}}}`); with `--environment` a remote host needs `--worktree`, which is always given. An Orca update can change it, and then the plus says what the CLI answered. The created terminal is a background tab when Orca's window cannot adopt it (`surface` `background`); it is then waited for until the 30 seconds end.

Unit tests (`cargo test`) cover the argument list of `terminal create` (the path joined to its selector, the environment last) and the reading of its reply (the handle, and a reply that is empty, odd or lacks it), and the project key that the worktrees carry (this machine, an SSH host, none); none runs the real CLI. The E2E spec `orca.e2e.ts` covers the plus (its place right after the last tab, and in view at the right end of the bar when the tabs overflow, and its being disabled without a project), its menu of three items (the scratchpad of A-29 has its own spec), the start at once in a project's one worktree and the dialog narrowed to the project's worktrees when it has several or none, the arguments of a launch and of a new terminal with the target, the following of each (the tab of a Claude session and of a plain terminal, from a read and from a stream) and its being dropped, a failure and the plus disabled while a start is on its way, and that the header has no 「新規」; and the plus of a second pane giving that pane the focus before the start (A-17).

## A-17 Split panes in the Orca work pane

The work pane of the Orca screen (A-6) can be split into panes, as Orca's own window is, and a pane has its own tabs: two terminals can be seen side by side or one above the other. Rust is `src-tauri/src/orca_panes.rs` (the command `orca_panes`); the frontend is `ts/orca-panes.ts` (what Rust answered), `ts/orca-pane-tree.ts` (the panes drawn, the drag of a tab and the drag of a divider) and `ts/orca.ts`.

Why. Seeing a Claude session and a terminal together took switching tabs. The owner chose the design of Orca itself (2026-11-08, Discussion #205, issue #191): both directions, the right-click menu of a tab and the drag of a tab as the ways to split, no limit on the number of panes, and a split that is remembered for each project. The tabs of the editor (A-18) are in the same layout; a tab of any kind that joins the work pane's tabs is split, moved and closed in the same way, because the layout holds tab ids and no more.

The layout. The layout of a project is a tree: a pane (its id, its tabs in order, and the tab it shows) or a split of two or more nodes, side by side (`row`) or one above the other (`column`). A pane has at least one tab. A split never has one node, and never has a split of its own direction as a child (they merge). The layout also names the pane that has the focus, which is the pane the plus of A-16 adds its new tab to, and whose shown tab is the selected tab of the project (A-6 and A-8: the session row that is pressed, the badge of A-6 and the following of A-16 all use it). The ids are `p1`, `p2` and so on, the smallest number not used, and mean nothing outside one layout. There is no limit on the number of panes. A split also holds the share of its size that each of its nodes takes (`sizes`, one number for each node, which add up to 1), and between two nodes is a divider to drag (below).

Splitting. Two operations split a pane, and both name a tab, a pane and an edge:
- The right-click menu of a tab (`contextmenu` on the tab, a menu of `openMenu` under it) has 「右に分割」 and 「下に分割」: the tab moves to a new pane at the right of, or below, the pane it is in. Each has a line icon at its left and no colored dot: `COLUMNS_SVG` for the right (a square cut by a vertical line) and `ROWS_SVG` for the bottom (a square cut by a horizontal line). A pane with one tab has no split, because it would leave the pane empty.
- The tab of a file open in the editor (A-18, `file:{n}`) has two more rows in the same menu: after a line under the split, 「パスのコピー」 and 「相対パスをコピー」, each with `COPY_PATH_SVG`, with the same texts and the same toasts (「パスをコピーしました」, 「相対パスをコピーしました」) as the file pane's menu of a file (A-18): the path of the file on the machine of the worktree (the worktree's path and the file's path from it) and the path from the worktree. The tab of a pane with one tab has the two copies alone, with no line before the first. A terminal, a Claude session and a diff (A-24) have no copy, so a pane with one such tab still has no menu.
- A tab dragged by the pointer to another pane (pointer events, not the drag and drop of HTML, so the window's file drop stays off as A-10 needs): after the pointer moved 5 px a hint (`.orca-drop`, a frame over the part of the pane that would take the tab) follows it. Over the tab bar of a pane, or the middle of its body, the tab joins that pane's tabs (at the end, and it is shown there); within a quarter of the body's width or height of an edge (the nearest, in a corner), the pane is split there, and the tab is a new pane at that edge (left, right, top or bottom). Releasing drops it, Escape or a cancel leaves it, and the click that follows a drag does not select the tab. The pane the tab is in takes only an edge, and only when it has another tab; its own bar or middle, and an edge of a pane that has no other tab, show no hint and change nothing. A press on the close button does not start a drag.
A tab that moved out of a pane leaves it; the pane shows the tab that followed it, else the one before; a pane left with no tab is closed, and a split left with one node is that node. A new pane is placed beside the pane it was split from, and joins its parent split when that has the same direction. The new pane has the focus.

Sizes. Each node of a split is as large as its share (`sizes`), and the nodes of a new split have equal shares. Between two nodes of a split is a divider (`.orca-divider`, `role="separator"`, `aria-orientation` "vertical" in a row and "horizontal" in a column; 7 px with a grip, drawn as the divider of the list, `.split-bar`). Dragging it by the pointer (pointer events on the document, as `ts/split.ts`; not the drag and drop of HTML) changes the sizes of the two nodes beside it, left and right in a row and up and down in a column, and of no other node; the two follow the pointer while it is held (drawn in TypeScript, one write for each animation frame), and the release sends `resize` with the ratio, which Rust keeps in the layout, so the project has it when it is opened again; the layout the screen holds takes the same shares at the release (`applyLocal`, clamped as Rust clamps), so a drawing made before Rust answers does not put the divider back. A press that never moved sends nothing, a cancel of the pointer puts the sizes back and sends nothing, and a layout drawn in another shape while a divider is held ends the drag. Each of the two nodes keeps at least a tenth of the split (`MIN_SHARE`; half of what the two have together, when that is less than two tenths), in the drawing of the drag as in Rust. The terminal of a pane is fitted to its new size as to any change of its size (A-8: the `ResizeObserver` of its host element). The divider is no part of a pane, so a press on it gives no pane the focus, and the drag of a tab does not take it. When the nodes of a split change, Rust keeps the shares in step: a new pane takes half of the share of the pane it was split from (in a new split, a half each), a node that closes gives its share to the rest in proportion, the nodes of a split that merges into its parent divide the share it had, and a node that takes the place of its split of one keeps that split's share. Shares that are not one positive number for each node (a file saved before the shares were kept has none) are made equal, and shares that do not add up to 1 are scaled to it.

Focus and selecting. Pressing anywhere in a pane gives it the focus (its tab strip, its terminal, its empty body). Pressing a tab shows it in its pane and gives that pane the focus. The pane with the focus has an accent line on its tab bar while there are two or more panes. The terminal of the pane with the focus takes the keyboard when the focus changes.

The call. `orca_panes(environment, project, tabs, handles, was, op)` answers the layout (`PaneLayout`, `PaneNode`, `PaneOp` and their parts are ts-rs types) of the project `project` (its key, A-8) of `environment` (where the project's row is: the name of a saved environment, null for this machine). `tabs` is the ids of the tabs the screen shows for the project now, in the order they were first seen (`claude:{pane key}` for a Claude session, `orca:{handle}` for a plain terminal, A-8, `file:{n}` for a file open in the editor, A-18, and `diff:{n}` for the diff of a file, A-24). `handles` is the Orca handle of each of those tabs that has a terminal (a tab id to its handle), and `was` is the same map for the tabs of the call before it for the project that worked (empty for the first one). `op` is what the user did, or null: `focus {pane}`, `select {tab}` (the tab is shown in its pane, and the pane has the focus) `move {tab, pane, edge}` with the edge `left`, `right`, `top`, `bottom` or `center`, or `resize {before, after, share}` (the divider between the node that holds the pane `before` and the next node of the same split, which holds the pane `after`, any pane of each: the first takes `share`, 0 to 1, of the size the two have together, within the least share above; panes that are not in two nodes next to each other in that order change nothing) (A tab or a pane that the layout does not have changes nothing.) Rust does, in this order, with no clock and no other input:
1. Takes the saved layout of the project (an empty one when there is none), follows the terminals that changed kind (below), and mends it against `tabs`: a layout deeper than 32 levels or with more than 500 tabs was not written by this app and is dropped; a tab that is not in `tabs`, and a tab that a pane already has, leave; a pane id used twice is renamed; empty panes close and single splits merge, and the shares of each split are mended (above); a tab in `tabs` that no pane has joins the end of the pane with the focus (the first pane when the focus names none, and a new pane `p1` when there is no pane); a focus that names no pane goes to the first pane; a shown tab that a pane lacks is the first of the pane.
   A terminal that changed kind keeps its tab: when Claude starts in a plain terminal, or ends in a terminal of its own, Orca lists the same terminal (the same handle) as `claude:{pane key}` where it was `orca:{handle}`, or the other way round. A tab of the saved layout that `tabs` no longer lists, whose handle is the one `was` gives for it (for a plain tab id, the one in the id), is replaced, in its pane at its place and as the pane's shown tab if it was, by the tab of `tabs` that the layout does not have and that has the same handle in `handles`; so the panes and splits stay as they were. A tab with no known handle (a Claude tab that `was` does not hold, as after the app was restarted) is only a tab that is gone. No call to Orca is added, and the file keeps its shape.
2. Does `op` on the mended layout.
3. Saves it when it differs from the saved one, and answers it. A layout with no tab is not saved and its entry is removed.
The saved layout is not read again by the screen: it keeps the last answer for each project and place (the `environment` of the project's row) in memory, and asks again (`op` null) when the tabs it shows for the selected project are not the ones it asked with the last time (the first time, and each time a tab came or went); a read that did not work, and a target that is switching, ask nothing, so a failed read never takes tabs out of the layout. Calls go one after another in the order they were made, and only the latest answer of a project is taken. A press (select, focus) is shown at once and then sent; a move is drawn when the answer comes, and so are the sizes that Rust kept for a dragged divider. A tab that came is in the pane with the focus when the answer comes, and until then it is not drawn. A failure shows its message (`#error`), and the project then has one pane with all its tabs, which works as before, until the next call that works.

The file. `orca-panes.json` in the app config directory: `{version: 1, entries: [{environment, project, layout}]}`, with `layout` as the tree above (`{root, focus}`, each node `{kind: "pane", id, tabs, selected}` or `{kind: "split", direction, children, sizes}`; a file with no `sizes` is read as equal shares). It holds tab ids and project keys of Orca, which are no secret, and nothing a terminal printed or was typed. It is written with a temporary file and a rename, one command at a time (a lock), and a file that cannot be read, or has another `version`, is taken as empty and replaced by the next save. The command rejects an empty or control-character `environment`, `project`, tab, handle or pane, one longer than 512 bytes, more than 500 tabs or handles, and a `share` that is not a number from 0 to 1, in Japanese.

Terminals. The terminal of the tab each pane shows is shown in that pane (A-8, A-12): this machine's are mirrors, a saved environment's are streams, one for each pane at once, and each is fitted to its pane. A tab that is not shown in a pane keeps its terminal (its screen and scrollback) but reads nothing and streams nothing. A tab moved to another pane keeps its terminal, which is fitted to its new pane. A terminal that changed kind (above) keeps its terminal too: the screen of a terminal is known by its handle, not by its tab id, so its screen and scrollback are not made again, and the tab keeps its place in the order the tabs were first seen. The keys typed in a terminal go to that terminal, and an image dropped or pasted on it goes to its worktree (A-10).

The empty pane. With no project selected, or a project with no session, the work pane is one empty pane with its tab bar and its plus and the line 「プロジェクトを選んでください」 or 「セッションはありません」; a pane whose shown tab is a session with no terminal says 「このセッションのターミナルはありません」, and a pane shows no line while a start is waited for (A-16).

Unit tests (`cargo test`) cover the mending (a new tab joining the focused pane, a tab that left and the pane that closed, a tab in two panes, a pane id used twice, a layout that is too deep or too big, flattening), selecting and focusing, a split at each edge of a pane (also its own pane, and the shown tab left behind), a tab alone in its pane, a tab or pane that is unknown, a split beside a split of the same direction and of the other, the center, the shares (a dragged divider changing the two nodes beside it and no other, the least share, a divider named by any pane of each side and one that is not there, the half a new pane takes, the share a closed pane leaves, a merged split, shares that are missing or wrong), the file (for each project and target, tabs that left, a project with none, a broken file, another version, a file with no shares and a ratio that comes back), the checks of the arguments and the shape of the types; none touches the real settings folder. The E2E spec `orca.e2e.ts` covers the call (its arguments with the tabs and with each operation), the panes drawn from the answer (a row, a column and a split in a split, each with its strip and plus, and the focus mark), the sizes of the panes from the shares of the answer, the drag of a divider (the two panes beside it following the pointer and the third unchanged, the `resize` it asks for at the release and the sizes of the answer drawn, the least share, a cancel, and a column's divider), the right-click menu and its two items with their line icons (no colored dot), the copies of a file's tab (their line, their texts, the clipboard and the toast, and the copies alone in a pane of one tab), no copy on a terminal, a Claude session and a diff, no menu for a pane of one tab with no copy, the drag to each edge and to the bar and the middle, the hint and its Escape, the drops that change nothing, the tab that was dragged not being selected, pressing a tab and a pane, the terminals of two panes on this machine and on a saved environment (each read or streamed, its events drawn in its own pane, the keys sent to its terminal, the close that names one terminal, and the new size of both after a drag of the divider), a tab that left and the answer without its pane, the plus of a second pane, and a failed call.

## A-18 Orca files and editor

The Orca screen (A-6) shows the files of a worktree as a tree on the right of the work pane, as Orca's own window does, and a file opens in an editor of つなぎAI as a tab of the work pane, where what is typed is saved by itself. The text has a box of line numbers at its left (`.orca-edit-gutter`, `aria-hidden`), as wide as the digits of its last number (its width is set in `ch` when the count of digits changes, not measured from the numbers). The numbers start at 1, one for each line of the textarea (the empty line after a last line break has its own number; an empty text is one line), right-aligned, in a fainter color (`--muted`) than the text, with the same font family, size (A-20) and line height as the text, so each number is on the line it numbers. The box follows the vertical scroll of the text and stays where it is under the horizontal one; the wheel over it scrolls the text (by pixels, by lines of the text's line height, or by the height of the textarea, as the wheel event counts). A line is not wrapped (`white-space: pre`), so a number is one line. The numbers are not part of the textarea, so they are not selected and not copied, and they are not read aloud. They are kept in step with the text at the read and at each `input` event: only the numbers that came or went are written at the end of the numbers (one text node, not rebuilt), and nothing when the count of lines is the same, so a file of 384 KiB is not drawn again at each key. Why. The line of an error or of a diff could not be found in a file without counting (the owner's issue #378). Not in scope: wrapping a line, marking the line of the caret, and selecting a line by its number.
- Saving. The file is saved by itself, and the screen has no save button. Once the typing has stopped for the time of the settings (below), the whole text is sent with `orca_file_write(path, relative, content, crlf, signature, environment)`; Orca writes it only if the disk still holds the text with `signature`, and Rust answers `saved` with the signature of what it wrote (the next save is made against that), or `changed`, `missing` or `not-utf8` when it refused. A CRLF file is written with CRLF. One save is on its way at a time; typing that came meanwhile is saved when it ends, by the same wait.
- The state at the right of the heading: nothing when nothing was typed; 「保存待ち」 from the first key until the save starts (each key restarts the wait); 「保存中」 while it is on its way; 「保存しました」 when it went through. The tab has a mark of unsaved typing (a dot, with the label 「未保存」) from the first key until a save went through with the text that is in the editor now; then the mark goes.
- A file that changed elsewhere. Before it writes, Orca compares the disk with the text that was read, so the editor never overwrites a change made elsewhere. When it refused, the heading says 「ディスクのファイルが変わっています」 (`changed`), 「ファイルが見つかりません」 (`missing`) or 「ディスクのファイルが UTF-8 ではなくなっています」 (`not-utf8`); nothing is written, the text stays in the editor and the tab keeps its mark, and no save is tried again for that tab (the user opens the file anew after closing it). Why this and not a read of the file's mtime before the write: `files.writeIfUnchanged` of Orca checks and writes in one step, so a change between the check and the write cannot slip through; the signature it compares is the one of Orca's `disk-baseline-signature.js` (two FNV lanes over the UTF-16 code units, and their count), which `orca_files.rs` computes of the text it read (`disk_signature`).
- A save that failed (the connection, a host that lacks `files.writeIfUnchanged`, a pairing that may not write) shows its message in `#error`, and the heading says 「保存できません」; the typing is kept, and the next key tries again. A text over 384 KiB is not sent.
- Closing the tab. A tab with unsaved typing is saved first (waiting for a save that is on its way, and saving what is typed), then closed. A save that cannot be made keeps the tab and shows its message (pressing the close button again tries the save again); a save that was refused (above) lets the tab close, as the heading has said the text is not saved.
- Closing the window. When the page is hidden for good (`pagehide`), the typing of every open file that can be saved (read, not refused, with typing not on the disk) is sent at once, without waiting for its timer, by the same call as a save. The window may close before Orca answers, so the answer is not shown.

The settings. The Orca tab of the settings screen has a card 「エディタ」 above the card of Ghostty (A-13), with the logo, the title and the `?` hint of the cards of the other integrations, and a row 「自動保存までの時間」 with a number field and 「ms」. ## A-19 Search the Orca list

The list pane of the Orca screen (A-8) has a search field above the list. What is typed narrows the list itself, the projects, to the rows whose name holds it. It is all in the frontend, `ts/orca.ts`; no command, file or call to Orca is added.

Why. The projects grew in number and the one wanted took a scan of the whole list. The owner chose the layout (2026-11-08, Discussion #199, issue #200): layout B, a field above the list that narrows the list, not a palette in the middle of the screen as Orca's own window has it, because the palette hides the work pane and the field leaves the terminals in view while the row is chosen. The wish to find a row by the name of a worktree or a branch was left out: the rows of the list are projects, with no row for a worktree or an SSH host (AI decision, written in the issue).

The field. `#orca-search` (`role="search"`) is between the header and the list, with a magnifier, the text field `#orca-search-input` (`aria-label` "プロジェクトを検索", the placeholder 「検索」, which is only the field's name) and, while something is typed, the button `#orca-search-clear` (`.icon-btn`, `aria-label` "検索を消す"). The screen has no other text about the field. The text is kept in memory.
- Cmd+J (Ctrl+J elsewhere), with the Orca screen shown and with the focus anywhere, including a terminal or the editor, moves the focus to the field and selects its text. No other key of the app is Cmd+J (no handler for it in `ts/`, no accelerator in `src-tauri`; Orca's own window uses the same key for its search).
- The match is a part of the row's name, with case ignored; the text is trimmed, and a blank text is no search. A character that a regular expression takes as its own (`.`, `(`) matches itself. Only the name is searched: the name of a project. The sessions under a project, the worktrees and the branches are not.
- The letters that match are bold (`<b>` in `.orca-project-name`), every place in the name where the text is found.
- The order of the rows is the list's own (the projects, in the order of A-8). A row that does not match is not drawn. If that is the selected project, its row goes and the sessions under it go with it (they are drawn only under a row). The selection, the tabs and the work pane do not change with the search.
- When nothing matches, the list says 「一致するプロジェクトがありません」 (while the first read is on its way it says it is reading, as before).
- The keys of the field. One matching row has a line in the accent color (`data-cursor="true"`): the first, until a key moves it; a change of the text puts it on the first again. Down and Up move it to the next and the previous row, stop at the ends, and scroll it into view. Enter selects the row (the same as pressing it: the project opens in the list and its tabs show) and keeps the text, so that the list stays narrowed; with no row it does nothing. An Enter or an arrow that confirms an IME conversion is not taken. Escape clears the text and takes the focus out of the field. The clear button clears the text and keeps the focus in the field. A cleared field shows the whole list.

Why this is not a Rust function. The testing rules want logic that needs a test to be a pure Rust function, and this is the one place where that costs more than it gives: the match is `RegExp.test` of an escaped text on a name, as the filter of the worktree dialog of A-16 does with `includes`, and the bold range is what `split` returns for it. A command would be called at each key for a list the page already holds, and would need its own mock in E2E for a one-line comparison. The E2E spec checks the whole behavior on the real WebView (rows kept and dropped, case, the escape of a special character, the bold ranges), so nothing here is left to a reading of the code.

Unit tests (`cargo test`): none; nothing of Rust is added. The E2E spec `orca.e2e.ts` covers the field and its place under the header, the focus by Cmd+J (also from a terminal), the narrowing by a part of a name with case ignored, the bold letters at every match, a special character that matches itself, the SSH heading shown only for a matching host, the rows that go with the project that does not match, the line that says nothing matches, the keys (the first row at first, Down and Up and their ends, Enter selecting and keeping the text, no row, Escape, the clear button), and a read in the background that keeps the text.

## A-21 Colors in the Orca editor

A file open in the editor of the Orca screen (A-18) is drawn in colors by its language: comments, keywords, strings, numbers, names and so on each have a color. The language is decided by Rust from the file's name, as Orca's own editor decides it, and the colors are drawn by highlight.js in the page. Rust is `src-tauri/src/orca_language.rs` (with `orca_language_associations.json`) and the answer of `orca_file_read` in `src-tauri/src/orca_files.rs`; the frontend is `ts/orca-editor.ts`, with `src/vendor/highlight.min.js`, `src/vendor/highlight-languages.js` and `src/style.css`.

Why. The editor was a plain textarea, and a source file was read as one color. The owner asked that a file open in it be colored by its language, as Orca's own editor does (2026-11-09, issue #296, parts #298 and #299). Everything else of A-18 stays as it was: the automatic save, the mark of unsaved typing, the handling of a file that changed elsewhere, the font of A-20 and the 384 KiB limit.

The language. `orca_file_read` answers two more fields. `language` is the name Orca's editor gives the file (`rust`, `dockerfile`, `plaintext` when it has none), and `highlight` is the name the highlighter of the page knows it by, or null when it has no grammar for it (then the text is drawn plain, as before). The decision is Orca 1.4.254's `detectLanguage` (`out/shared/editor-language/editor-language-detect.js`, `monaco-filename-language.js` and `monaco-language-associations.json` of `app.asar`), written again in Rust as a pure function (`detect_language(path, content)`) with its tables copied. In this order, the first that gives a language wins:
1. The file's name as it is in Orca's table of names (`Dockerfile`, `Jenkinsfile`, `Makefile`, `Justfile`, `CMakeLists.txt`, `.gitignore`, `.env`, `.bashrc` and so on), then the name in lower case in the same table.
2. The extension (from the last dot of the name, in lower case; a name that starts with a dot, `.gitignore`, is all extension) in Orca's table of extensions (`.ts`, `.rs`, `.py`, `.sh` and so on).
3. Monaco's own associations: its file names (`Gemfile`, `Rakefile`, `Vagrantfile`), then the longest of its extensions that the lower-case name ends with (`.hh`, `.csx`, `.vb`; a later language wins an extension that two claim).
4. A name that starts with `jenkinsfile.` is `groovy`; `.env` and a name that starts with `.env.` is `dotenv`.
5. Otherwise `plaintext`. Only a name with no extension then takes the language of its `#!` line (the first 256 characters of the text): the interpreter with its directory, `.exe` and the digits and dots at its end taken off, `env` and its flags skipped, looked up in Orca's table (`bash` and the other shells, `python`, `node`, `ruby`, `perl`, `php`, `lua`, `pwsh`, `groovy` and so on). A name with an extension that Orca does not know (`notes.txt`) stays plain whatever its first line says.

Orca decides again at each key; the editor of this app decides once, when the file is read, so a `#!` line typed into a file that had none colors it the next time it is opened. The name Orca gives is turned into the highlighter's by a table in Rust (`highlight_name`): the same name for most, and a close grammar for some (HTML, Vue, Svelte and Astro as `xml`, Apex as `java`, CUDA as `cpp`, `shell` as `bash`, `bat` as `dos`, `proto` as `protobuf`, `dotenv` as `ini`, `jsonl` and notebooks as `json`, Markdown variants as `markdown`). A language with no grammar in the page (`zig`, `lean`, `hcl`, `csv`, `mermaid` and so on) has `highlight` null.

The drawing. The editor is two layers of the same text (`.orca-edit-body`). The textarea is on top with its text transparent, so the caret, the selection (`--hl-select`) and the typing are its own; under it a `pre` (`.orca-edit-hl`, `aria-hidden`, no pointer events) carries the same text in `<span class="hljs-…">` elements that highlight.js returns, with its text escaped. Both take the same font family and size (A-20), padding, line height and tab width, so the letters sit on one another; the layer is moved by the scroll of the textarea (`transform`) and follows it again when the tab is shown after having been out of the page. The line numbers of A-18 are a third part beside the two layers: the two layers are in a box (`.orca-edit-text`) at the right of the numbers' box, so the layers' position and the text's padding are as they were, measured from the left edge of that box. The layer is drawn when the file is read and after each `input` event, so it holds the text of the textarea (the text of an IME conversion in progress too, without its underline). Up to 30,000 characters the text is colored again once a frame while keys come (the layer is the old one for at most that frame). A longer one is drawn plain at once when it is read and colored 150 ms later; while keys come, the layer keeps its old text and colors and is drawn again, colored, at most once in 150 ms (coloring 384 KiB takes longer than a key). A read that fails shows no layer, as no textarea. Nothing of the colors is saved, sent or logged.

The colors. They are the variables `--hl-comment`, `--hl-keyword`, `--hl-string`, `--hl-number`, `--hl-title`, `--hl-type`, `--hl-attr` and `--hl-meta` of `:root` in `src/style.css` (the colors of GitHub's light theme, each at least 4.5 to 1 on the editor's white ground), and `--ins`, `--del` and their grounds for the added and removed lines of a diff. The editor's ground is `--surface` and the app has no dark appearance for it (the terminals follow the system's, A-14, A-15), so there is one set; a dark set would be a second block of these variables with a dark ground.

The library. highlight.js 11.12.0 (BSD-3-Clause; 25,014 stars, last push 2026-11-01 as read from the GitHub API on 2026-11-09; languages are added by registering a grammar), as the files of `@highlightjs/cdn-assets`: `src/vendor/highlight.min.js` as it is (the common build of 36 languages) and `src/vendor/highlight-languages.js`, 23 more grammars of the same version joined as they are (`dockerfile`, `powershell`, `dos`, `dart`, `scala`, `groovy`, `elixir`, `erlang`, `haskell`, `clojure`, `protobuf`, `cmake`, `nim`, `verilog`, `delphi`, `fsharp`, `julia`, `tcl`, `coffeescript`, `handlebars`, `scheme`, `twig`, `pgsql`). Both are classic scripts that `ts/vendor-load.ts` reads together the first time a file or a diff is colored, not at start-up (#414): until they are read the editor draws the text plain and the diff draws its rows plain, and both are colored once the read is done. A read of a group that fails in part is tried again at the next ask for the scripts that failed only (`ts/vendor-load.ts` keeps the read of each script); after one failed read the editor gives up the colors of that file while it is open, so the keys do not read again. highlight.js loads no resource from outside, and the paths are inside `src/vendor/`, so the CSP is not loosened. Monaco, which Orca uses, needs a bundler, web workers and a loader, and CodeMirror 6 needs a bundler; neither fits a page without one.

Checked against. The tables were read in the `app.asar` of Orca 1.4.254 (`/Applications/Orca.app`, extracted with `npx @electron/asar extract`), and the expected answers of the unit test were taken by running Orca's own `detectLanguage` under node. An Orca update can change the tables; then they are taken again. No new call to Orca and no new saved file is added.

## A-22 Download an Orca file

A file in the file pane of the Orca screen (A-18) can be copied to this PC: the right button on its row opens the menu with the item 「ダウンロード」, and a save dialog asks where to put the copy. Rust is `src-tauri/src/orca_files.rs` (the command `orca_file_download`, which calls `download`); the frontend is `ts/orca-files.ts`.

Why. A file of a worktree on a saved environment (a paired server) could be read in the editor but not taken to this PC, and a file that is not text (an image, an archive, a build output) could not be seen at all. The owner asked for a download in the menu of the file pane (issue #243, part #320).

The menu. The item 「ダウンロード」 is the third of the menu of a file row (A-18), and the menu of a folder row has only the two copies. A pick closes the menu and calls `orca_file_download(path, relative, environment)` with the path of the worktree, the path of the file from it and the place of the worktree (the saved environment, or null for this machine), as the other commands of A-18 do. The page sends no place to save to.

The save dialog. Rust opens the system's save dialog (`tauri-plugin-dialog`, from the command, as a sheet of the window and without stopping the main thread) with the last part of the file's path as the first file name. The place to save is what the dialog gives and nothing else, so the page cannot make the app write to a path of its choice. A cancelled dialog is not an error: the command answers `null`, and the page shows nothing. The page has no permission of the dialog plugin (no permission of the plugin is in any capability; `capabilities/default.json` holds only the window's drag, A-23): only the command opens it.

The copy. After the dialog, Rust asks Orca the size of the file (`files.stat`), then calls `files.readChunk` (or `files.readPreview` on a host that lacks it, and on a host that lacks `files.stat`, which gives no size to hold the preview to) and writes the file to a temporary file beside the place picked, which is moved onto it when every byte has come (the copy is whole or absent; an old file at the place stays as it was when the copy fails). The temporary file is a new file named `.{name}.part` (`.{name}.{n}.part` when that name is taken, and the name is cut at a character so that the whole fits 255 bytes), so a file or a link of the owner's with that name is never written to or deleted. The file is read 384 KiB at a time, and the reading stops with 「ファイルを読めません」 when Orca sends more bytes than the size said, so an Orca that never says it has reached the end cannot fill the disk; a preview is held to the size too (3 times the size for a text, because a byte that is not UTF-8 comes back as 3). There is no other size limit, and a file that is not text (binary) is copied as it is. The copy is not marked as downloaded (no `com.apple.quarantine` attribute), because it is the owner's own worktree file that the owner copies by hand. On a host that lacks `files.readChunk`, the file is read by `files.readPreview`, and a text file then comes back as a UTF-8 string, so a text that is not UTF-8 is not the same bytes as the original; a binary file is exact. The command answers the name of the file saved, and the page says 「{name} をダウンロードしました」 in a notice; the full path is not shown or logged. A failure (the connection, a file that is gone, a place that cannot be written, an SSH host, which has no file calls as in A-18) shows its message in `#error`, with no notice. The relative path is refused as in A-18. The bytes of the file are in no log, no file of the app except the copy, and no return value.

The same command works on this machine's worktree and on a worktree of a saved environment.

Checked against. `files.stat`, `files.readChunk` and `files.readPreview` are not a public interface of Orca. They were tried on Orca 1.4.254 on this machine (unix socket); a saved environment (WebSocket) was not tried, and uses the same calls. An Orca update can change them.

Unit tests (`cargo test`) cover `download` (the chunks until `eof`, an Orca that never says `eof` stopped at the size, the size from `files.stat` and its failures, a host that lacks `files.stat` or `files.readChunk`, a preview held to the size, the temporary file removed on a failure, a temporary name that is taken or a link in its place left alone, a name of 255 bytes, the old file kept, the paths refused) and the first name of the dialog. The dialog cannot be opened in the E2E build, so the E2E spec `orca-files.e2e.ts` mocks the command and covers the item on a file row only, the arguments of the call (a file in an open folder too, and no place to save), the notice with the name, nothing shown when the dialog is cancelled, and the message of a failure.

## A-24 Orca file diff

The right button on a file of the file pane of the Orca screen (A-18) has the item 「差分を表示」, which opens a tab of the work pane with the difference between the file at HEAD and the file in the working tree (what is not committed yet is in it), side by side or in one column, as the diff of an editor does. Rust is `src-tauri/src/orca_files.rs` (the command `orca_file_diff`, which calls `git_diff` and `parse_diff`) and `src-tauri/src/orca_diff.rs` (the comparison of the lines); the frontend is `ts/orca-diff.ts` (the tab), `ts/orca-files.ts` (the item) and `ts/orca.ts` (the tab among the tabs).

Why. The owner asked to see the uncommitted diff of a file by the right button, as an IDE does (2026-11-11, issue #461; parts #462 and #463). The layout was chosen by the owner: side by side as the first view, and one column by a button of the tab. The difference between commits is A-27's: the same tab, opened from the history.

The menu. 「差分を表示」 is the fourth item of the menu of a file row (A-18), after 「ダウンロード」, with a line icon at its left; the menu of a folder row does not have it. A pick closes the menu and opens the tab (below).

The tab. It is a tab of the work pane (A-8) like a file of the editor (A-18): it joins the strip of the pane with the focus, after the tabs it has, with a diff mark (`DIFF_SVG`) in place of the status icon, its title is the file's name, it is selected, and it is closed with its close button (which asks nothing: it holds no typing). Its id is `diff:{n}`, and A-17 keeps it in the layout as it keeps `file:{n}`: the layout holds the id only, and the tab is in memory only, so after a restart the id is dropped from the layout. It is not a session, so it has no row in the list of A-8. A diff that is open for the file already (the same worktree and path) is selected and read again, and no second tab is opened. The tab shows in the place of the editor of its pane, and the tab strip, the split and the move of tabs (A-17) work on it. A diff of a file of a commit (A-27) is the same tab, with the short id of the commit after the path in the heading and after the file's name in the title.
- The heading (`.orca-diff-head`, the heading of the editor with the buttons) has the path of the file from the worktree, the count of the blocks of changes (「変更 {n} 件」, or 「変更はありません」 when there is none; nothing while it is read or when it failed), and four icon buttons (`.icon-btn`): 「前の変更」 and 「次の変更」, 「1 列で表示」 (「左右に並べて表示」 while it shows one column; `aria-pressed` is true while it shows one column), and 「読み直す」. A block of changes is a run of rows that are not the same. The two buttons of the changes are off when there is no block, and 「前の変更」 is off at the first block and 「次の変更」 at the last. The button of the view and the buttons of the changes are off while the diff is not drawn (read, failed), and the reload button is off while it is read.
- Side by side (the first view, `data-view` "side"). Each row has the line of HEAD on the left, the two numbers of the lines (HEAD's, then the working tree's) in the middle, and the line of the working tree on the right. A line that is only in one file has a blank on the other side (a gray ground and no number). Lines that were changed pair up, in order, on one row; when one side has more lines in a change than the other, the rest stands alone beside blanks. A removed line (or the left of a changed one) has a red ground, and an added line (or the right of a changed one) a green ground (the variables `--diff-del-bg` and `--diff-ins-bg` of `:root`). Long lines wrap.
- One column (`data-view` "inline"). Each row has the number of the line of HEAD, the number of the line of the working tree, a mark (`−` for a removed line, `+` for an added one, nothing otherwise) and the line. The removed lines of a change come first, then its added lines. A removed line is on the red ground and an added line on the green ground. The choice of the view is one for all the diff tabs and is kept in memory only; it is side by side at the start of the app.
- Colors. The text is colored by the language of the file (A-21: Rust names it, `language` and `highlight` of the answer, from the file's name and the first line of its text) with the highlighter of the editor, with the same colors. HEAD's text and the working tree's are each colored as a whole, so a token of several lines (a comment, a string) is colored on each of its lines. A language with no grammar is drawn plain, with the text escaped. A long text (over 30,000 characters in both) is drawn plain at once and colored 150 ms after, as the editor does.
- Moving. When the diff is first drawn, the rows scroll to the first block of changes. 「次の変更」 and 「前の変更」 scroll the rows to the block that follows or precedes the one last moved to (the row at the middle of the rows), and a block that was moved to stays the one the buttons count from. Changing the view scrolls to the block last moved to. A diff read again keeps the place in the rows. A difference from HEAD that a pane shows is read again by the clock of A-18 (every 10 seconds while the Orca screen and the file pane are shown), and when its tab comes back into a pane: the rows are drawn again only when the answer is not the one held, and a read that fails keeps what is shown. A file of a commit (A-27) does not change and is not read again. A tab that is taken out of the page (another tab of its pane is selected) and put back keeps its place.
- A reason. When Rust refuses (below) or the call fails, the reason takes the place of the rows, as a refused read takes the place of the editor (A-18), and nothing is shown in `#error`.

The call. `orca_file_diff(path, relative, environment)` takes the same arguments, and checks the worktree against the target's list and the relative path, as `orca_file_read` does (A-18: the worktree is believed for 60 seconds, an SSH host's worktree is refused, a failed call makes the next one confirm the worktree again). It calls `git.diff` of Orca's runtime with the worktree, `filePath` the relative path, `staged` false and `compareAgainstHead` true, over this machine's unix socket or a paired server's WebSocket. It answers the lines of HEAD and of the working tree (with LF; the rows hold their numbers), the rows of the two views, the blocks of changes (the row each starts at in each view) and the language of the file (the one of `orca_file_read`, from the working tree's text, else HEAD's). A file git does not know has no text at HEAD, and one that is not in the working tree any more is its text at HEAD against nothing.
- The reasons. A diff is not returned, and a reason in Japanese is, when Orca says the file is binary (the kind `binary`, or one side binary or an image), when Orca marks the diff too large to draw (`tooLarge`, `largeDiffRenderLimit`) or answers `diff_too_large` (over a paired server, a diff over about 4 MiB), when a side is over 384 KiB, when a side is not UTF-8 (Orca decodes bytes that are not UTF-8 into U+FFFD, as A-18), and when the answer lacks the text.
- The comparison. The lines of each text are compared with Myers' algorithm (the `similar` crate, which works in linear space; a deadline of 2 seconds gives a coarser, still correct, answer). CRLF is taken as LF before the comparison, so a change of the line ends alone is not a change. A line is its text and whether a line feed ends it, so a file that only lost or gained its last line feed differs (as `git diff` says). A change that replaces lines is a row of paired lines (side by side) and the removed lines before the added ones (one column).
- No text of the files is in a log or a file of the app, and `historyToken` is only Orca's handle of a list, held in memory, not a credential.

Checked against. `git.diff` is not a public interface of Orca. It was read in the `app.asar` of Orca 1.4.255 (the schema `GitDiff` in `git-params.js` and the handler of `git.diff`: a method of the permission `workspace`, with the result `kind`, `originalContent`, `modifiedContent`, `originalIsBinary`, `modifiedIsBinary`, `isImage`, `tooLarge`, `modifiedDeleted` and `largeDiffRenderLimit`), and a saved environment (WebSocket) was not tried. An Orca update can change it.

Unit tests (`cargo test`) cover the lines of a text and the rows (the same text, added and removed lines, changed lines that pair up and the rest of the longer side, a file with no line at HEAD or in the working tree, CRLF, the last line feed, the blocks of changes in both views, and two texts of 12,000 lines compared in time) and the answer of Orca (a new file, a deleted one, the reasons, the sizes, the arguments of `git.diff` and `diff_too_large`). The E2E spec `orca-files.e2e.ts` mocks the command and covers the item on a file row only, the arguments of the call (a file in an open folder too), the tab and its title, the two views and the button between them, the blanks and the grounds, the colors of the tokens (a comment of two lines on both), the plain text for a language with no grammar, the buttons of the changes (the rows scroll), a diff with no change, the reason in place of the rows and the reload after it, the second pick selecting the tab and reading again, and the close of a tab.

## A-25 Switch the branch from the Orca file pane

The branch in the heading of the file pane of the Orca screen (A-18, 「{repo} ・ {branch}」) is a button. The button. The branch is a `button` (`.orca-branch-btn`, `aria-expanded` while its list is open); the part before it stays text. The branch is the git branch the worktree is on (`branch` of `orca worktree ps` without `refs/heads/`, `OrcaWorktree.gitBranch`), not Orca's name of the worktree (`displayName`, `OrcaWorktree.branch`, the name in the heading): a worktree made with a name keeps that name after a switch (Orca 1.4.256), so the two can differ. The list. A heading is a band (`.orca-dest-sec`: 13px, bold, `--accent-text` on a `--soft` background with 6px corners) with a line icon at its left (the branch icon for 「ローカル」, a cloud for 「リモート」), its name (`.orca-dest-name`) and, at its right end, the count of the section (`.orca-dest-count`); it stays at the top of the list while the rows scroll (`position: sticky`, inside its own section, so the next heading takes its place). The count is drawn once the answer of its section has come (not for a read that failed), and it is the number of rows that match the filter, so with an empty filter it is the number of all the rows of the section (the remote ones included, folded or not). The layout was chosen by the owner: layout A (2026-11-15, issue #652).
- Local. The branches of `orca_local_branches(path, environment)`, in its order (the one checked out first), read when the list opens. The filter narrows them by the text (a part of the name, case does not count). Every local branch is shown. The branch the worktree is on has `aria-current="true"` and a check mark at its right; pressing it only closes the list. A branch another worktree has checked out (`inUse`) is drawn faint and is disabled: it cannot be picked, because git cannot check a branch out in two worktrees.
- Remote. The branches of `orca_remote_branches(path, repo, query, environment)`, named as Orca names them (`origin/feature/a`), where `repo` is the key of the project of the worktree (`OrcaProject.key`) and `query` the text of the filter, trimmed. It is asked once when the list opens (an empty text) and again 250 ms after the typing stops, and the rows are narrowed by the text at once as well, so a typing key does not leave the old rows until the answer. An answer that comes after a newer question, or after the list closed, is dropped. While the filter is empty, only the first five rows of the answer, in the order Rust returns them (below), are shown (the constant `REMOTE_FIRST` of `ts/orca-branch.ts`). When there are more, a line is drawn under them (`.orca-dest-more`) and, centered on it, a small round button (`.orca-dest-more-btn`: 12px gray text, a `--chip-line` border, a `--bar` background, ends rounded, and a chevron at its right that turns over while it is open) whose text is 「ほか {n} 件を表示」 ({n} is the number of rows left); it has `aria-expanded`. Pressing it shows the rest under the first five and changes the text to 「たたむ」, and pressing it again folds them. With five rows or fewer there is neither the line nor the button. While the filter has text, every row that matches is shown, with no line and no button, and clearing the text brings back the folded state (an opened one is closed by the text). The button is not a row: it picks no branch and does not close the list. The order of the answer: while the text is empty, `orca_remote_branches` puts first the remote branches that were picked before in this list (the pick of a remote row of A-25, and of the ref and of the existing branch of A-9) and that Orca's answer holds, the newest pick first, and the others follow in the order Orca returns them (a remembered branch that the first 50 of Orca's answer lack is asked of Orca by its name, one question for each, at most 5, and is added only when Orca answers a branch of exactly that name, so a branch that is gone is not added; a failed question adds nothing and does not fail the list), so the five shown are the last five picked, filled up with Orca's own first; a text leaves the answer as Orca gave it. The sorting is a pure function of Rust (`recent_first`), and the page only shows the first five rows it gets. No time is shown, because Orca gives none for a remote branch (the answer of `repo.searchRefs` is names only). The owner chose this order (2026-11-15, issue #653).
- A section with no row to show says 「該当するブランチがありません」 once its answer has come, and a read that failed shows its message in its section (in the warning color) and does not empty the other.

The switch. A pick closes the list and calls `orca_switch_branch(path, kind, name, environment)` with `kind` `local` for a local row and `remote` for a remote row (Orca makes the local branch that tracks it). A new branch cannot be made from here. When it answers, the tree of the pane is read again from the root with the folders that are open (the read of A-18's return of the focus) and the list of the screen is read again (`refreshOrca`), so the heading shows the new branch (on a saved environment, whose list is streamed, Rust has the stream read `worktree.ps` again, A-12; issue #600); the tabs of the work pane stay open, and the files and differences that the panes show are read again as by the clock of A-18 (a file with unsaved typing is left as it is, and is refused at its next save by A-18's own check when its text differs from the disk). A switch that worked with a `warning` (a step after the switch failed) shows 「{branch} に切り替えました: {warning}」 in a notice. A refusal (a change not committed, a merge or rebase in progress, an agent at work, and so on) shows Orca's own words in `#error`, as the other errors of the pane do, and nothing is read again. When the pane comes to show another worktree, an open list is closed.

What is remembered. A pick of a remote row (and a pick of the marked remote row again, where the list of A-9 allows it) calls `orca_branch_used(repo, name, environment)` with the key of the project (`OrcaProject.key`), the name as Orca names it and the Orca of the list (`null` is this machine); a local row calls nothing. Rust keeps, for each pair of an Orca and a repository, the last 5 names picked, the newest first, and a name picked again moves to the front; it keeps at most 50 pairs, and drops the pair picked from longest ago, so the file does not grow without end. It is saved in `orca-branch-recent.json` in the app config directory (`{"pairs": [{"environment", "repo", "names"}]}`, the pair picked last first), through a temporary file and a rename (`write_atomic`), by a call that reads the file again and writes all of it. A file that is missing, cannot be read or is not that shape remembers nothing, and the next pick writes it again. Rust refuses a `repo` that `orca_remote_branches` would refuse, a blank `name`, one with a control character or over 512 bytes, and an `environment` that is blank, has a control character or is over 256 bytes (a Japanese message); nothing is asked of Orca. The call only changes the order of the list, so a failure of it neither stops the pick (the switch, the ref or the existing branch) nor shows anything.

The calls. `orca_local_branches` and `orca_remote_branches` check the worktree against the target's list and refuse an SSH host's, as the file commands do (A-18); `orca_switch_branch` reads the list each time, as a save does, and forgets what it believed of the worktree afterwards. The names and the answers were read in the `app.asar` of Orca 1.4.256 and are not a public interface; `git.switchBranch` was never run on a real Orca, because it changes a worktree, and a saved environment was not tried. An Orca update can change them (`requirements/constraints.md`, Orca).

No screen text explains the list; the filter field and the list are named by their `aria-label` and headings only (`frontend.md`).

Unit tests (`cargo test`) cover the git branch of a worktree read from the list (`worktrees_of` in `orca.rs`: `refs/heads/` removed, none for a detached or missing one), the branches read, the remote search, the checks of the arguments and the answer of a switch (`orca_files.rs`), and the branches remembered: the order of the answer (the remembered first, the ones the answer lacks left out, no change with a text), the remembered branches outside the first answer (asked by name, added only on an exact name, at most five questions, a failed question adds nothing), what is kept (the front, five names, the limit of the pairs, a pair for each Orca and repository), the file (missing, broken, written and read back) and the checks of the arguments. The E2E spec `orca-files.e2e.ts` mocks the commands and covers the button and its place in the heading, the list under it with the two sections (their headings with the icon, the count and the sticky band, the first five remote branches and the button that opens and folds the rest, the filter that shows every match with no button and folds them again when it is cleared, and no button for five remote branches or fewer), the mark of the current branch, the faint and disabled branch in use, the filter on the local rows, the remote question (the arguments when it opens and after the typing), a pick of a local and of a remote branch (the arguments of the call, the tree and the list read again, the tabs kept), the remembering of a remote pick (the arguments of `orca_branch_used`, no call for a local row, and a failure of it that stops nothing and shows nothing; the same for the ref and the existing branch of A-9 in `orca-handoff.e2e.ts`), the heading of a saved environment after a switch from the app and after one made outside it (the list of the stream), a switch with a warning, a refusal in `#error`, a worktree whose Orca name differs from its git branch (the button shows the branch, before and after a switch), and no button for a worktree on no branch.

The limit of A-18 (a file over 384 KiB is not opened) is as it was.

The rich view. Milkdown draws the body of the text in an editor (`contenteditable`; read only for a file that cannot be edited in it, see "Editing"): the CommonMark and GFM presets, so tables, task lists, strikethrough and links are drawn too. The front matter (a block between `---` lines at the start) is cut off by Rust (`markdown_split(text)` answers `front` and `body`) and only the body is given to Milkdown. An image whose address is not `data:` or of the app is not loaded (the CSP is not loosened, `frontend.md`). If Milkdown cannot be read or the cut fails, the source is shown and the message goes to `#error`.

The library. Milkdown 7.23.0 (`@milkdown/kit`: core, the CommonMark and GFM presets, the history plugin and a small ProseMirror plugin of ours that tells the page that the document changed; MIT; 12,067 stars, last push 2026-11-12, read from the GitHub API on 2026-11-13), bundled with esbuild 0.28.2 (MIT; 40,141 stars, last push 2026-08-09, read the same way) into the one file `src/vendor/milkdown.js` by `scripts/build-milkdown.mjs` (`npm run vendor:milkdown`; the entry is `scripts/milkdown-entry.js`). Both are `devDependencies` and the app's own build is still `tsc` alone; the bundle is committed like the other files of `src/vendor/`, and holds the 87 packages Milkdown needs (ProseMirror, remark and so on, all MIT). It is a classic script that `ts/vendor-load.ts` reads the first time a Markdown file is drawn in the rich view, not at start-up (`#414`), under the global `TsunagiaiMilkdown`. It loads nothing from outside, uses no `eval` and no `new Function`, and its path is inside `src/vendor/`, so the CSP (`script-src 'self'`) is as it was. Milkdown has no theme here: `src/style.css` styles the elements of the rich view (headings, lists, task marks, quotes, code, tables) with the variables of `:root`.

Editing. The editor rewrites the notation of a text even when nothing is edited (bullet marks, the alignment of a table, indentation), so its export is never saved as it is. When the view is drawn, the page takes the export of the editor (`before`) and puts it through a second editor that is drawn nowhere (`TsunagiaiMilkdown.normalize`); the view can be edited only if that second export is the same text as `before` (loading and exporting twice is stable) and `markdown_patch(original, before, before)` answers `patched` with the original text (Rust answers `conflict` when the lines of the original cannot all be paired with the lines of the export, so a file it could not patch at an edit is known when it is opened). A file that fails either test is not edited in the rich view: it opens in the source (the first drawing of the file), and the rich view that the button shows afterwards is read only. After each change of the document the page waits 200 ms for more changes (at most one wait at a time), then sends `markdown_patch(original, before, after)`: `original` is the text of the text area when the view was drawn, `before` the export then, `after` the export now. Rust applies only the lines that differ between `before` and `after` to `original`, so every line the owner did not touch stays as it was in the file (its bullet mark, its spacing) and the front matter comes back as it was. An edit over several lines with a line only the original has between them (a comment the editor does not write out) is a `conflict`, not a change that drops that line. While the rich view is shown the text area's layers (colors, line numbers) are not drawn again at each edit; they are drawn when the source is shown. The answer `patched` replaces the text of the text area, which marks the file as changed and starts the wait of the automatic save, as typing in the source does; the heading shows the same states (changed mark, 「保存待ち」, 「保存中」, 「保存しました」, the failures of A-18). The automatic save, the close of the tab, the switch to the source and `pagehide` wait for an edit that is on its way to the text area, so no edit is lost. The answer `conflict` (or an error) leaves the text area as it was, switches the view to the source and sends the message to `#error`. The switch from the rich view to the source shows the text area with the edit in it, and the switch back draws the text of the text area, so the typing of either view is carried over.

The same bundle also draws and edits the Slack posting fields (S-21, the post to a channel, and S-6, the reply in a thread) and the body of a mail reply (M-10): `ts/rich-editor.ts` makes the editor with `TsunagiaiMilkdown.compose` and exports its Markdown, which is not patched into any original text and goes to Slack through `to_mrkdwn` (S-21) or into a mail as its Markdown and HTML parts (M-10). They load it the same way, the first time such a field is shown.

No new call to Orca, no new file saved and no new setting is added. No screen text explains the buttons (`frontend.md`).

Unit tests (`cargo test`) of the cut of the front matter and of putting an edit into the text are those of `markdown_patch.rs`. The E2E spec `orca-files.e2e.ts` mocks `markdown_split` and `markdown_patch` and covers a Markdown file drawn in the rich view (heading, bold, code, table, task items, editable, the source box hidden, the arguments of the cut and of the first `markdown_patch`), what is typed in the rich view reaching the arguments of the save through `markdown_patch` (`original` is the file's text with its front matter and its own notation, `after` has no front matter), the switch to the source carrying the edit over, a file Rust cannot patch opening in the source and its rich view read only, a conflict switching to the source, Milkdown read only with the first Markdown file, the body without the front matter, the switch to the source and back (the typing of the source in the next cut), the view kept while the tab is switched, and no button and no cut for a file that is not Markdown.

## A-31 Open an Orca HTML file in the browser

An HTML file in the file pane of the Orca screen (A-18) can be opened in the default browser of this PC: the app serves the files of the worktree from an HTTP server of its own on `127.0.0.1`, and hands the address of the file to the system. Rust is `src-tauri/src/orca_preview.rs` (the command `orca_file_open_in_browser`, and the server); the frontend is `ts/orca-files.ts`.

Why. An HTML file of a worktree (a report, a mock, a built page) could be read in the editor only as its source, and a file of a saved environment (a paired server) is not on this PC, so the browser could not be pointed at it. The owner asked to see such a file as a page (issue #620, parts #621 and #622).

The menu. 「ブラウザで開く」 is the fifth item of the menu of a file row (A-18), after 「差分を表示」 and before the line, with a line icon at its left. Only a file whose name ends with `.html`, whatever the case, has it: the menu of any other file and of a folder (one named like an HTML file too) does not. A pick closes the menu and calls the command below. Nothing is said when it works (the browser comes to the front), and a failure shows its message in `#error`.

The command. `orca_file_open_in_browser(path, relative, environment)` takes the path of the worktree, the path of the file from it and the place of the worktree (the saved environment, or null for this machine), as the other commands of A-18 do. It refuses a relative path as A-18 does, and a path whose name does not end with `.html`, whatever the case (「HTML のファイルだけをブラウザで開けます」). A path with a part that starts with `.` (`.a.html`, `.git/a.html`, `a/.b/c.html`) is refused with the same message, because the server answers such a path 404. It checks the worktree against the target's list read just now, as a download does (an SSH host has no file calls and is refused, as in A-18), starts the server when it does not run yet, and opens `http://127.0.0.1:{port}/{token}/{path}` with `tauri-plugin-opener`. It answers nothing: the address holds the token and is not given to the page of the app, logged, or put in an error (a failed open is 「ブラウザで開けません」). A failure shows its message in `#error`.

The server. It listens on `127.0.0.1` alone, on a port the OS gives, and starts at the first open; it then runs until the app ends. Each worktree (a target and a path) that was opened has a token of its own, 16 random bytes of the OS in hex, held in memory only, so an address of an earlier run of the app opens nothing. One connection carries one request and is closed after the answer (`Connection: close`); a request must come within 10 seconds and its first line and headers within 8 KiB.

What it answers, in this order:

- A request that is no HTTP/1 request is 400.
- A `Host` header that is not exactly `127.0.0.1:{port}` (none, two, `localhost`, another name or port) is 403, before anything else is looked at: a page that reached the port through a name of its own (DNS rebinding) sends that name.
- A method other than GET and HEAD is 405, with `Allow: GET, HEAD`. The body of a request is never read.
- The target is `/{token}/{path}`, without what follows a `?` or a `#`. A token that no worktree has is 404. The path has its percent escapes taken out and is then held to the path check of A-18 (no empty path, no control character, no `.`, `..` or empty part, so an escaped `..` or `/` is seen as what it is and a path that ends with `/` is refused); a path that fails it is 404, and Orca is not asked. A path with a part that starts with `.` (`.env`, `.git/config`, `.npmrc`, `a/.b/c`), looked at after the escapes are taken out, is 404 too, and Orca is not asked: the script of an opened page could otherwise fetch the settings and the secrets that a worktree keeps under such names. A folder has no list.
- Otherwise the worktree is confirmed as a read of A-18 confirms it (the target's list, believed for 60 seconds): a worktree that left the list, and an SSH host, are 404. Then the file is read over a connection to Orca of its own, as the download of A-22 reads it (`files.stat` for the size, `files.readChunk` 384 KiB at a time and never past the size, or `files.readPreview` on a host that lacks either), and each chunk goes to the browser as it is read; nothing of the file is kept. A file that is not there is 404, and any other failure before the first byte is 502. A read that fails after the headers went out closes the connection short of the `Content-Length` it promised. A HEAD gets the same headers and no body, from the size `files.stat` gives: nothing of the file is read (only a host that lacks `files.stat` has the file read for its size, and the read stops once the size is known). After a failed connection to Orca or a 502 the confirmation of the worktree is dropped, so the next request asks the target's list again; a 404 for a file that is not there keeps it.

What is left open. No CSP `sandbox` is set on a page, because a `type="module"` script and the page's own `fetch` would stop working and the page would not show as it is. So the script of an opened page can read every file of the same worktree that has no part starting with `.`. Whether Orca's `files.stat` and `files.readChunk` follow a symbolic link inside the worktree (one named without a `.` that points at a file outside it, or at a hidden one) was not checked.

Any file of a worktree that has a token is answered, not only an HTML one, so that a page gets the images, styles and scripts it names by a relative path.

The headers. ## A-34 Go to a definition in the Orca editor

The editor of A-18 goes to the definition of a Ruby name with ruby-lsp (#696). This section holds what the Rust side decides, saves and runs (issues #697, #698 and #699, `src-tauri/src/lsp.rs`, `lsp/protocol.rs`, `lsp/server.rs` and `lsp/outside.rs`) and the screen of the definition (issue #700, `lsp/view.rs`, `ts/orca-definition.ts`, `ts/orca-files.ts`, `ts/orca-editor.ts` and `ts/orca.ts`); the screen of the server's state and settings, its start and stop, and the start of the container (issue #701, `lsp/container.rs`, `ts/orca-lsp.ts`) is the last part of the same requirement and is below.

Why. The owner works in Ruby projects that run in Docker, and on the machines of saved environments (A-33), so the server cannot be assumed to be on the host (2026-11-15, issue #696). The way to start it is decided from the worktree, so that the owner sets nothing in the usual case, and the settings of a repository can replace what was decided.

How the server is started, in this order (`decide`, a pure function of two texts):

1. A compose file. When the worktree's folder holds `compose.yaml`, `compose.yml`, `docker-compose.yaml` or `docker-compose.yml`, `docker compose config --format json` is run in it, and the services whose `volumes` hold a bind (`type` `bind`) of the worktree itself (`source` equal to its path, a `/` at the end of either left off) with an absolute `target` are the candidates, in the order of their names. That output has the anchors and extensions expanded and every volume in the long form, so a service that took its volumes from an anchor is listed as any other. A named volume, a tmpfs, a bind of another folder (a folder inside the worktree, or its parent), and a service whose name is empty or starts with `-` are not candidates; a service that mounts the worktree twice counts once, at its first mount. The command is `docker compose exec -T -w {target} {service} bundle exec ruby-lsp`, and the path of the worktree where it runs is the `target`. `-w` is needed because `exec` runs in the working folder of the image or of the service, which is not always the mount (the `ruby:3.3` image works in `/`, where Bundler finds no `Gemfile` and ruby-lsp ends with "Could not locate Gemfile or .bundle/ directory"). The `target` and the service are quoted for a POSIX shell. All the candidates are returned and the first is used unless the settings choose another. Whether a container is running is not asked here.
2. A `Gemfile.lock` that lists the gem `ruby-lsp` (a spec or a dependency line; `ruby-lsp-rails` and a URL that holds the name are not it): `bundle exec ruby-lsp` on the host, and the worktree's own path is the path.
3. Neither: the server is not used.

A compose file whose services do not mount the worktree leaves the decision to the `Gemfile.lock`. A compose configuration that cannot be read as JSON is an error and is not passed over.

Where it is read. A worktree of this machine is read on the spot, by `/bin/sh -c`. A worktree of a saved environment (A-33) is read through this Mac's `ssh` to the host in the settings of its repository (`sshHost`, a Host of `~/.ssh/config`, refused when it is empty, starts with `-` or holds whitespace or a control character): Orca's environments say nothing of ssh, so the owner names it. `docker compose config` is run only when the folder has a compose file, and its failure (no `docker`, a broken file) is an error with ssh's or the shell's last line; the `Gemfile.lock` is read with `cat`, and only when no service of the compose configuration mounts the worktree (the lock then decides nothing). Both are read up to 4 MiB, within 30 seconds, as UTF-8, and nothing of them is kept. A project of an SSH host of Orca (its key is `ssh:{host}`) has no worktree to read and is refused.
The same route starts the server (`lsp_start`, below): the script is `PATH` with `/usr/local/bin` and `/opt/homebrew/bin` added (a program that is not started from a login shell does not have the folders of `docker`), `cd` to the worktree and the command; on this machine it is the argument of `/bin/sh -c`, and by ssh it is `sh -c '{the script, quoted}'` as the one element after the host, so that the login shell of the host reads it as it is. The worktree path and the service name are quoted; the command of the settings is the owner's own text and is run as written.

The settings of a repository are in `lsp-settings.json` in the app config directory (`{"version": 1, "repositories": [...]}`), one entry for each pair of the place of the project (`environment`: `null` for this machine, else the name of the saved environment) and its key (`OrcaProject.key`), which is the repository id of Orca. An entry holds `autoStart` (true when nothing is saved), `command` and `mount` (replace the command that is run in the worktree and the path the worktree has where it runs; none means what was decided), `service` (the choice among the candidates; a name that is not one is ignored) and `sshHost`. With a `command` and no method decided, the path is the worktree's own unless `mount` says otherwise. An entry with nothing set is not kept. A text is trimmed, and an empty one is not set; a text over 4096 characters or with a control character, a `mount` that is not an absolute path, and an `sshHost` that is empty, starts with `-` or holds whitespace are refused. A file that cannot be read, or has another `version`, is an error that names it, and a save never replaces it.

Commands. `lsp_settings(environment, project)` answers the saved settings, or the unset ones. `lsp_settings_set(settings)` saves them and answers what was saved. `lsp_launch(environment, project, worktree)` first checks the worktree (below), then reads it and answers `LspLaunch`: `method` (`compose`, `host` or `none`), `candidates` (service and mount), `service` (the one used), `command` and `mount`, with the settings applied. The types are ts-rs's (`LspLaunch`, `LspCandidate`, `LspMethod`, `LspRepoSettings` in `ts/bindings/`).
The worktree is checked. `lsp_launch`, `lsp_start`, `lsp_container_start` and `lsp_read_outside`, which run a command in a worktree, take its path and its project from the screen, so each first asks Orca's list of that place, as the other Orca commands do (`orca_files::check_worktree_of_project`): a path that the list does not have, and a project that is not the worktree's own, are refused with no command run. `lsp_stop`, `lsp_status` and `lsp_definition` only look up a server that is there, and need no such check.

The server (issue #698). `lsp_start(environment, project, worktree)` starts ruby-lsp the way `lsp_launch` reads it (the same script and route, `spawn_of`) as a child process of the app, and keeps it, one for each pair of the place of the project and the worktree. It answers the state at once, `indexing`; the start is done by a task that reads the worktree, starts the process, and talks to it. A server that is there and not stopped is left as it is, and one that is stopped is started again (the screen's restart). A worktree path that is not absolute, or has a control character, is refused; every other failure (no way to start it, no ssh Host, a failed `docker compose config`, a process that cannot run) is the state `stopped` with its message. The talk is LSP over the process's standard input and output: `Content-Length` frames, `initialize` (no process id; the worktree as the server sees it, the `mount`, is the root; UTF-16 positions; progress is shown by the client, as ruby-lsp sends its indexing only then), `initialized`, the answers to the server's own requests (`window/workDoneProgress/create` and `client/registerCapability` get `null`, any other a "method not found" error), `textDocument/didOpen`, `textDocument/didChange`, `textDocument/definition`, `textDocument/didClose`, `workspace/didChangeWatchedFiles`, then `shutdown` and `exit`.
The state. `lsp_status(environment, worktree)` answers `LspStatus` (`state`, and for `stopped` the `reason` and a `message`), and each change of it is the event `lsp-status` (`LspStatusEvent`: `environment`, `worktree`, `status`; the screen listens once for all the worktrees). It is `indexing` from the start until `initialized` and then until the end of every progress that ruby-lsp began (`$/progress`: `begin` opens a token, `end` closes it, at most 64 tokens), `running` after it, and `stopped` when the process is gone. A server that has shown no progress 3 seconds after `initialized` is taken as `running` (a progress that began holds `indexing` until it ends). `stopped` has the reason `notStarted` (there is no server for the worktree, or `lsp_stop` took it away), `containerDown` (the process ended and the last line of its standard error says that the container of the service is not running, `is not running` or `No container found`; an earlier line says nothing, so a server that ended for another reason is `failed`; the message is 「サービスのコンテナが動いていません」, so that the screen can offer the button that starts the container below; the app never starts it by itself) or `failed` (the message is what ended it, with the last line of the standard error or, for ssh's own failure, the failed connection). A server that ended is kept in that state until it is stopped or started again.
The definition. `lsp_definition(environment, worktree, relative, text, line, character)` first tells the server which Ruby files changed on the disk ("Files that change on the disk" below), then sends `text`, the editor's present text of the file `relative` (a path from the worktree: no empty name, `.` or `..`, no absolute path, no control character), as the whole text of the file (`didOpen`; more than 1 MiB is refused), asks `textDocument/definition` at the position (UTF-16 units, which is the index of a string of the editor, so nothing is converted), and answers the places as `LspLocation` (`path`, `outside`, `line`, `character`), at most 100, each once. The answer is read as `null` (none), a `Location`, or a list of `Location` and `LocationLink` (the place of the name, `targetSelectionRange`, else `targetRange`); an entry that cannot be read, or whose URI is not a `file:///` one, is left out. A path is decoded, its `.` and `..` are taken out, and it is mapped by the mount: below the mount it is `path` from the worktree (`outside` false); the mount itself is no file and is left out; any other path (a gem, for example) is the server's absolute path with `outside` true, and it is remembered for that server (`LspServers::outside_way`), because only such paths may be read from outside the worktree (#699). The answer is given to the screen first, then the file is closed (`textDocument/didClose`) unless another question about it still waits, so that a file is open for the server only while it is asked about: the server does not re-read an open file when it changes on the disk. A server that is started again after it stopped (the container) keeps the outside paths of the one it replaces, and so does the restart (`lsp_restart(environment, project, worktree)`, which has the same checks and the same start as `lsp_start`: it stops the server that is there, running or not, and starts the new one in its place, with the outside paths of the old one), because the list of definitions that shows them is still on the screen. `lsp_stop` followed by `lsp_start` would lose them, since a stop takes the server away with its paths. A server that is not running, a question before `initialized`, more than 32 questions waiting, an error of the server (its message) and no answer within 10 seconds are errors in Japanese.
Stopping. `lsp_stop(environment, worktree)` says `shutdown` and `exit` (each waited for 2 seconds at most), closes the standard input of the process, which ends ruby-lsp (also through `docker compose exec` and ssh), and kills a process that is still there after 2 seconds; a worktree with no server is no error. Nothing is written in the worktree, at most 4 MiB are kept, and it is given 5 seconds: a look that cannot be run, is cut or is late, or whose script did not run (no `--` line: the `cd` or the ssh failed), tells nothing and the question goes on without it. The exit code of the script does not decide: a folder that `find` cannot read makes the code 1, and what it listed is told all the same, while a full list without `--end` is not taken as all the files (so nothing is told as deleted, and the files known at the last look stay). The first look is made once when the server has answered `initialize` (at `initialized`) and tells nothing: it only sets the files known, so that a file that is gone or renamed between the start and the first question is told as deleted at that question. The files that changed are told as `changed` (2) and, when the full list says they were not there at the last look, as `created` (1); a file of the full list that was not known is `created` too, and a known file that is not in it any more is `deleted` (3), the last two only when the full list ended well (it ends with `--end`). ## A-37 Orchestration on the development screen

The side menu's Orca button is the development screen, and it has two modes: Orca (A-6) and the orchestration, where one Claude Code, the orchestrator, splits the owner's work into children that run in Orca (the owner's decision of 2026-11-16, issues #791, #795 and later ones). This requirement holds the screen, how the orchestrator starts, the tools that start and end the children, and the state of a child. The flow pane is #796, the children's terminals are #797, and #803 puts the two in one right pane.

The button. The switch of the mode. At the left end of the footer (A-35) is a group of two icon buttons (`#footer-modes`, `aria-label` 「開発のモード」), 「Orca」 (`#footer-mode-orca`) and 「オーケストレーション」 (`#footer-mode-formation`), with `aria-pressed` on the mode that is on. The screen (`#formation`, `ts/formation.ts`). Two panes side by side, from the left: the orchestrator (`#formation-orchestrator`, with a header band `#formation-head` headed 「司令塔」 and the terminal `#formation-term` under it) and the right pane (`#formation-flow`), which holds the view of the flow above and the session of the selected child under it, as the paragraphs below say.

Once it returns one child or more the right pane is shown, and when it returns none again it is hidden again.

The orchestrator's pane. The left pane is the Claude Code pane of A-36 with `kind: "formation"`: `showClaudeCode(host, {id: "formation", kind: "formation"}, "formation-screen")`, so its pane id is `formation` whatever is given, and Claude Code's own tools are on. Showing the mode starts the process with the size of the host, once. Leaving the mode or the screen hides the pane (`hideClaudeCode`) and ends nothing; showing it again draws the same process. How the orchestrator starts (`src-tauri/src/claude_code.rs`, `formation_claude.md`). Claude Code runs in `formation/` of the app config directory, which holds four files that the app writes at each start: `.claude/settings.json` (the project settings, which the script below reads: they are written as `{}` each time, so a permission or a hook that the orchestrator added to them in auto mode does not stay for the next start), `CLAUDE.md` (the orchestrator's instructions: it is named `formation`, starts the children with `formation_launch`, tells the ones to come with `formation_plan`, instructs them by SendMessage with a request to tell `formation` when the work ends or a decision is needed, puts text from outside (a mail, a Slack message) in a quote as material to read, asks the owner in text and not with AskUserQuestion, and calls `formation_close` only when the owner says a child's work may end), `mcp.json` (`tsunagiai-mcp` with the argument `--formation`, which is what makes the server offer the tools below; the panes of A-36 do not pass it) and the launch script. The script runs `exec claude -n formation --permission-mode auto --setting-sources user,project --strict-mcp-config --mcp-config {mcp.json} "$@"`: Claude Code's own tools stay on, the permission mode is `auto`, and the project settings of `formation/` are read too. Like every pane, the child process has no environment variable that starts with `ORCA_` or `CLAUDE_CODE_MESSAGING_` (A-36), so an app started from Orca's terminal does not make Claude Code take the pane for Orca's.

The children's tools (`tsunagiai-mcp --formation`, `src-tauri/src/formation.rs`). Only the orchestrator is given them; the other MCP clients and the panes of A-36 are not. The orchestrator runs in auto mode, so besides these it is offered only the read tools of `tsunagiai-mcp` (`list_inbox`, `get_thread`, `list_events` and `db_profiles`) and none that writes (`trash`, `archive`, `set_read`, `db_profile_save`, `db_test`), which the panes of A-36 ask the owner about each time. A child is a Claude Code in auto mode that runs in a terminal of Orca, in a worktree of its own. Every command of Orca and of git is run with an argument list and never through a shell, and what they print is quoted in an answer as data. The children are recorded in `formation/children.json` (`{"children": [...]}`, written through a temporary file and a rename, one change at a time), in the order they were planned or launched; the state of a child is not recorded, because it is Orca's. A change of the record reads a missing file as none, but a file that is there and cannot be read, or is not the record, is an error and nothing is written, so a broken file does not lose the record of the children already launched (the screen reads such a file as none).
- `formation_launch(repo, name, prompt)` makes a new worktree in the repository `repo` (its name in `orca repo list`, its id or its path, one repository exactly; a folder is not one), makes a terminal in it that runs `claude -n {name}` in auto mode, waits for Claude Code to take input, sends `prompt` as the first instruction, and records the child. `name` is a lowercase letter or a digit and then lowercase letters, digits and hyphens, at most 40 characters, not `formation`, and not the name of a child that is launched already; the prompt is 1 to 20,000 characters with no NUL and not blank, and it is sent with the hidden and control characters taken out as A-9 does (C0 controls other than the line break and the tab, DEL, zero-width, bidi and tag characters) and the C1 controls (U+0080 to U+009F) too, which the count and the blank check read as well. A planned child of that name is replaced in place. The answer is `{ok: true, name, repo, path, branch, handle, paneKey}`; a step that fails after the worktree was made answers `{ok: false, error, step, data, note}` and leaves the worktree, which `formation_close` removes.
- `formation_plan(children)` records children that are launched later, each `{name, repo}`: a planned child of the same name is replaced in place, a new one goes to the end, and a name that is launched already is refused with nothing changed. The screen shows a planned child as planned.
- `formation_close(name)` closes the child's terminals and removes its worktree with its branch, and its entry of the record. A worktree with a changed or untracked file, or with a commit that no remote has, is not removed (no `--force`), nothing else is done and the answer says why; a repository with no remote (`git remote` prints nothing) has no commit to ask for, so only the changed and untracked files are looked at. A child that is only planned is dropped from the record. The record is a file the orchestrator can write, so nothing is deleted on its word alone: the recorded path must be absolute and the handle must be a terminal handle, and `orca worktree ps` must list a worktree of that path that is not the repository's own folder (`isMainWorktree`), or the close is refused, with nothing deleted and the entry kept; the branch is not compared, because a child may switch it. When the recorded path is no folder any more (the owner removed the worktree in Orca), `orca worktree ps` is read, the child's terminal is closed only when an agent of the recorded `paneKey` is listed under a worktree of that path (when it is not, or the list cannot be read, no terminal is touched and `terminalClosed` is false), its entry is dropped, and the answer is `{ok: true, name, path, worktreeGone: true, terminalClosed}`, so that the name can be used again.

The state of a child (read by the command `formation_children` of #794, which the flow pane calls). A planned child is 予定.
