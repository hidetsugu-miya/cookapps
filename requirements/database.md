# Database requirements

## D-1 Database screen and connections

The sidebar has a button for the database screen (`#nav-database`, `aria-label` "データベース"), after Orca and before the bottom group. Its icon is a drawn cylinder (a line icon like the other buttons, not text; the owner's instruction, 2026-11-14), and it has no count.

The screen (`#database`) has two parts, as the Slack screen has (S-19, `#slack-screen`): the side menu at the left (`#database-side`, the `--bar` background) and the work pane at the right (`#database-pane`), with a divider (`#database-side-split`) that the user drags (`ts/split.ts`, `--side-w`, 15 to 40% of the screen, 20% at first, kept in memory only). The side menu has a header of the height of every header (A-23, `#database-side-head`, a place to drag the window by) with the title "接続" and the plus (`#database-add`, `.icon-btn`, `aria-label` "接続を追加"), and under it the list (`#database-side-feed`). The work pane has a header (`#database-header`, a place to drag the window by) with the title "データベース" and, at its right end, the icon button of the terminal pane (`#database-terminal-toggle`, D-7), and, under it, `#database-work`, which holds the tabs of the database that was pressed last, テーブル (its tables, D-3) and SQL (D-6), or the tabs of the table that was pressed (D-4, D-5, D-6). The screen shows no placeholder and no text that explains a field or a button, and nothing is drawn for an empty list.

The list is what `database_profiles` answers (the connections in the order they were made, each with `passwordSaved`), read each time the screen is shown and again after every save and every delete, so the list is the same after the app is opened again and is never kept apart from the file. A read that fails shows its error on the error line (`#error`). A row (`.database-item`) is a button (`.database-btn`: a cylinder icon and the name, cut with an ellipsis) with no button of a menu beside it. Pressing a row makes it the selected one (`aria-pressed` true; one at a time, in memory only, dropped when the connection is gone from the list) and opens the connection (D-3). A right press on a connection's row (`contextmenu`, the default menu of the WebView is not shown; the connection rows and the database rows, not a table) opens the menu (`menu.ts`) at the place of the pointer, as the right press of a row of the Orca file pane does (A-18): "編集", "切断" while the connection is open (D-3) and, in the danger color, "削除". The menu of a database row is D-3's. The list is drawn again only when what it shows changes, and the focus stays.

The plus and "編集" open the edit pane (`#database-edit`, which holds `#database-form`; the title is "接続を追加" or "接続を編集", and it is the `aria-label` of the form). It takes the place of the work pane: `#database-pane` is hidden while it is open, the side menu and the terminal pane stay as they are, and nothing is inert. When it closes, the work pane is shown again. Its header (`.database-edit-head`, as high as every header, A-23, a place to drag the window by) has the title (`h1`) and, at its right end, the buttons "接続をテスト" (D-2), "キャンセル" and "保存" (`.text-btn`; "保存" is the submit button of the form, `.primary`) and, after them, at the very right end, the icon button of the terminal pane (`#database-edit-terminal`, `.icon-btn`, `aria-label` "ターミナル", `aria-pressed`, the same drawn terminal icon and no text as D-7's). Under it are the fields, with their names above (no placeholder): 接続名, ユーザー名, パスワード (a password field; for a connection whose password is saved, a status label "保存済み" with a dot beside the name, and the field empty: the password is never sent to the screen), and then the way the connection goes, as a list of tabs (`role="tablist"`, `aria-label` "接続のしかた", a `.database-tab` with `role="tab"`, `aria-selected` and `data-mode` for each, as the tabs of D-3): "直接" (`data-mode` "direct") shows "DB のホスト" and "ポート" (a number field, 3306 for a new connection), and "スクリプト経由" (`data-mode` "script") shows "事前スクリプト" (a text area of several lines) in their place and asks for no host and no port. A connection that has a script opens on "スクリプト経由", and any other on "直接". A press on a tab only changes the tab and calls nothing: what was typed in the fields of the other way stays in the pane, and is not sent. The first field has the focus. "保存" sends `database_profile_save` with `profile` (the `id` empty for a new connection, else the connection's own, and the fields of the selected way as typed: on "直接" the `script` is empty, and on "スクリプト経由" the `dbHost` is empty and the `dbPort` is 0; a port that is empty or not a number is sent as 0, which Rust refuses in Japanese for a connection with no script) and `password` (the field as typed, empty to keep the saved one); the checks are Rust's, and the screen sends the fields as they are. On success the edit pane closes and the list is read again. A refusal shows its text in `#database-form-error` (`role="alert"`) under the fields, and the edit pane stays with what was typed, so that "保存" can be pressed again (it is off while the call is on its way). The list is read again after a failed save too: Rust writes the file before the keychain, so when the keychain refuses a new connection's password (「接続は保存しましたが、パスワードを保存できません: …」) the connection is saved, and the list then has a connection that it did not have. The edit pane closes then, and the error is shown on the error line (`#error`), because a second "保存" would make the same connection again and be refused for its name. "キャンセル" and Escape (unless it only cancels an IME conversion) close it and call nothing. Leaving the screen closes it.

The icon of the edit pane opens and closes the terminal pane of D-7, the same pane as the icon of the work pane's header does (the icon of the work pane is hidden with the work pane while the edit pane is open): a press toggles `#database-terminal` and its divider at the right of the edit pane, calls nothing, and both icons show the same `aria-pressed`, so a pane opened before the edit pane is open in it, and one opened in it is open when the work pane is shown again. The owner starts Claude Code in that pane (the pane is D-7's plain terminal; it starts nothing itself, and the pane that starts Claude Code is #730, not yet made), and Claude Code saves the connection through `cookapps-mcp` (D-8), so the edit pane of a saved connection reads the list again while it is open (#720): `database_profiles`, every 2 seconds (`databaseProfiles` of `ts/e2e-timers.ts`, which the E2E build shortens; not while the window is hidden), the same command as every read of the list, so the side menu follows too, and no new command is called. A field that was not changed by hand (名前, ユーザー名, 事前スクリプト, DB のホスト, ポート) takes the value that was saved, and a field the user typed in (an `input` event on it) is left as it is, even when typed back to its old value; the way (直接 or スクリプト経由) follows the saved connection (スクリプト経由 when it has a script) until a way tab is pressed, and is left as it is after. The password field is never read. The reading stops when the edit pane is closed and when the connection is gone from the list (the edit pane stays as it is, and its "保存" is refused by Rust as for any edited connection that is gone); the edit pane of a new connection reads nothing.

The script of a connection (`DatabaseProfile.script`, #718; `database/script.rs`) opens the way to the database before MySQL is logged in to, for a database that is reached through a port forward or any other way the owner writes. Rust trims it, turns CR LF into LF, and refuses a control character other than a line feed and a tab (「スクリプトに使えない制御文字があります」); an empty script is a connection with no script. A file of the form before #718, which has no `script` and has the fields of SSM (`useSsm`, `awsProfile`, `region`, `bastionName`), is read as a connection with no script, and the next save drops the old fields. A connection with a script needs no host and no port, because the script reaches the database and MySQL is logged in to at `127.0.0.1` and `COOKAPPS_PORT` (D-2): Rust does not check them, and a save of it keeps an empty host and the port 0 (`check` in `database.rs`; a file saved before that may still hold them, and they are not used). A connection with no script needs both, as before.
- The script is started as a child process, with no shell. Its body is written to a file of its own (mode 0700, in a folder of its own in the system's temporary folder, deleted when the script has ended), and that file is run, so its first line decides the interpreter; a body with no `#!` first line is run by `/bin/sh` (`#!/bin/sh` is put before it). The app picks a free port on `127.0.0.1` and gives it as the environment variable `COOKAPPS_PORT`; the script is to listen there (a port forward, for instance). The other variables are the app's own, the working folder is the script's own folder, and the standard input and output are closed; the standard error is read, and its last 5 lines are kept.
- The script is ready when a TCP connection to `127.0.0.1:{COOKAPPS_PORT}` succeeds (tried every 100 ms). MySQL is logged in to on that port (D-2).
- The connection fails when the script ends before it is ready (an exit code of 0 too): 「接続のスクリプトが、準備ができる前に終了しました（終了コード {n}）。標準エラーの最後の行: …」 (「シグナルで終了」 in place of the code when a signal ended it); when it is not ready in 2 minutes: 「接続のスクリプトが 2 分たっても準備できませんでした。標準エラーの最後の行: …」; and when it ends after it was ready, the connection is closed (D-3): 「接続のスクリプトが終了したため、接続を閉じました（終了コード {n}）。標準エラーの最後の行: …」. A script that cannot be started is 「スクリプトを起動できません: …」. The last lines are joined with " / " and each is cut to 300 characters; they are shown as text on the screen and go nowhere else.
- The script runs in a process group of its own. Closing the connection and the app's exit send SIGTERM to the group, and SIGKILL when something of it is still there after 5 seconds (also after the script ended by itself, for what it left behind). A script that was never ready is ended the same way. A script that is dropped while its group may still run (the runtime ended before the group was ended, as when `cookapps-mcp` ends while `db_test` waits) is sent SIGKILL to the group at once.
- A connection with no script goes to the host and the port directly, as before. The test of a connection (D-2) and the opening of one (D-3) start the script through the same function (`open_endpoint` in `database.rs`, which calls `script::Scripts::open`); the functions of `database/script.rs` take the folder for the script's file as a `&Path`, so that `cookapps-mcp` can start a script the same way.

"削除" opens the confirmation of `confirmDelete` (`ts/hint.ts`, `role="alertdialog"`: "削除しますか？", "{name} を完全に削除します。元に戻せません。", a red "削除" and "キャンセル", which has the keys) under the name of the row. "削除" calls `database_profile_delete` with the `id`, and the list is read again, also when the call failed, with its error on the error line; "キャンセル", Escape and a press elsewhere call nothing.

The unit tests (`cargo test`, `database.rs` and `database/script.rs`) cover the file (an old file read as a connection with no script), the checks (the script trimmed, its line breaks, its control characters, no host and no port needed with a script, and both needed without one, also through the save of `cookapps-mcp`) and the password, and, with short shell scripts and a local `TcpListener`, the script: ready when the port answers, `COOKAPPS_PORT` given, a body with and without an interpreter line, the end before it is ready (an exit code of 0 and not, with the last lines of the standard error), no readiness in time, the end after it was ready, the SIGTERM of the whole group (a child of the script too), the SIGKILL of a group that ignores SIGTERM, the SIGKILL of the group of a script that is dropped after its runtime ended (a child of the script too), the deletion of the folder of the script, and that the test and the opening of a connection both stop at a script that ends before it is ready. The E2E spec `database.e2e.ts` covers the icon of the edit pane (its place at the right end of its header after the buttons, the label, the icon with no text, `aria-pressed`, the open and the close of the terminal pane at the right of the edit pane, the icon of the work pane that follows, a pane that was open before the edit pane), the reload of a connection saved elsewhere (the fields that were not changed by hand take the saved values, the one typed in stays, the way follows until a tab is pressed, the side menu follows, the reading stops when the connection is gone and when the edit pane is closed, and none for a new connection), and the button (the label and the icon, no text), the two parts, the list in the order given and read again at each showing, the error of a failed read, the press that selects (what it opens is D-3's), the menu that a right press of a connection row opens at the pointer (編集 and 削除, no button of a menu in the row, Escape closes it), the edit pane (taking the place of the work pane, the buttons of its header, the fields, the way tabs and the fields each shows, the focus, no placeholder, nothing inert, closed when the screen is left), a save of a new connection and of an edit on both ways (the arguments of `database_profile_save`: no script on "直接", no host and port 0 on "スクリプト経由", the list read again), the port sent as 0, the refusal shown with the edit pane kept, the refusal of the keychain after a new connection was saved (the edit pane closed, the error on the screen, the connection listed), the saved password shown as a status, キャンセル and Escape (the work pane shown again), and the confirmation, the delete (`database_profile_delete` and the list read again), its failure and the selection of a connection that is gone.

## D-2 Connection to MySQL and the test of a connection

The server is MySQL 5.7, 8.0 or 8.4, and the login is `mysql_native_password` or `caching_sha2_password`. A session is opened by one function (`database/mysql.rs`, `connect`), which the connection test and the screens that come after it (tables, records, SQL) all use. It connects to `127.0.0.1` and the port that the script of the connection listens on (`COOKAPPS_PORT`) when the connection has a script (D-1, `database/script.rs`), and to the DB host and the port of the connection when it does not. TLS is used when the server offers it, and the password of `caching_sha2_password` goes through it (a server with no TLS that asks for it is the error 「このユーザーの認証 (caching_sha2_password) には TLS が要りますが、サーバーが TLS を使えません」). A connection that goes over a network (no script, and a host that is not `localhost` or a loopback address) requires TLS, so that nobody on the way can make it fall back to plain text: a server with no TLS is the error 「TLS の接続に失敗しました: …」. The certificate is not verified in either case. The time zone and the `sql_mode` of the session are the server's own: the defaults of sqlx (`time_zone='+00:00'`, `PIPES_AS_CONCAT` and `NO_ENGINE_SUBSTITUTION`) are turned off, so that a TIMESTAMP and `NOW()` read as any other client reads them and `||` is OR. The session is made read only at once (`SET SESSION TRANSACTION READ ONLY`), so that MySQL itself refuses a write. A connection has 15 seconds, from the first byte to the answer of the first query.

The edit pane of D-1 has a button "接続をテスト" in its header (a `.text-btn`, before "キャンセル" and "保存", `type` "button", so that Enter in a field still saves). It tests the connection as typed in the edit pane, not as saved: it sends `database_test` with `profile` (the fields as typed, as "保存" sends them) and `password` (the field as typed). Rust takes the password typed, and when the field is empty the one saved in the keychain for `profile.id` (none for a new connection, which logs in with no password), but only when the fields still say where and as whom the login goes as the saved connection does (the user name and the script, and the host and the port of a connection with no script; the name is not one of them, and neither are the host and the port of a connection with a script): otherwise the test is refused with 「接続先やユーザーを変えたときは、パスワードを入力してください」, so that the saved password is never sent to another place than the one it was saved for. The fields go through the same checks as a save (all but the name's being another connection's), and a refusal is the error. A connection with a script starts it first (D-1; the same function as D-3's opening of a connection), then logs in, runs `SELECT VERSION()` and closes the session, and the script is ended whatever the result was.

The answer is shown in `#database-test-result` (`role="status"`), under the fields of the way and above the error line of the save, and nowhere else: a success is a status with a dot, "MySQL {version}" (the version as `SELECT VERSION()` answers it, such as "MySQL 8.0.36"), and an error is its text in the danger color, as Rust words it (for a script that failed, with the last lines of its standard error, D-1), wrapped where it is long. It is hidden while a test is on its way and the button is off, so that two tests do not run at once; the button is on again when the answer is shown. A test saves nothing and does not close the edit pane. An edit pane closed while a test is on its way draws nothing when the answer comes (the script is ended in Rust all the same), and one opened again shows no answer.

The errors are told apart, and each is worded for the person who has to act:
- The script was ready and MySQL does not answer (the connection is closed or reset with nothing said, a time out, a refusal on the port of the script): 「スクリプトの準備はできましたが、MySQL が応えません。スクリプトが開いたポートの先に MySQL が届いているかを確かめてください」. It is never worded as a login that failed.
- MySQL refuses the user name or the password (1044, 1045, 1698): 「MySQL へのログインに失敗しました。ユーザー名とパスワードを確かめてください: {the server's message}」. The message holds no password.
- MySQL does not let the client's host in (1129, 1130), any other error of the server (its number and message), and an error of TLS or of the protocol, each with its own words.
- Without a script, the same failures name `{host}:{port}`: nothing answers, a refusal of the connection, a time out.
- The errors of the script itself (it ends before it is ready, it is not ready in 2 minutes, it cannot be started) are those of D-1's `database/script.rs`, and they stop the test before MySQL is tried.

The unit tests (`cargo test`, `database/mysql.rs` and `database.rs`) cover what each error of the server, of the socket and of the protocol is, the words of each (the script and the direct cases, the cut of a long message), the choice of the password (the typed, the saved, and the saved refused for each field of the login that changed: the host and the port only for a connection with no script) and of the endpoint, the TLS mode of each kind of host, that a session sets no `time_zone`, no `PIPES_AS_CONCAT` and no `NO_ENGINE_SUBSTITUTION`, and, against a MySQL server of a few lines on a local `TcpListener`, a server that closes the connection, one that says nothing (the time out), one that refuses the login (1045), a port that refuses, and that a session sends `SET SESSION TRANSACTION READ ONLY`. The E2E spec `database.e2e.ts` covers the button (its place and that it calls nothing before it is pressed), the arguments of `database_test` for a new connection and for an edit, on both ways (the id, the fields as typed now, the typed or the empty password), the version shown as a status, the error shown as it is (with the last lines of the standard error), that the edit pane stays and nothing is saved, the button off and the old answer hidden while the test is on its way, and an edit pane closed meanwhile.

## D-3 Open a connection, and the databases and tables under it

A press on a connection row opens it: the screen calls `database_connect` with the `id` and the row opens, with its databases under it (`.database-btn` rows of depth 1, keyed `{id}/d/{name}`, in the order of the server). A press on a database row opens it: the screen calls `database_tables` with the `id` and the `database`, and the tables of the database are under it (rows of depth 2, keyed `{id}/d/{name}/t/{table}`, by name; a view is among them). A row that can open has a chevron and `aria-expanded`; a press on one that is open closes it (nothing is called, and a connection that is closed in the tree stays connected), and a press on a closed one opens it and reads again, so that what is shown is never older than the press. A press selects the row (`aria-pressed`), a table row too, which draws the tabs of the table in the work pane in place of the table list (D-4). A press on a row whose read is on its way, or on a connection whose disconnect is on its way, does nothing but select it. A right press on a database row opens its own menu, below.

Rust keeps what a connection opened (`database/session.rs`, `Sessions`, managed by Tauri): one read only session for each connection (D-2, `database_connect` starts the script when the connection has one, logs in with the saved password, and reads the databases), used again by every read until it is closed. `database_connect` on a connection that is open reads only. The session is closed (and its script: SIGTERM to its process group, SIGKILL after 5 seconds, D-1) by "切断", by a save of that connection (its session was made with what is saved no more), by its delete, by a query that shows the stream broken (the connection is then closed and the screen is told so), and by the app's exit (the sessions, then the scripts, `lib.rs`). A connection whose databases cannot be read is closed again. `database_connections` answers the ids that are open, which the screen reads after a save, a delete and a failed read of tables, to close the trees that Rust closed. A session whose script has ended after it was ready is closed (D-1): Rust looks for such sessions before `database_connect`, `database_connections` and each read (`Sessions::reap`), a read on one is answered with the words of D-1's third failure, and a read that fails because the stream broke when the script ended is told with the same words. The screen learns it as it learns of any lost session: the next press opens the connection again, and `database_connections` no longer lists it. A connection that was deleted or edited while it opened is closed when it has opened (Rust reads the saved login again after the session is opened, and when it is changed it closes the session and answers 「接続が変更または削除されました。もう一度開いてください」, and when it cannot be read again (it is gone, the keychain or the file cannot be read) it closes the session and answers the error of that read; a delete closes the connection again after the file is changed, for a session that was added in between). A query that ends as lost closes the session it ran on and no other: a session opened again meanwhile stays.

The databases are read from `information_schema.SCHEMATA` (every one the user may see, the system ones too) and the tables from `information_schema.TABLES` with the name of the database bound as a value, never put in the SQL text. Each query has 30 seconds; one that is past it closes the connection (the stream is in an unknown state). The error is one of D-2's words for the connection, 「MySQL がエラーを返しました ({number}): …」 for an error of the server, 「MySQL との接続が切れました。もう一度開いてください: …」 for a broken stream, and 「接続が開いていません。もう一度開いてください」 for a read after the close.

The dot (`.database-dot`, at the right end of the connection row, `role="img"`, `data-state`): green and the label "接続済み" while the connection is open (`connected`), orange and "接続しています" while it opens (`connecting`), gray and "未接続" otherwise (`closed`). The menu of the row (the right press of D-1) has "切断" between "編集" and "削除" only while the connection is open. "切断" calls `database_disconnect` with the `id`, and the tree of the connection closes at once, the dot goes gray, and the connection is selected; its work pane empties when it showed one of its databases; a failure shows its error on the error line (`#error`) and the tree stays closed, and a press on the connection waits until the call has answered.

A right press on a database row (`contextmenu`, the default menu of the WebView is not shown; open or closed, and it selects nothing) opens the menu (`menu.ts`) at the place of the pointer, as D-1's does for a connection, with "新規クエリ" and "データベースを閉じる" (a line icon each). "新規クエリ" selects the database (`aria-pressed`, as a press on its row does, but it calls nothing and does not open the tree) and the work pane shows the tab SQL of the database (D-6) with the field empty, no result and the caret in the field: the text and the result that the SQL tab held for that connection and database are dropped, and a run still on its way is dropped too. "データベースを閉じる" closes the tree of the database (its row `aria-expanded` false and its tables gone) and nothing is called: the connection stays open and its dot stays green; when the work pane showed that database or one of its tables, it empties and the connection is selected, as after "切断"; a press on the row opens it and reads its tables again.

The loading and the failures are drawn in the tree and in the work pane, with no other text on the screen:
- While a connection opens, a line "接続中…" (`.database-note`, `role="status"`) is under its row and the dot is orange; while its databases are read again, the line is "読み込み中…". While a database's tables are read, the line "読み込み中…" is under its row and in the work pane.
- A failure is its text in the danger color (`.database-note.danger`, `role="alert"`) under the row that failed: a connection that could not be opened (the dot is gray and nothing is under it), a database whose tables could not be read (the connection stays open; the text is also in the work pane). The row stays open, and a press on it reads again. A read that shows the connection lost closes the tree of the connection and the text is under the connection, with the dot gray.

The work pane (`#database-work`) has, for the database pressed last (also when its row is closed again), its name (`h3`), its tabs (`.database-tabs`, `role="tablist"`, a `.database-tab` with `role="tab"` and `aria-selected` for each: "テーブル", `data-tab` "tables", and "SQL", `data-tab` "sql", the tab of D-6) and the body of the selected one. A press on a tab only changes the tab and calls nothing. "テーブル" is selected when the pane starts to show a database (a press on a database row while the pane showed another database, a table or nothing); a press on the row of the database that the pane already shows keeps the selected tab. The body of "テーブル" is the table list (`table.database-tables`; a table pressed in the tree draws the tabs of D-4 in place of the tabs of the database, and the press on the database row draws the tabs of the database again) with the columns 名前, 行数（概算）, サイズ and エンジン, a row for each table in the order of the tree. A row of the list (`tr`, `data-key` "table-{name}", `tabindex` 0, the pointer cursor, the hover color and the focus ring) is pressed as the row of that table in the tree is: a press with the pointer, or Enter or Space while it has the focus, selects the table row of the tree (`aria-pressed`) and reads the page 0 of its records (D-4), so the tabs of the table are drawn in place of the list; a press on a table that is already open reads again too. The row count is the estimate of `TABLE_ROWS` with thousands separators; the size is `DATA_LENGTH` plus `INDEX_LENGTH` as "512 B" or with one decimal in KB, MB, GB or TB (1024 each); the engine is `ENGINE`; Rust words the three (`format_rows`, `format_size`), and they are empty for a view. A database with no table draws its name only. Nothing is drawn when no database was pressed, or when the connection of it was closed.

Not tried against a real server by this code (only the pure parts and a local fake of the protocol, `cargo test`): the result of the two queries (the types of `information_schema` columns on MySQL 5.7, 8.0 and 8.4), which are cast in the SQL (`CAST … AS CHAR` and `AS UNSIGNED`) so that they decode as text and as unsigned numbers.

## D-4 Records of a table

A press on a table row of the tree, or on a row of the table list of the work pane (D-3), draws the tabs of the table in the work pane (`#database-work`, which then has the class `database-fill`, as it has while the SQL tab of a database is shown) in place of the tabs of the database: the title (`h3`, "{database}.{table}"), the tabs (`.database-tabs`, `role="tablist"`, a `.database-tab` with `role="tab"` and `aria-selected` for each; "レコード" and "構造" (D-5); "SQL" (D-6)) and the body of the selected tab. A press on the database row draws the tabs of the database again, with "テーブル" selected (D-3). A press on a table row selects "レコード".

The records tab reads one page with `database_records`, called with the `id` of the connection, the `database`, the `table` and the `page` (from 0). Every press on a table row (of the tree or of the list) reads the page 0 again, also on the table that is open, so what is shown is never older than the press. Rust reads ``SELECT * FROM `db`.`table` LIMIT ? OFFSET ?`` on the open session of D-3 (read only, 30 seconds like every query there): the names of the database and of the table are put in the SQL text between backticks with a backtick inside doubled (`records::quote_identifier`), and the limit and the offset are bound. A page is 100 rows (`PAGE_SIZE`). 101 rows are asked for, to know whether a next page exists (`hasMore`); the 101st is not sent. The offset is the page times 100. A connection that is not open, a read that fails and one that shows the stream broken are D-3's errors and words, and the last closes the connection as D-3 says.

Rust turns every value into text (`records::cell_of`), from the name of the column's type and the value in the binary protocol (the statement is a prepared one, because of the bound limit and offset); each cell is `{kind, text}`, and the screen draws the text and uses the kind only to style it:
- NULL is the text "NULL", kind `null`, in the quiet color and in italics. An empty string is an empty text, not NULL, and the text "NULL" is a text.
- An integer (TINYINT to BIGINT, signed or unsigned, BOOLEAN), a FLOAT, a DOUBLE, a DECIMAL (its own text as MySQL sent it), a YEAR (four digits) and a BIT (as the number of its bits) are kind `number`, right aligned.
- A DATE, a DATETIME, a TIMESTAMP and a TIME are kind `text` in MySQL's form: `2024-01-02`, `2024-01-02 03:04:05`, `-01:02:03`, with the days in the hours of a TIME (`838:59:59`) and the zero date as zeros. The fraction of a second is shown only when it is not zero, without its trailing zeros.
- A CHAR, a VARCHAR, a TEXT, an ENUM, a SET and a JSON are kind `text` (a JSON is the text MySQL sent). A text of more than 200 characters (`TEXT_MAX`, by characters, not bytes) is cut to 200 and ends with "…"; the rest is kept nowhere (not in Rust, not on the screen), so the full value of a long cell is not seen here. A text that is not valid UTF-8 is told as binary.
- A BINARY, a VARBINARY, a BLOB of any size and a GEOMETRY are kind `binary`: the text is the length only, "バイナリ 16 B" (the units of the table list of D-3), in the quiet color and in italics. Bytes that do not fit their type are told as binary too, and no value makes a read fail.

The answer is `{columns, rows, page, hasMore, estimate, summary, lastPage, pages, tsv}`. The estimate of `information_schema.TABLES` (`TABLE_ROWS`; none for a view) is read after the page on the same session for the page 0 and for a page that is asked with no estimate (a press on the table, a reload of the page 0, and a page read after a failed read dropped the one the screen held); `database_records` takes `estimate`, the one that the page shown holds (null when none is shown), and a later page answers it again when it is given, so that the move to another page costs one round trip. `database_records` takes `typed` too, the text of the page field of the footer, only when it is typed: it names the page (`records::page_of_input`) and `page` is not used. The text is read as the number of the page counted from 1, after the whitespace around it is cut: a text of ASCII digits only is that number, a number below 1 and anything else (empty, a sign, a separator, a fraction, a letter, other digits) is the page 1, and a number past what `u32` holds is the last page `u32` holds. The page is not held to the estimate, which is only an estimate, so a page past the last one is read and shows "0 行". `summary` is worded by Rust (`records::format_summary`): "{first}–{last} 行目" with thousands separators and, when the estimate is not below the last row shown, " / 約 {rows} 行"; a page with no row is "0 行". The columns are those of the rows, so a table with no row draws no header, and a table whose page has no row draws only the range. `lastPage` is the last page (from 0) that the estimate gives (`records::last_page`: the estimate in pages of 100, rounded up, less one), and `pages` is its wording for the footer (`records::format_pages`): "/ 約 {pages}" with thousands separators, such as "/ 約 15,062". Both are none and empty when the estimate is none (a view), when it is below the last row shown (the rule of the summary) and when the page has no row. Nothing more is asked for them: the number of rows is not counted, so the estimate that is off makes the last page empty or leaves rows after it (at the owner's decision, 2026-11-15; #667).

The grid (`table.database-grid`, drawn by `gridNode` of `ts/database-grid.ts`, which the SQL tab uses for its result with the same cells) has the column names as its header (kept at the top while the page scrolls) and a row of cells (`.database-cell`, `data-kind`). A cell is one line, cut with an ellipsis at 320 px, and a text cell has its text as its `title`. The grid scrolls in the work pane and the footer stays under it.

A vertical line (1 px, `var(--line)`) is drawn between two columns, on the header and on every cell, and not at the left of the first column. The right edge of each header has a grip (`.database-grip`, `role="separator"`, 8 px wide, the cursor `col-resize`): pressing it with the primary button and moving the pointer sideways changes the width of that column (the width of the header when the press began plus the move, at least 48 px), drawn at once on the header and on every cell of the column. A column that has a width is cut at that width with the ellipsis, and the 320 px limit does not apply to it; a column that never had a width stays as above. The widths are for one grid, named by the connection, the database, the table and the tab (records, structure) and by the place and the name of the column; the SQL result is named by the connection and the database alone, because the tab SQL of a database and the tab SQL of each of its tables show one result (D-6). They are held in memory until the app is closed and are written nowhere, so the next page, another tab, another table and back, and a read again draw the columns with the widths they were left with, and another table draws its own. The same grid and the same grip are those of D-5 and D-6, which use `gridNode` too (#669).

Under the grid is the footer (`.database-pager`), in one row. At the left are the reload (`.icon-btn`, `data-key` "reload", `aria-label` "再読み込み", the icon `RELOAD_SVG`, which reads the page that is shown again) the copy (`.icon-btn`, `data-key` "copy", `aria-label` "一覧をコピー", the icon `COPY_SVG`) and the range (`.database-range`, `role="status"`, "読み込み中…" while a page is read). At the right (`.database-pager-nav`) are, in order, five controls: the first page (`.icon-btn`, `data-key` "first", `aria-label` "最初のページ", off on the page 0), the previous page ("prev", "前のページ", off on the page 0), the field of the page number (`input.database-page-input`, `type` text, `data-key` "page", `aria-label` "ページ番号", no placeholder), the pages (`.database-pages`, `pages` of the answer, empty when none), the next page ("next", "次のページ", off when `hasMore` is false and after an error) and the last page ("last", "最後のページ", off when `lastPage` is none, after an error and on that page). The buttons have no text, only the icons (the first and the last page are a bar and a chevron, the previous and the next page are chevrons) and `aria-label`. The field holds the number of the page that is shown (page + 1), and Enter in it (not the Enter that confirms an IME conversion) calls `database_records` with the text as it is in `typed`, the page that is shown in `page` and the same `estimate`; Rust names the page, as above, and the screen draws the page that the answer has (`page` of the answer), so the field then holds it. Nothing is sent before Enter. All the buttons are off while a page is read, and the field is read only then (it keeps the focus) and Enter in it sends nothing. The first, previous, next and last page call `database_records` with the page 0, the page before, the page after and `lastPage`, and 再読み込み with the same page. While the next page is read the page shown stays; an error drops it and is shown in the danger color (`.database-note.danger`, `role="alert"`) in its place, with the buttons as above, so 再読み込み reads again. A read that ends after another press has replaced it is dropped. A table press, a database press or a disconnect leaves the records; they are held in memory for the last table only.

The copy (#668) puts the page that is shown in the clipboard as text, the same as the grid with the header (at the owner's decision, 2026-11-15: the place is the left of the footer, right of the reload, and the structure tab and the SQL tab have it too). The text is `tsv` of the answer, which Rust made with the page (`records::cells_tsv`, a pure function): the first line is the column names, then a line for each row, the fields of a line are separated by a tab and the lines by a line feed, with no line feed after the last line, so a spreadsheet takes it as it is. The value of a cell is the text that the grid draws, so a text cut at 200 characters is copied cut, a binary value is its length ("バイナリ 16 B") and NULL is `NULL`: Rust does not keep the full values (above). A field that holds a tab, a line feed, a carriage return or a double quote (the name of a column too) is put between double quotes with each double quote doubled (`records::tsv`), which is how a spreadsheet reads such a field; any other field is as it is. A page with no column has no text. The press calls no command: it writes `tsv` of the answer that is shown with `copyText` (`ts/view.ts`) straight from the click, because the clipboard of WKWebView refuses a write that comes after an `await`, and says 「一覧をコピーしました」 in a toast; a refusal of the clipboard is shown in `#error`. The button is off while a page is read, after an error and when the page has no column.

No control to add, edit or delete a row is anywhere on the screen, and a cell is not editable. The session is read only (D-2), so MySQL refuses a write all the same.

Not tried against a real server by this code (only the pure parts, `cargo test`): the binary forms of the types as a real MySQL 5.7, 8.0 and 8.4 sends them (the forms are those of the protocol documentation and of `sqlx-mysql`'s own decoding of rows), the name that sqlx gives each column type, and a BOOLEAN (a TINYINT of display width 1) that is UNSIGNED and holds more than 127, which is shown as a signed value.

The unit tests (`cargo test`, `database/records.rs` and `database/session.rs`) cover the quoting of a name (a backtick doubled, empty, with a dot or a space or a semicolon, Japanese) and that the statement binds only the limit and the offset, the cut of a text (the edge, characters against bytes), each type's conversion (the integers with their signs and edges, floats, year, bit, decimal, DATE, DATETIME and TIMESTAMP with and without a fraction, TIME with a sign, days and a fraction, the zero date, NULL, binary of several sizes and a text that is not UTF-8, JSON, ENUM and SET), that bytes that do not fit become binary, the summary (the range, thousands separators, a stale estimate left out, no row), the page of the typed text (a number counted from 1, whitespace around it, below 1, empty, a sign, a separator, a fraction, a letter, other digits, past `u32`), the last page (the estimate in pages, the edges of 100, a stale or no estimate and a page with no row) and the wording of the pages, the copy text (the header and the rows, NULL and a binary value as drawn, no row, no column, a tab, a line feed, a carriage return and a double quote in a field and in a name of a column, a field quoted once, Japanese and other whitespace as they are), and that a read of a connection that is not open fails with D-3's words. ## D-5 Structure of a table

The tab "構造" (`.database-tab`, `data-tab` "structure", after "レコード") of the work pane (D-4) shows the columns of the table that is pressed. A press on it only changes the tab: the table stays the same one (the title, `aria-pressed` of its row in the tree, and the records of D-4, which are kept as they are, so a press on "レコード" draws them again with no read). A press on the tab that is selected does nothing. A press on a table row of the tree selects "レコード" (D-4) and drops the structure.

The structure is read at every press of "構造", so what is shown is never older than the press, with `database_structure` called with the `id` of the connection, the `database` and the `table`. Rust reads, on the open session of D-3 (read only, 30 seconds like every query there), `information_schema.COLUMNS` with the schema and the table bound as values, never put in the SQL text, in the order of the table (`ORDINAL_POSITION`), and `information_schema.TABLES` with the same two values for the engine and the collation. Every column is cast in the SQL (`CAST … AS CHAR`), as D-3's. A connection that is not open, a read that fails and one that shows the stream broken are D-3's errors and words, and the last closes the connection as D-3 says.

The answer is `{columns, summary, tsv}`. A column is `{name, columnType, nullable, key, default, comment}`, worded by Rust (`structure::to_column`, `format_default`):
- `name` is `COLUMN_NAME`, `columnType` is `COLUMN_TYPE` as MySQL writes it (`bigint unsigned`, `varchar(255)`, `enum('a','b')`), `key` is `COLUMN_KEY` as it is (`PRI`, `UNI`, `MUL` or empty) and `comment` is `COLUMN_COMMENT`.
- `nullable` is true when `IS_NULLABLE` is `YES`.
- `default` is `COLUMN_DEFAULT` as text; an empty text is `''`. The server answers none both for a column with no default and for one whose default is NULL, so a column that may be NULL has "NULL" and one that may not has an empty text.

`summary` is worded by Rust (`structure::format_summary`): "{n} 列", then " / {engine}" and " / {character set}" when the table has them (a view has neither), such as "12 列 / InnoDB / utf8mb4". The character set is the collation of the table (`TABLE_COLLATION`) up to its first underscore (`charset_of`).

The screen draws the columns as a grid (`table.database-grid.database-structure`, `gridNode` of `ts/database-grid.ts`, the same as D-4's) with the header 名前, 型, NULL, キー, 既定値 and 注釈 and a row for each column, "YES" or "NO" for NULL, one line in each cell, cut with an ellipsis at 320 px (until a column is given a width with its grip, D-4), with the text of a cell as its `title`, and, under the grid, the footer (`.database-pager`) with the copy (#668; `.icon-btn`, `data-key` "copy", `aria-label` "一覧をコピー", at the left, as D-4's) and the summary (`.database-range`, `role="status"`). While it is read the footer says "読み込み中…" and the grid is not drawn; an error is its text in the danger color (`.database-note.danger`, `role="alert"`) in place of the grid, with the connection kept (a press on "構造" again reads it again); a table with no column draws only the summary. A read that ends after another press has replaced it is dropped. The structure is held in memory for the last table only.

The copy puts the columns in the clipboard as D-4's does (`copyText` of `tsv`, straight from the click, 「一覧をコピーしました」). `tsv` of the answer is made by Rust (`structure::columns_tsv`, which uses `records::tsv`): the header 名前, 型, NULL, キー, 既定値 and 注釈 and a line for each column with the cells of the grid ("YES" or "NO" for NULL), all the columns, a field quoted as D-4 says; a table with no column has no text. The button is off while the structure is read, after an error and for a table with no column.

Indexes, foreign keys and triggers are not shown, and nothing on the tab is editable.

Not tried against a real server by this code (only the pure parts, `cargo test`): the result of the two queries on MySQL 5.7, 8.0 and 8.4.

The unit tests (`cargo test`, `database/structure.rs` and `database/session.rs`) cover that the schema and the table are bound values, that no table of indexes, keys or triggers is read, the default (a value, empty text, NULL for a column that may be NULL and none for one that may not), the character set of a collation, the summary (with the engine and the character set, without them, a view), the row of a column (the key, NULL, the default and the comment), the copy text (the header, "YES" or "NO" for NULL, a field with a tab quoted, no column), and that a read of a connection that is not open fails with D-3's words. The E2E spec `database.e2e.ts` covers the three tabs and the selected one, the call of `database_structure` (its arguments, only on a press of 構造, again at every press, not on the tab that is selected), the columns and the summary as Rust gave them, the cut comment with its title, that the table (the title, the pressed row, the records and their calls) stays when the tab changes, that a press on a table selects "レコード", 読み込み中…, a table with no column, the error of a read (shown, the connection kept, the read again), a connection shown lost, and that the tab has no control but the copy and no input, and the copy (at the left of the footer, off while the structure is read, after an error and for a table with no column, the text of the answer written to the clipboard).

## D-6 SQL

The tab "SQL" (`.database-tab`, `data-tab` "sql", after "構造") of the work pane (D-4) runs a statement the user types and shows its result. A press on it only changes the tab: it calls nothing, and the records and the structure are kept as they are. The work pane of a database (D-3) has the same tab, after "テーブル", with the same body and the same state: the text and the result are those of the connection and database, whichever of the two panes shows them.

"新規クエリ" in the menu of a database row (D-3) selects the database and shows its SQL tab with the field empty, the result gone and the caret in the field (the text and the result held for that connection and database are replaced by an empty tab, and an answer of a run that was still on its way is not drawn). It calls nothing.

The body has, from the top, the field (`textarea.database-sql-text`, `aria-label` "SQL", 8 rows, resizable in height, in the monospace font; no placeholder and no text that explains it), the button "実行" (`.text-btn`, `data-key` "run", in a row of its own under the field, at the right), the result (the grid of D-4, `gridNode` of `ts/database-grid.ts`, in `.database-records-scroll`, so it scrolls and the footer stays) and the footer (`.database-pager` with the copy (#668; `.icon-btn`, `data-key` "copy", `aria-label` "一覧をコピー") at the left and `.database-range`, `role="status"`). Nothing is saved, formatted or listed: there is no history, no saved statement and no formatter, and no control but the tabs, "実行" and the copy.

The connection and the database are those the tree has selected: the connection and the database of the table that is pressed, or of the database that is pressed (D-3). "実行" calls `database_sql` with the `id` of the connection, the `database` and the `sql` as typed (an empty field too: Rust refuses it with 「SQL を入力してください」, shown as an error). The field and the result are held in memory for the connection and the database that were selected last: they stay when the tab changes and when another table of the same database is pressed, and they are dropped when the field is used in another connection or database, by "新規クエリ", and when the connection is shown lost. While a statement runs, the footer says "実行中…", "実行" is off, and the old result stays; a result that comes is drawn in its place, and an error drops the old result and is shown in the danger color (`.database-note.danger`, `role="alert"`) in place of the grid, with the text in the field kept and the connection kept (a press on "実行" runs it again). A run that shows the stream broken closes the connection as D-3 says, and the tree closes and says why. Pressing keys in the field draws nothing; the pane is made again by other changes and keeps the caret.

Rust (`database/sql.rs`, `Sessions::sql` of `database/session.rs`, the command `database_sql`) runs one statement:
- The text is passed to MySQL as it is, as a prepared statement (so its rows come in the binary protocol that D-4's `cells_of` reads, and it is not kept in sqlx's cache of statements). Only the whitespace around it and the semicolons at its end are cut (`sql::statement`), because a prepared statement is one statement and a `;` ends one by hand. Nothing else is rewritten, quoted or wrapped. The session is read only (D-2), so MySQL refuses a write itself.
- One statement is run at a time. A text with a second statement in it is a syntax error of MySQL (1064), and a statement that MySQL does not take as a prepared one (1295) is told too. A statement that gives no row gives no column and "0 行".
- The database is chosen before the text by a `USE` of its own, run as text (the protocol of a prepared statement does not take it), with the name quoted by `records::quote_identifier`. It is never put into the text of the user. Before the statement the run sends, in one round trip (the statements are run as text, one after the other, and stop at the first that fails), `SET SESSION TRANSACTION READ ONLY`, `SET SESSION max_execution_time = 30000, sql_select_limit = 1001` and the `USE`. After the statement, whatever it answered (a `USE` that failed too), it sends `SET SESSION TRANSACTION READ ONLY` and `SET SESSION max_execution_time = DEFAULT, sql_select_limit = DEFAULT`, so that the reads of the tree and of the tabs are as they were. The read only is sent again each time because the text of the user may have set the session to read write (`SET SESSION TRANSACTION READ WRITE`, `SET SESSION transaction_read_only = 0`), which would let the next run write; MySQL itself must keep refusing a write. The whole run is in one hold of the session, so no other read comes between its statements.
- The rows are limited to 1,000 (`sql::ROWS_MAX`). The result is read as a stream that is stopped after the 1,001st row: that one is not kept and the rows past it are never held, so the memory is that of 1,000 rows of cells (a text is cut to 200 characters and a binary value is its length, as D-4's). `sql_select_limit` is 1,001, so MySQL itself ends a SELECT with no LIMIT of its own one row past the limit, and nothing is left unread behind it. A SELECT with its own LIMIT above 1,001 sends more rows than are read: they are not held, and the next call on the session passes over them (sqlx does that before its next statement, inside that call's own time). A result that was cut shows 「先頭の 1,000 行だけを表示しています（残りは読み込んでいません） / {time}」 in the footer; the grid has the 1,000 rows.
- The time is limited twice. MySQL stops a SELECT that runs for 30 seconds (`max_execution_time`), with the error 3024, worded 「実行が 30 秒を超えたため、MySQL が止めました (3024): …」; the session stays and no query is left on the server. What `max_execution_time` does not stop (a statement that is not a SELECT, or a server that does not answer) is stopped by the app after 35 seconds (`sql::CLIENT_LIMIT`, the whole run: the preface, the statement and the restore): the connection and its script are ended (as D-3's time out), the error is 「実行が時間内に終わらなかったため、MySQL との接続を閉じました。もう一度開いてください」, and the tree closes and says why. `KILL QUERY` is not used: it needs a second connection, and so the password kept in memory for the life of the session, which D-2 avoids.
- The footer under the grid is `sql::format_summary`: 「{rows} 行 / {time}」 with thousands separators, the time of the statement alone (from its sending to the last row read) as 「12 ms」 and, from a second on, 「1.25 秒」 (the hundredths cut). A statement with no row is 「0 行 / {time}」, and a SELECT with no row has no header, as D-4's page has none.

## D-7 Terminal pane on the database screen

The screen has a third part at the right of the work pane (D-1): the terminal pane (`#database-terminal`, `aside`, `aria-label` "ターミナル", the `--bar` background). It is opened and closed by the icon button at the right end of the header of the work pane (`#database-terminal-toggle`, `.icon-btn`, `aria-label` "ターミナル", `aria-pressed`; a drawn terminal icon and no text; the same form as the icon buttons of the right side of the Todo screen, T-7: the button pressed is filled with `--accent`). The pane is closed at first (`aria-pressed` false, the pane and its divider hidden), a press on the button opens it (`aria-pressed` true), and a press again closes it. While the edit pane of D-1 is open the work pane and its icon are hidden, and the icon in the header of the edit pane (`#database-edit-terminal`) does the same and shows the same state. Opening and closing calls no command and sends nothing while the pane holds no terminal. The work pane takes the room that is left.

The pane has a head (`#database-terminal-head`, as high as every header, A-23, and a place to drag the window by) and, under it, the body (`#database-terminal-body`). The head holds the strip of tabs (`#database-terminal-tabs`, `role="tablist"`, `aria-label` "タブ") and, after it, the plus (`#database-terminal-plus`, `.icon-btn` with a plus and no text, `aria-label` "ターミナルを開く", `aria-haspopup` "dialog"). The strip is empty and the body is empty (no child, no text) until a terminal is opened. The screen shows no help text.

The plus opens a plain terminal of Orca (A-6, A-16), as the item 「ターミナルを開く」 of the plus of the Orca work pane does, and starts nothing in it (no `mysql`: the terminal is for starting Claude or for `ssh`, at the owner's instruction, 2026-11-15; #672). It reads Orca's list for the target that the Orca screen holds (`refreshOrca` of `ts/orca.ts`, `orca_overview`; a list streamed from a saved environment is taken as it is held, A-12), and opens the dialog of the worktrees of A-6 (`openWorktreeDialog`, `.orca-dest-pop`) under the plus with every worktree of that list, narrowed by its filter; no project is asked first, because the worktree is the project's. Picking one calls `orca_terminal_create(path, environment)` with the worktree's path and `OrcaWorktree.environment` (null: this machine); no command is added. The plus is disabled while the list is read and while the terminal is opened. When the list cannot be read, the pane says why in a notice (`.pending.fail`, the first child of the body): the message of A-6 (`noticeOf`: 「orca コマンドが見つかりません。…」 when the command is missing, 「読み込めませんでした: {message}」 when the read failed), and no dialog opens. A failure of `orca_terminal_create` is the notice with Rust's message, and Orca's reply that names no handle is 「Orca がターミナルの名前を返しませんでした」; nothing is opened, and the terminal held before stays. A new press of the plus clears the notice.

Each terminal opened is held by the pane (memory only), in the order of opening, with a tab in the strip: a wrapper (`.database-terminal-tab`, `role="presentation"`) of the tab button (`button[role="tab"]`, `aria-selected`, the title `{repo} ・ {branch}` of the worktree) and, beside it, the close button (`.icon-btn`, `aria-label` "閉じる", a drawn cross and no text, the form of the tabs of the Orca screen, A-6). The tab of the terminal just opened is the selected one (`aria-selected` "true", the others "false"; the selected tab is on the `--surface` ground with a thin border, as the selected tab of the Orca screen is). Pressing a tab selects it: its terminal is drawn in the box under the strip (`.database-terminal-term`, one box for all, filling the body under the notice) by `ts/orca-terminal.ts` (A-8, A-12), with this pane as the owner of those terminals (`showTerminals` with the owner `database-terminal`), so it takes the keys, the fonts, the colors and the files dropped on it as the Orca screen's terminals do, and the terminal that was shown is let go (its screen stays in Orca). Only the selected terminal is shown, so only its stream (`orca_stream_terminal`) or its reads (`orca_terminal_read`) run: a terminal of a saved environment that the Orca screen streams (`streamsEnvironment`, A-12) is streamed, any other, this machine's or a saved environment's, is mirrored (`orca_terminal_read` every second, every 2 seconds for a saved environment), and the terminals of the other tabs read and stream nothing until their tab is pressed again. A second press of the plus opens another terminal and a second tab; the first stays, with its tab. Pressing the selected tab changes nothing.

The close button calls `orca_close(handle, environment)` (A-6, "Closing": the same command as the close button of the Orca screen's tab, with the terminal's handle and its `OrcaWorktree.environment`), and presses no tab. The button is disabled while its close is on its way. When Orca has closed the terminal, its tab goes at once, and its stream or reads end (the list is not waited for). A failure of `orca_close` is the notice with Rust's message (`.pending.fail`, the first child of the body), keeps the tab, enables the button again and reads Orca's list for that terminal at once, so that a terminal Orca no longer holds goes as below. A new press of the plus or of a close button clears the notice. When the tab that goes is the selected one, the tab that followed it is selected, else the one before it; with no tab left the strip and the body are empty again, as before the first terminal, and the tick stops.

What reads at an interval stops with its target. A tick (every second, the period of the mirror) runs while the pane holds a terminal and the pane is open: it shows the selected terminal when the pane is in view (and lets the one shown before go, `hideTerminals`), and lets every stream and read go when the screen is left or the window is hidden; closing the pane does the same at once and stops the tick, and opening it again starts the tick and shows the selected terminal anew. While the pane is in view the tick also reads Orca's list for the terminals (`refreshOrca` while the target of a terminal is the Orca screen's, else `readDestination`; one read for each place that the terminals are in, not one for each terminal): the selected terminal is shown only once a list holds its handle, which is read at each tick for at most 30 seconds (then the pane says 「ターミナルが Orca の一覧に現れませんでした」 and forgets that terminal), and afterwards, for every terminal, at the period of the Orca clock (10 seconds); a ready list that no longer holds the handle of a terminal that it held (the terminal was closed in Orca) makes the pane forget that terminal, whether its tab is selected or not: its tab goes and its stream or reads end (no notice), the selection follows as for a close, and with no terminal left the box goes and the tick stops. A read of the list that failed or is not ready changes nothing.

No new command, no new saved file and no new call to an outside service.

The divider between the work pane and the pane (`#database-terminal-split`, `role="separator"`, `aria-label` "ターミナルの幅", shown only while the pane is open) is dragged with the pointer or moved with the arrow keys (`ts/split.ts`, the same part as the divider of D-1; the left arrow widens the pane). The pane is 35% of the screen at first (`aria-valuenow` 35), widened or narrowed by the divider between 25% and 50% of the screen (`aria-valuemin` 25, `aria-valuemax` 50; the CSS holds the same range, `--terminal-w`). Whether the pane is open and its width are held in memory only: closing the pane keeps its width for the next opening, leaving the screen keeps both, and no file is added.

The E2E spec `database.e2e.ts` covers the button (its place at the right end of the header, the label, the icon with no text, `aria-pressed`), the pane and the divider hidden at first, the open and the close with the press, the empty strip and body, the drag of the divider (the width, held to the range) and the arrow keys, and that the width is kept over a close and an opening; and, for the terminal: the plus (its label, no text), the dialog of the worktrees under it with the list's worktrees, `orca_terminal_create` called with the path and the environment of the one picked (and nothing called before the pick), the tab and the screen of the terminal drawn from what Orca gave (mirrored, with the handle read), a terminal of a saved environment streamed (`orca_stream_terminal` and the snapshot drawn), the reads stopped when the pane is closed (and none begun when the pane was closed while the terminal was being opened: no watch is set, and the reads begin when the pane is opened), when the screen is left and when the list no longer holds the terminal (the tab and the box gone) and begun again when the pane is opened, the notices (Orca missing, a failed read, a failed `orca_terminal_create`, a reply with no handle), the plus disabled while the terminal is opened, and, for the tabs: a second terminal getting a second tab that is selected, with the first kept, the switch by pressing a tab (`aria-selected`, the reads of the terminal left stopped and those of the other begun, a stream ended with `orca_stream_terminal_close` and the other opened), the close button of each tab (its label, no text, the call of `orca_close` with the handle and the environment, the tab pressed not selected by it, the button disabled while the close is on its way, the tab gone at once with its reads, the tab that followed selected and the one before when the last tab closed, the strip and the body empty after the last, the notice and the tab kept after a failure, with the list read again), and one terminal gone from the list while the other stays.

## D-8 Claude Code prepares a connection

`cookapps-mcp` (A-1) has three tools for the connections of the database screen, so that Claude Code writes the script of a connection (D-1), tries it and mends it until it connects, without the owner's copying text between the app and a terminal (#721, from #717). The tools change no screen; the edit pane that is open for the connection reads the saved one again (D-1, #720).

`db_profiles` answers the saved connections as the app's `database_profiles` does (D-1): `id`, `name`, `username`, `script`, `dbHost`, `dbPort` and `passwordSaved`. The password is never in the answer.

`db_profile_save` takes `id` (left out for a new connection, else the saved one it replaces), `name`, `username`, `script`, `dbHost` and `dbPort`, and answers the connection as saved. It goes through the same function as the app's save (`database::save_without_password`, then `save`: the same trimming, the same checks and refusals in Japanese, the same `write_atomic` of `database-profiles.json`), so the name, the script and, for a connection with no script, the host and the port are held to the rules of D-1: `dbHost` and `dbPort` may be left out when there is a script, and are then an empty host and the port 0. It sets no password: a new connection has none, and the owner types the password in the app. An edit keeps the saved password only while the connection still logs in as the saved one does (the user name and the script, and the host and the port of a connection with no script, as D-2's test decides); an edit that changes any of them deletes the saved password from the keychain first (after the checks, so a refused save deletes nothing), so that no password is sent to another place than the one it was saved for, and `passwordSaved` of the answer is then false. An edit of the name, or of the host and the port of a connection with a script, keeps it. A save here does not close a connection that is open in the app (D-3), whose session was made with the old login; the app closes it when the owner saves in the app or presses "切断".

`db_test` takes the `id` of a saved connection and tests it as saved, with its saved password (none is a login with no password), through `database::test_connection`, the function of the test of D-2: it starts the script, logs in, reads `SELECT VERSION()` and ends the script whatever the result was. The answer is `{"ok": true, "version": …}`, or `{"ok": false, "error": …, "note": …}`. The error is the words of Rust as D-2 and D-1 give them, in Japanese, and when the script ended it holds the last lines of its standard error (`script.rs`). That text came from the script, MySQL or the network, so it is a JSON string and the `note` says that it is data and not instructions. A connection that is not saved is the error 「接続が見つかりません。一覧を読み直してください」. A test may take as long as a script's wait (D-1: 120 seconds).

Claude Code writes the script, saves it, tests it, and mends it, until the test passes. The profile file is read and replaced whole by both the app and `cookapps-mcp`; a save of each takes the lock of its own process only, so two saves at the very same moment in two processes may lose one of them, and the file is never half written.

The two tools that change or run something ask the client for a check each time (the owner's decision, #722 decision 1: a tool that writes is allowed by the owner every time): `db_profile_save` is annotated `destructive_hint` true (it saves a script that `db_test` and the app run, and may delete a password) and not idempotent, and `db_test` is annotated `destructive_hint` true and `open_world_hint` true (it runs the saved script and reaches a MySQL server); `db_profiles` is `read_only_hint` true. Whether a client asks is the client's setting, and the annotations are what it reads.

No new command of the app, no new saved file and no new call to an outside service (the test is the one of D-2).

Unit tests (`cargo test`): a save without a password keeps the saved password and sets none while the login stays (a rename, and a change of the host and the port of a connection with a script), deletes it when the user, the script, the host or the port is changed (`passwordSaved` false), and deletes nothing when the save is refused, and is refused as the app's save is; the tools' annotations (`db_profile_save` and `db_test` destructive, `db_test` open world, `db_profiles` read only); a test of a connection that is not saved is refused; a test of a saved connection with a script that ends starts it and tells the end of its standard error; the arguments of a save make a new connection without `id`; and a failed test quotes its error as a JSON string. No E2E: no screen.
