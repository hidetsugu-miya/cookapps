# Database requirements

## D-1 Database screen and connections

The sidebar has a button for the database screen (`#nav-database`, `aria-label` "データベース"), after Orca and before the bottom group. Its icon is a drawn cylinder (a line icon like the other buttons, not text; the owner's instruction, 2026-11-14), and it has no count.

The screen (`#database`) has two parts, as the Slack screen has (S-19, `#slack-screen`): the side menu at the left (`#database-side`, the `--bar` background) and the work pane at the right (`#database-pane`), with a divider (`#database-side-split`) that the user drags (`ts/split.ts`, `--side-w`, 15 to 40% of the screen, 20% at first, kept in memory only). The side menu has a header of the height of every header (A-23, `#database-side-head`, a place to drag the window by) with the title "接続" and the plus (`#database-add`, `.icon-btn`, `aria-label` "接続を追加"), and under it the list (`#database-side-feed`). The work pane has a header (`#database-header`, a place to drag the window by) with the title "データベース" and, under it, `#database-work`, which holds the tables of the database that was pressed last (D-3), or the tabs of the table that was pressed (D-4, D-5); the tab of SQL is D-6's. The screen shows no placeholder and no text that explains a field or a button, and nothing is drawn for an empty list.

The list is what `database_profiles` answers (the connections in the order they were made, each with `passwordSaved`), read each time the screen is shown and again after every save and every delete, so the list is the same after the app is opened again and is never kept apart from the file. A read that fails shows its error on the error line (`#error`). A row (`.database-item`) is a button (`.database-btn`: a cylinder icon and the name, cut with an ellipsis) with no button of a menu beside it. Pressing a row makes it the selected one (`aria-pressed` true; one at a time, in memory only, dropped when the connection is gone from the list) and opens the connection (D-3). A right press on a connection's row (`contextmenu`, the default menu of the WebView is not shown; only the connection rows, not a database or a table) opens the menu (`menu.ts`) at the place of the pointer, as the right press of a row of the Orca file pane does (A-18): "編集", "切断" while the connection is open (D-3) and, in the danger color, "削除". The list is drawn again only when what it shows changes, and the focus stays.

The plus and "編集" open the popup (`#database-form`, `role="dialog"`, in the middle of a dimmed screen; the screen behind is inert while it is open, so Tab stays inside; the title is "接続を追加" or "接続を編集"). Its fields, with their names above (no placeholder), are the ones of the profile of Rust (`DatabaseProfile`): 接続名, ユーザー名, パスワード (a password field; for a connection whose password is saved, a status label "保存済み" with a dot beside the name, and the field empty: the password is never sent to the screen), the checkbox "SSM 経由で接続する", and, only while it is checked, "AWS のプロファイル名", "リージョン" and "踏み台の名前", then "DB のホスト" and "ポート" (a number field, 3306 for a new connection). The first field has the focus. "保存" sends `database_profile_save` with `profile` (the `id` empty for a new connection, else the connection's own, and the fields as typed; a port that is empty or not a number is sent as 0, which Rust refuses in Japanese) and `password` (the field as typed, empty to keep the saved one); the checks are Rust's, and the screen sends the fields as they are, also those of a hidden group. On success the popup closes and the list is read again. A refusal shows its text in `#database-form-error` (`role="alert"`) under the fields, and the popup stays with what was typed, so that "保存" can be pressed again (it is off while the call is on its way). The list is read again after a failed save too: Rust writes the file before the keychain, so when the keychain refuses a new connection's password (「接続は保存しましたが、パスワードを保存できません: …」) the connection is saved, and the list then has a connection that it did not have. The popup closes then, and the error is shown on the error line (`#error`), because a second "保存" would make the same connection again and be refused for its name. "キャンセル" and Escape (unless it only cancels an IME conversion) close it and call nothing; a press on the dimmed part does not, so that typed text is not lost by accident. Leaving the screen closes it.

"削除" opens the confirmation of `confirmDelete` (`ts/hint.ts`, `role="alertdialog"`: "削除しますか？", "{name} を完全に削除します。元に戻せません。", a red "削除" and "キャンセル", which has the keys) under the name of the row. "削除" calls `database_profile_delete` with the `id`, and the list is read again, also when the call failed, with its error on the error line; "キャンセル", Escape and a press elsewhere call nothing.

The unit tests (`cargo test`, `database.rs`) cover the file, the checks and the password. The E2E spec `database.e2e.ts` covers the button (the label and the icon, no text), the two parts, the list in the order given and read again at each showing, the error of a failed read, the press that selects (what it opens is D-3's), the popup (the fields, the group that the checkbox shows, the focus, no placeholder), a save of a new connection and of an edit (the arguments of `database_profile_save`, the list read again), the port sent as 0, the refusal shown with the popup kept, the refusal of the keychain after a new connection was saved (the popup closed, the error on the screen, the connection listed), the saved password shown as a status, キャンセル and Escape, and the confirmation, the delete (`database_profile_delete` and the list read again), its failure and the selection of a connection that is gone.

## D-2 Connection to MySQL and the test of a connection

The server is MySQL 5.7, 8.0 or 8.4, and the login is `mysql_native_password` or `caching_sha2_password`. A session is opened by one function (`database/mysql.rs`, `connect`), which the connection test and the screens that come after it (tables, records, SQL) all use. It connects to `127.0.0.1` and the local port of the tunnel when the connection goes through SSM (D-1, `database/ssm.rs`), and to the DB host and the port of the connection when it does not. TLS is used when the server offers it, and the password of `caching_sha2_password` goes through it (a server with no TLS that asks for it is the error 「このユーザーの認証 (caching_sha2_password) には TLS が要りますが、サーバーが TLS を使えません」). A connection that goes over a network (no SSM, and a host that is not `localhost` or a loopback address) requires TLS, so that nobody on the way can make it fall back to plain text: a server with no TLS is the error 「TLS の接続に失敗しました: …」. The certificate is not verified in either case. The time zone and the `sql_mode` of the session are the server's own: the defaults of sqlx (`time_zone='+00:00'`, `PIPES_AS_CONCAT` and `NO_ENGINE_SUBSTITUTION`) are turned off, so that a TIMESTAMP and `NOW()` read as any other client reads them and `||` is OR. The session is made read only at once (`SET SESSION TRANSACTION READ ONLY`), so that MySQL itself refuses a write. A connection has 15 seconds, from the first byte to the answer of the first query.

The popup of D-1 has a button "接続をテスト" (a `.text-btn`, between "保存" and "キャンセル", `type` "button", so that Enter in a field still saves). It tests the connection as typed in the popup, not as saved: it sends `database_test` with `profile` (the fields as typed, as "保存" sends them) and `password` (the field as typed). Rust takes the password typed, and when the field is empty the one saved in the keychain for `profile.id` (none for a new connection, which logs in with no password), but only when the fields still say where and as whom the login goes as the saved connection does (the user name, the checkbox, the AWS profile, the region, the bastion, the host and the port; the name is not one of them): otherwise the test is refused with 「接続先やユーザーを変えたときは、パスワードを入力してください」, so that the saved password is never sent to another place than the one it was saved for. The fields go through the same checks as a save (all but the name's being another connection's), and a refusal is the error. A connection that uses SSM opens its tunnel first, then logs in, runs `SELECT VERSION()` and closes the session, and the tunnel is closed whatever the result was; a tunnel that cannot be closed after a test that passed is told as the error 「MySQL {version} に接続できましたが、トンネルを閉じられませんでした: …」, because its session is left at AWS.

The answer is shown in `#database-test-result` (`role="status"`), under the port and above the error line of the save, and nowhere else: a success is a status with a dot, "MySQL {version}" (the version as `SELECT VERSION()` answers it, such as "MySQL 8.0.36"), and an error is its text in the danger color, as Rust words it. It is hidden while a test is on its way and the button is off, so that two tests do not run at once; the button is on again when the answer is shown. A test saves nothing and does not close the popup. A popup closed while a test is on its way draws nothing when the answer comes (the tunnel is closed in Rust all the same), and a popup opened again shows no answer.

The errors are told apart, and each is worded for the person who has to act:
- The tunnel is open and MySQL does not answer (the connection is closed or reset with nothing said, a time out, a refusal on the local port): 「トンネルは開きましたが、MySQL が応えません。踏み台から DB のホストとポートに届くか（DB のセキュリティグループが踏み台からの接続を許しているか）を確かめてください」. It is never worded as a login that failed.
- MySQL refuses the user name or the password (1044, 1045, 1698): 「MySQL へのログインに失敗しました。ユーザー名とパスワードを確かめてください: {the server's message}」. The message holds no password.
- MySQL does not let the client's host in (1129, 1130), any other error of the server (its number and message), and an error of TLS or of the protocol, each with its own words.
- Without a tunnel, the same failures name `{host}:{port}`: nothing answers, a refusal of the connection, a time out.
- The errors of the tunnel itself (an AWS login that is gone, a bastion that is not found, no `session-manager-plugin`, a time out) are those of D-1's `database/ssm.rs`, and they stop the test before MySQL is tried.

The unit tests (`cargo test`, `database/mysql.rs` and `database.rs`) cover what each error of the server, of the socket and of the protocol is, the words of each (the tunnel and the direct cases, the cut of a long message), the choice of the password (the typed, the saved, and the saved refused for each field of the login that changed) and of the endpoint, the TLS mode of each kind of host, that a session sets no `time_zone`, no `PIPES_AS_CONCAT` and no `NO_ENGINE_SUBSTITUTION`, the outcome of a test with a tunnel that cannot be closed, and, against a MySQL server of a few lines on a local `TcpListener`, a server that closes the connection, one that says nothing (the time out), one that refuses the login (1045), a port that refuses, and that a session sends `SET SESSION TRANSACTION READ ONLY`. The E2E spec `database.e2e.ts` covers the button (its place and that it calls nothing before it is pressed), the arguments of `database_test` for a new connection and for an edit (the id, the fields as typed now, the typed or the empty password), the version shown as a status, the error shown as it is, that the popup stays and nothing is saved, the button off and the old answer hidden while the test is on its way, and a popup closed meanwhile.

## D-3 Open a connection, and the databases and tables under it

A press on a connection row opens it: the screen calls `database_connect` with the `id` and the row opens, with its databases under it (`.database-btn` rows of depth 1, keyed `{id}/d/{name}`, in the order of the server). A press on a database row opens it: the screen calls `database_tables` with the `id` and the `database`, and the tables of the database are under it (rows of depth 2, keyed `{id}/d/{name}/t/{table}`, by name; a view is among them). A row that can open has a chevron and `aria-expanded`; a press on one that is open closes it (nothing is called, and a connection that is closed in the tree stays connected), and a press on a closed one opens it and reads again, so that what is shown is never older than the press. A press selects the row (`aria-pressed`), a table row too, which draws the tabs of the table in the work pane in place of the table list (D-4). A press on a row whose read is on its way, or on a connection whose disconnect is on its way, does nothing but select it.

Rust keeps what a connection opened (`database/session.rs`, `Sessions`, managed by Tauri): one read only session for each connection (D-2, `database_connect` opens the tunnel when the connection uses SSM, logs in with the saved password, and reads the databases), used again by every read until it is closed. `database_connect` on a connection that is open reads only. The session is closed (and its tunnel, which stops the plugin and ends the SSM session) by "切断", by a save of that connection (its session was made with what is saved no more), by its delete, by a query that shows the stream broken (the connection is then closed and the screen is told so), and by the app's exit (the sessions, then the tunnels, `lib.rs`). A connection whose databases cannot be read is closed again. `database_connections` answers the ids that are open, which the screen reads after a save, a delete and a failed read of tables, to close the trees that Rust closed. A tunnel that cannot be closed after a save or a delete is told in the error (「接続は保存しましたが、トンネルを閉じられませんでした: …」), because its session is left at AWS. A connection that was deleted or edited while it opened is closed when it has opened (Rust reads the saved login again after the session is opened, and when it is changed it closes the session and answers 「接続が変更または削除されました。もう一度開いてください」, and when it cannot be read again (it is gone, the keychain or the file cannot be read) it closes the session and answers the error of that read; a delete closes the connection again after the file is changed, for a session that was added in between). A query that ends as lost closes the session it ran on and no other: a session opened again meanwhile stays.

The databases are read from `information_schema.SCHEMATA` (every one the user may see, the system ones too) and the tables from `information_schema.TABLES` with the name of the database bound as a value, never put in the SQL text. Each query has 30 seconds; one that is past it closes the connection (the stream is in an unknown state). The error is one of D-2's words for the connection, 「MySQL がエラーを返しました ({number}): …」 for an error of the server, 「MySQL との接続が切れました。もう一度開いてください: …」 for a broken stream, and 「接続が開いていません。もう一度開いてください」 for a read after the close.

The dot (`.database-dot`, at the right end of the connection row, `role="img"`, `data-state`): green and the label "接続済み" while the connection is open (`connected`), orange and "接続しています" while it opens (`connecting`), gray and "未接続" otherwise (`closed`). The menu of the row (the right press of D-1) has "切断" between "編集" and "削除" only while the connection is open. "切断" calls `database_disconnect` with the `id`, and the tree of the connection closes at once, the dot goes gray, and the connection is selected; its work pane empties when it showed one of its databases; a failure shows its error on the error line (`#error`) and the tree stays closed, and a press on the connection waits until the call has answered.

The loading and the failures are drawn in the tree and in the work pane, with no other text on the screen:
- While a connection opens, a line "接続中…" (`.database-note`, `role="status"`) is under its row and the dot is orange; while its databases are read again, the line is "読み込み中…". While a database's tables are read, the line "読み込み中…" is under its row and in the work pane.
- A failure is its text in the danger color (`.database-note.danger`, `role="alert"`) under the row that failed: a connection that could not be opened (the dot is gray and nothing is under it), a database whose tables could not be read (the connection stays open; the text is also in the work pane). The row stays open, and a press on it reads again. A read that shows the connection lost closes the tree of the connection and the text is under the connection, with the dot gray.

The work pane (`#database-work`) has, for the database pressed last (also when its row is closed again), its name (`h3`) and the table list (`table.database-tables`; a table pressed in the tree draws the tabs of D-4 in its place, and the press on the database row draws the list again) with the columns 名前, 行数（概算）, サイズ and エンジン, a row for each table in the order of the tree. The row count is the estimate of `TABLE_ROWS` with thousands separators; the size is `DATA_LENGTH` plus `INDEX_LENGTH` as "512 B" or with one decimal in KB, MB, GB or TB (1024 each); the engine is `ENGINE`; Rust words the three (`format_rows`, `format_size`), and they are empty for a view. A database with no table draws its name only. Nothing is drawn when no database was pressed, or when the connection of it was closed.

Not tried against a real server by this code (only the pure parts and a local fake of the protocol, `cargo test`): the result of the two queries (the types of `information_schema` columns on MySQL 5.7, 8.0 and 8.4), which are cast in the SQL (`CAST … AS CHAR` and `AS UNSIGNED`) so that they decode as text and as unsigned numbers.

The unit tests (`cargo test`, `database/session.rs`, `database/mysql.rs` and `database.rs`) cover the rows with separators, the size in each unit (the edges 1023 B, 1.0 KB, a value that rounds to 1024 of a unit, TB), the size of data and index together and empty, the row of a table and of a view, that the database is a bound value, the reads and the close of a connection that is not open, which error is a lost session (a broken stream, the protocol) and which is not, the words of each, the saved login of an id (the profile and the password, none, a connection that is gone), and the words of a tunnel that cannot be closed. The E2E spec `database.e2e.ts` covers the open of a connection (the call and its argument, the databases in order, the dot), 接続中… and the orange dot while it opens, a press meanwhile, the error of a connection and the open again, the close and the open again of a connection (a read each time), the open of a database (the call and its arguments, the tables under it, the table list with its columns), 読み込み中… in the tree and in the pane, the error of a read of tables (in both, the connection kept, the open again), a connection shown lost, the close of a database and the pane that stays, a table pressed (its tabs, D-4), a database with no table, the menu with and without "切断", the disconnect (the call, the tree closed, the dot, the pane, the open again) and its failure, a save and a delete of an open connection, and a connection deleted while it opens.

## D-4 Records of a table

A press on a table row of the tree (D-3) draws the tabs of the table in the work pane (`#database-work`, which then has the class `database-table-mode`) in place of the table list: the title (`h3`, "{database}.{table}"), the tabs (`.database-tabs`, `role="tablist"`, a `.database-tab` with `role="tab"` and `aria-selected` for each; "レコード" and "構造" (D-5); "SQL" (D-6)) and the body of the selected tab. A press on the database row draws the table list again. A press on a table row selects "レコード".

The records tab reads one page with `database_records`, called with the `id` of the connection, the `database`, the `table` and the `page` (from 0). Every press on a table row reads the page 0 again, also on the table that is open, so what is shown is never older than the press. Rust reads ``SELECT * FROM `db`.`table` LIMIT ? OFFSET ?`` on the open session of D-3 (read only, 30 seconds like every query there): the names of the database and of the table are put in the SQL text between backticks with a backtick inside doubled (`records::quote_identifier`), and the limit and the offset are bound. A page is 100 rows (`PAGE_SIZE`). 101 rows are asked for, to know whether a next page exists (`hasMore`); the 101st is not sent. The offset is the page times 100. A connection that is not open, a read that fails and one that shows the stream broken are D-3's errors and words, and the last closes the connection as D-3 says.

Rust turns every value into text (`records::cell_of`), from the name of the column's type and the value in the binary protocol (the statement is a prepared one, because of the bound limit and offset); each cell is `{kind, text}`, and the screen draws the text and uses the kind only to style it:
- NULL is the text "NULL", kind `null`, in the quiet color and in italics. An empty string is an empty text, not NULL, and the text "NULL" is a text.
- An integer (TINYINT to BIGINT, signed or unsigned, BOOLEAN), a FLOAT, a DOUBLE, a DECIMAL (its own text as MySQL sent it), a YEAR (four digits) and a BIT (as the number of its bits) are kind `number`, right aligned.
- A DATE, a DATETIME, a TIMESTAMP and a TIME are kind `text` in MySQL's form: `2024-01-02`, `2024-01-02 03:04:05`, `-01:02:03`, with the days in the hours of a TIME (`838:59:59`) and the zero date as zeros. The fraction of a second is shown only when it is not zero, without its trailing zeros.
- A CHAR, a VARCHAR, a TEXT, an ENUM, a SET and a JSON are kind `text` (a JSON is the text MySQL sent). A text of more than 200 characters (`TEXT_MAX`, by characters, not bytes) is cut to 200 and ends with "…"; the rest is kept nowhere (not in Rust, not on the screen), so the full value of a long cell is not seen here. A text that is not valid UTF-8 is told as binary.
- A BINARY, a VARBINARY, a BLOB of any size and a GEOMETRY are kind `binary`: the text is the length only, "バイナリ 16 B" (the units of the table list of D-3), in the quiet color and in italics. Bytes that do not fit their type are told as binary too, and no value makes a read fail.

The answer is `{columns, rows, page, hasMore, estimate, summary}`. The estimate of `information_schema.TABLES` (`TABLE_ROWS`; none for a view) is read after the page on the same session for the page 0 and for a page that is asked with no estimate (a press on the table, a reload of the page 0, and a page read after a failed read dropped the one the screen held); `database_records` takes `estimate`, the one that the page shown holds (null when none is shown), and a later page answers it again when it is given, so that 前へ and 次へ cost one round trip each. `summary` is worded by Rust (`records::format_summary`): "{first}–{last} 行目" with thousands separators and, when the estimate is not below the last row shown, " / 約 {rows} 行"; a page with no row is "0 行". The columns are those of the rows, so a table with no row draws no header, and a table whose page has no row draws only the range.

The grid (`table.database-grid`, drawn by `gridNode` of `ts/database-grid.ts`, which the SQL tab uses for its result with the same cells) has the column names as its header (kept at the top while the page scrolls) and a row of cells (`.database-cell`, `data-kind`). A cell is one line, cut with an ellipsis at 320 px, and a text cell has its text as its `title`. The grid scrolls in the work pane and the footer stays under it.

Under the grid is the footer (`.database-pager`): the range (`.database-range`, `role="status"`, "読み込み中…" while a page is read) and three buttons (`.text-btn`): "前へ" (off on the page 0), "次へ" (off when `hasMore` is false and after an error) and "再読み込み" (reads the page that is shown again). All three are off while a page is read. 前へ and 次へ call `database_records` with the page before and after, and 再読み込み with the same page. While the next page is read the page shown stays; an error drops it and is shown in the danger color (`.database-note.danger`, `role="alert"`) in its place, with the buttons as above, so 再読み込み reads again. A read that ends after another press has replaced it is dropped. A table press, a database press or a disconnect leaves the records; they are held in memory for the last table only.

No control to add, edit or delete a row is anywhere on the screen, and a cell is not editable. The session is read only (D-2), so MySQL refuses a write all the same.

Not tried against a real server by this code (only the pure parts, `cargo test`): the binary forms of the types as a real MySQL 5.7, 8.0 and 8.4 sends them (the forms are those of the protocol documentation and of `sqlx-mysql`'s own decoding of rows), the name that sqlx gives each column type, and a BOOLEAN (a TINYINT of display width 1) that is UNSIGNED and holds more than 127, which is shown as a signed value.

The unit tests (`cargo test`, `database/records.rs` and `database/session.rs`) cover the quoting of a name (a backtick doubled, empty, with a dot or a space or a semicolon, Japanese) and that the statement binds only the limit and the offset, the cut of a text (the edge, characters against bytes), each type's conversion (the integers with their signs and edges, floats, year, bit, decimal, DATE, DATETIME and TIMESTAMP with and without a fraction, TIME with a sign, days and a fraction, the zero date, NULL, binary of several sizes and a text that is not UTF-8, JSON, ENUM and SET), that bytes that do not fit become binary, the summary (the range, thousands separators, a stale estimate left out, no row), and that a read of a connection that is not open fails with D-3's words. The E2E spec `database.e2e.ts` covers the press on a table (the call and its arguments, the tab, the title, the table list gone), the header and the cells drawn as Rust gave them (NULL, binary, a long text with its title and the cut by the width, a number at the right, the kinds), the range with the estimate, 次へ, 前へ and 再読み込み (the arguments of each call, the buttons off at the first page, at the last and while a page is read, the page kept meanwhile), the page 0 again on a second press of the table, the estimate that the page shown holds sent with every call, the grid kept while only the footer changes, a table with no row, the error of a read (shown, the page dropped, 再読み込み reads again), a connection shown lost, the press on the database that draws the table list again, and that nothing on the pane adds, edits or deletes.

## D-5 Structure of a table

The tab "構造" (`.database-tab`, `data-tab` "structure", after "レコード") of the work pane (D-4) shows the columns of the table that is pressed. A press on it only changes the tab: the table stays the same one (the title, `aria-pressed` of its row in the tree, and the records of D-4, which are kept as they are, so a press on "レコード" draws them again with no read). A press on the tab that is selected does nothing. A press on a table row of the tree selects "レコード" (D-4) and drops the structure.

The structure is read at every press of "構造", so what is shown is never older than the press, with `database_structure` called with the `id` of the connection, the `database` and the `table`. Rust reads, on the open session of D-3 (read only, 30 seconds like every query there), `information_schema.COLUMNS` with the schema and the table bound as values, never put in the SQL text, in the order of the table (`ORDINAL_POSITION`), and `information_schema.TABLES` with the same two values for the engine and the collation. Every column is cast in the SQL (`CAST … AS CHAR`), as D-3's. A connection that is not open, a read that fails and one that shows the stream broken are D-3's errors and words, and the last closes the connection as D-3 says.

The answer is `{columns, summary}`. A column is `{name, columnType, nullable, key, default, comment}`, worded by Rust (`structure::to_column`, `format_default`):
- `name` is `COLUMN_NAME`, `columnType` is `COLUMN_TYPE` as MySQL writes it (`bigint unsigned`, `varchar(255)`, `enum('a','b')`), `key` is `COLUMN_KEY` as it is (`PRI`, `UNI`, `MUL` or empty) and `comment` is `COLUMN_COMMENT`.
- `nullable` is true when `IS_NULLABLE` is `YES`.
- `default` is `COLUMN_DEFAULT` as text; an empty text is `''`. The server answers none both for a column with no default and for one whose default is NULL, so a column that may be NULL has "NULL" and one that may not has an empty text.

`summary` is worded by Rust (`structure::format_summary`): "{n} 列", then " / {engine}" and " / {character set}" when the table has them (a view has neither), such as "12 列 / InnoDB / utf8mb4". The character set is the collation of the table (`TABLE_COLLATION`) up to its first underscore (`charset_of`).

The screen draws the columns as a grid (`table.database-grid.database-structure`, `gridNode` of `ts/database-grid.ts`, the same as D-4's) with the header 名前, 型, NULL, キー, 既定値 and 注釈 and a row for each column, "YES" or "NO" for NULL, one line in each cell, cut with an ellipsis at 320 px, with the text of a cell as its `title`, and, under the grid, the footer (`.database-pager`) with the summary (`.database-range`, `role="status"`) and no button. While it is read the footer says "読み込み中…" and the grid is not drawn; an error is its text in the danger color (`.database-note.danger`, `role="alert"`) in place of the grid, with the connection kept (a press on "構造" again reads it again); a table with no column draws only the summary. A read that ends after another press has replaced it is dropped. The structure is held in memory for the last table only.

Indexes, foreign keys and triggers are not shown, and nothing on the tab is editable.

Not tried against a real server by this code (only the pure parts, `cargo test`): the result of the two queries on MySQL 5.7, 8.0 and 8.4.

The unit tests (`cargo test`, `database/structure.rs` and `database/session.rs`) cover that the schema and the table are bound values, that no table of indexes, keys or triggers is read, the default (a value, empty text, NULL for a column that may be NULL and none for one that may not), the character set of a collation, the summary (with the engine and the character set, without them, a view), the row of a column (the key, NULL, the default and the comment), and that a read of a connection that is not open fails with D-3's words. The E2E spec `database.e2e.ts` covers the three tabs and the selected one, the call of `database_structure` (its arguments, only on a press of 構造, again at every press, not on the tab that is selected), the columns and the summary as Rust gave them, the cut comment with its title, that the table (the title, the pressed row, the records and their calls) stays when the tab changes, that a press on a table selects "レコード", 読み込み中…, a table with no column, the error of a read (shown, the connection kept, the read again), a connection shown lost, and that the tab has no control and no input.

## D-6 SQL

The tab "SQL" (`.database-tab`, `data-tab` "sql", after "構造") of the work pane (D-4) runs a statement the user types and shows its result. A press on it only changes the tab: it calls nothing, and the records and the structure are kept as they are.

The body has, from the top, the field (`textarea.database-sql-text`, `aria-label` "SQL", 8 rows, resizable in height, in the monospace font; no placeholder and no text that explains it), the button "実行" (`.text-btn`, `data-key` "run", in a row of its own under the field, at the right), the result (the grid of D-4, `gridNode` of `ts/database-grid.ts`, in `.database-records-scroll`, so it scrolls and the footer stays) and the footer (`.database-pager` with `.database-range`, `role="status"`). Nothing is saved, formatted or listed: there is no history, no saved statement and no formatter, and no control but the tabs and "実行".

The connection and the database are those the tree has selected: the connection and the database of the table that is pressed (D-3). "実行" calls `database_sql` with the `id` of the connection, the `database` and the `sql` as typed (an empty field too: Rust refuses it with 「SQL を入力してください」, shown as an error). The field and the result are held in memory for the connection and the database that were selected last: they stay when the tab changes and when another table of the same database is pressed, and they are dropped when the field is used in another connection or database, and when the connection is shown lost. While a statement runs, the footer says "実行中…", "実行" is off, and the old result stays; a result that comes is drawn in its place, and an error drops the old result and is shown in the danger color (`.database-note.danger`, `role="alert"`) in place of the grid, with the text in the field kept and the connection kept (a press on "実行" runs it again). A run that shows the stream broken closes the connection as D-3 says, and the tree closes and says why. Pressing keys in the field draws nothing; the pane is made again by other changes and keeps the caret.

Rust (`database/sql.rs`, `Sessions::sql` of `database/session.rs`, the command `database_sql`) runs one statement:
- The text is passed to MySQL as it is, as a prepared statement (so its rows come in the binary protocol that D-4's `cells_of` reads, and it is not kept in sqlx's cache of statements). Only the whitespace around it and the semicolons at its end are cut (`sql::statement`), because a prepared statement is one statement and a `;` ends one by hand. Nothing else is rewritten, quoted or wrapped. The session is read only (D-2), so MySQL refuses a write itself.
- One statement is run at a time. A text with a second statement in it is a syntax error of MySQL (1064), and a statement that MySQL does not take as a prepared one (1295) is told too. A statement that gives no row gives no column and "0 行".
- The database is chosen before the text by a `USE` of its own, run as text (the protocol of a prepared statement does not take it), with the name quoted by `records::quote_identifier`. It is never put into the text of the user. Before the statement the run sends, in one round trip (the statements are run as text, one after the other, and stop at the first that fails), `SET SESSION TRANSACTION READ ONLY`, `SET SESSION max_execution_time = 30000, sql_select_limit = 1001` and the `USE`. After the statement, whatever it answered (a `USE` that failed too), it sends `SET SESSION TRANSACTION READ ONLY` and `SET SESSION max_execution_time = DEFAULT, sql_select_limit = DEFAULT`, so that the reads of the tree and of the tabs are as they were. The read only is sent again each time because the text of the user may have set the session to read write (`SET SESSION TRANSACTION READ WRITE`, `SET SESSION transaction_read_only = 0`), which would let the next run write; MySQL itself must keep refusing a write. The whole run is in one hold of the session, so no other read comes between its statements.
- The rows are limited to 1,000 (`sql::ROWS_MAX`). The result is read as a stream that is stopped after the 1,001st row: that one is not kept and the rows past it are never held, so the memory is that of 1,000 rows of cells (a text is cut to 200 characters and a binary value is its length, as D-4's). `sql_select_limit` is 1,001, so MySQL itself ends a SELECT with no LIMIT of its own one row past the limit, and nothing is left unread behind it. A SELECT with its own LIMIT above 1,001 sends more rows than are read: they are not held, and the next call on the session passes over them (sqlx does that before its next statement, inside that call's own time). A result that was cut shows 「先頭の 1,000 行だけを表示しています（残りは読み込んでいません） / {time}」 in the footer; the grid has the 1,000 rows.
- The time is limited twice. MySQL stops a SELECT that runs for 30 seconds (`max_execution_time`), with the error 3024, worded 「実行が 30 秒を超えたため、MySQL が止めました (3024): …」; the session stays and no query is left on the server. What `max_execution_time` does not stop (a statement that is not a SELECT, or a server that does not answer) is stopped by the app after 35 seconds (`sql::CLIENT_LIMIT`, the whole run: the preface, the statement and the restore): the connection and its tunnel are closed (as D-3's time out), the error is 「実行が時間内に終わらなかったため、MySQL との接続を閉じました。もう一度開いてください」, and the tree closes and says why. `KILL QUERY` is not used: it needs a second connection, and so the password kept in memory for the life of the session, which D-2 avoids.
- The footer under the grid is `sql::format_summary`: 「{rows} 行 / {time}」 with thousands separators, the time of the statement alone (from its sending to the last row read) as 「12 ms」 and, from a second on, 「1.25 秒」 (the hundredths cut). A statement with no row is 「0 行 / {time}」, and a SELECT with no row has no header, as D-4's page has none.
- An error that MySQL answered is worded in Japanese by `sql::server_message` as 「{words} ({number}): {the server's message, cut}」, and leaves the session as it was. The words: 1792 and 1290, the refusal of a write on the read only session or server (「この接続は読み取り専用です。データを書き換える文は実行できません」, 「MySQL サーバーが読み取り専用のため、この文は実行できません」); 1044, 1142, 1143 and 1227, no right (「このユーザーには、この操作の権限がありません」); 1064, syntax (「SQL の文法が正しくありません。1 回に実行できる文は 1 つです」); 1295 (「この種類の文は実行できません」); 1049, 1146 and 1054, no database, table or column; 1317, interrupted; 3024, the time; and 「MySQL がエラーを返しました」 for any other. A broken stream, TLS or the protocol is D-3's 「MySQL との接続が切れました。もう一度開いてください: …」 and closes the connection, and a connection that is not open is D-3's 「接続が開いていません。もう一度開いてください」.

Not tried against a real server by this code (only the pure parts and the stream, `cargo test`): the whole run on MySQL 5.7, 8.0 and 8.4: that `max_execution_time` and `sql_select_limit` are settable there and stop a SELECT as written, that `USE` as text is taken by the session, that the refusal of an `INSERT` is the error 1792, and that MySQL ends a statement whose connection was closed.

The unit tests (`cargo test`, `database/sql.rs` and `database/session.rs`) cover the cut of the text (the whitespace and the semicolons at its ends, nothing inside it, nothing to run), the statements that set the session read only again and set and put back the limits, in this order and with the name quoted, the `USE` with a quoted name, the time in milliseconds and in seconds, the footer (the rows, the time, a cut result), the words of each error of the server (the refusal of a write first, a long message cut) and that an error that is not the server's is worded as every query's, and, on a stream, that at most 1,000 rows are kept and only one more is read, that a result of exactly the limit is not cut and that an error ends the read. The E2E spec `database.e2e.ts` covers the tab and its body (the field and the button, no placeholder, nothing called when the tab is pressed), the call of `database_sql` (the id, the database and the text as typed), the grid and the footer as Rust gave them (the kinds of the cells), 実行中… with the button off and the old result kept, a cut result's footer with its 1,000 rows, a statement with no row, the error (in the danger color, the old result dropped, the text and the connection kept, the run again), a connection shown lost, the text and the result kept when the tab changes and when another table of the database is pressed, the database of the table that is pressed with an empty field for a database not used, an empty field sent as it is, and that the tab has no other control and one input.
