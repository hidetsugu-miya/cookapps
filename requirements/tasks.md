# Tasks requirements

## T-1 Todoist

Work with Todoist tasks in per-project and today lists and a detail view (description, subtasks, the direct parent of a subtask as a chip above its name that opens the parent when pressed and has a round checkbox at its left that completes the parent, which takes the open task out of the list too so the detail falls back to the list, and a three-dot menu to copy the task link or the description, or delete it; the description can also be copied by selecting its text, which does not start editing, or with an icon shown on hover), and create a task from a mail. Authentication is a personal API token, and the settings screen shows the connection and unlinks it The header of the detail has the icon button "Orca に渡す" (A-9).

## T-2 Nest and unnest tasks

In the task list (a project's list and the flat "today" list), drag the grip at the left end of a row (pointer events) onto another task's row to make the dragged task, with its own subtasks, the last subtask of that task (`todoist_move_under`, which sends `parent_id` to `POST /tasks/{id}/move`). The row under the pointer is marked while it can take the drop; the task itself, a task below it and its current parent cannot. The parent opens so the moved row shows. A subtask is made a top-level task again with the "親タスクから外す" button of its row, or by dropping it on the project it is in in the side list (`todoist_move` with its current project ID, which Todoist makes the last top-level task of that project). The screen changes first and a failure is undone by the reload, as for the other task changes; the depth limit is not checked on the screen, Todoist's error is shown

## T-3 Comments

In the task detail, after the subtask adder, a section "コメント N" (with a fold chevron) lists the task's Todoist comments (`todoist_comments`, oldest first, deleted ones left out). Each row has an avatar with the author's initials, the name, the date (written as the due dates are), the body as Markdown (sanitized as the description is, and a table in either has ruled cells; left out when it is only the file's name) and, for a file, a card (document icon and file name) that is a link, opened in the default browser, only for an `https://` address (its `title` is the host). The author's name comes from `GET /user`, and from the project's collaborators only when someone else wrote a comment; a name neither gives is "不明". The comments are fetched when the detail of a task is opened (another task, or the detail was not showing) and again when the Todo screen is shown with a task's detail still open, not on the redraws of the 10-second reload, and are kept in memory only (shown while a new fetch is on its way); a failed fetch shows a message in the section. At the bottom, a rounded field "コメント" (one line high, growing to 6 lines; Enter is a line break, and Cmd+Enter (Ctrl+Enter off macOS) or the send button sends) has a clip icon that picks one file (a hidden `<input type="file">`; another pick replaces it, a chip with ✕ shows it, and a file over 100 MB is refused on the screen). Sending uploads the file first (`todoist_upload`: the raw bytes through Tauri's raw IPC with the name percent-encoded in the `x-file-name` header, sent to `POST /uploads` as multipart with a 300-second limit) and then adds the comment (`todoist_add_comment`, `POST /comments`, with the upload's answer as the `attachment`; blank text with a file sends the file's name, and text over 15,000 characters is refused). The text and the file are kept per task in memory until sent, and a failure shows the error and keeps them (a file that was uploaded is not uploaded again when the send is tried again with the same file). Nothing is sent to Todoist until the user presses send

## T-4 Labels

In the task detail's side pane, after the date, a field "ラベル" has a + button (`aria-label` "ラベルを追加") at the right of its header, and under the header the task's labels as chips (a dot in the label's color, the name, and an × button, `aria-label` "ラベル「{name}」を外す", that takes the label off and sends `todoist_update` with the labels that remain, an empty list when it was the last; nothing is drawn under the header while there are none). The + opens a popover (`.menu`, one at a time, in `document.body`) with a field (placeholder "ラベルを検索または作成") over the labels narrowed by the typed text (case-insensitive substring), each with its dot and `aria-current` when it is on the task, in a list that scrolls when long. Pressing a row toggles that label on the task and closes the popover. When the trimmed text is no label's exact name (case-insensitive), a last row "「{text}」を作成" makes it (`todoist_create_label`: Rust trims and checks the name, which must not be empty or longer than 128 characters (a refusal is a Japanese message), `POST /labels` with `{name}`, then updates the task with its whole list of labels, the new name in it) and puts it on the task. Enter does what the row of an exact match does, else what the create row does. The screen changes first and a failure is undone by the reload, as for the other task changes; a redraw of the detail does not close the popover or touch what was typed in it. The labels to pick from (`Todo.labels`) are the personal labels (the Sync API's `labels`, by `item_order`, in the color of their name) and then the names found on open tasks that are not among them (shared labels are not in the sync answer, only in a task's `labels`), by name, in the gray of `charcoal`; a cache written before labels existed still reads. A label's name comes from Todoist and may be a collaborator's, so it is drawn as text, never as markup. Not in the list rows, the add field or the Slack card, and not renamed, deleted or recolored here

## T-5 Count by due moment

The number on the sidebar's Todo button and the Dock badge count an open task only once its due moment has come: its due date and time in local time, 00:00 of the date when it has no time, so a task due today at 12:00 is not counted at 08:49 and is counted from 12:00 (to the minute). A task with no due date is never counted. The button's `aria-label` says "期限到来". The "今日" list, its rows and its count in the project pane keep today's meaning (overdue and today). The screen counts again from the tasks last given every 10 seconds with no fetch, also while the window is hidden or a field is typed in. The Dock badge is mail unread plus that count, and the screen also sends `set_badge` the due moments (epoch milliseconds) of the open tasks still ahead (`upcoming`); it skips the call only when neither the sum nor the moments changed. Rust keeps the two in managed state and a task started in `setup` checks the wall clock about every 15 seconds (the clock is read each time, so a sleeping machine notices at the next check), adding the moments that have come to the count (`badge_total`), and sets the badge of the window `main` only when the value changed, so the Dock follows the time while the WebView's timers are suspended
