# Tasks requirements

## T-1 Todoist

Work with Todoist tasks in per-project and today lists and a detail view (description, subtasks, the direct parent of a subtask as a chip above its name that opens the parent when pressed and has a round checkbox at its left that completes the parent, which takes the open task out of the list too so the detail falls back to the list, and a three-dot menu to copy the task link or the description, or delete it; the description can also be copied by selecting its text, which does not start editing, or with an icon shown on hover; a description longer than 10 lines as drawn, a wrapped line counting as one each, is folded at the 10th line, which fades downward, with a text button under it, "… 続きを表示（残り n 行）", that shows the whole text and then reads "折りたたむ", while a press on the text itself still starts editing, and a description of 10 lines or fewer is shown in full with no button), and create a task from a mail. Authentication is a personal API token, and the settings screen shows the connection and unlinks it The header of the detail has the icon button "Orca に渡す" (A-9). The detail has two columns, the body (description, subtasks, comments) and the side pane of 220px (project, date, labels); the body column keeps at least 320px, and where the width left to the detail (the window, the project list and the right pane of T-7 taking their share) is under 556px (320px, the 16px gap and 220px), the side pane goes under the body, with the body first, at the same 220px width and the same look, by width alone.

The row of the task list (`li.task.tall`; a project's list and the flat "today" list) has three lines, so that it reads at half the screen (a list about 460px wide). The first line holds the round checkbox, the mail icon where the task links a mail of a connected account, and the name (cut with an ellipsis where it does not fit). The second line (`.desc`) is the first line of the description that is not empty, in the muted color, cut with an ellipsis, and underlined (`.desc.url`) when it begins with `http://` or `https://` (it is not a link: a press on the row opens the task); a task with an empty description has no second line. The third line (`.meta`) holds, at the left on one line (what does not fit is hidden), the due moment (`.due`, the accent color, red for an overdue task, with the date icon; none for a task with no due date), the labels (`.label`, the label icon and the name), the subtask count (`.subcount`, "done/total") and, in the "today" list, the parent of a subtask (`.parent`); the project (`.ptag`, a dot in its color and the name) is at the right end, only in the "today" list. A task with nothing for the third line has none. The comment count is not drawn (the task has none). The row buttons (`.row-actions`) show over the top right of the row on hover and focus and leave the third line alone; the grip, the mark of a drop, the strike-through of a done task, the edit of the name and the indent of subtasks are as before. Rows are told apart by a thin line.

## T-2 Nest and unnest tasks

In the task list (a project's list and the flat "today" list), drag the grip at the left end of a row (pointer events) onto another task's row to make the dragged task, with its own subtasks, the last subtask of that task (`todoist_move_under`, which sends `parent_id` to `POST /tasks/{id}/move`). The row under the pointer is marked while it can take the drop; the task itself, a task below it and its current parent cannot. The parent opens so the moved row shows. A subtask is made a top-level task again with the "親タスクから外す" button of its row, or by dropping it on the project it is in in the side list (`todoist_move` with its current project ID, which Todoist makes the last top-level task of that project). The screen changes first and a failure is undone by the reload, as for the other task changes; the depth limit is not checked on the screen, Todoist's error is shown. The subtask rows of a task's detail move the same way (T-6)

## T-3 Comments

In the task detail, after the subtask adder, a section "コメント N" (with a fold chevron) lists the task's Todoist comments (`todoist_comments`, oldest first, deleted ones left out). Each row has an avatar with the author's initials, the name, the date (written as the due dates are), the body as Markdown (sanitized as the description is, and a table in either has ruled cells; left out when it is only the file's name) and, for a file, a card (document icon and file name) that is a link, opened in the default browser, only for an `https://` address (its `title` is the host). The author's name comes from `GET /user`, and from the project's collaborators only when someone else wrote a comment; a name neither gives is "不明". The comments are fetched when the detail of a task is opened (another task, or the detail was not showing) and again when the Todo screen is shown with a task's detail still open, not on the redraws of the 10-second reload, and are kept in memory only (shown while a new fetch is on its way); a failed fetch shows a message in the section. At the bottom, a rounded field "コメント" (one line high, growing to 6 lines; Enter is a line break, and Cmd+Enter (Ctrl+Enter off macOS) or the send button sends) has a clip icon that picks one file (a hidden `<input type="file">`; another pick replaces it, a chip with ✕ shows it, and a file over 100 MB is refused on the screen). Sending uploads the file first (`todoist_upload`: the raw bytes through Tauri's raw IPC with the name percent-encoded in the `x-file-name` header, sent to `POST /uploads` as multipart with a 300-second limit) and then adds the comment (`todoist_add_comment`, `POST /comments`, with the upload's answer as the `attachment`; blank text with a file sends the file's name, and text over 15,000 characters is refused). The text and the file are kept per task in memory until sent, and a failure shows the error and keeps them (a file that was uploaded is not uploaded again when the send is tried again with the same file). Nothing is sent to Todoist until the user presses send

## T-4 Labels

In the task detail's side pane, after the date, a field "ラベル" has a + button (`aria-label` "ラベルを追加") at the right of its header, and under the header the task's labels as chips (a dot in the label's color, the name, and an × button, `aria-label` "ラベル「{name}」を外す", that takes the label off and sends `todoist_update` with the labels that remain, an empty list when it was the last; nothing is drawn under the header while there are none). The + opens a popover (`.menu`, one at a time, in `document.body`) with a field (placeholder "ラベルを検索または作成") over the labels narrowed by the typed text (case-insensitive substring), each with its dot and `aria-current` when it is on the task, in a list that scrolls when long. Pressing a row toggles that label on the task and closes the popover. When the trimmed text is no label's exact name (case-insensitive), a last row "「{text}」を作成" makes it (`todoist_create_label`: Rust trims and checks the name, which must not be empty or longer than 128 characters (a refusal is a Japanese message), `POST /labels` with `{name}`, then updates the task with its whole list of labels, the new name in it) and puts it on the task. Enter does what the row of an exact match does, else what the create row does. The screen changes first and a failure is undone by the reload, as for the other task changes; a redraw of the detail does not close the popover or touch what was typed in it. The labels to pick from (`Todo.labels`) are the personal labels (the Sync API's `labels`, by `item_order`, in the color of their name) and then the names found on open tasks that are not among them (shared labels are not in the sync answer, only in a task's `labels`), by name, in the gray of `charcoal`; a cache written before labels existed still reads. A label's name comes from Todoist and may be a collaborator's, so it is drawn as text, never as markup. Not in the list rows, the add field or the Slack card, and not renamed, deleted or recolored here

## T-5 Count by due moment

The number on the sidebar's Todo button and the Dock badge count an open task only once its due moment has come: its due date and time in local time, 00:00 of the date when it has no time (Rust works it out into `TaskItem.dueAt`, in epoch milliseconds, `null` with no due date, and sets it again when it reads the cache; a time the clock skips is read an hour later; the screen only reads it), so a task due today at 12:00 is not counted at 08:49 and is counted from 12:00 (to the minute). A task with no due date is never counted. The button's `aria-label` says "期限到来". The "今日" list, its rows and its count in the project pane keep today's meaning (overdue and today). The screen counts again from the tasks last given every 10 seconds with no fetch, also while the window is hidden or a field is typed in. The Dock badge is mail unread plus that count, and the screen also sends `set_badge` the due moments (epoch milliseconds) of the open tasks still ahead (`upcoming`); it skips the call only when neither the sum nor the moments changed. Rust keeps the two in managed state and a task started in `setup` checks the wall clock about every 15 seconds (the clock is read each time, so a sleeping machine notices at the next check), adding the moments that have come to the count (`badge_total`), and sets the badge of the window `main` only when the value changed, so the Dock follows the time while the WebView's timers are suspended. When the due date of a task is changed from its detail, the screen puts on the task at once, before `todoist_update` answers, the due, bucket and `dueAt` that Rust gives for the text (`todoist_picked_due`: a day picked in the calendar, `YYYY-MM-DD` with ` HH:MM` for a time, or an empty text for no due date); for other text, which Todoist reads, the task stays as it is until the reload

## T-6 Move a subtask from the detail

In the detail of a task, each subtask row that is not done and has a row among the tasks moves as a row of the task list does (T-2). On hover the row shows the grip at its left and, at its right, the buttons "プロジェクトを移動" and "親タスクから外す". "プロジェクトを移動" opens the menu of projects of the list's row (`todoist_move`). "親タスクから外す" makes the subtask a top-level task of its project (`todoist_move` with its current project ID). The grip is dragged (pointer events) onto a project in the side list (`todoist_move`; the project the subtask is in too, which makes it stand alone) or onto another subtask row of the same detail, which makes it the last subtask of that task (`todoist_move_under`). A row that cannot take the drop is not marked, by the rule of T-2 (the task itself, a task below it and its current parent). The screen changes first and a failure is undone by the reload, as for the other task changes. A done subtask has no grip or buttons, and the order of subtasks under the same parent is not changed here. No command and no communication is added

## T-7 Claude pane on the Todo screen

The right side. The Todo screen has a right side (`#todo-side`) that is always open while the task list or an open task is shown, and is hidden while the token form or the page of a draft (S-2) is shown (it comes back after them). It has two rows and, under them, the pane chosen. The first row (`#todo-tools`, over the header of the tasks, a band to drag the window by) holds only two icon buttons, at its right end and not as tabs: `#todo-tool-claude` (`.icon-btn`, `aria-label` "Claude に相談", `aria-pressed`, the ✳ mark in `--claude`) and `#todo-tool-orca` (`.icon-btn`, `aria-label` "Orca に渡す", `aria-pressed`, the Orca icon of the sidebar). The row and the header of the tasks (`#todo-body > header`) are tinted the same: the background `--soft` and a 2px line of `--accent` under it, and both are as high as every header (`--header-h`, 40px at the default font and stretching to fit a larger one, A-23) and have the buttons of every header (24px, with 15px icons), so that the two lines meet; the icon pressed is filled with `--accent`. The header of the tasks keeps only the controls of the Todo itself: the list button, the back button, the heading, and "その他" (A-9's old buttons for Claude and Orca, the ✳ of S-3 and the close icon of this pane are gone). The second row is the heading and the controls of the pane chosen, 48px high: for Claude's pane `.chat-head` (the mark, the title "Claude" and "クリア"), for the Orca pane (A-9) its title row "Orca に渡す" with no close icon. Under it is the content of the pane.

Which pane. Claude's pane `#todo-claude` (`aside.chat-pane`, `aria-label` "Claude") is shown at first, and whenever the Orca pane is not. The Orca pane `#todo-handoff` (A-9) is tied to the open task, so its icon is disabled unless a task is open (the detail is shown); pressing it shows the Orca pane in place of Claude's, and pressing Claude's icon (which also puts the focus in the request field) shows Claude's again. The two panes are never shown together. Leaving the task for the list, a draft or the token form hides the Orca pane, and Claude's comes back (the icon of Orca waits for a task again); a task that has a session shows its Orca pane by itself, with the icon of Orca pressed. Nothing closes the right side, so the choice is not saved and no file is added. The two panes share the divider `#todo-split` (its `aria-label` is "Claude の幅" while Claude's pane is shown and "Orca の幅" for the pane of A-9) and the width of the side: 30% of the screen at first, its least (`aria-valuenow` 30), widened or narrowed by the divider between 30% and 45% of the screen (`aria-valuemin` 30, `aria-valuemax` 45; the CSS holds the same range, with no least width in pixels), held in memory. A read of Todoist in the background neither changes the choice nor redraws the pane.

The pane. Its head (the second row) has the Claude mark and the title "Claude", and the clear button `#todo-claude-clear` ("クリア", two presses as in S-7), and no close icon. Under it are the log `#todo-claude-log`, the note `#todo-claude-chat-note` (shown while Claude cannot be used, A-4) and the request field `#todo-claude-input` (`aria-label` "Claude への依頼", one line high and growing with its text, no placeholder) in the frame that `ts/composer.ts` makes for every Claude request field (S-7 and S-18 have the same part; the form is made by TS, not written in `index.html`), with in the frame one row under the field: the two selects of the model and effort of `todoChat` (`#todo-claude-model`, the same values as A-2) at the left and the round send button `#todo-claude-send` (`aria-label` "送信") at the right. The conversation is that of `ts/claude-chat.ts`, as S-7 and S-18 have it: Enter is a line break and Cmd+Enter (Ctrl+Enter off macOS) sends; the owner's request is a bubble at the right; while the answer is awaited the log says "Claude が考えています…" and the field and the send button stop; a failure is a line in the log, "送れませんでした: {message}", and is not sent as part of the next request; while Claude cannot be used the field and the send button are off (as in S-7). Pressing the send button calls `claude_chat_todo` (A-2) with the conversation so far (as their text; Rust gives Claude the last 20 turns of it) and the request. Rust adds today's date and the Todoist projects of the last load.

The answer. Claude's reply is drawn as text, and each task of the answer is a card (`.chat-task`) under it, one under another. The card has three lines. The first is the name, a field (`.chat-task-name`, `aria-label` "タスクの名前") the owner can edit. The second is two chips (`.review-chip`, buttons): the date (`.chat-task-due`, the calendar icon and the date as the task list writes it when the text is `YYYY-MM-DD` with ` HH:MM`, else the text as it is, "期限なし" for none) and the project (`.chat-task-project`, its color dot and its name, "インボックス" for the inbox, which is also where a task with no project goes). The chips are always both drawn. The date chip opens the popover of the task detail's date (the calendar and the text field, `openDueEditor`; the card keeps the text typed or the day picked, with no check in the screen), and the project chip the menu of projects of the task detail (`openProjectPicker`). The third line, at the right, has "却下" (`.text-btn`) and "追加" (`.text-btn.primary`, `.chat-task-add`). Nothing is written in Todoist until "追加" is pressed.

"追加" calls `todoist_add_task` once with the values on the card: `content` the name, `due` the date text (`null` when empty) and `projectId` the project picked (`null` while none was picked, the inbox). Rust checks them (the name must not be empty or too long, the date must be `YYYY-MM-DD` or `YYYY-MM-DD HH:MM`, the project must be one of the last load), so the screen decides nothing about the date or the project. An empty name does not call the command and puts the focus on the name. While the call is on its way the card's name, chips, "却下" and "追加" are off and "追加" shows a spinner and "追加中", so the same card creates one task, and the other cards stay free. When it succeeds the card becomes one line, `.chat-task-done`, "✓ {name} を追加しました", and the Todo list is read again as after any other change of a task (`todoCall`: the read is scheduled shortly after the last change). When it fails, the refusal is shown on the card as "追加できませんでした: {message}" (`.review-err`, not the error line of the screen), and the card stays with the values as the owner left them; the next press tries again. When the answer is `null` (Todoist needs a token) the card stays as it was with no message, and the read that follows shows the token form, as for Quick Add and the page of S-2. "却下" calls no command and takes the card off; when every card of an answer is gone the reply stays and the box of the cards takes no room.

Asking again. A card's values (the edited name, date and project, and whether it is added or rejected) are held in memory with the conversation: a read of Todoist in the background, going between the list and a task, and the Orca pane being shown in its place neither redraw them away nor reset them, and "クリア" drops them with the conversation. The history sent with the next request (`claude_chat_todo`; Rust gives Claude the last 20 turns of it) carries, after the text of an assistant turn, one line for each of its cards that was not rejected, as the card holds it now: `- {name}（日付: {date, なし for none}、プロジェクト: {project name}）`, the date being the card's text as it is (`YYYY-MM-DD` with ` HH:MM`, not the label of the chip), so that a request such as "make the earlier proposals shorter" is understood. The shape of the turn (`role` and `text`) is not changed and Rust cuts each turn's length: a turn of the user at 2,000 characters, and a turn of the assistant at 2,000 characters plus the room of the lines of 50 cards with the longest names, so that no card falls off the end (the other conversations cut an assistant turn at 2,000 characters). The conversation is held in memory, one for the whole screen, and is kept while the Orca pane is shown in its place and while the screen is left; it is in no file, and goes when the app ends or at "クリア". Claude writes nothing in Todoist: the only commands the pane calls are `claude_chat_todo` and, for "追加", `todoist_add_task`. No saved file is added. What Anthropic is sent is that of `claude_chat_todo` (A-2) with the lines above. The add field above the list (Quick Add and the Slack summary of S-2) is as it was, and shows no placeholder.
