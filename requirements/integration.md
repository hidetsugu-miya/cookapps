# Integration requirements

## A-1 Claude integration

A local MCP server (`cookapps-mcp`, stdio) lets Claude list, read, archive, mark read and trash inbox threads, and list events

## A-2 Claude model and effort

The Claude tab of the settings screen has a card "モデルと effort" (shown whether or not Claude can be used; the columns are headed "用途", "モデル" and "effort", and a note says the next call uses the choice and the default is Sonnet and medium, Sonnet and high for the Slack thread conversation, so the options carry no "(デフォルト)") with, for each of five purposes, a name, where it is used, and two narrow selects that choose its model and its effort: the Slack summary (S-2, "Slack の要約", used when a Todo is made from a Slack message), the mail summary (M-8, "メールの要約", the AI summary of the mail detail), the prompt conversation (S-3, "プロンプトの会話", editing the Todo summary prompt with Claude) the Slack text proofreading (S-4, "Slack に貼る文章の校正", the "Claude と校正" pane) and the Slack thread conversation (S-7, "Slack のスレッドの相談", the Claude pane of the thread detail). Each `claude -p` call uses the model and effort of its own purpose. The model is Haiku, Sonnet (the default) or Opus (Fable is not offered; a saved `"fable"` is an invalid value and gives Sonnet). The effort is low, medium (the default), high, xhigh or max, and `--effort` is always passed. Changing the model also switches the effort to the one the documentation recommends for it, saved in the same write: Haiku medium, Sonnet high, Opus medium (Rust `recommended_effort`, from https://platform.claude.com/docs/en/build-with-claude/effort, "Recommended effort levels"); the screen sends the model alone, and `claude_model_settings_save` takes an optional `effort` that defaults to the recommended one, while changing the effort sends both. The first default (nothing saved) stays Sonnet and medium, and Sonnet and high for `slackReply`. An effort select is colored by its value (`data-effort`, variables in `:root`): low gray, medium green, high yellow, xhigh orange, max red, following a change, a save and a failed save; the settings card colors the background and the text, and the frameless select of S-3 the text only. A change is saved at once, for that purpose only, in `claude-settings.json` in the app config directory (an object keyed by `slackSummary`, `mailSummary`, `promptChat`, `proofread` and `slackReply`, each `{model, effort}`; one save reads the file again, changes one purpose and writes all five through a temporary file and a rename), and the next call uses it. Rust checks the purpose, the model and the effort against their lists when saving (a refusal is a Japanese message), and a missing file, an unreadable file or an invalid value gives the default for that purpose, so only a listed value reaches `--model` and `--effort`. A file in the old form, one `{model, effort}` pair for every call, gives that pair to all five purposes until a purpose is saved, and a file without `slackReply` gives that purpose its default. From high up (high, xhigh, max) a call may run 300 seconds (`--effort max` took 61 seconds on a small input); below that it is 60 seconds for the summaries and 120 seconds for the prompt conversation and the proofreading. The `?` hint of the Claude card says that each of the five calls has its own model and effort. The thread detail of S-6 shows the selects of `slackReply` under its request field, as S-3 shows those of the prompt conversation. The screen of S-3 shows the selects of the prompt conversation too

## A-4 Claude connection

The `claude -p` calls of M-8, S-2, S-3, S-4 and S-7 go through the Claude Code CLI, which signs in either with the Claude subscription (the default) or with an Anthropic API key. The first card of the Claude tab ("Claude", with ↻ and `?`) has two rows with radios, "サブスクリプション" (email, plan, Claude Code version and state: ログイン中, 未ログイン with the `claude auth login` guidance, 未導入, 確認できません) and "API キー" (the workspace ID when Anthropic says it, the note that every call is billed, the state 未登録, 確認済み, 確認できません or 使えません, "貼り直す" and the disconnect button), so the state of the one not in use shows too. Pressing the radio of the API key row with no key stored, or with a key Anthropic refuses, only opens the key field ("確認して保存"); nothing is switched or logged out. If the keychain cannot be read, only the key row says 確認できません with the error; if asking for the connection itself fails, the card shows one failed row with the error and no radio, so nothing can be pressed, and Claude is in its failed state. At start only `claude_status` is called (so a start without the settings never asks Anthropic about a key); `claude_connection`, which answers the three parts of the card and the usable state `claude` with each state read once, is called when the Claude tab is first shown, by ↻ and after a change of the connection, and only the latest answer of the reads is used. While a change is on its way ↻ and the radios wait, and so does the button of the key field (also while the states are being read); sending the field while a change is on its way does nothing and does not empty it. A change of the connection redraws the connection card only, so the model selects and the prompt row keep their place and focus. Only the radio of a row switches the method (the radios are not grouped by name, so the arrow keys move none of them, and are disabled while a change is on its way); clicking or double-clicking the text of a row does nothing. The key is never shown, and the field is emptied as soon as it is read. The method is saved in `claude-auth.json` in the app config directory (`{"method":"subscription"|"apiKey"}`, written through a temporary file and a rename; a missing file, an unreadable one or an invalid value gives the subscription), and the key is in the OS keychain (service `jp.mysis.cookapps.claude`). Rust does not call the API for the work: the `claude -p` child process gets the key as `ANTHROPIC_API_KEY`, and `ANTHROPIC_AUTH_TOKEN` is taken out (the CLI prefers it) together with `ANTHROPIC_BASE_URL`, `CLAUDE_CODE_USE_BEDROCK`, `CLAUDE_CODE_USE_VERTEX` and `CLAUDE_CODE_USE_FOUNDRY` (they would send the key to another host or provider than the one it was checked against), while the subscription takes `ANTHROPIC_API_KEY`, `ANTHROPIC_AUTH_TOKEN` and `CLAUDE_CODE_OAUTH_TOKEN` out. The key is in no command-line argument, log line or error text. `claude auth status` answers `loggedIn: true` for a made-up key (measured), so it does not check a key. A pasted key is trimmed, must start with `sk-ant-` and must not be an Admin key (`sk-ant-admin`) (a refusal is a Japanese message), then `GET https://api.anthropic.com/v1/models?limit=1` with `Authorization: Bearer` and `anthropic-version: 2026-10-21` (a short timeout) asks Anthropic, and the response header `anthropic-workspace-id` is shown on the key row. 401 and 403 mean the key cannot be used; any other failure means it cannot be checked. At registration neither is saved. When `claude_status` asks again later, a key that cannot be checked stays usable (only the state says 確認できません), and a key Anthropic refuses is not usable. A key registered from the field that the radio of the API key row opened (`claude_key_save` with `switch`: after the check, the keychain write and the `claude-auth.json` write), and pressing the radio of a stored key (`claude_method_set` asks Anthropic first and refuses a rejected key; one that cannot be asked about is let through), switch to the API key and run `claude auth logout` for Claude Code, unless the API key is the method already (then nothing is logged out, so a login made again by hand is kept). The logout is checked by reading `claude auth status` again (that alone, no `--version`): only logged out or no Claude Code counts, and a login that remains, or a status that cannot be read, means the logout is not confirmed (the switch stays). `claude_method_set` then answers an error; `claude_key_save` answers that the key is stored, with `logoutError`, and the screen closes the field and shows that text as the error. A key pasted again with "貼り直す" (`switch` false) only replaces the key: the method does not change and nothing is logged out. Going back to the subscription only changes the method (the key is kept, and a logged-out row says 未ログイン with the `claude auth login` guidance). Deleting the key asks for confirmation, and when the key was in use the method goes back to the subscription (the logout is not undone). The usable state the whole screen follows (`Claude`: the sidebar, Todo, M-8, S-4, S-7, S-3) is `ready` for a logged-in subscription, or for an API key that is not refused (then email and plan are empty, the sidebar popup and the button's `aria-label` say "API キー" instead of the email); it is not `ready` while the key is refused or missing. The `?` hint explains the key (made in the Console, limited to a workspace, kept in the keychain, switching logs Claude Code out on this device). No cost is shown. Unit tests and E2E never run a real logout

## A-3 Settings tabs

The settings screen has six tabs, in order Google, カレンダー, Todoist, Slack, Claude and アップデート (`role="tablist"`), and shows the cards of the selected tab only (the Slack tab has two, the connection and the channels kept off the list of S-9; the Claude tab has three: the connection of A-4, the model and effort of A-2, and the prompt row of S-3, in a tab panel that is no card itself, so the panel keeps its `role="tabpanel"`). The side menu's settings button opens it on Google, and so does a way in that names no tab; the "設定を開く" of the Claude popup of the side menu opens it on Claude, and the ways to add a Slack workspace (the notice of the Slack compose screen, and the failed Slack summary of the Todo add field) open it on Slack. "戻る" of the prompt screen returns to the tab it was opened from. Left and right arrow keys move between the tabs (the first and the last are neighbours). Selecting a tab closes an open `?` hint and scrolls the settings to the top. The heading "設定" and the tabs stay at the top (`position: sticky`) while a card scrolls under them; only the underline of the tabs divides them, with no shadow. A red dot is on the アップデート tab while a newer version is out (U-1)

## A-5 Side menu by screen

The sidebar runs, top to bottom: inbox, calendar, the Google accounts (`#account-list`), Todo, Slack (`nav-slack`), the Slack workspaces (`#slack-workspace-list`), Orca (`nav-orca`, the terminal icon, with the count of A-6), then the bottom group (Claude, settings). Each list sits in a tray (background `--side-hover`, radius 12px, 28px round avatars; an empty tray is hidden) under the icon of its function and shows only while that function is on screen: the Google accounts while the screen is the inbox (list, thread, the Slack compose screen of S-1) or the calendar, the Slack workspaces while the screen is the Slack list or thread; Todo, Orca and settings show neither, and the prompt screen follows the screen it was reached from. The popup of an avatar closes when the screen changes. A Google avatar opens the account popup beside itself as before; a workspace avatar opens the same popup with the workspace name, the user, a status label (what the last read of the list found: 接続済み, 読み込み失敗, 権限が不足) and "設定を開く" (the Slack tab), its tooltip is the workspace name, and its picture is the user's own icon there (`slack_icons`, fetched through `fetch_images`), the initial on the workspace's color until it is here

## A-6 Orca

A screen of its own (`nav-orca`, `#orca`) shows which agents run in Orca, a desktop agent orchestrator with a CLI (`orca`), and posts to them. It keeps no conversation history, has no detail screen and stores nothing about a session: every read asks the CLI again. The header bar (as `#slack-header`) has the heading "Orca", a status label with a dot, and the update button (`↻`, `aria-label` "更新"). Below it are three groups with `.feed-heading` headings that carry their number: "入力待ち n" (above the others, shown only when it has rows, orange dot, because the user has to act), "動作中 n" (green dot) and "完了 n" (gray dot); a group with no rows has no heading, and with no rows at all the list says "動いているエージェントはありません". A row (a button) has the status dot, the repository in bold and the branch, one line of text, an agent chip ("Claude", "Codex" or the agent's own type) and a time. Under the list, pinned, is the composer: the label "宛先" with a chip, a textarea and a primary button. `nav-count` of the Orca button shows the number of agents that wait or run (入力待ち plus 動作中, not 完了), with the label "Orca（動作中 n 件）"; it does not enter the Dock badge.

Selection is by clicking a row (`aria-pressed`, the `--soft` background); a row whose terminal handle is not known cannot be selected. With a row selected the chip names it ("{repo} ・ {branch} のセッション"), the button is "送る", the placeholder is "追加の指示を書く", and "新しく起動する" clears the selection. With nothing selected the chip is a menu of every worktree ("{repo} ・ {displayName}"), a second chip is a menu of the agent (Claude, the default, or Codex), the button is "起動する" and it is disabled until a worktree is chosen; the placeholder is "起動するエージェントへの指示を書く". The button is also disabled while the text is blank or a post is on its way, and when the command is missing. While a post is on its way the textarea is disabled, and it has the focus again afterwards. A post that works clears the textarea and reads the list at once; one that fails keeps the text and shows the CLI's message (`error.message`) above the composer. A send whose answer says `result.send.accepted` is false is a failure too (Japanese message), so the text stays. Selecting a row clears the worktree chosen for a launch, so the next launch chooses it again. A post is never tried again, because after a lost reply a second one would post twice (the CLI forbids a fresh retry of a launch).

The CLI is found among the absolute places `/usr/local/bin/orca` and `/Applications/Orca.app/Contents/Resources/bin/orca` (a GUI app has no shell PATH), and run with an argument list, never through a shell, in the temporary folder, with stderr dropped and a timeout (15 seconds for a read, 60 seconds for a launch and a send) after which the child is killed, off the UI thread. The commands are `orca worktree ps --limit 200 --json` and `orca terminal list --json` (the list), `orca terminal send --terminal <handle> --text=<text> --enter --json` (send), `orca agent launch --agent <id> --worktree path:<path> --surface terminal --prompt=<text> --json` (launch), `orca environment list --json` and `orca skills installed --json`; the text of the user is joined to its flag (`--text=--json` is accepted, while `--text --json` is refused as "requires a value"), and `--environment=<name>` is added to every one of them but the list of environments when a target is chosen. The output is JSON, `{ok, result, error: {code, message}}`, also on failure, so stdout is read whatever the exit code and `error.message` is shown (the code when there is no message); an empty output or one that is no JSON gives a Japanese message. The prompt text is in no log line.

Rows are built by a pure function from the two documents (`result.worktrees[].agents[]` and `result.terminals[]`), tolerant of absent fields. An agent is kept when it is top-level (`parentPaneKey` null) and `hasLivePty` is true. Its group follows `state`: `waiting` and `blocked` are 入力待ち, `done` is 完了, and every other state (`working`, and a state not known yet) is 動作中. The line is `taskTitle`, else `conversationName`, else the first line of `prompt`; for a done agent the first line of `lastAssistantMessage` is preferred; for a running agent (not a waiting one) " ・ {toolName} を実行中" follows when `toolName` is present. The branch is the worktree's `displayName` and the repository its `repo`. The time is `stateStartedAt` for an agent that runs or waits ("2 分", the time since) and `updatedAt` for a done one ("18 分前"), sent as epoch milliseconds and formatted by the screen. The terminal handle is found by joining the agent's `paneKey` with the terminals' `"{tabId}:{leafId}"`. Rows are sorted by `updatedAt`, newest first. The launch targets are all worktrees, with their path, repository and `displayName`.

Just before it acts, Rust reads the list again (with the environment): a send goes only to a handle that belongs to a row of that list (a top-level agent of a live terminal; `writable` and `orphaned` are not used, because a plain shell terminal is writable and not orphaned), and a launch only into a worktree of it; otherwise the answer is a Japanese error and nothing is sent. Rust validates before it runs anything and answers in Japanese: the text is not blank and at most 100,000 characters; the agent is `claude` or `codex`; the handle begins with `term_` and holds only `[A-Za-z0-9_-]`; the path is absolute; the environment is one listed by `orca environment list --json` (`result.environments`, each a name or an object with a `name`, else an `id`).

The target is "このマシン" or a saved environment (a paired server). It is saved in `orca-settings.json` in the app config directory (`{"kind":"local"}` or `{"kind":"environment","name":"..."}`, written through a temporary file and a rename), and only when the file does not exist yet the first saved environment is used, else this machine. A saved environment that is no longer listed, or a file that cannot be used while an environment is saved, never switches the target by itself: the read is a failed one with 「保存した接続先が見つかりません」 (the label names the saved environment), the menu lists the environments and "このマシン", and the owner chooses again (with no environment saved there is nothing else to choose, so a file that cannot be used gives this machine). The status label shows it: green "{target} に接続中" after a read that worked, orange "{target} に接続できません" with the message in a notice when it failed (the rows of the last good read stay while the target is the same), and gray "未インストール" with a notice when no `orca` was found. The label is plain text until an environment is saved, and from then on a menu of "このマシン" and the environments; choosing one saves it, drops the selection and the rows of the old target, and reads again; until that first read of the new target returns, the label says 確認中 and the list 「読み込んでいます…」 (nothing is said about the target), and the menu stays. The environments are listed even when a read failed, so the target can still be changed. When `orca environment list` itself fails, the screen keeps the target, the environments and the rows it had, and shows the failure.

The list is read at startup (for the count), every 10 seconds while the Orca screen is shown and every 60 seconds otherwise, one read at a time, and no more by the clock once the command was found missing (the update button looks again). The environments are read (`orca environment list`, and the target resolved) only at startup, when the screen is shown, by the update button, when the target changes and in a read after a failure; the clock reads the agents and terminals of the target held while the screen is shown, and only `orca worktree ps` (for the count, with no terminal list) while another screen is shown. A read in the background swaps the rows in place and keeps the selection (dropped only when its session is gone), the text in the textarea and the scroll position, and never calls `show()`.

While the destination is Claude (a selected row whose agent is Claude, or a launch with the Claude chip; Codex has none), a skill list completes commands as Claude Code's does. `orca skills installed --json` (`result.skills[]` with `name`, `description`, `providers`, `sourceKind`, `sourceLabel`) is read once when the screen is first shown with a working command, again when the target changes and by the update button, never per keystroke; a failure gives no list and never blocks a post. A pure function keeps the skills whose `providers` include `claude` and turns each into the command `/{name}`, or `/{plugin}:{name}` for `sourceKind` `plugin` with a `sourceLabel` of the form `Claude plugin {plugin}` (its `name` has no plugin prefix); it drops a command listed twice, sorts by command and cuts the description to its first line. The list opens when the text starts with `/` and the caret is still in that first word (no whitespace yet), and only while the textarea has the focus (a read in the background does not open it). It is a popup (`role="listbox"` with `aria-activedescendant`) directly above the composer, with the frame and shadow of `#account-popup`, the command in monospace and its description on one line with an ellipsis, 8 rows at most before it scrolls. It shows the commands that contain the text after `/`, case-insensitively, those that begin with it first. Up and Down move the highlight and wrap around, Tab or Enter put the command and one space in the place of the first word (the caret after the space, and nothing is posted), Escape closes it until the text changes, and a click on a row does what Tab does. Enter does not submit while the list is open. A read in the background does not close it or move the highlight.

Unit tests (`cargo test`) cover row building, the argument lists (the `--flag=value` form and the environment), the validation, the parsing of the output and the environments, the target setting and the skill list; none of them runs the real CLI. The E2E spec `orca.e2e.ts` covers the drawing, the selection, the arguments of a send and a launch, a failure keeping the text, the missing command, a failed read, the target menu, a read in the background and the skill list.
