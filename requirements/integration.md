# Integration requirements

## A-1 Claude integration

A local MCP server (`cookapps-mcp`, stdio) lets Claude list, read, archive, mark read and trash inbox threads, and list events

## A-2 Claude model and effort

The Claude tab of the settings screen has a card "モデルと effort" (shown whether or not Claude can be used; the columns are headed "用途", "モデル" and "effort", and a note says the next call uses the choice and the default is Sonnet and medium, Sonnet and high for the Slack thread conversation, so the options carry no "(デフォルト)") with, for each of seven purposes, a name, where it is used, and two narrow selects that choose its model and its effort: the Slack summary (S-2, "Slack の要約", used when a Todo is made from a Slack message), the mail summary (M-8, "メールの要約", the AI summary of the mail detail), the prompt conversation (S-3, "プロンプトの会話", editing the Todo summary prompt with Claude) the Slack text proofreading (S-4, "Slack に貼る文章の校正", the "Claude と校正" pane) the Slack thread conversation (S-7, "Slack のスレッドの相談", the Claude pane of the thread detail) and the summary of a handoff (A-9, "Orca に渡す要約", "Orca に渡すペインで、渡す内容を要約するとき", the Claude call `claude_summarize_handoff` that returns the points of a summary of the content, quoted as data; the instruction the user wrote is not sent to it; the pane of A-9 calls it when the hand-over is pressed, and shows the selects of `orcaHandoff` under its field before a hand-over, as S-7 shows those of `slackReply`) and the Todo conversation ("Todo の相談", "Todo の Claude ペインで、タスクを頼むとき", the Claude call `claude_chat_todo` that returns a short reply and the proposed tasks, each a name, a date and a project, from the conversation so far, the new request, today's date and the Todoist projects of the last load; no tools and no MCP servers, as S-7, and the conversation and the request are enclosed as untrusted data; a request of more than 2000 characters is refused, a task is returned only with a name of 1 to 500 characters and a date of `YYYY-MM-DD` or `YYYY-MM-DD HH:MM` or none, a project that was not given is none, and an answer of more than 50 tasks is refused; the Claude pane of the Todo screen (T-7) calls it and shows the selects of `todoChat` under its request field, as S-7 shows those of `slackReply`). Each `claude -p` call uses the model and effort of its own purpose. The model is Haiku, Sonnet (the default) or Opus (Fable is not offered; a saved `"fable"` is an invalid value and gives Sonnet). The effort is low, medium (the default), high, xhigh or max, and `--effort` is always passed. Changing the model also switches the effort to the one the documentation recommends for it, saved in the same write: Haiku medium, Sonnet high, Opus medium (Rust `recommended_effort`, from https://platform.claude.com/docs/en/build-with-claude/effort, "Recommended effort levels"); the screen sends the model alone, and `claude_model_settings_save` takes an optional `effort` that defaults to the recommended one, while changing the effort sends both. The first default (nothing saved) stays Sonnet and medium, and Sonnet and high for `slackReply`. An effort select is colored by its value (`data-effort`, variables in `:root`): low gray, medium green, high yellow, xhigh orange, max red, following a change, a save and a failed save; the settings card colors the background and the text, and the frameless select of S-3 the text only. A change is saved at once, for that purpose only, in `claude-settings.json` in the app config directory (an object keyed by `slackSummary`, `mailSummary`, `promptChat`, `proofread`, `slackReply`, `orcaHandoff` and `todoChat`, each `{model, effort}`; one save reads the file again, changes one purpose and writes all seven through a temporary file and a rename), and the next call uses it. Rust checks the purpose, the model and the effort against their lists when saving (a refusal is a Japanese message), and a missing file, an unreadable file or an invalid value gives the default for that purpose, so only a listed value reaches `--model` and `--effort`. A file in the old form, one `{model, effort}` pair for every call, gives that pair to all seven purposes until a purpose is saved, and a file without `slackReply` gives that purpose its default (and one without `orcaHandoff` or `todoChat` gives it Sonnet and medium). From high up (high, xhigh, max) a call may run 300 seconds (`--effort max` took 61 seconds on a small input); below that it is 60 seconds for the summaries and 120 seconds for the prompt conversation, the proofreading, the summary of a handoff and the Todo conversation. The `?` hint of the Claude card says that each of the seven calls has its own model and effort. The thread detail of S-6 shows the selects of `slackReply` under its request field, as S-3 shows those of the prompt conversation. The screen of S-3 shows the selects of the prompt conversation too

## A-4 Claude connection

The `claude -p` calls of M-8, S-2, S-3, S-4 and S-7 go through the Claude Code CLI, which signs in either with the Claude subscription (the default) or with an Anthropic API key. The first card of the Claude tab ("Claude", with ↻ and `?`) has two rows with radios, "サブスクリプション" (email, plan, Claude Code version and state: ログイン中, 未ログイン with the `claude auth login` guidance, 未導入, 確認できません) and "API キー" (the workspace ID when Anthropic says it, the note that every call is billed, the state 未登録, 確認済み, 確認できません or 使えません, "貼り直す" and the disconnect button), so the state of the one not in use shows too. Pressing the radio of the API key row with no key stored, or with a key Anthropic refuses, only opens the key field ("確認して保存"); nothing is switched or logged out. If the keychain cannot be read, only the key row says 確認できません with the error; if asking for the connection itself fails, the card shows one failed row with the error and no radio, so nothing can be pressed, and Claude is in its failed state. At start only `claude_status` is called (so a start without the settings never asks Anthropic about a key); `claude_connection`, which answers the three parts of the card and the usable state `claude` with each state read once, is called when the Claude tab is first shown, by ↻ and after a change of the connection, and only the latest answer of the reads is used. While a change is on its way ↻ and the radios wait, and so does the button of the key field (also while the states are being read); sending the field while a change is on its way does nothing and does not empty it. A change of the connection redraws the connection card only, so the model selects and the prompt row keep their place and focus. Only the radio of a row switches the method (the radios are not grouped by name, so the arrow keys move none of them, and are disabled while a change is on its way); clicking or double-clicking the text of a row does nothing. The key is never shown, and the field is emptied as soon as it is read. The method is saved in `claude-auth.json` in the app config directory (`{"method":"subscription"|"apiKey"}`, written through a temporary file and a rename; a missing file, an unreadable one or an invalid value gives the subscription), and the key is in the OS keychain (service `jp.mysis.cookapps.claude`). Rust does not call the API for the work: the `claude -p` child process gets the key as `ANTHROPIC_API_KEY`, and `ANTHROPIC_AUTH_TOKEN` is taken out (the CLI prefers it) together with `ANTHROPIC_BASE_URL`, `CLAUDE_CODE_USE_BEDROCK`, `CLAUDE_CODE_USE_VERTEX` and `CLAUDE_CODE_USE_FOUNDRY` (they would send the key to another host or provider than the one it was checked against), while the subscription takes `ANTHROPIC_API_KEY`, `ANTHROPIC_AUTH_TOKEN` and `CLAUDE_CODE_OAUTH_TOKEN` out. The key is in no command-line argument, log line or error text. `claude auth status` answers `loggedIn: true` for a made-up key (measured), so it does not check a key. A pasted key is trimmed, must start with `sk-ant-` and must not be an Admin key (`sk-ant-admin`) (a refusal is a Japanese message), then `GET https://api.anthropic.com/v1/models?limit=1` with `Authorization: Bearer` and `anthropic-version: 2026-10-21` (a short timeout) asks Anthropic, and the response header `anthropic-workspace-id` is shown on the key row. 401 and 403 mean the key cannot be used; any other failure means it cannot be checked. At registration neither is saved. When `claude_status` asks again later, a key that cannot be checked stays usable (only the state says 確認できません), and a key Anthropic refuses is not usable. A key registered from the field that the radio of the API key row opened (`claude_key_save` with `switch`: after the check, the keychain write and the `claude-auth.json` write), and pressing the radio of a stored key (`claude_method_set` asks Anthropic first and refuses a rejected key; one that cannot be asked about is let through), switch to the API key and run `claude auth logout` for Claude Code, unless the API key is the method already (then nothing is logged out, so a login made again by hand is kept). The logout is checked by reading `claude auth status` again (that alone, no `--version`): only logged out or no Claude Code counts, and a login that remains, or a status that cannot be read, means the logout is not confirmed (the switch stays). `claude_method_set` then answers an error; `claude_key_save` answers that the key is stored, with `logoutError`, and the screen closes the field and shows that text as the error. A key pasted again with "貼り直す" (`switch` false) only replaces the key: the method does not change and nothing is logged out. Going back to the subscription only changes the method (the key is kept, and a logged-out row says 未ログイン with the `claude auth login` guidance). Deleting the key asks for confirmation, and when the key was in use the method goes back to the subscription (the logout is not undone). The usable state the whole screen follows (`Claude`: the sidebar, Todo, M-8, S-4, S-7, S-3) is `ready` for a logged-in subscription, or for an API key that is not refused (then email and plan are empty, the sidebar popup and the button's `aria-label` say "API キー" instead of the email); it is not `ready` while the key is refused or missing. The `?` hint explains the key (made in the Console, limited to a workspace, kept in the keychain, switching logs Claude Code out on this device). No cost is shown. Unit tests and E2E never run a real logout

Selecting a tab closes an open `?` hint and scrolls the settings to the top. The heading "設定" and the tabs stay at the top (`position: sticky`) while a card scrolls under them; only the underline of the tabs divides them, with no shadow. A red dot is on the アップデート tab while a newer version is out (U-1)

## A-6 Orca

A screen of its own (`nav-orca`, `#orca`) shows which Claude agents run in Orca, a desktop agent orchestrator with a CLI (`orca`), shows their terminals (A-8, A-12) and starts new ones. It stores nothing about a session: every read asks the CLI again. Only agents of type `claude` are listed and started; an agent of another type (Codex) has no row, and a launch always starts Claude.

The screen is two panes side by side (`#orca` is a `.split-main`): the list pane `#orca-list` on the left, the divider `#orca-split` (a `.split-bar` with `role="separator"`, `aria-orientation="vertical"`, `aria-label` "一覧の幅", `aria-valuemin` 20, `aria-valuemax` 50 and `tabindex` 0), and the work pane `#orca-work`. The list is 25% of the screen at first and the user sets it between 20% and 50% by dragging the divider, or with the arrow keys (Right widens, Left narrows, 2% a step); the ratio is kept in memory (as the divider of S-1 and S-6, `ts/split.ts` serves both). The list pane has a header bar of 32 px (`#orca-header`), level with the tab strip of the work pane, and no heading: at its right the bell `#orca-bell` (A-8) and the reload button `#orca-refresh` (`↻`, `.icon-btn`, `aria-label` "読み直す"); the two buttons are 24 px high. It has no new button: a session is started from the plus of the work pane (A-16). The status label with a dot (`#orca-status`, or `#orca-target`) is in a footer (`#orca-foot`) at the bottom of the list pane, under the list. The list shows the projects (A-8) first; with the bell pressed it shows the working view: three groups with a heading that has the arrow of A-8 at its left, the status icon of A-8, the name and the number at the right end: "入力待ち" (above the others, because the user has to act), "作業中" and "完了"; a group with no rows has no heading, and with no rows at all the list says "動いているエージェントはありません". The heading is one button (`.orca-group-btn` in the `h2.orca-group`, `aria-expanded`, `data-key` `group:{waiting|working|done}`) that opens and closes its group with the pointer and with Enter or Space: while the group is closed its rows are not drawn, and the heading and the number stay. Every group is open at first, and which groups are closed is kept in memory only (the projects of A-8 are kept the same way). A row (a button) has three lines: the status icon, the title (the first line of the prompt) and the time at the right; the latest action of the agent (A-8); and Claude's mark with "{repo} ・ {branch}". There is no repository heading, no filter and no agent chip. `nav-count` of the Orca button shows the number of sessions that need the user: the rows that wait (入力待ち) plus the notices below, with the label "Orca（確認待ち n 件）"; 作業中 is not counted, and the count does not enter the Dock badge. The bell's shoulder and the numbers of the group headings are not changed by it.

The work pane is split into panes (A-17); each has the tab bar (A-8, A-16: the tab strip of the selected project, shown also when it is empty, and the plus right after its last tab), and under it the terminal of the tab it shows (A-8, A-12), or a line (`.orca-empty`) that says why there is none: 「プロジェクトを選んでください」 when no project is selected, 「セッションはありません」 for a project with no session, and 「このセッションのターミナルはありません」 for a Claude session with no terminal handle. The screen has no composer and no history: the user types into the terminal. The pane of A-9 shows the terminal of the session it handed to (A-9). A row of the working view is selected by clicking it (`aria-pressed`, the `--soft` background), which also selects its project and its tab (A-8); a row with no pane key cannot be selected.

New session. A session is started from the plus of the work pane (A-16), which calls `orca_start(path, environment)` with the target the screen shows: it starts Claude in that worktree with no first prompt (the user types it in the terminal). The dialog of the worktrees (`openWorktreeDialog`, `showMenu`, `role="dialog"`, shared with the chip of A-9) has a filter field (`aria-label` "worktree を絞り込む", case-insensitive on "{repo} ・ {branch}") and two-line rows (the repository, then the branch) of the worktrees it is given; picking one closes it. A launch is never tried again, because after a lost reply a second one would start twice (the CLI forbids a fresh retry of a launch); a failure shows the CLI's message (`error.message`) in `#error`. The side pane of A-9 launches and sends through the same checks (`orca_handoff` composes the prompt and then runs the same launch or send once); a send whose answer says `result.send.accepted` is false is a failure too (Japanese message).

After a launch. A launch that works follows the session it started (`orca_start` answers `{paneKey, handle}`, and A-9 uses the same answer): the project and the tab that were selected stay meanwhile, and once a read holds the row of that `paneKey` or of that `handle` (the one that is not `null`; the read after the launch, a later one or a list of the stream of A-12, for at most 30 seconds), the screen selects its project and its tab, so its terminal shows. Until the row is in the list the work pane shows a note (`#orca-started`, `role="status"`: 「セッションを始めました。一覧に現れるのを待っています…」), and the plus is disabled, so a second session cannot be started meanwhile. Selecting a project, a tab or a row, changing the target, or a read after the 30 seconds (one that failed too) drops the wait; the launch is never followed after the user selected another project or tab while it was on its way. When Orca's reply had neither a `paneKey` nor a `handle` (both `null`), nothing can be waited for: the note says 「セッションを始めました。Orca の画面で開けます。」, the plus stays enabled, and the note goes at the next selection.

The CLI is found among the absolute places `/usr/local/bin/orca` and `/Applications/Orca.app/Contents/Resources/bin/orca` (a GUI app has no shell PATH), and run with an argument list, never through a shell, in the temporary folder, with stderr dropped and a timeout (15 seconds for a read, 60 seconds for a launch and a send) after which the child is killed, off the UI thread. The commands are `orca worktree ps --limit 200 --json` and `orca terminal list --json` (the list), `orca terminal send --terminal <handle> --text=<text> --enter --json` (send), `orca terminal create --worktree path:<path> --json` (a new terminal, A-16), `orca worktree create --repo=id:<repository id> --name=<name> [--branch=<branch>] [--base-branch=<ref>] --no-parent --json` (a new worktree, A-9; `--branch` and `--base-branch` only when given; `orca_worktree_create` answers `result.worktree.path`), `orca agent launch --agent claude --worktree path:<path> --surface terminal --prompt=<text> --json` (launch; `orca_start` gives no `--prompt`, and only the handoff of A-9 gives one; its reply holds `result.outcome` `{kind: "terminal", handle, paneKey}`, which `orca_start` and `orca_handoff` return as `{paneKey, handle}`, each `null` when the reply lacks it or holds it in a shape that is not a pane key (at most 256 characters of `[A-Za-z0-9:_-]`) or a terminal handle), and `orca environment list --json`; the text of the user is joined to its flag (`--text=--json` is accepted, while `--text --json` is refused as "requires a value"), and `--environment=<name>` is added to every one of them but the list of environments when a target is chosen. The output is JSON, `{ok, result, error: {code, message}}`, also on failure, so stdout is read whatever the exit code and `error.message` is shown (the code when there is no message); an empty output or one that is no JSON gives a Japanese message. The prompt text is in no log line.

Rows are built by a pure function from the two documents (`result.worktrees[].agents[]` and `result.terminals[]`), tolerant of absent fields. An agent is kept when its `agentType` is `claude`, it is top-level (`parentPaneKey` null) and `hasLivePty` is true. Its group follows `state`: `waiting`, `blocked` and `permission` are 入力待ち, `done` is 完了, and every other state (`working`, and a state not known yet) is 作業中. The line (the title of the row and of its tab) is the first line of `prompt`, else of `taskTitle`, `conversationName` and `lastAssistantMessage`, in this order, else the first line of the `title` of the terminal of the same pane (`result.terminals[]`, joined as below) without the status mark Claude Code puts in front of it (a first character that is no letter or digit, followed by a space; taken off once, with the spaces after it), whatever the state. The activity (A-8), the second line of a row, is `{toolName}: {first line of toolInput}` (the name alone when the input is not text or is blank), else the first line of `lastAssistantMessage`, else empty, cut to 200 characters. The branch is the worktree's `displayName`, the repository its `repo` and the path its `path`. A row also carries the agent's `paneKey` (null when it has none), which names its tab (A-12), and its `activity`, `status` and `projectKey` (A-8). The time is `stateStartedAt` for an agent that runs or waits ("2 分", the time since) and `updatedAt` for a done one ("18 分前"), sent as epoch milliseconds and formatted by the screen. The terminal handle is found by joining the agent's `paneKey` with the terminals' `"{tabId}:{leafId}"` (an orphaned terminal by its `recordedPaneKey`, as below). Rows are sorted by `updatedAt`, newest first. The launch targets are all worktrees, with their path, repository and `displayName`.

Just before it acts, Rust reads the list again (with the environment): a send goes only to a handle that belongs to a row of that list (a top-level agent of a live terminal; `writable` is not used, because a plain shell terminal is writable too; an orphaned terminal, one that lost its tab and still runs, belongs to the agent whose pane is its `recordedPaneKey` when its `agentIdentity` is `claude` and no other orphaned terminal recorded that pane, and a live terminal of that pane comes first), and a launch or a new terminal (A-16) only into a worktree of it; otherwise the answer is a Japanese error and nothing is sent. Rust validates before it runs anything and answers in Japanese: the text is not blank and at most 100,000 characters; the handle begins with `term_` and holds only `[A-Za-z0-9_-]`; the path is absolute; the environment is one listed by `orca environment list --json` (`result.environments`, each a name or an object with a `name`, else an `id`).

The target is "このマシン" or a saved environment (a paired server). It is saved in `orca-settings.json` in the app config directory (`{"kind":"local"}` or `{"kind":"environment","name":"..."}`, written through a temporary file and a rename), and only when the file does not exist yet the first saved environment is used, else this machine. A saved environment that is no longer listed, or a file that cannot be used while an environment is saved, never switches the target by itself: the read is a failed one with 「保存した接続先が見つかりません」 (the label names the saved environment), the menu lists the environments and "このマシン", and the owner chooses again (with no environment saved there is nothing else to choose, so a file that cannot be used gives this machine). The status label shows it: green "{target} に接続中" after a read that worked, orange "{target} に接続できません" with the message in a notice when it failed (the rows of the last good read stay while the target is the same), and gray "未インストール" with a notice when no `orca` was found. The label is plain text until an environment is saved, and from then on a menu of "このマシン" and the environments; choosing one saves it, drops the selection and the rows of the old target, and reads again; until that first read of the new target returns, the label says 確認中 and the list 「読み込んでいます…」 (nothing is said about the target), and the menu stays. The environments are listed even when a read failed, so the target can still be changed. When `orca environment list` itself fails, the screen keeps the target, the environments and the rows it had, and shows the failure. While the target is a saved environment that is listed, its list is streamed (A-12) and not read by the clock.

The list is read at startup (for the count), every 10 seconds while the Orca screen is shown and every 60 seconds otherwise, one read at a time, and no more by the clock once the command was found missing (the reload button looks again); a streamed list (A-12) is not read by the clock. The count of the Orca button follows every read (the clock's read for the count alone included) through one function. A row has stopped when its group is 完了 or its status is `failed` or `interrupted` (Orca says an agent stopped with Esc as `state` `done` with `interrupted` true). A stopped row has a notice when, while the app runs, it went from not stopped to stopped between two reads, or it first appeared in a read after the first of the target and had already stopped (a pane the app has seen stopped is remembered, so it has no new notice when it leaves the list and comes back stopped, and the memory ends when it is seen running or the target changes). The rows of the first read of a target (at startup, and after the target is changed) are only the base and have no notice, so what had finished before is not counted; changing the target drops every notice, and so does a read that names another target than the one held. A notice goes when the session is shown on the Orca screen (the screen is shown, the window is not hidden, and the row is the selected tab; the session seen only in the side pane of A-9 does not clear it), when the row runs again (it is no longer stopped), or when it leaves the list; a row that stops while it is shown has no notice. A row with no pane key cannot be opened, so it has no notice (it is still counted while it waits). A failed read, and a read that did not find the rows while the command is there, leave the notices as they are; a missing command drops them. The notices are held in memory only. While one row or more is working (its group is 作業中 and its status is `working` or `monitoring`), the icon of `#nav-orca` (the `svg` only, not `.nav-count`) is yellow (`--agent-working`) and fades slowly (`opacity` between 1 and .55 over 2 seconds, `ease-in-out`, endless), by the class `working` on the button; under `prefers-reduced-motion: reduce` it stays yellow and does not fade. The number that work is not on the button: it is in the `aria-label` (read aloud, and in the tooltip on hover), after the count of the waiting ones (「Orca（確認待ち 1 件、作業中 2 件）」, 「Orca（作業中 2 件）」, 「Orca（確認待ち 1 件）」, else 「Orca」). The class and the label follow every read the count follows, so a read for the count alone moves them too; a failed read cannot say that a session works, so it takes the mark and that part of the label away and leaves the count of the waiting ones as it is, and a missing command or a change of the target removes them all.

The environments are read (`orca environment list`, and the target resolved, together with the SSH hosts of A-8) only at startup, when the screen is shown, by the reload button, when the target changes and in a read after a failure (when the file says this machine, `orca worktree ps` and `orca terminal list` of this machine are read at the same time as `orca environment list`, since the target cannot be another one; they are dropped if another target is resolved); the clock reads the agents and terminals of the target held while the screen is shown, and only `orca worktree ps` (for the count, with no terminal list) while another screen is shown. A read in the background swaps the rows in place and keeps the selection (dropped only when its session is gone), the terminal shown and the scroll position, and never calls `show()`.

Unit tests (`cargo test`) cover row building, the argument lists (the `--flag=value` form and the environment), the validation, the parsing of the output and the environments and the target setting, and the decision that the lists of this machine are read at the same time as the environments only when the saved target is this machine (`reads_local_lists_early`: not for a saved environment, a missing file or an unusable one); none of them runs the real CLI. The E2E spec `orca.e2e.ts` covers the header, the two panes and the divider, the drawing of the working view, the selection, the start from the plus (A-16: its menu, the dialog, the arguments of a launch and the following of its session, a failed launch), the missing command, a failed read, the target menu, a read in the background, and the count and its notices.

## A-7 Orca session history

Retired (#478, the owner's decision 2026-11-12). The history of a session (what the user asked, what the agent answered and the tools it ran) is no longer read or drawn, and the app has no command for it: the pane of A-9 and the Orca screen show the terminal of the session (A-9, A-12), where a question of Claude is answered as well (A-11).

What stays is the connection to Orca's runtime, which the history was the first to use and which the other requirements name as A-7's (`src-tauri/src/orca_link.rs`, with the framing of `orca_e2ee.rs`). The runtime is not a public interface. It was written against Orca 1.4.248, and an Orca update can change it. This machine is reached over the unix socket of `orca-runtime.json` in Orca's settings folder (`authToken`, and the transport of kind `unix` with its `endpoint`): one JSON line `{id, authToken, method, params}` and one line back, a connection for each call. The socket exists on macOS and Linux; on another OS a call fails with a message that says so. A saved environment (A-6) is reached over its WebSocket (`ws://` only: the frames are encrypted end to end, with the pairing's key, and TLS is not built in) with the device token and the public key of `orca-environments.json`, using Orca's own framing. Both files are read at each connect and never written. A failed call shows Orca's code (「Orca がエラーを返しました（{code}）」), never Orca's own message; when Orca is not running on this machine the message is 「Orca に接続できません。Orca が起動しているか確認してください」. A token, a key or an authentication frame is in no log, no error text and no event. A caller that keeps a connection open tries again after 1, 2, 5, 10 and then 30 seconds.

Unit tests (`cargo test`) cover the framing and encryption of the paired connection against fixed vectors, the choice of the pairing and the endpoint, the answer of a call (the result, or the code and never the message), the handshake and a refused token against a stand-in server, a call over the unix socket, and the back-off; none of them talks to a real Orca.

## A-8 Orca terminal and project list

The Orca screen (A-6) shows the terminals of Orca, one for each tab, and its list pane is a list of projects with a switch to the working agents. It was written against Orca 1.4.248.

Projects. The list pane shows the projects first (the choice of view is kept in memory). A row (a button, `.orca-project` in a `.orca-proj`, `aria-pressed` for the selected one) has the status icon, the name and the number of sessions (nothing when it is 0). The number stays a number when the project is open. A pure function builds them from the two documents of A-6: one project for each `repoId` among the worktrees that are not archived (`isArchived` is not true), have a path, and whose `hostId` is `local` (a worktree with no `hostId` is this machine's); the name is the worktree's `repo`. The worktrees of an SSH host (any other `hostId`) are not projects: they make the row `ssh:{hostId}` of that host. The sessions of a project are its Claude rows (A-6) and its plain terminals. The projects with a working session (a session of the project whose icon is the yellow ring; the icon of the project itself may be a question or a failure, which outrank working, and the project is still one of them; also a project whose own icon works when no Claude row of it does, as when another agent or a worktree's status works) come first. The stopped projects follow: those with one session or more (the number of sessions shown on the row is not 0) that are not in the working group. The projects with no session come last. The stopped projects are newest first by the latest `lastActivityAt` of the project's worktrees, as the pure function lists them, and so are the projects with no session (the SSH hosts below keep that order alone). The working projects are not reordered by their activity, which moves with the work: the screen keeps them in the order they entered the working group, in memory only. A project that begins to work (it had no working session at the last read that worked, or it is new, or the screen has just started) goes in front of the ones that already work, and several that begin together keep the order the function lists them in (newest first); one with no working session left leaves the group and goes among the stopped projects, or those with no session. A project whose sessions only wait for the user is not in the working group and stays below it; one with a session that works and another that waits is in the group, and a question asked or answered there moves nothing. A read that failed changes none of this, and a change of the target starts it again. Below the projects, under the heading "SSH", are the SSH hosts, in Orca's order, drawn the same way: the name is the host's `label`, and the icon and the number are what the worktrees with its `hostId` show (idle and none when there are none). A host that the worktrees of the target have (`ssh:{hostId}`) but that this machine's Orca does not list is a row of that group too, named by its worktrees' host name, after the listed ones. The search field above the list (A-19) narrows them by name.

Sessions under a project. Each project opens and closes by itself, so any number can be open at once. A project (or SSH host) that has a tab other than a file (a Claude session with a pane, or a plain terminal) has an arrow at the left of its row (`.orca-arrow`, an `.icon-btn` of 24 px with a chevron that turns down when open, `aria-expanded`, `aria-label` "セッションを開く" and "セッションを閉じる"); a project with no session has none. Selecting a project (its row, a session row, a row of the working view, or a session started from the plus) opens it and closes no other. The arrow opens or closes its own project whether it is selected or not; it changes only the list, and the selection, the tabs, the panes and the terminals of the work pane stay as they are. Selecting a closed project again opens it. At first every working project is open and the others are closed, and a project opens, also when the user had closed it with its arrow, when a read has a working session in it that the last read that worked did not have (a session that begins to work, or a project that begins to work, above; a project that works with no working Claude row counts as one such work); one whose working sessions are the same as at the last read stays as the user left it. Under an open project (`.orca-sessions`, one level in from the project: its rows start right of the project's name, with the status icon and the title) is one row for each session of its tabs (`.orca-session`, a button: the status icon of the tab and its title, `data-session` the id of the tab; not `data-tab`, which marks a tab of the work pane). A file open in the editor (A-18) and the diff of a file (A-24) are tabs but not sessions, so they have no row. The rows are in the order of the tabs of the project as the work pane first sees them (the order of "Tabs" below, whatever the panes it is split into, A-17). The selected row (`aria-pressed`, the `--soft` background) is the row of the tab selected, which is the tab the focused pane shows (A-17), so pressing a tab in any pane moves the selection of the list to its row (only in the selected project); no row is selected while a file tab is. Pressing a row selects its project (when it is not the selected one) and its tab (it takes the focus of its pane, as pressing the tab does). Whether a project is open is kept in memory only (as the choice of view and the order of the working projects), and the bell (the working view) is unchanged. The order of the working projects is kept in TypeScript with the open state, because it is a state between reads, which Rust does not keep (every read asks the CLI again); the status and the order of the rest stay in the pure function.

Status icons, the same as Orca's. A pure function maps an Orca state word to one of seven: `waiting`, `blocked` and `permission` are `question` (the `message-circle-question-mark` icon, orange); `failed` is a small red dot; `working` is a yellow ring that turns (it stops under `prefers-reduced-motion`); `monitoring` is the `activity` icon; `interrupted` and `unconfirmed` are a small gray dot; `done` and `active` are a green dot ("完了", or "起動中" on the tab of a terminal); `inactive` is a faint gray dot ("動いていない"). The colors are variables in `:root`. A word not known yet is idle for a worktree and working for an agent, as in A-6, and an agent with `interrupted` true is interrupted unless it waits or failed. The status of a row is its agent's; the status of a project is the highest rank among its top-level agents with a live pty, its worktrees' `sidebarStatus` (else `status`), and its plain terminals (a green dot), in Orca's rank: question, failed, working, monitoring, interrupted, done, idle (`unconfirmed` is drawn as interrupted and ranks with it, one place above where Orca ranks it).

The bell (`#orca-bell`, `.icon-btn`, `aria-pressed`, `aria-label` "作業中を表示する", and "作業中の表示をやめる" while pressed) switches the list between the projects and the working view of A-6 (the list pane has no heading). At its right shoulder it shows the question icon and the number of agents that wait; with none, the working mark and the number that work; with none, nothing.

The SSH hosts are read from this machine's Orca over its unix socket (`ssh.listEditableTargets`, `result.targets[]` with `id`, `label`, `configHost`; the socket of A-7, not a public interface), whatever the target is. Only `id` and `label` cross to the screen; the label is the first line of `label`, else the `configHost`, and a target with no `id` or no name is dropped. They are read with the environments (startup, the screen shown, the reload button, a change of the target), never by the clock, and a read that does not say what the target is leaves the ones the screen holds. A failure gives no SSH group and no error line.

Tabs. Selecting a project opens it in the list (its sessions under it, above; the other open projects stay open) and shows its sessions as tabs in the work pane, which is split into panes (A-17; a project that was never split has one pane with all its tabs), and selects the tab that the pane with the focus shows (A-17; the first of a project that has no saved layout). Each pane has its own tab strip (`.orca-tabs`, `role="tablist"`, each tab a `role="tab"` button with `aria-selected`, which is true for the tab each pane shows). The tab bar of a pane (`.orca-tabbar`) is 32 px high at the first size of the work pane (A-20; in proportion to the size chosen, so that its text stays inside), level with the header of the list pane at the first size; it holds the strip (`.orca-tabs`, as wide as its tabs, which scrolls sideways when the tabs do not fit the bar) and, right after the strip, the plus of A-16 (when the tabs scroll, the plus stays in view at the right end of the bar, before the button of the file pane (A-18) in the pane that has it), and it is shown also when the strip is empty. A tab is 28 px high at the first size (in proportion to the size chosen) and at most 220 px wide, the selected one on the `--surface` ground with a thin border; it has the status icon and the title on one line, and a close button (`.icon-btn`, `aria-label` "閉じる") beside it, which never selects the tab. The tabs are the project's Claude sessions (rows with a pane key), and its plain terminals, in the order they were first seen, so a read that reorders the sessions does not move them (a tab keeps its place in its pane, A-17). A project with no session says 「セッションはありません」 in the work pane, with the strip empty, and the plus of A-16 is the way to start one. The selection survives a read while its tab exists; when its session leaves Orca's list the pane shows the tab that followed it, else the one before (A-17). Nothing closes by itself, a finished session included. Every tab is a terminal (below, and A-12): a Claude session shows the terminal of its handle, and a plain terminal its own. A terminal in which `claude` starts is listed as a Claude session under the same handle (and as a plain terminal again when it ends there): its tab keeps its place in its pane, its selection and its screen (A-17).

Closing. The close button of a Claude session or a plain terminal of Orca calls `orca_close(handle, environment)`, which runs `orca terminal close --terminal <handle> --tab --json` (with `--environment=<name>` for a saved environment) with a timeout of 15 seconds; the handle is validated as in A-6, and the environment must be a saved one. The answer's `ptyKilled` is not looked at (it is false on a real machine although the process stops), and `error.code` `terminal_handle_stale`, which is what Orca answers when the terminal was closed first, is a success. On success the screen reads the list at once (a streamed list, A-12, says it by itself and is not read) and the tab leaves with it; on a failure the message is shown (`#error`) and the tab stays. A tab whose session is gone from Orca's list leaves at the next read. A Claude session with no terminal handle cannot be closed.

Terminals of Orca. A terminal of `orca terminal list` that no Claude row of the same read holds (A-6: the row's handle is the terminal's; a shell, or another agent), still has its tab (not `orphaned`), and is in the worktree of a project is a tab of that project, titled by its `title`, with the green dot; the floating terminal has no worktree and is left out. A Claude session's tab shows the terminal of its handle. The kind is the row's alone, and `agentIdentity` is not looked at, because Orca sets it from the process or the title before `worktree ps` has the agent (and the other way round when the agent ends): so in every read a terminal is held by a Claude row or is a plain terminal, never neither and never both. Every terminal is drawn by xterm.js (`src/vendor/xterm.js`, `xterm.css`, `addon-fit.js`, `addon-unicode11.js` and `addon-web-links.js`, kept as distributed, with their version and license in a comment, and read as classic scripts by `ts/vendor-load.ts` the first time a terminal is to be shown, not at start-up, so a terminal waits for that one read and the start of the app does not; the CSP is unchanged; scrollback 5000 lines; `ts/orca-terminal.ts`). The colors of every terminal, and of the pane around it, are those of the theme chosen in the settings for the appearance of A-15 (by default the system's, A-14); the font and the keys that send a text are Ghostty's (A-13). With a saved environment as the target the terminal is streamed (A-12). With this machine as the target the tab is a mirror, because this machine's Orca cannot stream the bytes of a terminal to this app (A-12 has the measured reason): sized to its pane when it is shown (`fit`, and a `ResizeObserver` on the host element of each pane whose fit waits until the size has rested for 50 ms), and while it is shown (in each pane, the tab it shows, A-17) the screen reads the terminal over this machine's unix socket (the socket of A-7; `terminal.read` with `{terminal, screen: true}`, which is what `orca terminal read --screen` sends, so no CLI process is started: the CLI costs about 0.1 seconds of start-up each) every second, one at a time, and takes `result.terminal.tail`, an array of lines with no colors; an answer with no `result.terminal.source` is an Orca that ignores `screen` (it answers the accumulated output), which is refused with a message to update Orca, as the CLI refuses it (`incompatible_runtime`), and draws the frame again in xterm.js when it changed. The keys typed are sent with no Enter added, so control bytes reach the terminal as typed, batched (at most 50,000 characters a send) and one send at a time, and the frame is read again soon after while the terminal is shown; the keys not sent yet go on to the terminal when it stops showing, and are dropped only when it leaves the list (A-12). What is typed can be a password, so it is kept out of the arguments of a process (`ps` shows them): the keys go to this machine's Orca over the unix socket of A-7 as `terminal.send` (`{terminal, text, enter: false, client: {id: "cookapps", type: "desktop"}}`, as the CLI sends them; the answer's `result.send.accepted` false is a failure). A key text is not checked for blank, but it may not be empty or hold a NUL or more than 100,000 characters. The handle must belong to a row or a plain terminal of the list read just now, for a read as for keys; it is checked the first time a read or keys go to that handle, and again after a read or a send of it failed. The mirror has no text colors (it draws the screen in the theme's foreground on its background), a full-screen program is only approximate, and a size change is not sent. A terminal's screen and keys are in no log line, error text or event of the app. A failed send shows its message (`#error`); a failed read is tried again at the next second. The reads of a terminal stop while another tab is shown in its pane, another screen is shown or the window is hidden (the terminals shown read at once when the window is shown again), and the screen of a terminal is dropped when it leaves the list or the target changes. Links. A URL in the text of a terminal (this machine's mirror and a saved environment's stream alike), and a link that a program sets with OSC 8, is a link: the text `http://` or `https://` up to a space, a quote, a bracket, or a full-width punctuation mark or bracket (U+3000 to U+303F and U+FF00 to U+FFEF, so a URL in a Japanese sentence ends where the sentence goes on), found by `addon-web-links.js` (`@xterm/addon-web-links` 0.12.0, the version that goes with xterm.js 6.0.0) and, for OSC 8, by `linkHandler` of xterm.js with `allowNonHttpProtocols` (as Orca sets it; without it xterm.js drops a link of another scheme before the click), both with the same click rule. A click opens the link in the default browser only with ⌘ held, Ctrl and Alt not held, and the left button; a click without ⌘ selects as before. After it opens, the selection is cleared. While the pointer is over a link, the URL is the `title` of the terminal's box. The click calls `orca_open_url(url)`, which reads the URL again with the `url` crate and opens it with the opener only when its scheme is `http` or `https` and it has a host (any other scheme, such as `file:` or `javascript:`, and text that is no URL, fail with 「開けるのは http か https の URL だけです」, shown in `#error`). The rules follow Orca 1.4.250's own terminal and its `shell:openUrl`.

Keys. While a terminal has the focus the app's own key handlers do not act: Escape only closes a menu, popup or hint that is open (none is while a terminal is clicked), and Cmd+Z of the inbox leaves a textarea's own, which is xterm.js's input. Cmd+C copies the selection and Cmd+V pastes, as in any field. Cmd+J of A-19 is the one key that acts then: it moves to the search field.

Unit tests (`cargo test`) cover the status mapping and rank, the activity line, the projects and their order, count and status, the plain terminals, the SSH targets, the screen lines, the stale answer, the arguments of close, read and send, the params and the answer of the screen read over the socket, the params of the keys sent over the socket, the validation of keys and handles (a Claude session's and a plain terminal's), the one-time check of a mirrored handle (kept for each target: a handle checked on this machine or in one environment is not checked for another), and the check of the URL of a link (`http` and `https` only); none touches Orca or the settings folder. The E2E spec `orca.e2e.ts` covers the project list, the arrows and the sessions under the open projects (an arrow only for a project with sessions, the working projects open at first, several projects open at once, a session row indented right of the project's name, the close and the reopen by the arrow with the tabs, the work pane and the number kept, the rows in the order of the tabs, a row selecting its project and its tab and a tab moving the selected row), the order of the working projects (kept through a read that reorders them, a project that begins to work in front and open again, one that stops below, one that only waits below the working ones, one with a working and a waiting session in the group and open through a question and its answer, and one the user closed that opens when another session of it begins to work and stays closed on a read that adds none), the icons, the bell and its badge, the tabs and their selection and order, the close of an Orca tab (with its arguments, a failure and a tab that Orca closed first), and the mirror of a Claude session and a plain terminal (the reads, the frames, the fit inside the pane, the keys and the pause while the window is hidden), and the ⌘+click on a link (the URL sent to `orca_open_url`, nothing sent without ⌘, with Ctrl or Alt, or by another button, the URL cut at a full-width mark and before a closing bracket, the title, an OSC 8 link, and a refused URL shown) in the mirror and in the stream.

The card. It is built when the pane opens (not for each item that is merely in view) and drawn as plain text (`textContent`): a mail is the open thread, oldest message first, each as `差出人: {from}`, `日時: {date}` and its text (the path of the summary, `mailText`), separated by `----`; the title is the subject and the line under it `{sender of the newest message} ・ 本文 {n} 字`. A Slack thread is its messages as the screen holds them, each `{name}  {time}` and the text (the text S-7 sends to Claude); the title is `#{channel} のスレッド` and the line `{first name} ほか ・ {n} 件` (the name alone when there is one author). A Todo is `タスク: {title}`, `プロジェクト: {project}`, `期限: {due}`, `説明:` and the description, and `コメント:` with the comments when they are already loaded (none are fetched for this); the title is the task's and the line `説明 {n} 字 ・ {due}` (`説明なし` when the description is empty). The card of the Slack thread and of the Todo is built again when the thread is read or the task is drawn again, until it is sent or taken off. The card shows no text of the content: its title and the line under it are all it shows, and there is no way to read the text that will be sent before it is sent (the body is exactly the string the command gets as `context.body`). The app does not try to detect hidden text (text hidden by a style, for one), so what a mail holds that the screen does not show is sent with the rest. The card keeps its nodes when it is drawn again (the Slack thread read again, the Todo drawn again, the one-second follow of the host): only their text is set. Another item drops it, and taking the card off drops it. Taking the card off makes the post a plain one, with no block.

The command. `orca_handoff(destination, instruction, files, summary, context, environment)`: `destination` is `{kind: "new", path}` (a worktree); `instruction` is what the user wrote, as it was written; `files` is the text that each upload of A-10 answered; `summary` is the points of Claude's summary of the content (empty without a card); `context` is `null` or `{kind, title, body}`; `environment` is the destination of the pane (`null`: this machine, else a saved environment's name), not the target the Orca screen holds. Rust composes the prompt with pure functions (`orca_handoff::handoff_instruction`, which makes the instruction as it was written, then, after a blank line, each file's text on a line of its own, a blank file left out; and then `orca_handoff::compose`, which quotes the content after it, with the summary inside the block) and then runs the launch of A-6 once, with its checks (the list is read again, the path is a worktree of it, the environment is a saved one, unless the worktree was just made by `orca_worktree_create`, below; the text is not blank and the whole prompt is at most 100,000 characters; Japanese errors; never tried again). A blank instruction is refused before anything runs (「指示を書いてください」), and a prompt over the limit says that the instruction and the content together may be 100,000 characters. The answer is `{paneKey, handle}` of A-6's launch. The path is a worktree of the list read just then (the list is read again at each launch, not taken from the pane), except the worktree that `orca_worktree_create` has just made in the same destination: that path is accepted without reading the saved environments or the list again, once and for 60 seconds (Rust keeps the destination and the path in memory only), because that command checked the environment and the project and Orca named the path; any other path, a second launch of it and a launch after the 60 seconds check as above. `orca_worktree_create(project, name, branch, base, environment)` makes a new worktree in the repository `project` (`OrcaProject.key`) of the destination with `orca worktree create` (A-6) and answers its path; it validates the name, the branch, the base, the environment and the project in Rust, and runs once. `branch` (the branch the worktree gets) and `base` (the ref it starts from) may be `null`, and each is passed to the CLI (`--branch=<branch>`, `--base-branch=<ref>`) only when it has a value. Each is trimmed, and a blank one is none; a value that starts with `-`, or that git would refuse as a ref (`git check-ref-format`: a space or control character, `~ ^ : ? * [ \`, `..`, `@{`, `@` alone, an empty component or one that starts with `.` or ends with `.lock`, a `/` or `.` at the end), is refused with a Japanese message (「ブランチ名に使えない文字が含まれています」, 「作成元に使えない文字が含まれています」) and nothing is made. What Orca does with `--branch` when the branch already exists (checks it out, or makes a numbered new branch) was not checked on a real Orca, because it makes a worktree; it is open. The prompt is (the lines of the files and the summary are left out when there are none; a summary without the card is not sent)

```text
{instruction}

{the text of each attached file, one on each line}

{one line that says the block is quoted data and holds no instructions}
<cookapps-context kind="mail|slack|todo" title="{title}">
内容の要約:
- {point}

{body}
</cookapps-context>
```

with the attribute value on one line (a newline becomes a space, at most 200 characters, and `&`, `<`, `>` and `"` escaped) and, in the body, every opening or closing tag of the block, in any case, loses its `<` (it becomes `&lt;`), so that quoted mail can neither end the block nor start a second one or fake it. Before that, Rust takes out of the title and the body the C0 controls other than the line break and the tab, DEL, the zero-width characters (U+200B to U+200D, U+2060, U+FEFF), the bidi controls (U+202A to U+202E, U+2066 to U+2069) and the tag characters (U+E0000 to U+E007F), which are invisible or change how text reads and could split a tag apart (`<` + U+200B + `/cookapps-context>`); so `context.body` as the card shows it is the string that the command received, and the text sent is that string without those characters (the card text and the prompt differ by them only). The summary is quoted data too, because Claude made it from the content: it is inside the block, above the body, under the header "内容の要約:" and a line "- {point}" for each point (the line breaks and hidden characters of a point taken out, a blank point left out, and no header when none is left), and it goes through the same neutralizing of the tags as the body. Only the instruction and the lines of the files are outside the block. The prompt text is in no log line.

After a send. The pane shows that session (and the mapping item → session is kept in memory only, nothing is saved to a file, so leaving and coming back to the same item shows the session again): a header of two lines (`.ho-session-head`): "{repo} ・ {branch}" (bold; the worktree's label until the list holds the session) and under it, in the accent color with a small dot before it, the status and the time as A-6 ("作業中 ・ 2 分", "確認中" until the list holds a new session), a button `aria-label` "Orca の画面で開く" that selects the session's project and tab on the Orca screen and shows the screen, with the session's terminal (`openInOrca`; the session of a launch that is not listed yet leaves the selection as it is), and the close icon `aria-label` "閉じる", which forgets the mapping of the item (the next open shows the send form; for the mail and the Todo it also closes the pane). Under it, the notice of A-6 when a read failed, and the terminal of the session (`.ho-term`), which takes the rest of the height. There is no field for more instructions and no strip of files: the user types into the terminal, and the files are pasted or dropped on it (A-10). The pane stays as it is until its close icon is pressed, and the terminal follows Orca meanwhile (A-12). The list of the session's own destination (the one it was started with) is read again every 10 seconds while a session is shown (not while the window is hidden, not while the command is missing, and not while a read is on its way) for the header. The terminal. The terminal is that of A-12 (`ts/orca-terminal.ts` is the one place that loads and draws xterm.js; the pane is an owner of the terminals it shows, and shows and lets go of only its own). Before the first read or send of a terminal, Rust checks that the environment is a saved one and that the handle is a terminal of that environment's list read just then (a Claude session's or a plain one, as for this machine's mirror), and does not check it again until a read or a send of it fails. The screen is read every 2 seconds, not every second, because each read starts a process of the CLI (a read of this machine's list by the CLI took 0.3 seconds, measured; a saved environment answers over the network and takes longer); the reads stop while the pane is not in view, as above, and a read does not start while the one before is on its way. When the Orca screen begins or stops streaming that environment while the pane shows the session, the pane's terminal changes from the mirror to the stream, or back, with no change to the pane. ## A-10 Attach a file in Orca

A terminal of the Orca screen (A-8, A-12) and the pane of A-9 take files by paste and by drop, an image or a file of any other kind. Each is put in `.orca/drops/` of the worktree of the session, and its absolute path reaches Claude, which reads the file from that path: a terminal types the path into itself, as Orca's own terminal does, and the pane adds it to the instruction it sends. It works for a worktree of this machine and for one of a saved server (the target of A-6). The file is kept in memory only, in no log line and in no file of this app. Rust is `src-tauri/src/orca_attach.rs`, and the frontend is `ts/orca-attach.ts` (taking, reading and uploading the files, shared) with `ts/orca-terminal.ts` and `ts/orca-handoff.ts`. It was written against Orca 1.4.248, as A-6 to A-9, and the file names and the typed text follow Orca 1.4.253. This was first a part of the composer of the Orca screen (v0.42.0); A-12 replaced the composer by the terminal and retired it, and it is back for the terminal and the pane (#135).

Taking a file. `ts/orca-attach.ts` makes an element take files (`listenForFiles`): a paste takes the files of `clipboardData` (listened to while capturing, since the terminal's own paste handler stops the event; the event is cancelled only when there is a file, so pasting text works as before; a file copied in Finder is one), and a drop takes the files dropped, all of them. While a file is dragged over the element it has a dashed outline (`.dropping`). The elements are the terminal area of each pane of the work pane (`.orca-term`, A-17; the terminal shown in it) and the form of each pane of A-9 before a handoff (`.ho-main` in `#mail-handoff`, `#todo-handoff` and `#st-orca`; after a handoff the terminal of its session takes the files, as the terminal of the Orca screen). `dragDropEnabled` is `false` for the window (`tauri.conf.json` and `tauri.e2e.conf.json`), so a drop gives `File` objects to the page. The other choice, `onDragDropEvent` with the window's file drop on, gives the page only the paths of the files, so a command would have to read a file from a path the page names (a command that reads any file of the machine), and the page would have to find the element under the pointer by itself; the drop events of the page do both, and need no path. `initFileDrops` (called by `main.ts`) puts a document-level `dragover` and `drop` that cancel a drag that holds files, wherever it is outside those elements, so that a file dropped elsewhere does not make the webview navigate to it (a drag with no file is left alone, and the Todo list's row drag uses pointer events). A file that `FileReader` cannot read (a dropped folder is one, and one that reads as empty is refused by Rust with 「ファイルを読めません」) is refused with the message 「{name} を読めません」, and then none of the files of that paste or drop is taken. The file is read with `FileReader` into base64 and a `data:` URL, which is the thumbnail of an image in the pane (the CSP allows `data:`, not `blob:`). Whether the pane draws a file as a thumbnail is decided by its type (`image/*`); what is typed for it is decided in Rust by its bytes.

The terminal. A file taken on the terminal shown is put at once in the worktree of that terminal (`path` of its tab: the row's for a Claude session, the terminal's for a plain one, which `OrcaTerminal.path` carries) with `orca_attach_file(path, name, data, environment)`, `environment` being the target the screen shows. Then the texts the command answered for the files (`AttachedFile.text`: the path as Claude reads it, with one blank after it), in order, go into the terminal: the neighbours whose `bracketed` is true are joined and pasted (`Terminal.paste`, so a program that asked for the bracketed paste gets them as one), and those whose `bracketed` is false are typed as they are (added to the keys not sent yet), by the keys of A-12 (`orca_stream_input`) or those of A-8 (`orca_terminal_input`). A message (a file that cannot be read, a failed upload or send, a file over 20 MiB, refused by the page before it is read, with the message of Rust, and no call of `orca_attach_file`) goes to `#error`, as a failed send of keys does. The paths go only to the terminal the files were put for: when another terminal is shown by the time the upload ends, nothing is typed.

The pane. The form of A-9 (before a send) has a strip `.attachments`, between the card and the field of the instruction, hidden when there is no file; after a send the pane has no strip (the files go to the terminal of the session, above). Each file is a 64 px box (`.attachment`) with a remove button (`.icon-btn`, `aria-label` "{name} を外す"): an image is a thumbnail (`img` with `alt` the file name), and any other file shows its name (`.attachment-name`, set as text, at most three lines). The files belong to the item (the mail, the thread or the task) as its draft does: they stay while another item is in view, and nothing is added or removed while a send of the item is on its way. A file that cannot be read, or that is over 20 MiB (refused by the page before it is read, so it is not added and `orca_attach_file` is not called), or that the upload refuses, gives its message in the line of the failed send (`.pending.fail`). The files are not sent to Claude, and before a hand-over they do not enable the button "Orca に渡す" (it needs the instruction; the other conditions of A-9 are unchanged). On "Orca に渡す", the files are put one by one in the worktree of the destination (the chosen worktree for a new session), to the target of the pane. `orca_handoff` gets the `text` the command answered for each file as `files` and puts each (without its trailing blank) on a line of its own after the instruction and a blank line. A failed upload shows its message, keeps the instruction and the files and sends nothing. The text for Claude of an upload is remembered for the file by worktree and target, so a press after a failed handoff does not put the file there again; a worktree or target that differs puts it again. A success clears the field and the files that were sent; a file still being read when the send began is not sent, and it stays with the item (it is not drawn while the session is shown, and the strip of the form shows it again once the session is closed). The handoff itself is that of A-9 and A-6: never tried twice, and checked against the list read just now.

`orca_attach_file` (it takes a file of any kind) checks, in Rust and in Japanese: the path is absolute; the data is base64 of a file that is not empty and at most 20 MiB (an overlong string is refused before it is decoded); the name is checked as below; then it reads the worktree list of the target just now (as a launch does), requires the path to be in it and takes the `hostId` Orca names for it (none: 「Orca が worktree のホストを答えませんでした」), and refuses a worktree of an SSH host (`hostId` of the form `ssh:{id}`, which has no file calls) with 「SSH の接続先の worktree にはファイルを添付できません」. The page names the worktree (one the list holds) and the file name only, and never a place inside the folder: the file goes in the fixed folder `.orca/drops/`, so nothing can be written outside it.

The name. The file keeps the name it was given (the page sends `File.name`, or `image` for an image and `file` for any other file when it has none), as Orca does for a file dropped on a worktree. The name comes from outside, so Rust refuses one that is empty, `.` or `..`, that holds `/`, `\`, a control character (NUL, a line end, DEL and the C1 controls among them) or a bidirectional formatting character (U+200E, U+200F, U+202A to U+202E and U+2066 to U+2069, which would make the terminal show another name than the file's), or that is over 255 bytes (`NAME_MAX`, 「ファイル名が長すぎます（255 バイトまで）」). Any other character stays as it is (blanks, quotes, `$`, non-ASCII). Whether the file is an image is read from its bytes, never from its name: PNG, JPEG, GIF and WebP by their magic bytes (SVG is not one). An image whose name has no extension (no dot after the first character) gets the one of its kind (`png`, `jpg`, `gif`, `webp`), as Orca names an image pasted with none; any other name is kept as it is, even when its extension says another kind. When the name is taken in `.orca/drops/`, the name is changed by Orca's rule (1.4.253, read in its `app.asar`; the name is split at the last dot unless that dot is the first character, so `.env` has no extension): `{stem} copy{ext}`, then `{stem} copy 2{ext}`, up to `{stem} copy 9999{ext}`; when all of them are taken, the upload is refused with 「同じ名前のファイルが多すぎます」. The stem of a name with `copy` added is cut, on a character, so that the name stays within 255 bytes; an extension too long to leave a stem is refused.

The upload is made over Orca's runtime, as A-7 reads it: this machine over its unix socket, a saved server over its WebSocket (one connection kept for the whole upload), with the pairing read from Orca's files at that moment; no token is in a return value, a log line or an error text. Every call takes `worktree` as `path:{absolute path}`, and a change also takes `expectedExecutionHostId`, the `hostId` above (without it, or with another value, Orca refuses it). The steps, in this order:
1. `files.stat` of `.orca/drops/.gitignore`; only when it answers `ENOENT`, `files.writeBase64Chunk` writes it with the content `*` and a newline, so the images do not show as changes of the repository. A failure of this write is ignored (as Orca does). Any other failure of the `stat` is the upload's.
2. One `files.readDir` of `.orca/drops` (with `limit` 5000, as A-18) gives the names the folder holds, and the first name in the order above that is not among them is free; a folder that answers `ENOENT` (the message of Orca starts with it) holds none. Step 4 refuses an existing file, so a name taken in between (or beyond the page the answer holds) fails the upload and overwrites nothing. Any other failure of the read is the upload's.
3. The bytes are written to `.orca/drops/.orca-upload-{16 hex digits}` (a short name of its own, whatever the file's name is, so it never passes 255 bytes) with `files.writeBase64Chunk` in chunks of 384 KiB (a larger frame closes the host's socket): `append` is `false` for the first chunk (the file is created, and an existing one is refused) and `true` for the others; the folders are created by the call (`files.write` does not create them and is not used).
4. `files.commitUpload` copies the temporary file to `.orca/drops/{name}`, which fails when that exists, so a file is never overwritten.
5. `files.delete` (`recursive` false) removes the temporary file, after the commit and also after a failed chunk or commit; its result is ignored.
The answer is `{ text, bracketed }` (`AttachedFile`), made from `{worktree path}/.orca/drops/{name}`: for an image `text` is the path with a backslash before a blank, a double quote, a single quote, a backtick, a backslash and each of `$ ; & | < > ( ) { } [ ] * ? ! #` (as Orca's own paste of an image path does, and Claude reads the image from such a path, a path with blanks included), and `bracketed` is true, so the screen pastes it as a bracketed paste; for any other file `text` is the path in POSIX single quotes (a `'` inside written `'\''`) and `bracketed` is false, so the screen types it as it is. Each `text` ends with one blank. A path with a control or bidirectional formatting character is refused. Nothing in `.orca/drops/` is deleted later: Orca has no clean-up of it either, and the `.gitignore` keeps it out of the repository.

Errors. The message of a failed call is Orca's code (「Orca がエラーを返しました（{code}）」), never Orca's own message, as A-7 (`LinkError::Remote` holds the message only for the caller to tell `ENOENT`). A saved server whose pairing has only the `mobile` scope answers `forbidden` to these calls; the message then says the pairing has no permission to put files there, with the code. When Orca is not running on this machine, the message of A-7 for the unix socket is shown. `files.*` is not a public interface of Orca: an update can change it, and then an upload fails with a message while the rest keeps working without files.

Unit tests (`cargo test`) cover the kind by the magic bytes, the base64 and the limit, the file name (kept as given, the names refused, the extension added to an image with none, the split at the last dot), the numbered names (Orca's rule, the limit of 255 bytes with the cut on a character, 9999 tries and then the refusal), the name chosen from the names of one read of the folder (a folder not there yet, a failed read), the escaped path of an image and the quoted path of any other file with their `bracketed`, and the refusal of a control or bidirectional formatting character, the refusal of an SSH host, the message of `forbidden`, the `hostId` lookup, the message of Orca held by an error answer, the worktree path of a plain terminal, and the upload driven by a stand-in for Orca's calls (the order of the calls and the `hostId` in them, the chunk sizes and `append`, the `.gitignore` only when missing and its failure ignored, a taken name, a failed commit and a failed chunk with the temporary file deleted and the error passed, a failed delete not failing the upload, a `stat` that fails for another reason); none of them talks to a real Orca. The E2E specs cover, in `orca.e2e.ts`, the terminal of this machine and the stream of a saved environment (the paste and the drop, a paste with no file left alone, the arguments of `orca_attach_file` for an image and for a file that is not an image, the text typed with the handle, an answer that is not bracketed typed as it is while an image is pasted as a bracketed paste, a file that cannot be read refused, a file over 20 MiB refused with the message, with no call of the command, and typing nothing, a failed upload typing nothing, a file dropped elsewhere, the worktree of a Claude session and of a plain terminal, and the tab changed while the file went), and in `orca-handoff.e2e.ts` the pane (the thumbnail of an image and the name of any other file, each with its remove button, the paste and the drop, a file over 20 MiB refused with the message, with no call of the command, a file dropped elsewhere, the button enabled by a file alone, the arguments of `orca_attach_file` and the instruction of a new session and of a running one, also with a blank instruction, a failed upload keeping the text and the images, a press after a failed handoff not uploading again, and an image pasted on the terminal of the session shown, put in its worktree with its path typed there).

## A-12 Orca terminal stream

Every tab of the Orca screen (A-8) is a terminal, drawn from what Orca streams; the work pane shows the tab selected in each of its panes (A-17), so several terminals are streamed at once. Rust is `src-tauri/src/orca_stream.rs`; the frontend is `ts/orca-terminal.ts`, with the list in `ts/orca.ts`. The methods it calls (`session.tabs.subscribeAll`, `terminal.subscribe`, `terminal.updateViewport`, `terminal.unsubscribe` and `terminal.send`) are not a public interface of Orca. They were checked on Orca 1.4.249, and an update can change them; then the list or the terminal of a saved environment says it cannot connect, while this machine keeps working.

Routes. A saved environment (the target of A-6, while it is listed) is streamed over the end-to-end encrypted WebSocket of A-7, with the pairing of `orca-environments.json`, read at each connect and never written. This machine is not streamed, and keeps the routes of A-6 and A-8: its list is read with the CLI by the clock, and its terminal is the mirror of A-8. The reason was measured on Orca 1.4.248's source and on this machine. The unix socket answers one request with one answer and refuses a streaming method with `method_not_supported` (`rpc-request-admission-prologue.ts`); the streaming methods are dispatched only over the WebSocket (`runtime-rpc-websocket-dispatch.ts`). The local WebSocket (the transport `websocket` of `orca-runtime.json`) takes only the token of a paired device, checked against the devices of `orca-devices.json` (`device-registry.ts`, `validateToken`), and the `authToken` of `orca-runtime.json` is none of them (compared on this machine). Streaming it would need this app paired as a device, which writes Orca's device registry, or another device's token; neither is done.

The list. `orca_stream_open(environment, channel)` connects, asks `worktree.ps` (`{limit: 200}`) once, and subscribes `session.tabs.subscribeAll`. Its `snapshots` replace the tabs held of every worktree, `updated` replaces the tabs of one (`removed` drops it), and `end` ends the connection, which is made again. A pure function turns the tabs into the two documents of the CLI that A-6 reads: an agent from the `agentStatus` of each terminal tab (`hasLivePty` while the tab has a terminal handle, `agentType` else the tab's `launchAgent`; Orca drops `agentStatus` for a moment while the pane keeps its terminal, so a tab that launched Claude and has a terminal handle but no `agentStatus` is an idle agent of its pane, `{parentTabId}:{leafId}`, and its row and tab do not come and go with the status), a terminal from each terminal tab with a handle (`parentTabId` and `leafId` as its pane; it is a plain terminal unless a row holds its handle, A-8), and a worktree's last activity the latest of its own and its agents'. So the rows, projects and plain terminals are built by the same functions as A-6 and A-8. `worktree.ps` is asked again only when a worktree with terminals appears that it did not list (once for each), and nothing is read by a clock. The screen gets `list {rows, worktrees, projects, hosts, terminals}` only when the list changed, and takes it as a read that worked; the clock of A-6 reads nothing while the list is streamed, and the reload button still reads it once with the CLI (with the environments). A failed or lost connection, or 60 seconds with no frame (A-7), sends `status {live: false, message}`, which the screen shows as a failed read of A-6 (the orange label and the notice, the rows kept), and is tried again after 1, 2, 5, 10 and then 30 seconds; the first list of a connection, after `status {live: true}`, makes it live again and starts the waits again. A change of the target to this machine, or a target that is not listed, ends the stream (`orca_stream_close`); one stream runs at a time, so a change to another saved environment only calls `orca_stream_open`, which ends the old stream first (a close is a call of its own, and could reach Rust after the open and end the new stream).

The terminal. Showing a tab of a streamed list (the tab selected in a pane, A-17) calls `orca_stream_terminal(handle, generation, viewport, channel)` (the generation is a number the page takes anew for each showing); each terminal shown has its own channel, and the terminals of the other panes stay subscribed. Once the list holds the handle, Rust sends `terminal.subscribe` (`{terminal, client: {id, type: "desktop"}, viewport}`, JSON frames), else the channel gets `ended` with 「このターミナルは一覧にありません」. The client id is `cookapps-` and 16 hex digits, new for each stream. The channel gets `snapshot {data, cols, rows}` (the screen as Orca serializes it, from `scrollback`, or the lines of `subscribed`; it replaces what is drawn), `output {data}` (the bytes printed), `size {cols, rows}` (`fit-override-changed`) and `ended {message}`. A terminal that stops being shown (another tab selected in its pane, a tab that leaves the list, a pane that closes, another screen, or a hidden window) is ended by `orca_stream_terminal_close(handle, generation)`, which sends `terminal.unsubscribe` (`{subscriptionId: "{handle}:{client}"}`), so Orca gives the terminal back its own size. A close names its terminal, so it ends no other subscription, and it cannot end one made after it for another handle, and a close of an earlier generation of the same handle changes nothing (the calls may reach Rust in the other order); the end of the stream ends them all. Showing a handle that is already subscribed subscribes it anew in place of the old subscription. After `ended`, a change of the list does not subscribe that terminal again nor send `ended` again; showing a terminal anew, or the next connection, does. A window shown again, or a connection made again, subscribes again, and a new snapshot replaces the screen.

The owners. Two kinds of screen show terminals: the work pane of the Orca screen and the pane of A-9 after a handoff (A-9), each an owner of the terminals it shows (`showTerminals(placements, focusId, owner)` and `hideTerminals(owner)` of `ts/orca-terminal.ts`, the one place that loads and draws xterm.js). An owner shows and ends only its own; a terminal wanted by two (the session shown on the Orca screen and in the pane) goes to the one that asked last, with its screen and without a new subscription. The Orca screen's pruning of the terminals that left its list (`pruneTerminals`) touches only those of its own target. The stream of a terminal needs the stream of the list (`orca_stream_open`), which is the Orca screen's and for one saved environment at a time, so the pane streams a session only when it runs on that environment (`streamsEnvironment`); any other session, of this machine or of a saved environment, is mirrored in the pane (a saved environment's through the CLI, every 2 seconds, A-9).

Size. The terminal is always fitted to the pane (`FitAddon`), and there is no switch for it. Its size goes with the subscription, and each new size of a terminal's pane goes with `orca_stream_viewport(handle, viewport)` as `terminal.updateViewport` (`{terminal, client, viewport, claim: true}`), so Orca sizes the terminal to its pane; the keys typed claim the pane's size again (below, Keys), because Orca keeps the size of the screen that claimed last and its own screen claims at every key. The size Orca sends is drawn, from the snapshot and each `size`, so the terminal is drawn as Orca has it even when another screen of Orca took the size; the next change of the pane or the next key claims the pane's size again. A size is kept within 20 to 1000 columns and 8 to 500 rows, which both methods take. The mirror of this machine is always drawn at the pane's width. Each terminal is fitted to its own pane (a `ResizeObserver` on the host element of each pane), so a split or a drag of the divider sends the new size of every terminal whose pane changed.

The bottom row. The box of a terminal is placed absolutely inside the host element of its pane (`.orca-term`, `position: relative`), 8 px from its top, right and bottom and 12 px from its left, so the fit measures the space the box has. The fit runs again once the fonts are loaded (`document.fonts.ready`), and the last row is inside the pane, for the mirror too.

Wide characters. `@xterm/addon-unicode11` 0.9.0 (`src/vendor/addon-unicode11.js`, MIT, kept as distributed with its version and license in a comment) is loaded for every terminal, with `allowProposedApi` and `unicode.activeVersion` "11", so an emoji or a CJK character takes the cells Orca's own terminal gives it.

Keys. The keys typed go with `orca_stream_input(handle, text)`, the handle of the terminal they were typed in (validated as in A-6), as `terminal.send` (`{terminal, text, enter: false, client}`, and a stream's send also carries `viewport` (the size Rust holds for the pane, kept within the limits above) and `claimViewport: true`, as Orca's own screen sends them) on the same connection, so they are in no argument of a process. They go only to that terminal, because each send names its handle, and they go also when the terminal is no longer shown (another tab showed in its pane, another screen showed, or the window was hidden meanwhile): a terminal that is in the list of Orca held but not subscribed gets the send with no `viewport` and no `claimViewport`, as it has no pane. A terminal that is not in the list held gets nothing and the answer is 「入力したターミナルは Orca の一覧にないため、送りませんでした」. Unverified: whether Orca takes `terminal.send` for a terminal this app does not subscribe (the CLI, `orca terminal send`, sends with no subscription and works, so it is expected to). One send goes at a time, and the keys typed meanwhile go together in the next (at most 50,000 characters a send; Rust takes up to 100,000, not empty and with no NUL); the keys not sent yet are not dropped when the terminal stops showing (another tab shows in its pane, another screen shows, or the window is hidden): they go on to the terminal they were typed in. They are dropped only when the terminal leaves the list (its tab is gone). An answer whose `result.send.accepted` is false is a failure. With no connection, or no list held yet, or a terminal that is shown but not yet subscribed, the answer is 「接続先につながっていません」, and a connection lost before the answer gives 「接続が切れたため、入力を送れたか分かりません」. A failure shows its message (`#error`). An image pasted or dropped on a terminal shown is put in its worktree and its path is pasted into the terminal by these same keys (A-10).

Selection and the clipboard. A program such as Claude Code tracks the mouse (`?1003h`, `?1006h`) and draws its own selection, so xterm.js sends the drag to it as mouse reports and has no selection of its own; the program then puts what it selected in the clipboard with OSC 52 (`ESC ] 52 ; c ; {base64} BEL`). The terminal answers that request as Orca's own terminal does (`osc52-clipboard.js` of Orca 1.4.250): `term.parser.registerOscHandler(52, …)` takes the target (empty or `c`; any other is ignored), reads the text as base64 of UTF-8 (line breaks and spaces are dropped; a text that is not base64, an empty text, and a request of more than 128 KiB of base64 characters are ignored) and writes it with `navigator.clipboard.writeText`. Requests that come in one chunk of output write only the last, once the chunk is parsed (a microtask, as Orca's own terminal does). A read (the text is `?`) is never answered, so nothing of the clipboard reaches a program. Only what the terminal prints live is made: an OSC 52 request in a snapshot (the screen drawn again after `term.reset()`) or in a frame of the mirror (A-8) writes nothing, so a replay cannot overwrite a newer clipboard. A request comes by the stream and not from an action of the owner, so WKWebView may refuse the write (`NotAllowedError`; it was not checked on a real machine), and nothing is shown for a refusal. The terminal holds the latest text that the clipboard has not taken, and the next copy event of the owner (⌘C or Edit > Copy, which are both an action of the owner) puts it in the clipboard (`clipboardData.setData("text/plain", …)` and `preventDefault`) when xterm.js has no selection, and drops it; with a selection xterm.js copies its own as before. A write that was taken, a new selection in xterm.js (not the clearing of none, which xterm.js reports for a mouse mode, the alternate screen and a resize), and a snapshot also drop the held text. `macOptionClickForcesSelection` is on (as Orca sets it), so Option+drag selects in xterm.js even while a program tracks the mouse, and ⌘C copies that selection. The text is in no log line, error text or event of the app, and nothing is stored.

What a terminal prints and the keys typed are in no log line, no error text and no event but the channel of the terminal shown, and no token or key of the pairing is in any of them. Nothing is stored.

Unit tests (`cargo test`) cover the snapshots, updates and end of the tabs, the list built from the tabs and named by the worktrees, a tab with no terminal, the agent type taken from the launch, a Claude tab without a status kept as an idle row of its pane, the worktrees that make `worktree.ps` be asked again, odd documents, the terminal events, the params and the size limits, where keys go (`input_route`: subscribed, listed but not shown, or refused), and the shape of the events. None of them talks to a real Orca. The E2E spec `orca-handoff.e2e.ts` covers the terminal of the pane of A-9 (mirrored, streamed, and mirrored through a saved environment). The E2E spec `orca.e2e.ts` covers the stream opened for a saved environment and its lists drawn with no clock read, a lost connection, the terminal streamed at the pane's size with its snapshot, output and keys with its handle, the keys not sent yet still sent to their terminal when another tab shows, a failed send, a new size after a drag of the divider, another tab subscribed and the one it replaces closed by its handle, the next tab subscribed and the one that left closed when the tab shown leaves the list (and a close when none is left), the end of the terminal's stream for another screen and a hidden window, and the streams of two panes (each at its pane's size, its events drawn in its own pane, the keys sent to the terminal of the pane typed in, a close that names one terminal, and the new size of both panes after a drag of the divider), a close with no read, the end of the stream when the target becomes this machine, the clipboard written by an OSC 52 request of the output (the target `c` and none, and only the last of one chunk) but not by a snapshot, a read, another target, an empty, too long or non-base64 text, nor by a mirror frame, a refused write that shows nothing and whose text the next copy event takes once, a copy event left to xterm.js after a taken write, the held text dropped by a snapshot, and the last row of a mirror inside the pane.

## A-13 Ghostty settings in the Orca terminal

The terminals of the Orca screen (A-8, A-12) take their font and some keys from Ghostty's config, which the owner reads in once from the settings screen. The colors of the import are read and listed as before, but the terminals draw the theme chosen in the settings (A-14) in preference to them; they use the colors of the import only while no theme has been read. Rust is `src-tauri/src/ghostty.rs`; the frontend is `ts/ghostty.ts` (the card) and `ts/orca-terminal.ts` (the terminals). The app reads Ghostty's files and never writes them.

Where the config is read. This was read from the source of Orca 1.4.250's own Ghostty import (`app.asar`, `out/main/index.js`, the functions that discover, load and map a Ghostty config) and from Ghostty 1.4.0's `ghostty.5.md`; an Orca update can change it. The files are `$XDG_CONFIG_HOME/ghostty/` (`~/.config/ghostty/` when it is not set or empty), then `~/Library/Application Support/com.mitchellh.ghostty/`, and in each folder `config.ghostty` and then `config`. Every one that exists as a regular file of at most 1,000,000 bytes is read, in that order, and their entries make one list: a later entry replaces an earlier one, as in Ghostty. With none, the import fails with 「Ghostty の設定ファイルが見つかりません」 and the places it looked in (shown with `~`). A line is `key = value` with the spaces around `=` free; a line that starts with `#` is a comment, and a `#` after a value is part of it (Ghostty has no comment after a value); a value in double quotes loses them; a line with no `=` is ignored. An empty value gives the key its default again (`font-family =` forgets the families before it). Ghostty's `config-file` is not followed.

Themes. `theme` is a name or an absolute path (a path starting with `~/` too, as Orca has it), or `light:A,dark:B` with both parts, in either order and with the spaces around a name trimmed. A name has no `/` or `\` and is not `.` or `..`. A name is looked for in `$XDG_CONFIG_HOME/ghostty/themes` (else `~/.config/ghostty/themes`), then in `$GHOSTTY_RESOURCES_DIR/themes` when that is set, else in `/Applications/Ghostty.app/Contents/Resources/ghostty/themes` and `~/Applications/Ghostty.app/Contents/Resources/ghostty/themes` (the folders Orca and Ghostty's documentation name); the first folder that holds a regular file of that name of at most 262,144 bytes gives it. A theme file is a config file: only its `palette`, `background`, `foreground`, `cursor-color`, `cursor-text`, `selection-background` and `selection-foreground` are read, and any other entry in it is ignored without a note. The colors of the config itself (the same keys) lie over those of the theme, as Ghostty says. A single theme gives its colors to the light and the dark appearance alike.

What is imported. `font-family` (every entry, in order: the first is the font and the others come after it, then the app's own `"SF Mono", Menlo, Monaco, monospace`, the start of Orca 1.4.254's own list, so that a terminal has the cells of Orca's: on a Mac without SF Mono both draw with Menlo), `font-size` (a number from 1 to 200, in pixels, as Orca takes it), `font-thicken` (`true` or `false`: `true` sets the font weight to 500, so a font without that weight draws as usual), the six colors `background`, `foreground`, `cursor-color`, `cursor-text` (the color under the cursor), `selection-background` and `selection-foreground`, `palette` (`N=color`, N from 0 to 255), `theme`, and the `keybind` entries that send a text. A color is `#rrggbb`, `rrggbb`, `#rgb` or `rgb`; a color name, or a value such as `cell-foreground`, is not imported. A key is `trigger=text:...`: the trigger is one key with its modifiers (`shift`, `ctrl` or `control`, `alt`, `opt` or `option`, `super`, `cmd` or `command`, each at most once), the key a single character or one of `enter`/`return`, `tab`, `space`, `backspace`, `delete`, `escape`/`esc`, `up`, `down`, `left`, `right` (also as `arrow_up` and so on), `home`, `end`, `page_up`, `page_down`, `insert`, `f1` to `f12`, `plus`, `equal`, `minus`, `comma`, `period`, `semicolon`, `apostrophe`, `slash`, `backslash`, `bracket_left`, `bracket_right`, `backquote`. The text is a Zig string literal: `\n`, `\r`, `\t`, `\\`, `\'`, `\"`, `\xNN` (00 to 7f) and `\u{N}`; it is not empty, has no NUL and is at most 1,000 characters. A later key with the same trigger replaces the earlier, `keybind = clear` forgets the keys before it, and a key for another action (or a text that cannot be read) with the same trigger takes the trigger away from the earlier text. In the terminal a trigger matches the key event whose `key` (a single character case folded) is the key and whose Shift, Ctrl, Alt and Meta are exactly the modifiers; Ghostty matches the unshifted character, so `shift+1` does not match. With Alt held, macOS makes another character from the key (Option+B is `∫`), so a one-character trigger with `alt` also matches the key whose `code` names that character on a US keyboard (`KeyB` is `b`, `Digit1` is `1`, and the punctuation and space codes `Minus`, `Equal`, `BracketLeft`, `BracketRight`, `Backslash`, `Semicolon`, `Quote`, `Backquote`, `Comma`, `Period`, `Slash` and `Space`), so `alt+b=text:\x1bb` works. Cmd+J (Ctrl+J outside macOS) is taken by the search of A-19 before any terminal key, so a `keybind` on that trigger never acts. The keys are made once, when the settings are applied.

What is not imported. Every other entry, and an entry of the above whose value cannot be used, is listed with the reason: 「対応していません」 for a key the terminals do not take (`window-width`, `cursor-style`, `config-file`, `font-thicken-strength` and so on, and a `keybind` for `csi:`, `esc:` or another action, with a sequence `a>b`, a prefix such as `global:` or a key such as `key_a`, each with the detail in brackets), or what is wrong with the value. A theme that is not found says which names; with `light:` and `dark:` and one of them found, the found one is imported and the other is listed. A value that is replaced by a later entry of the same key is not listed.

Saving and applying. The import is saved in `ghostty-settings.json` in the app config directory (written through a temporary file and a rename): the settings (`fontFamilies`, `fontSize`, `fontThicken`, `light` and `dark` colors with the palette as `{index, color}`, `keybinds`), the entries imported and left, and the files read. `ghostty_import` reads the files, saves and answers it; `ghostty_saved` answers the file or `null` (also when the file cannot be used). At startup the app reads the saved import and draws every terminal with it; pressing the import button draws the terminals again at once, with the font changed in place (xterm.js `options`) and the terminal shown fitted to the pane again (A-12 sends the new size); the colors of the import show only while no theme has been read (A-14), in the pane around each terminal (`.orca-term`) too, and follow the system's appearance (`prefers-color-scheme`), also when it changes. Without an import the terminals keep the app's own font (A-8). A font chosen for the terminals in the settings (A-20) takes the place of the font of the import (the family and the size; the thickening of `font-thicken` is Ghostty's own and is not drawn with it); the choice 「Ghostty の設定に従う」, which is the first one, keeps the font of the import as above. A failed import keeps the one that was saved and shows the message (`#error`).

Keys. A key of the import sends its text in place of the key: the text goes with the keys typed (A-8, A-12) to the terminal the key was pressed in, once at the keydown, and xterm.js does not see the key's events (its keypress would print the character too). A key pressed while an input method is composing is left to the input method. Shift+Enter, with no other modifier, sends ESC and a carriage return (`\x1b\r`), which is what Orca sends for it when a program has not asked for the Kitty keyboard protocol (xterm.js has none), and which Claude Code's input takes as a newline without sending; a key of the import for Shift+Enter comes first.

The card. The settings screen has the tab Orca (A-3) with one card, 「Ghostty の設定」, in the shape of the other integrations: the header row (the logo, the name and the `?` hint `#ghostty-help` with where the files are, what is imported and the Shift+Enter note), a row `#ghostty-items` and the add row with the button 「取り込む」 (`#ghostty-import`, disabled while an import runs). The row says 「まだ取り込んでいません」 with the gray label 「未取り込み」, and after an import the green label 「取り込み済み」 with the files read (「読んだファイル: …」, each file with `~`); under it, two blocks, each a heading with the number and a list of entries: 「取り込んだ項目（n）」 (`#ghostty-imported`) with each entry as written (`key = value`), and 「取り込めなかった項目（n）」 (`#ghostty-skipped`) with each entry and its reason (`.ghostty-reason`); a block with no entry has the heading only. Nothing is read from Ghostty until the button is pressed.

Unit tests (`cargo test`) cover the file format, the places of the config and of the themes, the font entries and their limits, the colors and the palette, the theme names and the light and dark themes, a theme that is not found or not written right, the colors of the config over those of the theme, the keys (modifiers, named keys, Zig escapes, replacement, `clear`, other actions, sequences and prefixes), the report of the entries left, the files (their order, the limits, a folder, an empty file, no file) read from a temporary folder, the saved file and its case. The E2E specs `settings.e2e.ts` (the card: nothing imported, the import with its lists, the saved import, a failed import) and `orca.e2e.ts` (the terminal's font from the saved import and from an import made in the settings, the text of a key of the import, Shift+Enter, and a key of the import for Shift+Enter) cover the screen.

## A-14 Terminal colors

The terminals of the Orca screen (A-8, A-12) are drawn in the colors of a theme that the owner chooses in the settings, one for the light appearance and one for the dark. Rust is `src-tauri/src/orca_theme.rs` (with the table `orca_themes.json`); the frontend is `ts/orca-theme.ts` (the card) and `ts/orca-terminal.ts` (the terminals).

Themes. The choice is among Orca's built-in themes, which this app holds as a table (31 themes in Orca 1.4.250): for each, the background, foreground, cursor, cursor text, selection background and foreground, and the 16 ANSI colors (the palette colors 0 to 15), all `#rrggbb`. The table was taken from the Orca 1.4.250 installed in `/Applications/Orca.app`: `app.asar` was extracted (`npx @electron/asar extract /Applications/Orca.app/Contents/Resources/app.asar DIR`) and `TERMINAL_THEME_CATALOG` of `DIR/out/shared/terminal-themes/terminal-theme-catalog.js` (the themes of `defaults.js`, `popular-dark*.js`, `popular-light.js` and `classic.js`, in that order) was written out with `node`, with `black` to `brightWhite` as the 16 colors of `ansi`. The same account is in the doc comment of `orca_theme.rs`. An Orca update can add themes or change colors; then the table is taken again. The defaults are Orca's own: `Builtin Tango Light` for the light appearance and `Ghostty Default Style Dark` for the dark. Any theme may be chosen for either appearance.

The choice. It is saved in `terminal-theme.json` in the app config directory, `{"light": "<name>", "dark": "<name>", "appearance": "system" | "light" | "dark"}` (`appearance` is A-15), written through a temporary file and a rename. A name read from the file that is not a built-in theme is replaced by the default of its slot, and a file that cannot be used is as good as none. `terminal_theme_set` takes the choice (`selection`, the two names and the `appearance` of A-15), refuses a name that is not a built-in theme with 「テーマ {name} は選べません」 (nothing is saved), saves and answers the choice. `terminal_themes` answers `{themes, selection}`: the table in its order and the choice in use. The screen asks for it once, at startup.

The first choice. While `terminal-theme.json` does not exist, the first time the settings of the Orca on this Mac can be read they give the choice, which is saved then; after that Orca's settings are not read again, and a later change in Orca is not followed. Whatever the target of the Orca screen is (this machine or a saved environment, A-6), it is this Mac's Orca that is read. The settings are in `profiles/local-default/profile-state.db` of Orca's settings folder (`~/Library/Application Support/orca`), a SQLite file: the row with `domain = 'settings'` of the table `profile_state_documents`, whose `payload` is JSON. This is not a public interface, and it was read on Orca 1.4.250; an Orca update can change it. The file is opened read-only (`SQLITE_OPEN_READ_ONLY`, with a busy timeout of 500 ms; Orca keeps it in WAL mode, so a reader does not wait for Orca's writes) and is never written, and only `terminalThemeLight` and `terminalThemeDark` of the payload are used; the payload is kept and logged nowhere. Orca's `theme` (light, dark, system) and `terminalUseSeparateLightTheme` are not looked at: the app has its own appearance rule, below. A value that is missing, empty or not text gives the default of its slot, as in Orca. A name that is not a built-in theme (a theme the owner added in Orca, which Orca writes as `custom:...` and lists in `terminalCustomThemes`, a plugin's palette `plugin:...`, or a name the table lacks) gives the default of its slot, and the other slot keeps what Orca has. When the file cannot be opened, has no such table or row, or the payload is not a JSON object, the defaults are used and nothing is saved, so that the next start tries to read Orca again. The SQLite library is `rusqlite` (with its bundled SQLite).

Appearance. The terminals take the theme of the appearance that A-15 gives: the system's (`prefers-color-scheme`), also when it changes while the app runs, unless the owner fixes it to light or dark there. Orca's own `theme`, even when it is fixed to light or dark, does not matter. The theme's colors set the terminal (xterm.js `options.theme`: background, foreground, cursor, cursor text, selection, and the palette colors 0 to 15) and the background of the pane around it (`.orca-term`); a chosen theme is drawn in every terminal at once, with no restart, and the colors that Ghostty's import (A-13) sets lie under it: the theme wins, and the import's colors show only while no theme has been read (a failed `terminal_themes`), when they follow the system's appearance. The font and the keys of the import are used as before.

The card. The Orca tab of the settings screen (A-3) holds two cards, this one above the Ghostty settings (A-13), in the shape of the other integrations: the header row (the logo, the name 「ターミナルの配色」 and the `?` hint `#terminal-theme-help`, which says that the light and the dark are chosen apart, that they follow the system's appearance unless the appearance row fixes one of them (A-15), that the themes are Orca's built-in ones, where the first choice comes from, and that the theme comes before Ghostty's colors) and the rows `#terminal-theme-items`. There are three rows (`.item`): the appearance row of A-15, then 「ライト」 (「ライトの外観で使うテーマ」) and 「ダーク」 (「ダークの外観で使うテーマ」), each with a swatch (`.theme-swatch`: the theme's background, 「Aa」 in its foreground, and its 16 colors in `.theme-dots`), the name and a select (`#terminal-theme-light` and `#terminal-theme-dark`, `aria-label` 「ライトのテーマ」 and 「ダークのテーマ」) of every theme, in the order of the table, with the chosen one selected. Choosing a theme sends both names, with the appearance as it is, to `terminal_theme_set`; the selects wait while the save is on its way, the swatch and the terminals follow the answer, and a failure shows its message (`#error`) and leaves the saved choice in the select. Before the themes are read the card has no row, and a failed read shows its message.

Unit tests (`cargo test`) cover the table (31 themes, unique names, the 22 colors of each as `#rrggbb`, the palette colors 0 to 15, the colors of `Builtin Tango Light`), the choice that Orca's settings make (both built in, values missing, empty or not text, a custom, plugin or unknown theme replaced by the default of its slot only, a payload that is not an object), the replacement of an unknown name in a choice, the read of the settings from a temporary SQLite file in WAL mode (the row, no row, no file and the file not made, a file that is not a database, a database of another shape, the file not changed by the read), the saved file and its shape, that a saved choice is not replaced and Orca is not read after it, the first choice from Orca saved once, the defaults used and not saved while Orca cannot be read, a failed save of the first choice, and `terminal_theme_set` with a built-in and an unknown name. None of them reads Orca's real settings folder or the app's config folder. The E2E specs `settings.e2e.ts` (the card above Ghostty's, the three rows, the options and the swatch, a save and its arguments, a failed save, the startup read, a failed read) and `orca.e2e.ts` (the terminal's colors for the system's appearance (the default) and when it changes, the theme over the Ghostty import, the import's colors while no theme was read, a theme chosen in the settings) cover the screen; the E2E page replaces `matchMedia` for the dark appearance (`e2e/fixtures.js`) so that a spec can change the appearance.

## A-15 Terminal appearance

The Orca terminals (A-8, A-12) draw the theme of the light appearance or the one of the dark appearance (A-14). The owner chooses in the settings which one: the system's appearance, or always the light one, or always the dark one. Rust is `src-tauri/src/orca_theme.rs` (the `appearance` of the choice); the frontend is `ts/orca-theme.ts` (the row) and `ts/orca-terminal.ts` (the terminals).

Why. The app's own screens have no dark appearance, so a system that turns dark (macOS "Auto") made the terminals dark under a light app. The owner can now keep them light, or dark, whatever the system does.

The choice. It is one of three values: `system` (the default), `light` and `dark`. With `system` the terminals take the theme of the system's appearance (`prefers-color-scheme`) and follow it when it changes, as A-14 says. With `light` or `dark` they always draw the theme chosen for that appearance, and a change of the system's appearance does not change them. The pane around the terminal (`#orca-term`) takes the same theme. The choice is drawn in every terminal at once, with no restart.

Saving. It is the `appearance` entry of `terminal-theme.json` (A-14), `"system"`, `"light"` or `"dark"`. A file without the entry (written before A-15), or with a value that is none of the three (unknown, not text, `null`), reads as `system`; the names of the themes are read as A-14 says. The first choice taken from Orca's settings (A-14) is `system`: Orca's own `theme` is not looked at. `terminal_theme_set` takes and answers the choice with the `appearance` in it, and `terminal_themes` answers it in `selection`; no new file and no new communication is added.

The row. The card of A-14 has the appearance row first (`.item`, the name 「外観」 and the note 「ターミナルが使うテーマ」, with no swatch) with a select `#terminal-theme-appearance` (`aria-label` 「ターミナルの外観」) of 「システムに合わせる」, 「ライト」 and 「ダーク」, in that order, the saved one selected. Choosing one sends the choice with the other entries as they are to `terminal_theme_set` (and choosing a theme sends the appearance as it is); the selects wait while the save is on its way, the terminals follow the answer, and a failure shows its message (`#error`) and leaves the saved choice in the select. The `?` hint of the card says what the three values do.

Unit tests (`cargo test`) cover the save and the read back of each value, the file shape, a file without the entry and one with an unknown, mistyped or `null` value (read as `system`), that the entry survives the replacement of an unknown theme name, and that the defaults and the choice taken from Orca are `system`. None of them reads Orca's real settings folder or the app's config folder. The E2E specs `settings.e2e.ts` (the row and its options, the saved value shown, a save and its arguments, the appearance kept when a theme is chosen, a failed save) and `orca.e2e.ts` (the terminal fixed to light or to dark when the system's appearance changes, the terminal drawn again at once when the appearance is chosen in the settings, and back to following the system) cover the screen.

## A-16 Start from the plus of the Orca work pane

The work pane of the Orca screen (A-6) starts a session from a plus right after the last tab of the tab bar of each of its panes (A-17), as Orca does: Claude in a worktree, or a plain terminal in it. The list pane's header has no new button. Rust is `orca_terminal_create` and `orca_start` in `src-tauri/src/orca.rs`; the frontend is `ts/orca.ts`.

Why. A session starts where the user is looking: the project selected in the list pane. The plus sits beside the tabs it adds to, and a plain terminal could not be started from the app at all.

The plus. `.orca-plus` (an `.icon-btn` of 24 px with a plus, `aria-label` 「セッションを始める」, `aria-haspopup` "menu"; one in each pane) is the last child of the tab bar `.orca-tabbar` (A-8), after the strip of tabs, which is as wide as its tabs and no wider than the room that is left: the plus follows the last tab, and when the tabs do not fit, the strip scrolls sideways and the plus stays in view at the right end of the bar, before the button of the file pane (A-18) in the pane that has it. It is disabled while no project is selected (a project row, or an SSH host row, of the list pane; a row of the working view selects its project), before the first read, when the command is missing, while a start is on its way and while its tab is waited for (A-6). Pressing it first gives its pane the focus (A-17), so the new tab joins that pane, then opens a menu (`openMenu`, `role="menu"`) of two items, in this order: 「Claude を起動」 and 「ターミナルを開く」, each with a line icon at its left and no colored dot (`CLAUDE_SVG` for Claude, `TERMINAL_SVG` for the terminal: a rounded square with `>_` in it). The start is of the project selected in the list pane, whichever pane's plus was pressed.

Where. The worktrees of the selected project or SSH host are the worktrees of the list that carry its key (`OrcaWorktree.projectKey`: the project key of A-8, the `repoId` on this machine and `ssh:{hostId}` on a host; empty when a repository has none). With exactly one, the start runs in it at once. With none or with two or more, the dialog of the worktrees of A-6 opens under the plus, with only the worktrees of that project (a project with none shows 「該当する worktree がありません」 and nothing starts), and picking one starts there. The target is the one the screen shows, as in A-6.

Claude. 「Claude を起動」 is the start of A-6: `orca_start(path, environment)`, the same checks, the same follow (A-6, "After a launch").

Terminal. 「ターミナルを開く」 calls `orca_terminal_create(path, environment)`, which answers `{paneKey, handle}` as `orca_start` does: `paneKey` is always `null` (a plain terminal has no pane that Orca names) and `handle` is `result.terminal.handle`, `null` when the reply lacks it or holds it in a shape that is not a terminal handle (`term_` and `[A-Za-z0-9_-]`). Rust runs `orca terminal create --worktree path:<path> --json` (`--environment=<name>` when a target is chosen), with no `--focus`, no `--title` and no `--command`, in the temporary folder with an argument list, never through a shell, and a timeout of 60 seconds, once (a lost reply is never followed by a second run). Just before, it validates and reads the list again, as a launch does: the path is absolute, the environment is a saved one, and the path is a worktree of the list read just now; otherwise the answer is a Japanese error and nothing is made. The terminal that was made is a plain terminal of A-8 (no Claude row holds it, it still has its tab and it is in a listed worktree), so it is a tab of its project with no change to the list.

After it. The terminal is followed as a session is (A-6, "After a launch"): the project and the tab that were selected stay, the note and the disabled plus show while it is waited for, and once a read or a streamed list (A-12) holds a plain terminal of that `handle`, for at most 30 seconds, the screen selects its project and its tab, so its terminal shows (mirrored on this machine, streamed from a saved environment, A-8, A-12). Selecting a project or a tab, changing the target or the 30 seconds drop the wait, and a start is never followed after the user selected another project or tab while it was on its way. A failure shows its message (`#error`) and the selection stays. A start made as Claude is waited for as a Claude row only, and one made as a terminal as a plain terminal only.

The CLI. `orca terminal create` was read on Orca 1.4.250 (`orca terminal create --help`, and `cli/handlers/terminal.js` and `cli/terminal-format.js` of its app: the reply is `{ok, result: {terminal: {handle, title, surface, warning}}}`); with `--environment` a remote host needs `--worktree`, which is always given. An Orca update can change it, and then the plus says what the CLI answered. The created terminal is a background tab when Orca's window cannot adopt it (`surface` `background`); it is then waited for until the 30 seconds end.

Unit tests (`cargo test`) cover the argument list of `terminal create` (the path joined to its selector, the environment last) and the reading of its reply (the handle, and a reply that is empty, odd or lacks it), and the project key that the worktrees carry (this machine, an SSH host, none); none runs the real CLI. The E2E spec `orca.e2e.ts` covers the plus (its place right after the last tab, and in view at the right end of the bar when the tabs overflow, and its being disabled without a project), its menu, the start at once in a project's one worktree and the dialog narrowed to the project's worktrees when it has several or none (also for an SSH host), the arguments of a launch and of a new terminal with the target, the following of each (the tab of a Claude session and of a plain terminal, from a read and from a stream) and its being dropped, a failure and the plus disabled while a start is on its way, and that the header has no 「新規」; and the plus of a second pane giving that pane the focus before the start (A-17).

## A-17 Split panes in the Orca work pane

The work pane of the Orca screen (A-6) can be split into panes, as Orca's own window is, and a pane has its own tabs: two terminals can be seen side by side or one above the other. Rust is `src-tauri/src/orca_panes.rs` (the command `orca_panes`); the frontend is `ts/orca-panes.ts` (what Rust answered), `ts/orca-pane-tree.ts` (the panes drawn, and the drag of a tab) and `ts/orca.ts`.

Why. Seeing a Claude session and a terminal together took switching tabs. The owner chose the design of Orca itself (2026-11-08, Discussion #205, issue #191): both directions, the right-click menu of a tab and the drag of a tab as the ways to split, no limit on the number of panes, and a split that is remembered for each project. The tabs of the editor (A-18) are in the same layout; a tab of any kind that joins the work pane's tabs is split, moved and closed in the same way, because the layout holds tab ids and no more.

The layout. The layout of a project is a tree: a pane (its id, its tabs in order, and the tab it shows) or a split of two or more nodes, side by side (`row`) or one above the other (`column`). A pane has at least one tab. A split never has one node, and never has a split of its own direction as a child (they merge). The layout also names the pane that has the focus, which is the pane the plus of A-16 adds its new tab to, and whose shown tab is the selected tab of the project (A-6 and A-8: the row of the working view that is pressed, the badge of A-6 and the following of A-16 all use it). The ids are `p1`, `p2` and so on, the smallest number not used, and mean nothing outside one layout. There is no limit on the number of panes. The panes of a split share its size equally, and there is no divider between them to drag.

Splitting. Two operations split a pane, and both name a tab, a pane and an edge:
- The right-click menu of a tab (`contextmenu` on the tab, a menu of `openMenu` under it) has 「右に分割」 and 「下に分割」: the tab moves to a new pane at the right of, or below, the pane it is in. A pane with one tab has no menu, because the split would leave it empty.
- A tab dragged by the pointer to another pane (pointer events, not the drag and drop of HTML, so the window's file drop stays off as A-10 needs): after the pointer moved 5 px a hint (`.orca-drop`, a frame over the part of the pane that would take the tab) follows it. Over the tab bar of a pane, or the middle of its body, the tab joins that pane's tabs (at the end, and it is shown there); within a quarter of the body's width or height of an edge (the nearest, in a corner), the pane is split there, and the tab is a new pane at that edge (left, right, top or bottom). Releasing drops it, Escape or a cancel leaves it, and the click that follows a drag does not select the tab. The pane the tab is in takes only an edge, and only when it has another tab; its own bar or middle, and an edge of a pane that has no other tab, show no hint and change nothing. A press on the close button does not start a drag.
A tab that moved out of a pane leaves it; the pane shows the tab that followed it, else the one before; a pane left with no tab is closed, and a split left with one node is that node. A new pane is placed beside the pane it was split from, and joins its parent split when that has the same direction. The new pane has the focus.

Focus and selecting. Pressing anywhere in a pane gives it the focus (its tab strip, its terminal, its empty body). Pressing a tab shows it in its pane and gives that pane the focus. The pane with the focus has an accent line on its tab bar while there are two or more panes. The terminal of the pane with the focus takes the keyboard when the focus changes.

The call. `orca_panes(environment, project, tabs, handles, was, op)` answers the layout (`PaneLayout`, `PaneNode`, `PaneOp` and their parts are ts-rs types) of the project `project` (its key, A-8) of `environment` (the saved environment that is the target, or null for this machine). `tabs` is the ids of the tabs the screen shows for the project now, in the order they were first seen (`claude:{pane key}` for a Claude session, `orca:{handle}` for a plain terminal, A-8, `file:{n}` for a file open in the editor, A-18, and `diff:{n}` for the diff of a file, A-24). `handles` is the Orca handle of each of those tabs that has a terminal (a tab id to its handle), and `was` is the same map for the tabs of the call before it for the project that worked (empty for the first one). `op` is what the user did, or null: `focus {pane}`, `select {tab}` (the tab is shown in its pane, and the pane has the focus) or `move {tab, pane, edge}` with the edge `left`, `right`, `top`, `bottom` or `center` (A tab or a pane that the layout does not have changes nothing.) Rust does, in this order, with no clock and no other input:
1. Takes the saved layout of the project (an empty one when there is none), follows the terminals that changed kind (below), and mends it against `tabs`: a layout deeper than 32 levels or with more than 500 tabs was not written by this app and is dropped; a tab that is not in `tabs`, and a tab that a pane already has, leave; a pane id used twice is renamed; empty panes close and single splits merge (above); a tab in `tabs` that no pane has joins the end of the pane with the focus (the first pane when the focus names none, and a new pane `p1` when there is no pane); a focus that names no pane goes to the first pane; a shown tab that a pane lacks is the first of the pane.
   A terminal that changed kind keeps its tab: when Claude starts in a plain terminal, or ends in a terminal of its own, Orca lists the same terminal (the same handle) as `claude:{pane key}` where it was `orca:{handle}`, or the other way round. A tab of the saved layout that `tabs` no longer lists, whose handle is the one `was` gives for it (for a plain tab id, the one in the id), is replaced, in its pane at its place and as the pane's shown tab if it was, by the tab of `tabs` that the layout does not have and that has the same handle in `handles`; so the panes and splits stay as they were. A tab with no known handle (a Claude tab that `was` does not hold, as after the app was restarted) is only a tab that is gone. No call to Orca is added, and the file keeps its shape.
2. Does `op` on the mended layout.
3. Saves it when it differs from the saved one, and answers it. A layout with no tab is not saved and its entry is removed.
The saved layout is not read again by the screen: it keeps the last answer for each project and target in memory, and asks again (`op` null) when the tabs it shows for the selected project are not the ones it asked with the last time (the first time, and each time a tab came or went); a read that did not work, and a target that is switching, ask nothing, so a failed read never takes tabs out of the layout. Calls go one after another in the order they were made, and only the latest answer of a project is taken. A press (select, focus) is shown at once and then sent; a move is drawn when the answer comes. A tab that came is in the pane with the focus when the answer comes, and until then it is not drawn. A failure shows its message (`#error`), and the project then has one pane with all its tabs, which works as before, until the next call that works.

The file. `orca-panes.json` in the app config directory: `{version: 1, entries: [{environment, project, layout}]}`, with `layout` as the tree above (`{root, focus}`, each node `{kind: "pane", id, tabs, selected}` or `{kind: "split", direction, children}`). It holds tab ids and project keys of Orca, which are no secret, and nothing a terminal printed or was typed. It is written with a temporary file and a rename, one command at a time (a lock), and a file that cannot be read, or has another `version`, is taken as empty and replaced by the next save. The command rejects an empty or control-character `environment`, `project`, tab, handle or pane, one longer than 512 bytes, and more than 500 tabs or handles, in Japanese.

Terminals. The terminal of the tab each pane shows is shown in that pane (A-8, A-12): this machine's are mirrors, a saved environment's are streams, one for each pane at once, and each is fitted to its pane. A tab that is not shown in a pane keeps its terminal (its screen and scrollback) but reads nothing and streams nothing. A tab moved to another pane keeps its terminal, which is fitted to its new pane. A terminal that changed kind (above) keeps its terminal too: the screen of a terminal is known by its handle, not by its tab id, so its screen and scrollback are not made again, and the tab keeps its place in the order the tabs were first seen. The keys typed in a terminal go to that terminal, and an image dropped or pasted on it goes to its worktree (A-10).

The empty pane. With no project selected, or a project with no session, the work pane is one empty pane with its tab bar and its plus and the line 「プロジェクトを選んでください」 or 「セッションはありません」; a pane whose shown tab is a session with no terminal says 「このセッションのターミナルはありません」, and a pane shows no line while a start is waited for (A-16).

Unit tests (`cargo test`) cover the mending (a new tab joining the focused pane, a tab that left and the pane that closed, a tab in two panes, a pane id used twice, a layout that is too deep or too big, flattening), selecting and focusing, a split at each edge of a pane (also its own pane, and the shown tab left behind), a tab alone in its pane, a tab or pane that is unknown, a split beside a split of the same direction and of the other, the center, the file (for each project and target, tabs that left, a project with none, a broken file, another version), the checks of the arguments and the shape of the types; none touches the real settings folder. The E2E spec `orca.e2e.ts` covers the call (its arguments with the tabs and with each operation), the panes drawn from the answer (a row, a column and a split in a split, each with its strip and plus, and the focus mark), the right-click menu and its two items, no menu for a pane of one tab, the drag to each edge and to the bar and the middle, the hint and its Escape, the drops that change nothing, the tab that was dragged not being selected, pressing a tab and a pane, the terminals of two panes on this machine and on a saved environment (each read or streamed, its events drawn in its own pane, the keys sent to its terminal, the close that names one terminal, and the new size of both after a drag of the divider), a tab that left and the answer without its pane, the plus of a second pane, and a failed call.

## A-18 Orca files and editor

The Orca screen (A-6) shows the files of a worktree as a tree on the right of the work pane, as Orca's own window does, and a file opens in an editor of cookapps as a tab of the work pane, where what is typed is saved by itself. Rust is `src-tauri/src/orca_files.rs` (the commands `orca_files_list`, `orca_files_ignored`, `orca_file_read`, `orca_file_write`, `editor_settings` and `editor_settings_set`; the language of a file is A-21); the frontend is `ts/orca-files.ts` (the file pane), `ts/orca-editor.ts` (the editor), `ts/editor-settings.ts` (the card of the settings), `ts/orca-pane-tree.ts` (the button and the editor's place in a pane) and `ts/orca.ts`.

Why. Seeing and fixing a file next to the session that works on it took another window. The owner chose the layout and the behavior (2026-11-06, Discussion #119, issue #120): layout A for the file pane and design 1 for the editor.

The file pane. The Orca screen has three columns: the list (A-8), the work pane, and the file pane, with a divider between the work pane and the file pane that the user drags (its width is 15% to 40% of the screen, 22% at the start, and is kept in memory). The pane is hidden at the start. A button shows and hides it; it has the label 「ファイル欄」 and is pressed while the pane is shown. While the pane is shown, it has two rows: the upper row, as high as the tab strip of the work pane, holds the button at its right end, and the lower row is the heading (below). While the pane is hidden, the button is at the right end of the tab strip of the pane in the top right corner of the work pane (the last pane of a row, the first of a column, and so on down to a pane), and no other pane has it. So the button is always one, at the right end of a row as high as the tab strip.
- The heading is the worktree the pane shows: 「{repo} ・ {branch}」, with the button 「ファイルを読み直す」 at its right. While a tab is selected (the tab shown in the pane with the focus, whatever its kind), it is the worktree of that tab, and a tab of another worktree gives another tree, read at once. With no tab (no session and no file open in the project), it is the main worktree of the project selected in the list pane (A-8), that is, the one Orca marks `isMainWorktree` (the repository's own folder; `OrcaWorktree.isMain`, read from the list the screen already holds, with no new call), even when the project has other worktrees. The pane is empty when no project is selected, when the selected row is an SSH host (its files cannot be read, below) or when the project has no main worktree in the list. The git branch of the worktree is a button in the heading, except for an SSH host's worktree, a worktree the list of the screen does not hold and a worktree on no branch (A-25). The tree belongs to one worktree of one target: nothing of the old tree is kept. Why: the files could be seen only after a terminal or Claude was started in the project, which was a nuisance for just looking at the files; the owner asked that the selected project's folder show without one (2026-11-09, issue #268).
- The tree starts with the entries of the worktree's own folder. A folder is a row with a chevron; pressing it the first time opens it and reads its entries from Orca; pressing it again closes it (no read), and pressing it once more opens it again and draws it from the entries that were read, with no read (a file added or removed on the disk in the meantime shows after the reload button below). A folder whose read failed has no entries to draw from, so it is read again when it is opened. Pressing it while its first read is on its way starts no second read. Why: Orca's own window draws a folder it has read without reading it again (2026-11-10, issue #361). Entries are one step in for each level. The folders come first, then the files, each group in the natural order of Orca's own list (a number in a name counts by its value, case does not decide). A folder that holds more entries than the 5,000 one read takes shows 「ほか {n} 件」 under its last entry. A read that fails shows its message in the place of the entries of that folder (an open folder keeps the entries it had).
- What git ignores (Orca's `git.checkIgnored`) is drawn in italics and in a faint color, as Orca does. A folder is drawn from `files.readDir` alone, with no entry marked; after it is drawn the screen asks `orca_files_ignored` for the paths of its entries, and the entries the answer names are drawn in italics and a faint color when it comes (the entries of the list are not redrawn otherwise). The entries a folder that is ignored holds are ignored too (a folder the list marked as ignored is read with `ignored` true, its entries are marked by the list itself, and `orca_files_ignored` is not asked). A folder that is read again (the reload button) keeps the mark of an entry the earlier listing marked, with the same path, until the answer of git comes, which replaces the marks (an entry it does not name loses its mark). A check that fails marks nothing new, leaves the kept marks as they are, and shows no message. An answer that comes after the tree became another worktree's, or after the folder was read again, is dropped. Why: the check took longer than the list and held the folder back, and Orca's own window draws the list first (2026-11-10, issue #363).
- A file open in the editor (of this worktree) is drawn in the accent color. A single press on a file does nothing. A double press (or Enter on the focused row) opens the file.
- The right button on a row, a file or a folder, opens a menu (`openMenu`, `role="menu"`, under the row) of two items in this order: 「パスのコピー」 and 「相対パスをコピー」, and, on a file only, a third, 「ダウンロード」 (A-22), and a fourth, 「差分を表示」 (A-24), and the browser's own menu does not show on a row (the right button elsewhere is unchanged). The first writes the path of the entry on the machine of the worktree (the worktree's path, `/`, and the entry's path from the worktree) to the clipboard, the second the entry's path from the worktree; each says 「パスをコピーしました」 or 「相対パスをコピーしました」 in a notice, and a refused write shows its message in `#error`. The menu closes on a pick, on a press elsewhere and on Escape, and its first item has the focus. Why: the owner asked for a menu in Japanese with the two copies, as Orca's own file pane has (2026-11-09, issue #269); the download of a file (#243) is A-22.
- The reload button reads the root first, alone, and when it is read every open folder again, side by side, at most 16 at a time on this machine and 8 on a saved environment (Orca's own window reads 16, 8 for a paired server); a folder that was read and is closed is dropped, so that it is read when it is opened next. The pane is drawn again once for the reads that end before the next frame. Why: five open folders took about 0.8 seconds one after the other (2026-11-10, issue #361); the root goes first so that the check of the worktree that a read may start (`orca worktree ps`) is not started by every read of the first round at once.

The editor. A file opens as a tab in the strip of the pane with the focus, after the tabs it has, with a file mark in place of the status icon; its title is the file's name. The tab is selected and its editor shows in the pane where a terminal would, with the cursor in the text. The editor has a heading with the file's path (relative to the worktree) and, at its right, the state of the save; under it a text area for the whole file (a textarea that takes the typing; the colors of A-21 are drawn in a layer under it, and a language the highlighter has no grammar for is plain text). The editor and the terminals are switched by their tabs. A file that is open already is selected, not read again. An open file keeps its text, its timer and its save while its tab is not shown, while another project or target is, and while the screen is not; closing the tab drops it.
- Reading. `orca_file_read(path, relative, environment)` answers the text (with LF line ends), whether the file has CRLF, the signature of what the disk holds, and the language of the file (`language` and `highlight`, A-21). It is refused, with a message shown in the place of the editor, when the file is binary, is larger than 384 KiB, is not UTF-8, or has line ends that differ (a CR that is not part of a CRLF at every line end, which a text area would change). The tab stays and can be closed.
- Line numbers. The text has a box of line numbers at its left (`.orca-edit-gutter`, `aria-hidden`), as wide as the digits of its last number (its width is set in `ch` when the count of digits changes, not measured from the numbers). The numbers start at 1, one for each line of the textarea (the empty line after a last line break has its own number; an empty text is one line), right-aligned, in a fainter color (`--muted`) than the text, with the same font family, size (A-20) and line height as the text, so each number is on the line it numbers. The box follows the vertical scroll of the text and stays where it is under the horizontal one; the wheel over it scrolls the text (by pixels, by lines of the text's line height, or by the height of the textarea, as the wheel event counts). A line is not wrapped (`white-space: pre`), so a number is one line. The numbers are not part of the textarea, so they are not selected and not copied, and they are not read aloud. They are kept in step with the text at the read and at each `input` event: only the numbers that came or went are written at the end of the numbers (one text node, not rebuilt), and nothing when the count of lines is the same, so a file of 384 KiB is not drawn again at each key. Why. The line of an error or of a diff could not be found in a file without counting (the owner's issue #378). Not in scope: wrapping a line, marking the line of the caret, and selecting a line by its number.
- Saving. The file is saved by itself, and the screen has no save button. Once the typing has stopped for the time of the settings (below), the whole text is sent with `orca_file_write(path, relative, content, crlf, signature, environment)`; Orca writes it only if the disk still holds the text with `signature`, and Rust answers `saved` with the signature of what it wrote (the next save is made against that), or `changed`, `missing` or `not-utf8` when it refused. A CRLF file is written with CRLF. One save is on its way at a time; typing that came meanwhile is saved when it ends, by the same wait.
- The state at the right of the heading: nothing when nothing was typed; 「保存待ち」 from the first key until the save starts (each key restarts the wait); 「保存中」 while it is on its way; 「保存しました」 when it went through. The tab has a mark of unsaved typing (a dot, with the label 「未保存」) from the first key until a save went through with the text that is in the editor now; then the mark goes.
- A file that changed elsewhere. Before it writes, Orca compares the disk with the text that was read, so the editor never overwrites a change made elsewhere. When it refused, the heading says 「ディスクのファイルが変わっています」 (`changed`), 「ファイルが見つかりません」 (`missing`) or 「ディスクのファイルが UTF-8 ではなくなっています」 (`not-utf8`); nothing is written, the text stays in the editor and the tab keeps its mark, and no save is tried again for that tab (the user opens the file anew after closing it). Why this and not a read of the file's mtime before the write: `files.writeIfUnchanged` of Orca checks and writes in one step, so a change between the check and the write cannot slip through; the signature it compares is the one of Orca's `disk-baseline-signature.js` (two FNV lanes over the UTF-16 code units, and their count), which `orca_files.rs` computes of the text it read (`disk_signature`).
- A save that failed (the connection, a host that lacks `files.writeIfUnchanged`, a pairing that may not write) shows its message in `#error`, and the heading says 「保存できません」; the typing is kept, and the next key tries again. A text over 384 KiB is not sent.
- Closing the tab. A tab with unsaved typing is saved first (waiting for a save that is on its way, and saving what is typed), then closed. A save that cannot be made keeps the tab and shows its message (pressing the close button again tries the save again); a save that was refused (above) lets the tab close, as the heading has said the text is not saved.
- Closing the window. When the page is hidden for good (`pagehide`), the typing of every open file that can be saved (read, not refused, with typing not on the disk) is sent at once, without waiting for its timer, by the same call as a save. The window may close before Orca answers, so the answer is not shown.

The settings. The Orca tab of the settings screen has a card 「エディタ」 above the card of Ghostty (A-13), with the logo, the title and the `?` hint of the cards of the other integrations, and a row 「自動保存までの時間」 with a number field and 「ms」. The time is how long after the typing stops a file is saved: 100 to 3000 ms in steps of 100, 1000 at the start. A value out of the range becomes 100 or 3000, and one between two steps the nearer step (the upper one from the middle). `editor_settings` answers the saved settings and `editor_settings_set(autosaveMs)` saves a number and answers what it saved (so the field shows the value after the change). It is saved in `editor-settings.json` in the app config directory: `{"autosaveMs": 1000}`. A file that is missing or cannot be read gives 1000 (one that holds a number out of the range is brought into it). A failed save shows its message and the field shows the value held; a field that is not a number sends nothing. A change takes effect for the next key typed. The family and size of the text in the editor are chosen in the フォント tab (A-20), apart from the terminals; with none chosen the editor draws in `ui-monospace, Menlo, monospace` at 12.5 px, as before.

The calls. `orca_files_list(path, dir, ignored, environment)` takes `ignored`, whether the list marked `dir` as ignored, and answers the entries of `dir` from one `files.readDir`. `orca_files_ignored(path, paths, environment)` takes the paths of the entries of one list (at most 5,000, each checked like a file's path below) and answers those of them that `git.checkIgnored` names, in the order asked (a path that was not asked for is never answered; a check that fails answers none). The four file commands (`orca_files_list`, `orca_files_ignored`, `orca_file_read` and `orca_file_write`) take `environment` (the saved environment that is the target, or null for this machine) like A-10 and A-16. Orca is called as A-10 does it: `files.readDir` (with `limit` 5000), `files.read`, `files.writeIfUnchanged` (with `expectedExecutionHostId`, which Orca requires for a change, and `diskPrecondition` with `requireLosslessUtf8` true) and `git.checkIgnored` (at most 2,000 paths a call), over this machine's unix socket and a paired server's WebSocket; the worktree must be one of the target's list (`orca worktree ps`), and an SSH host's worktree has no file calls (a message says so). The three reads (`orca_files_list`, `orca_files_ignored` and `orca_file_read`) do not start the CLI for each call: the worktree is confirmed against the list once, and the path and its `hostId` are believed for 60 seconds after, for that path (compared exactly, as the list is) of that target alone. The confirmation goes earlier when the screen's own read of the target's list no longer holds the worktree (a changed `hostId` is taken in at once, and the time is not renewed), when the environment is no longer a saved one, and when a call made with it fails; a path that was never confirmed, and an SSH host's worktree, are refused as before. `orca_file_write` and the download (A-22), like A-10, ask the list each time. Why: the start of `orca worktree ps` was about 120 ms of the 130 ms a folder took (2026-11-10, issue #362, measured in #360). The relative path is refused, in Japanese, when it is empty (a file), absolute, has a `.` or `..` or an empty element, a control character, or more than 4,096 bytes. Orca refuses the same, and a path outside the worktree. No token is in an error, a log or a return value, and the text of a file is in no log.

Checked against. The names and arguments of the calls were read in the `app.asar` of Orca 1.4.253 and tried on this machine's Orca (a list, a read, a write in a throwaway file of a worktree: with the signature of the text read, with a stale one, of a file that is gone, and of a file whose bytes are not UTF-8); they are not a public interface of Orca. A saved environment (WebSocket) was not tried: it uses the same calls as A-10.

Unit tests (`cargo test`) cover the path checks, the path of an entry, the order of the names and the folders first, the reading of a page and of a bare array of entries, the list of a folder (one call, no mark), the ignored marks asked after it (in the order asked, only the paths asked for), the list of an ignored folder (no check), the chunks of the check, the paths of the check (inside the worktree, at most a list), a failed check, the confirmed worktrees (believed for the target and the exact path, the time up, forgotten after a failed call, dropped by a list read again, dropped with an environment that is no longer saved), the signature against Orca's own values, the line ends and the refusals of a text (too large, truncated, not UTF-8, mixed line ends), the answer of a save (saved, each refusal, an old host's empty answer), what is sent to Orca by a read and a save (with a fake Orca), the messages of failures, a CRLF file written back, the limits of the time and its steps, and the settings file (saved, read back, broken, out of the range); none touches the real settings folder or a real Orca. ## A-19 Search the Orca list

The list pane of the Orca screen (A-8) has a search field above the list. What is typed narrows the list itself, the projects and the SSH hosts, to the rows whose name holds it. It is all in the frontend, `ts/orca.ts`; no command, file or call to Orca is added.

Why. The projects grew in number and the one wanted took a scan of the whole list. The owner chose the layout (2026-11-08, Discussion #199, issue #200): layout B, a field above the list that narrows the list, not a palette in the middle of the screen as Orca's own window has it, because the palette hides the work pane and the field leaves the terminals in view while the row is chosen. The wish to find a row by the name of a worktree or a branch was left out: the rows of the list are projects and SSH hosts, with no row for a worktree (AI decision, written in the issue).

The field. `#orca-search` (`role="search"`) is between the header and the list, with a magnifier, the text field `#orca-search-input` (`aria-label` "プロジェクトを検索", the placeholder 「検索」, which is only the field's name) and, while something is typed, the button `#orca-search-clear` (`.icon-btn`, `aria-label` "検索を消す"). The screen has no other text about the field. The field belongs to the list of projects: while the bell is pressed (the working view of A-6) it is hidden and the working view is not narrowed. The text is kept in memory, so it is still there when the bell is pressed again.
- Cmd+J (Ctrl+J elsewhere), with the Orca screen shown and with the focus anywhere, including a terminal or the editor, moves the focus to the field and selects its text; the working view gives way to the projects first. No other key of the app is Cmd+J (no handler for it in `ts/`, no accelerator in `src-tauri`; Orca's own window uses the same key for its search).
- The match is a part of the row's name, with case ignored; the text is trimmed, and a blank text is no search. A character that a regular expression takes as its own (`.`, `(`) matches itself. Only the name is searched: the name of a project, or the label of an SSH host. The sessions under a project, the worktrees and the branches are not.
- The letters that match are bold (`<b>` in `.orca-project-name`), every place in the name where the text is found.
- The order of the rows is the list's own (the projects first, the SSH hosts under the heading 「SSH」). The heading shows only when an SSH host matches. A row that does not match is not drawn. If that is the selected project, its row goes and the sessions under it go with it (they are drawn only under a row). The selection, the tabs and the work pane do not change with the search.
- When nothing matches, the list says 「一致するプロジェクトがありません」 (while the first read is on its way it says it is reading, as before).
- The keys of the field. One matching row has a line in the accent color (`data-cursor="true"`): the first, until a key moves it; a change of the text puts it on the first again. Down and Up move it to the next and the previous row (SSH hosts after the projects), stop at the ends, and scroll it into view. Enter selects the row (the same as pressing it: the project opens in the list and its tabs show) and keeps the text, so that the list stays narrowed; with no row it does nothing. An Enter or an arrow that confirms an IME conversion is not taken. Escape clears the text and takes the focus out of the field. The clear button clears the text and keeps the focus in the field. A cleared field shows the whole list.

Why this is not a Rust function. The testing rules want logic that needs a test to be a pure Rust function, and this is the one place where that costs more than it gives: the match is `RegExp.test` of an escaped text on a name, as the filter of the worktree dialog of A-16 does with `includes`, and the bold range is what `split` returns for it. A command would be called at each key for a list the page already holds, and would need its own mock in E2E for a one-line comparison. The E2E spec checks the whole behavior on the real WebView (rows kept and dropped, case, the escape of a special character, the bold ranges), so nothing here is left to a reading of the code.

Unit tests (`cargo test`): none; nothing of Rust is added. The E2E spec `orca.e2e.ts` covers the field and its place under the header, the focus by Cmd+J (also from the working view and from a terminal), the narrowing by a part of a name with case ignored, the bold letters at every match, a special character that matches itself, the SSH heading shown only for a matching host, the rows that go with the project that does not match, the line that says nothing matches, the keys (the first row at first, Down and Up and their ends, Enter selecting and keeping the text, no row, Escape, the clear button), the field hidden in the working view with its text kept, and a read in the background that keeps the text.

- メール (the whole screen: the header, the list, a thread and its Orca pane), カレンダー (the whole screen) and Slack (the Slack list with its side menu of S-19, the history of a channel of S-20, a thread and the compose screen): one pick each.
- Todo: プロジェクト一覧 (the list on the left, `#projects`) and 作業スペース (the right side: the header, the list, the detail and the Orca pane of A-9) apart.
- Orca: プロジェクト一覧 (`#orca-list`), 作業スペース（チャットとファイル）(`#orca-work` and `#orca-files` of the Orca screen: the tab strip, the file pane and the heading of the editor), 作業スペース（ターミナル）(the xterm.js terminals of the work pane) and エディタ (the text of the editor of A-18) apart. The Orca pane inside the mail and Todo screens follows the font of its screen.
- アプリ全体 (`app`): every part that no place above holds, that is the settings screen, the side menu, the popups and the tooltips. Its family is also the family of a place whose own family is 「システム標準」; its size reaches only the parts outside the places, and a place keeps its own size.
- 等幅の文字 (`mono`): the family only, with no size (see below). The text of an HTML mail body, the window title and the system's dialogs keep their own fonts.

The card. The tab has one card, 「画面ごとのフォント」, in the shape of the other settings: the header row (the logo, the name and the `?` hint `#font-help`), and under it one row for each place, in the order of the list above (`#font-items`). A row has the name of the screen (`.item-name`), the place (`.item-meta`), a select of the family (`#font-{place}-family`) and a select of the size (`#font-{place}-size`), with `{place}` the area in kebab case (`app`, `mail`, `calendar`, `todo-list`, `todo-work`, `slack`, `orca-list`, `orca-pane`, `orca-work`, `editor`, `mono`). The rows are in the order アプリ全体 (`app`), メール, カレンダー, Todo (the list and the work space), Slack, Orca プロジェクト一覧, Orca 作業スペース（チャットとファイル）(`orca-pane`), Orca 作業スペース（ターミナル）, Orca エディタ and 等幅の文字 (`mono`, the last); the row of `mono` has the family select only (`#font-mono-size` does not exist), and its second text is 「書体のみ」. The family select starts with 「システム標準」 (the app's own: the sans-serif stack of the app, the monospace stack of the terminals and the editor, and, for the monospace text, the stacks as they are), and goes on with the families of the fonts on this Mac in alphabetical order, case ignored; only the select of the work space of Orca has 「Ghostty の設定に従う」 as its second entry. The size select has 8 px to 32 px in steps of 1 px, and, for a size held between two of them (the editor's 12.5), that one too. A family that is held but is not on this Mac stays in its select as 「{name}（この Mac にありません）」, so that drawing the card never changes the choice. While Ghostty's settings are followed, the size select of the work space of Orca is disabled. A select waits (is disabled) while a save is on its way, and has the focus again when it ends. The card shows no text about what the selects do (the `?` hint has it).

The size. The size of a place is the size of its ordinary text, in pixels, as 14 px is the app's own. The text in the place that sets its own size in `src/style.css` takes it in the same ratio: every `font-size` there is its pixels times the variable `--fs`, which is the size chosen divided by 14 (so 21 px makes the text that is 12 px on its own 18 px). The family is not changed for the text that names a family of its own (code, the body of a mail, the monospace parts): those take the family of the place `mono` instead, and the size of the place they are in. The terminals and the editor are not scaled: they take the size itself (xterm.js `fontSize`; the text area's `font-size`).

Applying. At the start the app reads the saved choice and applies it before the settings are opened; a choice made in the card applies when Rust answers, and a failed save leaves the screens as they were. For the HTML screens `ts/font-settings.ts` sets `--ff-{place}` (the family, quoted, with the app's own after it) and `--fs-{place}` on `:root`, and removes them for the app's own family and for 14 px; `src/style.css` reads them on the root of each place. For the places of the Orca work pane the variables are `--ff-orca-pane` and `--fs-orca-pane`, read on `#orca-work` and `#orca-files`. For `app` they are `--ff-app` (the family, quoted, with `-apple-system, sans-serif` after it) and `--fs-app`: `:root` takes `--ff-base` from `--ff-app` (the family that every place falls back to with `var(--ff-{place}, var(--ff-base))`, so a place at 「システム標準」 follows it) and `--fs` from `--fs-app`, and `body` draws with them; a place sets its own `--fs` on its root, so `--fs-app` reaches the parts outside the places only. The settings screen's tabs wrap and its selects have a minimum height, so a large size does not push anything out of the window. For `mono` the variable is `--ff-mono`, the family quoted and followed by a comma, and every monospace stack of `src/style.css` starts with `var(--ff-mono, )` (the body of a text mail `.plain`, the code of Markdown and of popups, the prompt, the diffs and the Slack code); with none chosen the variable is missing and every stack is as it was. The stack of `.plain` keeps `"HackGen Console NF no U+3000"` after the chosen family, so a full-width space is still drawn by the next font as a blank (#114). The color swatch of the terminal themes (A-14), the terminals and the editor's text are not touched. The terminals are drawn with the family (the app's own after it) and size chosen, with the weight normal, and fitted to their panes again; the choice 「Ghostty の設定に従う」 gives them Ghostty's import (A-13) as it was. The editor reads `--editor-family` and `--editor-size`. No font is loaded from outside, and the page has no list of fonts of its own: the families come from Rust.

The families. `font_families` answers the family names of the fonts on this Mac: CoreText's `CTFontManagerCopyAvailableFontFamilyNames` (`objc2-core-text`, the crate that Tauri's own dependencies already contain). The names the system hides (those that start with a dot) and the ones that cannot be used (see below) are left out; the rest are in alphabetical order, case ignored, once each. Other systems answer none. The list is read each time the app starts, and again by a save that names a family (outside the lock of the save, and not at all for a save without one); it is not saved.

The commands. `font_settings` answers the saved settings. `font_settings_set(area, family, size, ghostty)` takes one place (`app`, `mail`, `calendar`, `todoList`, `todoWork`, `slack`, `orcaList`, `orcaPane`, `orcaWork`, `editor` or `mono`; any other name is refused by the type), saves it and answers all the settings. `family` is null for the app's own; a name must be one that `font_families` answers, with the case of the system, or the family that the place holds already (so the size of a place, and the work space of Orca's choice of Ghostty, can still be saved after this Mac has lost the font); anything else is refused, in Japanese, with 「書体「{name}」はこの Mac にありません」. `size` is brought into 8 to 32 and to the nearest half pixel (the upper one from the middle); a size that is not a number is refused with 「大きさが正しくありません」. The place `mono` has no size: the size sent for it is not saved, and its pick keeps 14. `ghostty` may be true only for `orcaWork` (otherwise 「Ghostty の設定に従えるのは、Orca の作業スペースだけです」); the family and the size are kept then, for the day the choice is changed. A save reads the file, changes the one place and writes it again; two saves at once are made one after the other.

The file. `font-settings.json` in the app config directory (written through a temporary file and a rename): an object with a pick for each place, `{"app": {"family": null, "size": 14.0, "ghostty": false}, "mail": …, "calendar": …, "todoList": …, "todoWork": …, "slack": …, "orcaList": …, "orcaPane": …, "orcaWork": {"family": null, "size": 13.0, "ghostty": true}, "editor": {"family": null, "size": 12.5, "ghostty": false}, "mono": {"family": null, "size": 14.0, "ghostty": false}}`. The first values are 14 for the app and for every screen (the pane of Orca included), 13 and Ghostty's for the terminals and 12.5 for the editor, so that nothing looks different until a choice is made. A file written before the places `app`, `orcaPane` and `mono` were added has no key for them and reads with their first values; the `size` of `mono` read from a file is always 14. A file that is missing, is not JSON or is not an object gives the first values. A place that is missing or is not an object gives its first values; inside a pick, each field is mended on its own: a family that is not a string, is blank, has a control character or is over 200 characters becomes the app's own; a size that is not a number becomes the first size, and one out of the range is brought into it and to the half pixel; `ghostty` that is not true or false is the first value, and is false for every place but the work space of Orca. The family of a saved pick is not checked against the fonts on this Mac, so a font that is removed later does not lose the choice (the screen falls back to the app's own font while it is missing). A failed read of the settings (the config directory cannot be found) shows its message (`#error`) and draws no row; a failed read of the families shows its message and leaves the family selects with 「システム標準」 (and 「Ghostty の設定に従う」); a failed save shows its message, and the selects show the saved choice again.

Unit tests (`cargo test`) cover the first values (the app, the pane of Orca and the monospace text included), the old file without the three keys, the new places read from a file and mended, the size of `mono` that stays 14 whatever is sent or read, the size (the range, the half pixel, the middle going up, infinity), the family name (trim, blank, control characters, 200 characters not bytes), the list of families (hidden names, trim, order, case, duplicates), the file (saved and read back, its keys, a file that cannot be used, each field mended on its own, the work space that stops following Ghostty), the setting of a pick (the family checked against the installed ones and trimmed, the other places unchanged, a refused family, a size that is not a number, `ghostty` for the work space of Orca only, each area set in its own place, the area names, among them `app`, `orcaPane` and `mono`) and, on macOS, that the Mac has families to choose from; none touches the real config folder. The E2E spec `settings.e2e.ts` covers the tab (its place among the eight, the eleven rows and their order with no size select for the monospace text, the families offered and Ghostty's only for the work space of Orca, the sizes and the half size, the saved choice shown, a family this Mac lacks, the choice applied at the start, the family and the size sent and drawn at once, the list and the work space of Todo apart, the places of Todo, Slack and Orca, the way back to the system's font, following Ghostty and stopping, the editor's variables, the whole app's family reaching the places at the system's font and its size reaching only the parts outside them, the settings kept inside the window at 32 px, the pane of Orca's variables, the monospace family put in front of the stacks (the `.plain` stack keeping the face without U+3000) and the first values putting no variable, a failed save, a failed read of the settings and of the families, and the hint), and `orca.e2e.ts` covers the terminals (the font chosen, Ghostty's kept while it is followed, a font chosen in the settings drawn with no restart, and the project list) and the editor (the font chosen and the first one, and its heading drawn with the font of the work pane), and the work pane (the file pane drawn with the family and size chosen for it, apart from the list, and with the family of the whole app when none is chosen).

## A-21 Colors in the Orca editor

A file open in the editor of the Orca screen (A-18) is drawn in colors by its language: comments, keywords, strings, numbers, names and so on each have a color. The language is decided by Rust from the file's name, as Orca's own editor decides it, and the colors are drawn by highlight.js in the page. Rust is `src-tauri/src/orca_language.rs` (with `orca_language_associations.json`) and the answer of `orca_file_read` in `src-tauri/src/orca_files.rs`; the frontend is `ts/orca-editor.ts`, with `src/vendor/highlight.min.js`, `src/vendor/highlight-languages.js` and `src/style.css`.

Why. The editor was a plain textarea, and a source file was read as one color. The owner asked that a file open in it be colored by its language, as Orca's own editor does (2026-11-09, issue #296, parts #298 and #299). Everything else of A-18 stays as it was: the automatic save, the mark of unsaved typing, the handling of a file that changed elsewhere, the font of A-20 and the 384 KiB limit.

The language. `orca_file_read` answers two more fields. `language` is the name Orca's editor gives the file (`rust`, `dockerfile`, `plaintext` when it has none), and `highlight` is the name the highlighter of the page knows it by, or null when it has no grammar for it (then the text is drawn plain, as before). The decision is Orca 1.4.254's `detectLanguage` (`out/shared/editor-language/editor-language-detect.js`, `monaco-filename-language.js` and `monaco-language-associations.json` of `app.asar`), written again in Rust as a pure function (`detect_language(path, content)`) with its tables copied. In this order, the first that gives a language wins:
1. The file's name as it is in Orca's table of names (`Dockerfile`, `Jenkinsfile`, `Makefile`, `Justfile`, `CMakeLists.txt`, `.gitignore`, `.env`, `.bashrc` and so on), then the name in lower case in the same table.
2. The extension (from the last dot of the name, in lower case; a name that starts with a dot, `.gitignore`, is all extension) in Orca's table of extensions (`.ts`, `.rs`, `.py`, `.sh` and so on).
3. Monaco's own associations: its file names (`Gemfile`, `Rakefile`, `Vagrantfile`), then the longest of its extensions that the lower-case name ends with (`.hh`, `.csx`, `.vb`; a later language wins an extension that two claim).
4. A name that starts with `jenkinsfile.` is `groovy`; `.env` and a name that starts with `.env.` is `dotenv`.
5. Otherwise `plaintext`. Only a name with no extension then takes the language of its `#!` line (the first 256 characters of the text): the interpreter with its directory, `.exe` and the digits and dots at its end taken off, `env` and its flags skipped, looked up in Orca's table (`bash` and the other shells, `python`, `node`, `ruby`, `perl`, `php`, `lua`, `pwsh`, `groovy` and so on). A name with an extension that Orca does not know (`notes.txt`) stays plain whatever its first line says.

Orca decides again at each key; the editor of this app decides once, when the file is read, so a `#!` line typed into a file that had none colors it the next time it is opened. The name Orca gives is turned into the highlighter's by a table in Rust (`highlight_name`): the same name for most, and a close grammar for some (HTML, Vue, Svelte and Astro as `xml`, Apex as `java`, CUDA as `cpp`, `shell` as `bash`, `bat` as `dos`, `proto` as `protobuf`, `dotenv` as `ini`, `jsonl` and notebooks as `json`, Markdown variants as `markdown`). A language with no grammar in the page (`zig`, `lean`, `hcl`, `csv`, `mermaid` and so on) has `highlight` null.

The drawing. The editor is two layers of the same text (`.orca-edit-body`). The textarea is on top with its text transparent, so the caret, the selection (`--hl-select`) and the typing are its own; under it a `pre` (`.orca-edit-hl`, `aria-hidden`, no pointer events) carries the same text in `<span class="hljs-…">` elements that highlight.js returns, with its text escaped. Both take the same font family and size (A-20), padding, line height and tab width, so the letters sit on one another; the layer is moved by the scroll of the textarea (`transform`) and follows it again when the tab is shown after having been out of the page. The line numbers of A-18 are a third part beside the two layers: the two layers are in a box (`.orca-edit-text`) at the right of the numbers' box, so the layers' position and the text's padding are as they were, measured from the left edge of that box. The layer is drawn when the file is read and after each `input` event, so it holds the text of the textarea (the text of an IME conversion in progress too, without its underline). Up to 30,000 characters the text is colored again once a frame while keys come (the layer is the old one for at most that frame). A longer one is drawn plain at once when it is read and colored 150 ms later; while keys come, the layer keeps its old text and colors and is drawn again, colored, at most once in 150 ms (coloring 384 KiB takes longer than a key). A read that fails shows no layer, as no textarea. Nothing of the colors is saved, sent or logged.

The colors. They are the variables `--hl-comment`, `--hl-keyword`, `--hl-string`, `--hl-number`, `--hl-title`, `--hl-type`, `--hl-attr` and `--hl-meta` of `:root` in `src/style.css` (the colors of GitHub's light theme, each at least 4.5 to 1 on the editor's white ground), and `--ins`, `--del` and their grounds for the added and removed lines of a diff. The editor's ground is `--surface` and the app has no dark appearance for it (the terminals follow the system's, A-14, A-15), so there is one set; a dark set would be a second block of these variables with a dark ground.

The library. highlight.js 11.12.0 (BSD-3-Clause; 25,014 stars, last push 2026-11-01 as read from the GitHub API on 2026-11-09; languages are added by registering a grammar), as the files of `@highlightjs/cdn-assets`: `src/vendor/highlight.min.js` as it is (the common build of 36 languages) and `src/vendor/highlight-languages.js`, 23 more grammars of the same version joined as they are (`dockerfile`, `powershell`, `dos`, `dart`, `scala`, `groovy`, `elixir`, `erlang`, `haskell`, `clojure`, `protobuf`, `cmake`, `nim`, `verilog`, `delphi`, `fsharp`, `julia`, `tcl`, `coffeescript`, `handlebars`, `scheme`, `twig`, `pgsql`). Both are classic scripts that `ts/vendor-load.ts` reads together the first time a file or a diff is colored, not at start-up (#414): until they are read the editor draws the text plain and the diff draws its rows plain, and both are colored once the read is done. highlight.js loads no resource from outside, and the paths are inside `src/vendor/`, so the CSP is not loosened. Monaco, which Orca uses, needs a bundler, web workers and a loader, and CodeMirror 6 needs a bundler; neither fits a page without one.

Checked against. The tables were read in the `app.asar` of Orca 1.4.254 (`/Applications/Orca.app`, extracted with `npx @electron/asar extract`), and the expected answers of the unit test were taken by running Orca's own `detectLanguage` under node. An Orca update can change the tables; then they are taken again. No new call to Orca and no new saved file is added.

Unit tests (`cargo test`) cover the decision of the language against 204 pairs of a path and a text for which Orca's `detectLanguage` was run (names, extensions in either case, Monaco's names and extensions, `Jenkinsfile.*`, `.env.*`, a path with `/` and `\`, empty and dotted names, and the `#!` lines: `env` and its flags, versions, `.exe`, a first line that is not the first, a name with an extension), the order of the decision, that every name of the highlighter is a grammar that the two vendor files hold, that every Orca language in the table of the highlighter is one that Orca decides, the language without a grammar, and the fields of the answer of a read. The E2E spec `orca.e2e.ts` covers the libraries read only with the first terminal and the first colored file (and `inbox.e2e.ts` that the start reads none of them), the layer and its place under the textarea, the tokens of a Rust file (keywords, string, comment) and the text that equals the textarea's, the colors and the transparent text of the textarea, a language with no grammar drawn plain, the text escaped, the colors drawn again at a key, the layer moved with the scroll, a long text drawn plain and then colored, and the colors as variables of the page.

## A-22 Download an Orca file

A file in the file pane of the Orca screen (A-18) can be copied to this PC: the right button on its row opens the menu with the item 「ダウンロード」, and a save dialog asks where to put the copy. Rust is `src-tauri/src/orca_files.rs` (the command `orca_file_download`, which calls `download`); the frontend is `ts/orca-files.ts`.

Why. A file of a worktree on a saved environment (a paired server) could be read in the editor but not taken to this PC, and a file that is not text (an image, an archive, a build output) could not be seen at all. The owner asked for a download in the menu of the file pane (issue #243, part #320).

The menu. The item 「ダウンロード」 is the third of the menu of a file row (A-18), and the menu of a folder row has only the two copies. A pick closes the menu and calls `orca_file_download(path, relative, environment)` with the path of the worktree, the path of the file from it and the target (the saved environment, or null for this machine), as the other commands of A-18 do. The page sends no place to save to.

The save dialog. Rust opens the system's save dialog (`tauri-plugin-dialog`, from the command, as a sheet of the window and without stopping the main thread) with the last part of the file's path as the first file name. The place to save is what the dialog gives and nothing else, so the page cannot make the app write to a path of its choice. A cancelled dialog is not an error: the command answers `null`, and the page shows nothing. The page has no permission of the dialog plugin (no permission of the plugin is in any capability; `capabilities/default.json` holds only the window's drag, A-23): only the command opens it.

The copy. After the dialog, Rust asks Orca the size of the file (`files.stat`), then calls `files.readChunk` (or `files.readPreview` on a host that lacks it, and on a host that lacks `files.stat`, which gives no size to hold the preview to) and writes the file to a temporary file beside the place picked, which is moved onto it when every byte has come (the copy is whole or absent; an old file at the place stays as it was when the copy fails). The temporary file is a new file named `.{name}.part` (`.{name}.{n}.part` when that name is taken, and the name is cut at a character so that the whole fits 255 bytes), so a file or a link of the owner's with that name is never written to or deleted. The file is read 384 KiB at a time, and the reading stops with 「ファイルを読めません」 when Orca sends more bytes than the size said, so an Orca that never says it has reached the end cannot fill the disk; a preview is held to the size too (3 times the size for a text, because a byte that is not UTF-8 comes back as 3). There is no other size limit, and a file that is not text (binary) is copied as it is. The copy is not marked as downloaded (no `com.apple.quarantine` attribute), because it is the owner's own worktree file that the owner copies by hand. On a host that lacks `files.readChunk`, the file is read by `files.readPreview`, and a text file then comes back as a UTF-8 string, so a text that is not UTF-8 is not the same bytes as the original; a binary file is exact. The command answers the name of the file saved, and the page says 「{name} をダウンロードしました」 in a notice; the full path is not shown or logged. A failure (the connection, a file that is gone, a place that cannot be written, an SSH host, which has no file calls as in A-18) shows its message in `#error`, with no notice. The relative path is refused as in A-18. The bytes of the file are in no log, no file of the app except the copy, and no return value.

The same command works on this machine's worktree and on a worktree of a saved environment.

Checked against. `files.stat`, `files.readChunk` and `files.readPreview` are not a public interface of Orca. They were tried on Orca 1.4.254 on this machine (unix socket); a saved environment (WebSocket) was not tried, and uses the same calls. An Orca update can change them.

Unit tests (`cargo test`) cover `download` (the chunks until `eof`, an Orca that never says `eof` stopped at the size, the size from `files.stat` and its failures, a host that lacks `files.stat` or `files.readChunk`, a preview held to the size, the temporary file removed on a failure, a temporary name that is taken or a link in its place left alone, a name of 255 bytes, the old file kept, the paths refused) and the first name of the dialog. The dialog cannot be opened in the E2E build, so the E2E spec `orca.e2e.ts` mocks the command and covers the item on a file row only, the arguments of the call (a file in an open folder too, and no place to save), the notice with the name, nothing shown when the dialog is cancelled, and the message of a failure.

## A-23 No title bar

The window has no title bar: every screen reaches the top edge of the window, and the traffic lights (close, minimize, zoom) of macOS sit on the top of the green icon column (`#sidebar`). The window is set in `app.windows` of `src-tauri/tauri.conf.json` (`titleBarStyle` `Overlay`, `hiddenTitle` true and `trafficLightPosition`), the permission to move the window is `src-tauri/capabilities/default.json`, and the frontend is `src/index.html` and `src/style.css`.

Why. The gray title bar took a band of height off every screen and showed a title (cookapps) the owner does not need. The owner asked for the screens to fill the window to the top (issue #314, part of #222; Discussion #221).

The icon column. The traffic lights are at the top of `#sidebar`, at `trafficLightPosition` x 9 and y 20 (the column is 78px wide, and the three buttons are 60pt wide, 9pt from each side; measured on macOS 27.2.1, where macOS puts the close button at x 9 itself, and x 6 had put the edge of the window over the buttons, #421), and the icons start 48px from the top, below them. Apart from the width of the column, which moves the screens to its right by the same amount, nothing else moves: the header of the list, the bell and the reload of the Orca screen and the bands of the other screens keep their places.

The bands to drag the window by. The band at the top of each screen carries `data-tauri-drag-region`, so pressing an empty place of it and dragging moves the window, and a double press zooms it as the title bar did. The bands are the header of the mail list (`#inbox-header`) and of a thread (`#mail-header`), the bar of the calendar (`#cal-bar`), the header of the Todo screen (`#todo-body > header`) and the row of icons over its right side (`#todo-tools`, T-7), the heading and tabs of the settings (`#settings-head`), the header of the Slack list (`#slack-header`), of a Slack thread (`#st-head`), of the Slack compose screen and of the Todo prompt screen, the header of the Orca list (`#orca-header`), the bar of each pane of the work pane (`.orca-tabbar`, set in `ts/orca-pane-tree.ts`), the bar of the file pane (`#orca-files-bar`), and `#sidebar` itself. The value is `deep` on a band with a title (a press on its text moves the window) and bare on a band whose empty place is the band itself. A button, a link, a field, and an element with a `tabindex` or a role of a control still take the press (Tauri's own rule), so nothing in a band changes what it does.

The list of projects of the Orca screen can be closed (issue #318, part of #222). A button, `.icon-btn.list-toggle` with the icon of a window with a side column (`SIDEBAR_SVG` in `ts/icons.ts`; made by `listToggle` in `ts/list-toggle.ts`), has `aria-label` 「プロジェクト一覧」 and says by `aria-expanded` whether the list is open, so that the Todo screen's list can take the same button. While the list is open, the button is the first in the list's header (`#orca-header`), at its left end, and the bell and the reload keep their places at the right. ## A-24 Orca file diff

The right button on a file of the file pane of the Orca screen (A-18) has the item 「差分を表示」, which opens a tab of the work pane with the difference between the file at HEAD and the file in the working tree (what is not committed yet is in it), side by side or in one column, as the diff of an editor does. Rust is `src-tauri/src/orca_files.rs` (the command `orca_file_diff`, which calls `git_diff` and `parse_diff`) and `src-tauri/src/orca_diff.rs` (the comparison of the lines); the frontend is `ts/orca-diff.ts` (the tab), `ts/orca-files.ts` (the item) and `ts/orca.ts` (the tab among the tabs).

Why. The owner asked to see the uncommitted diff of a file by the right button, as an IDE does (2026-11-11, issue #461; parts #462 and #463). The layout was chosen by the owner: side by side as the first view, and one column by a button of the tab. The difference between commits is not included.

The menu. 「差分を表示」 is the fourth item of the menu of a file row (A-18), after 「ダウンロード」, with a line icon at its left; the menu of a folder row does not have it. A pick closes the menu and opens the tab (below).

The tab. It is a tab of the work pane (A-8) like a file of the editor (A-18): it joins the strip of the pane with the focus, after the tabs it has, with a diff mark (`DIFF_SVG`) in place of the status icon, its title is the file's name, it is selected, and it is closed with its close button (which asks nothing: it holds no typing). Its id is `diff:{n}`, and A-17 keeps it in the layout as it keeps `file:{n}`: the layout holds the id only, and the tab is in memory only, so after a restart the id is dropped from the layout. It is not a session, so it has no row in the list of A-8. A diff that is open for the file already (the same worktree and path) is selected and read again, and no second tab is opened. The tab shows in the place of the editor of its pane, and the tab strip, the split and the move of tabs (A-17) work on it.
- The heading (`.orca-diff-head`, the heading of the editor with the buttons) has the path of the file from the worktree, the count of the blocks of changes (「変更 {n} 件」, or 「変更はありません」 when there is none; nothing while it is read or when it failed), and four icon buttons (`.icon-btn`): 「前の変更」 and 「次の変更」, 「1 列で表示」 (「左右に並べて表示」 while it shows one column; `aria-pressed` is true while it shows one column), and 「読み直す」. A block of changes is a run of rows that are not the same. The two buttons of the changes are off when there is no block, and 「前の変更」 is off at the first block and 「次の変更」 at the last. The button of the view and the buttons of the changes are off while the diff is not drawn (read, failed), and the reload button is off while it is read.
- Side by side (the first view, `data-view` "side"). Each row has the line of HEAD on the left, the two numbers of the lines (HEAD's, then the working tree's) in the middle, and the line of the working tree on the right. A line that is only in one file has a blank on the other side (a gray ground and no number). Lines that were changed pair up, in order, on one row; when one side has more lines in a change than the other, the rest stands alone beside blanks. A removed line (or the left of a changed one) has a red ground, and an added line (or the right of a changed one) a green ground (the variables `--diff-del-bg` and `--diff-ins-bg` of `:root`). Long lines wrap.
- One column (`data-view` "inline"). Each row has the number of the line of HEAD, the number of the line of the working tree, a mark (`−` for a removed line, `+` for an added one, nothing otherwise) and the line. The removed lines of a change come first, then its added lines. A removed line is on the red ground and an added line on the green ground. The choice of the view is one for all the diff tabs and is kept in memory only; it is side by side at the start of the app.
- Colors. The text is colored by the language of the file (A-21: Rust names it, `language` and `highlight` of the answer, from the file's name and the first line of its text) with the highlighter of the editor, with the same colors. HEAD's text and the working tree's are each colored as a whole, so a token of several lines (a comment, a string) is colored on each of its lines. A language with no grammar is drawn plain, with the text escaped. A long text (over 30,000 characters in both) is drawn plain at once and colored 150 ms after, as the editor does.
- Moving. When the diff is first drawn, the rows scroll to the first block of changes. 「次の変更」 and 「前の変更」 scroll the rows to the block that follows or precedes the one last moved to (the row at the middle of the rows), and a block that was moved to stays the one the buttons count from. Changing the view scrolls to the block last moved to. A diff read again keeps the place in the rows. A tab that is taken out of the page (another tab of its pane is selected) and put back keeps its place.
- A reason. When Rust refuses (below) or the call fails, the reason takes the place of the rows, as a refused read takes the place of the editor (A-18), and nothing is shown in `#error`.

The call. `orca_file_diff(path, relative, environment)` takes the same arguments, and checks the worktree against the target's list and the relative path, as `orca_file_read` does (A-18: the worktree is believed for 60 seconds, an SSH host's worktree is refused, a failed call makes the next one confirm the worktree again). It calls `git.diff` of Orca's runtime with the worktree, `filePath` the relative path, `staged` false and `compareAgainstHead` true, over this machine's unix socket or a paired server's WebSocket. It answers the lines of HEAD and of the working tree (with LF; the rows hold their numbers), the rows of the two views, the blocks of changes (the row each starts at in each view) and the language of the file (the one of `orca_file_read`, from the working tree's text, else HEAD's). A file git does not know has no text at HEAD, and one that is not in the working tree any more is its text at HEAD against nothing.
- The reasons. A diff is not returned, and a reason in Japanese is, when Orca says the file is binary (the kind `binary`, or one side binary or an image), when Orca marks the diff too large to draw (`tooLarge`, `largeDiffRenderLimit`) or answers `diff_too_large` (over a paired server, a diff over about 4 MiB), when a side is over 384 KiB, when a side is not UTF-8 (Orca decodes bytes that are not UTF-8 into U+FFFD, as A-18), and when the answer lacks the text.
- The comparison. The lines of each text are compared with Myers' algorithm (the `similar` crate, which works in linear space; a deadline of 2 seconds gives a coarser, still correct, answer). CRLF is taken as LF before the comparison, so a change of the line ends alone is not a change. A line is its text and whether a line feed ends it, so a file that only lost or gained its last line feed differs (as `git diff` says). A change that replaces lines is a row of paired lines (side by side) and the removed lines before the added ones (one column).
- No text of the files is in a log or a file of the app, and no token is in an error or a return value.

Checked against. `git.diff` is not a public interface of Orca. It was read in the `app.asar` of Orca 1.4.255 (the schema `GitDiff` in `git-params.js` and the handler of `git.diff`: a method of the permission `workspace`, with the result `kind`, `originalContent`, `modifiedContent`, `originalIsBinary`, `modifiedIsBinary`, `isImage`, `tooLarge`, `modifiedDeleted` and `largeDiffRenderLimit`), and a saved environment (WebSocket) was not tried. An Orca update can change it.

Unit tests (`cargo test`) cover the lines of a text and the rows (the same text, added and removed lines, changed lines that pair up and the rest of the longer side, a file with no line at HEAD or in the working tree, CRLF, the last line feed, the blocks of changes in both views, and two texts of 12,000 lines compared in time) and the answer of Orca (a new file, a deleted one, the reasons, the sizes, the arguments of `git.diff` and `diff_too_large`). The E2E spec `orca.e2e.ts` mocks the command and covers the item on a file row only, the arguments of the call (a file in an open folder too), the tab and its title, the two views and the button between them, the blanks and the grounds, the colors of the tokens (a comment of two lines on both), the plain text for a language with no grammar, the buttons of the changes (the rows scroll), a diff with no change, the reason in place of the rows and the reload after it, the second pick selecting the tab and reading again, and the close of a tab.

## A-25 Switch the branch from the Orca file pane

The branch in the heading of the file pane of the Orca screen (A-18, 「{repo} ・ {branch}」) is a button. Pressing it opens, right under it, a list of branches with a filter field, and picking a branch switches the worktree of the pane to it. Rust is `src-tauri/src/orca_files.rs` (the commands `orca_local_branches`, `orca_remote_branches` and `orca_switch_branch`); the frontend is `ts/orca-branch.ts` (the list), `ts/orca-files.ts` (the heading and the button) and `ts/orca.ts` (which worktree the pane shows, and the read of the list of Orca after a switch).

Why. The heading showed the branch but could not change it. The owner asked to switch the branch from there (2026-11-11, issue #438; parts #439, #440 and #441). The layout was chosen by the owner: layout A, the button in the heading with the list right under it, the tree staying in view.

The button. The branch is a `button` (`.orca-branch-btn`, `aria-expanded` while its list is open); the part before it stays text. The branch is the git branch the worktree is on (`branch` of `orca worktree ps` without `refs/heads/`, `OrcaWorktree.gitBranch`), not Orca's name of the worktree (`displayName`, `OrcaWorktree.branch`, the name in the heading): a worktree made with a name keeps that name after a switch (Orca 1.4.256), so the two can differ. When the name ends with the branch the button is that end of the name; otherwise the button follows the name, after 「 ・ 」 (「{repo} ・ {name} ・ {branch}」). It is a button only for a worktree that the list of the screen holds, whose name in the heading is the list's, that is on a git branch (a detached HEAD, or a `branch` that is not `refs/heads/...`, gives none), and whose project is not an SSH host's; elsewhere (an SSH host's worktree, whose branches Rust does not read, and a worktree the list lacks, or one on no branch) the heading is the plain text it was. The heading is drawn again only when the name or the branch changes, so the button stays while its list is open.

The list. It is a dialog (`role="dialog"`, `aria-label` 「ブランチ」) of the same make as the list of worktrees of the plus (A-16: the class `orca-dest-pop`, a filter field with the focus, a scrolling list under it), opened under the button and closed by a pick, a press elsewhere and Escape. It has two sections with a heading each, 「ローカル」 and 「リモート」, and a row is a button with the name of the branch (`data-kind` `local` or `remote`, `data-name` the name).
- Local. The branches of `orca_local_branches(path, environment)`, in its order (the one checked out first), read when the list opens. The filter narrows them by the text (a part of the name, case does not count). The branch the worktree is on has `aria-current="true"` and a check mark at its right; pressing it only closes the list. A branch another worktree has checked out (`inUse`) is drawn faint and is disabled: it cannot be picked, because git cannot check a branch out in two worktrees.
- Remote. The branches of `orca_remote_branches(path, repo, query, environment)`, named as Orca names them (`origin/feature/a`), where `repo` is the key of the project of the worktree (`OrcaProject.key`) and `query` the text of the filter, trimmed. It is asked once when the list opens (an empty text) and again 250 ms after the typing stops, and the rows are narrowed by the text at once as well, so a typing key does not leave the old rows until the answer. An answer that comes after a newer question, or after the list closed, is dropped.
- A section with no row to show says 「該当するブランチがありません」 once its answer has come, and a read that failed shows its message in its section (in the warning color) and does not empty the other.

The switch. A pick closes the list and calls `orca_switch_branch(path, kind, name, environment)` with `kind` `local` for a local row and `remote` for a remote row (Orca makes the local branch that tracks it). A new branch cannot be made from here. When it answers, the tree of the pane is read again from the root with the folders that are open (the reload button of A-18) and the list of the screen is read again (`refreshOrca`), so the heading shows the new branch; the tabs of the work pane, the editors among them, stay open and are not read again, and a file whose text differs from the disk is refused at its next save by A-18's own check. A switch that worked with a `warning` (a step after the switch failed) shows 「{branch} に切り替えました: {warning}」 in a notice. A refusal (a change not committed, a merge or rebase in progress, an agent at work, and so on) shows Orca's own words in `#error`, as the other errors of the pane do, and nothing is read again. When the pane comes to show another worktree, an open list is closed.

The calls. `orca_local_branches` and `orca_remote_branches` check the worktree against the target's list and refuse an SSH host's, as the file commands do (A-18); `orca_switch_branch` reads the list each time, as a save does, and forgets what it believed of the worktree afterwards. The names and the answers were read in the `app.asar` of Orca 1.4.256 and are not a public interface; `git.switchBranch` was never run on a real Orca, because it changes a worktree, and a saved environment was not tried. An Orca update can change them (`AGENTS.md`, the technical constraints).

No screen text explains the list; the filter field and the list are named by their `aria-label` and headings only (`frontend.md`).

Unit tests (`cargo test`) cover the git branch of a worktree read from the list (`worktrees_of` in `orca.rs`: `refs/heads/` removed, none for a detached or missing one), the branches read, the remote search, the checks of the arguments and the answer of a switch (`orca_files.rs`). The E2E spec `orca.e2e.ts` mocks the commands and covers the button and its place in the heading, the list under it with the two sections, the mark of the current branch, the faint and disabled branch in use, the filter on the local rows, the remote question (the arguments when it opens and after the typing), a pick of a local and of a remote branch (the arguments of the call, the tree and the list read again, the tabs kept), a switch with a warning, a refusal in `#error`, a worktree whose Orca name differs from its git branch (the button shows the branch, before and after a switch), no button for a worktree on no branch, and no button for an SSH host's worktree.
