# Integration requirements

## A-1 Claude integration

A local MCP server (`cookapps-mcp`, stdio) lets Claude list, read, archive, mark read and trash inbox threads, and list events

## A-2 Claude model and effort

The Claude tab of the settings screen has a card "モデルと effort" (shown whether or not Claude can be used; the columns are headed "用途", "モデル" and "effort", and a note says the next call uses the choice and the default is Sonnet and medium, Sonnet and high for the Slack thread conversation, so the options carry no "(デフォルト)") with, for each of five purposes, a name, where it is used, and two narrow selects that choose its model and its effort: the Slack summary (S-2, "Slack の要約", used when a Todo is made from a Slack message), the mail summary (M-8, "メールの要約", the AI summary of the mail detail), the prompt conversation (S-3, "プロンプトの会話", editing the Todo summary prompt with Claude) the Slack text proofreading (S-4, "Slack に貼る文章の校正", the "Claude と校正" pane) and the Slack thread conversation (S-7, "Slack のスレッドの相談", the Claude pane of the thread detail). Each `claude -p` call uses the model and effort of its own purpose. The model is Haiku, Sonnet (the default) or Opus (Fable is not offered; a saved `"fable"` is an invalid value and gives Sonnet). The effort is low, medium (the default), high, xhigh or max, and `--effort` is always passed. Changing the model also switches the effort to the one the documentation recommends for it, saved in the same write: Haiku medium, Sonnet high, Opus medium (Rust `recommended_effort`, from https://platform.claude.com/docs/en/build-with-claude/effort, "Recommended effort levels"); the screen sends the model alone, and `claude_model_settings_save` takes an optional `effort` that defaults to the recommended one, while changing the effort sends both. The first default (nothing saved) stays Sonnet and medium, and Sonnet and high for `slackReply`. An effort select is colored by its value (`data-effort`, variables in `:root`): low gray, medium green, high yellow, xhigh orange, max red, following a change, a save and a failed save; the settings card colors the background and the text, and the frameless select of S-3 the text only. A change is saved at once, for that purpose only, in `claude-settings.json` in the app config directory (an object keyed by `slackSummary`, `mailSummary`, `promptChat`, `proofread` and `slackReply`, each `{model, effort}`; one save reads the file again, changes one purpose and writes all five through a temporary file and a rename), and the next call uses it. Rust checks the purpose, the model and the effort against their lists when saving (a refusal is a Japanese message), and a missing file, an unreadable file or an invalid value gives the default for that purpose, so only a listed value reaches `--model` and `--effort`. A file in the old form, one `{model, effort}` pair for every call, gives that pair to all five purposes until a purpose is saved, and a file without `slackReply` gives that purpose its default. From high up (high, xhigh, max) a call may run 300 seconds (`--effort max` took 61 seconds on a small input); below that it is 60 seconds for the summaries and 120 seconds for the prompt conversation and the proofreading. The `?` hint of the Claude card says that each of the five calls has its own model and effort. The thread detail of S-6 shows the selects of `slackReply` under its request field, as S-3 shows those of the prompt conversation. The screen of S-3 shows the selects of the prompt conversation too

## A-4 Claude connection

The `claude -p` calls of M-8, S-2, S-3, S-4 and S-7 go through the Claude Code CLI, which signs in either with the Claude subscription (the default) or with an Anthropic API key. The first card of the Claude tab ("Claude", with ↻ and `?`) has two rows with radios, "サブスクリプション" (email, plan, Claude Code version and state: ログイン中, 未ログイン with the `claude auth login` guidance, 未導入, 確認できません) and "API キー" (the workspace ID when Anthropic says it, the note that every call is billed, the state 未登録, 確認済み, 確認できません or 使えません, "貼り直す" and the disconnect button), so the state of the one not in use shows too. Pressing the radio of the API key row with no key stored, or with a key Anthropic refuses, only opens the key field ("確認して保存"); nothing is switched or logged out. If the keychain cannot be read, only the key row says 確認できません with the error; if asking for the connection itself fails, the card shows one failed row with the error and no radio, so nothing can be pressed, and Claude is in its failed state. At start only `claude_status` is called (so a start without the settings never asks Anthropic about a key); `claude_connection`, which answers the three parts of the card and the usable state `claude` with each state read once, is called when the Claude tab is first shown, by ↻ and after a change of the connection, and only the latest answer of the reads is used. While a change is on its way ↻ and the radios wait, and so does the button of the key field (also while the states are being read); sending the field while a change is on its way does nothing and does not empty it. A change of the connection redraws the connection card only, so the model selects and the prompt row keep their place and focus. Only the radio of a row switches the method (the radios are not grouped by name, so the arrow keys move none of them, and are disabled while a change is on its way); clicking or double-clicking the text of a row does nothing. The key is never shown, and the field is emptied as soon as it is read. The method is saved in `claude-auth.json` in the app config directory (`{"method":"subscription"|"apiKey"}`, written through a temporary file and a rename; a missing file, an unreadable one or an invalid value gives the subscription), and the key is in the OS keychain (service `jp.mysis.cookapps.claude`). Rust does not call the API for the work: the `claude -p` child process gets the key as `ANTHROPIC_API_KEY`, and `ANTHROPIC_AUTH_TOKEN` is taken out (the CLI prefers it) together with `ANTHROPIC_BASE_URL`, `CLAUDE_CODE_USE_BEDROCK`, `CLAUDE_CODE_USE_VERTEX` and `CLAUDE_CODE_USE_FOUNDRY` (they would send the key to another host or provider than the one it was checked against), while the subscription takes `ANTHROPIC_API_KEY`, `ANTHROPIC_AUTH_TOKEN` and `CLAUDE_CODE_OAUTH_TOKEN` out. The key is in no command-line argument, log line or error text. `claude auth status` answers `loggedIn: true` for a made-up key (measured), so it does not check a key. A pasted key is trimmed, must start with `sk-ant-` and must not be an Admin key (`sk-ant-admin`) (a refusal is a Japanese message), then `GET https://api.anthropic.com/v1/models?limit=1` with `Authorization: Bearer` and `anthropic-version: 2026-10-21` (a short timeout) asks Anthropic, and the response header `anthropic-workspace-id` is shown on the key row. 401 and 403 mean the key cannot be used; any other failure means it cannot be checked. At registration neither is saved. When `claude_status` asks again later, a key that cannot be checked stays usable (only the state says 確認できません), and a key Anthropic refuses is not usable. A key registered from the field that the radio of the API key row opened (`claude_key_save` with `switch`: after the check, the keychain write and the `claude-auth.json` write), and pressing the radio of a stored key (`claude_method_set` asks Anthropic first and refuses a rejected key; one that cannot be asked about is let through), switch to the API key and run `claude auth logout` for Claude Code, unless the API key is the method already (then nothing is logged out, so a login made again by hand is kept). The logout is checked by reading `claude auth status` again (that alone, no `--version`): only logged out or no Claude Code counts, and a login that remains, or a status that cannot be read, means the logout is not confirmed (the switch stays). `claude_method_set` then answers an error; `claude_key_save` answers that the key is stored, with `logoutError`, and the screen closes the field and shows that text as the error. A key pasted again with "貼り直す" (`switch` false) only replaces the key: the method does not change and nothing is logged out. Going back to the subscription only changes the method (the key is kept, and a logged-out row says 未ログイン with the `claude auth login` guidance). Deleting the key asks for confirmation, and when the key was in use the method goes back to the subscription (the logout is not undone). The usable state the whole screen follows (`Claude`: the sidebar, Todo, M-8, S-4, S-7, S-3) is `ready` for a logged-in subscription, or for an API key that is not refused (then email and plan are empty, the sidebar popup and the button's `aria-label` say "API キー" instead of the email); it is not `ready` while the key is refused or missing. The `?` hint explains the key (made in the Console, limited to a workspace, kept in the keychain, switching logs Claude Code out on this device). No cost is shown. Unit tests and E2E never run a real logout

The heading "設定" and the tabs stay at the top (`position: sticky`) while a card scrolls under them; only the underline of the tabs divides them, with no shadow. A red dot is on the アップデート tab while a newer version is out (U-1)

## A-6 Orca

A screen of its own (`nav-orca`, `#orca`) shows which Claude agents run in Orca, a desktop agent orchestrator with a CLI (`orca`), posts to them, shows the history of the selected one (A-7) and starts new ones. It stores nothing about a session: every read asks the CLI again. Only agents of type `claude` are listed and started; an agent of another type (Codex) has no row, and a launch always starts Claude.

The screen is two panes side by side (`#orca` is a `.split-main`): the list pane `#orca-list` on the left, the divider `#orca-split` (a `.split-bar` with `role="separator"`, `aria-orientation="vertical"`, `aria-label` "一覧の幅", `aria-valuemin` 20, `aria-valuemax` 50 and `tabindex` 0), and the work pane `#orca-work`. The list is 30% of the screen at first and the user sets it between 20% and 50% by dragging the divider, or with the arrow keys (Right widens, Left narrows, 2% a step); the ratio is kept in memory (as the divider of S-1 and S-6, `ts/split.ts` serves both). The list pane has a header bar (as `#slack-header`) with the heading "プロジェクト" (`#orca-heading`) and, at its right, in this order, the bell `#orca-bell` (A-8), the update button (`↻`, `aria-label` "更新") and the new button `#orca-new` (`+`, `.icon-btn`, `aria-label` "新しく起動する", `aria-haspopup` "menu": it opens the menu of A-8). The status label with a dot (`#orca-status`, or `#orca-target`) is in a footer (`#orca-foot`) at the bottom of the list pane, under the list. The list shows the projects (A-8) first; with the bell pressed it shows the working view: three groups with a heading that has the status icon of A-8, the name and the number at the right end: "入力待ち" (above the others, because the user has to act), "作業中" and "完了"; a group with no rows has no heading, and with no rows at all the list says "動いているエージェントはありません". A row (a button) has three lines: the status icon, the title (the first line of the prompt) and the time at the right; the latest action of the agent (A-8); and Claude's mark with "{repo} ・ {branch}". There is no repository heading, no filter and no agent chip. `nav-count` of the Orca button shows the number of sessions that need the user: the rows that wait (入力待ち) plus the notices below, with the label "Orca（確認待ち n 件）"; 作業中 is not counted, and the count does not enter the Dock badge. The bell's shoulder and the numbers of the group headings are not changed by it.

The work pane has a header that is the tab strip of the selected project (A-8), or, while no tab shows, `#orca-work-title` ("新しいセッション" when no project is selected, else the project's name); the history `#orca-chat` that scrolls (A-7); and under it, pinned, the composer: a textarea and a primary button. A row of the working view is selected by clicking it (`aria-pressed`, the `--soft` background), which also selects its project and its tab (A-8); a row with no pane key cannot be selected. With a row selected, the button is "送る", and the button is disabled when that row has no terminal handle (its history can still be read). In the new-session pane (no project selected: the first state, and "Claude を起動" of the plus menu), a row above the composer has the label "起動先" and the chip `#orca-dest-pick`, which opens a dialog (`showMenu`, `role="dialog"`) with a filter field (`aria-label` "worktree を絞り込む", case-insensitive on "{repo} ・ {branch}") and two-line rows (the repository, then the branch) of every worktree; picking one closes it and the chip names it. The button is "起動する" and it is disabled until a worktree is chosen. The textarea has no placeholder, with a row selected or not; its accessible name is `aria-label` "Orca への投稿". The button is also disabled while the text is blank and no image is attached (A-10), or a post is on its way, and when the command is missing. While a post is on its way the textarea is disabled, and it has the focus again afterwards. A post that works clears the textarea (and the attached images, A-10) and reads the list at once; one that fails keeps the text (and the images) and shows the CLI's message (`error.message`) above the composer. A send whose answer says `result.send.accepted` is false is a failure too (Japanese message), so the text stays. Selecting a row clears the worktree chosen for a launch, so the next launch chooses it again. A post is never tried again, because after a lost reply a second one would post twice (the CLI forbids a fresh retry of a launch). The side pane of A-9 launches and sends through the same checks (`orca_handoff` composes the prompt and then runs the same launch or send once).

The CLI is found among the absolute places `/usr/local/bin/orca` and `/Applications/Orca.app/Contents/Resources/bin/orca` (a GUI app has no shell PATH), and run with an argument list, never through a shell, in the temporary folder, with stderr dropped and a timeout (15 seconds for a read, 60 seconds for a launch and a send) after which the child is killed, off the UI thread. The commands are `orca worktree ps --limit 200 --json` and `orca terminal list --json` (the list), `orca terminal send --terminal <handle> --text=<text> --enter --json` (send), `orca agent launch --agent claude --worktree path:<path> --surface terminal --prompt=<text> --json` (launch; its reply holds `result.outcome` `{kind: "terminal", handle, paneKey}`, which `orca_launch` returns as `{paneKey, handle}`, each `null` when the reply lacks it or holds it in a shape that is not a pane key (at most 256 characters of `[A-Za-z0-9:_-]`) or a terminal handle (A-9 uses it to read the history of the session it started)), `orca environment list --json` and `orca skills installed --json`; the text of the user is joined to its flag (`--text=--json` is accepted, while `--text --json` is refused as "requires a value"), and `--environment=<name>` is added to every one of them but the list of environments and the list of skills when a target is chosen (`orca skills installed` refuses `--environment` with `invalid_environment`, because it lists the skills of the machine it runs on). The output is JSON, `{ok, result, error: {code, message}}`, also on failure, so stdout is read whatever the exit code and `error.message` is shown (the code when there is no message); an empty output or one that is no JSON gives a Japanese message. The prompt text is in no log line.

Rows are built by a pure function from the two documents (`result.worktrees[].agents[]` and `result.terminals[]`), tolerant of absent fields. An agent is kept when its `agentType` is `claude`, it is top-level (`parentPaneKey` null) and `hasLivePty` is true. Its group follows `state`: `waiting`, `blocked` and `permission` are 入力待ち, `done` is 完了, and every other state (`working`, and a state not known yet) is 作業中. The line (the title of the row and of its tab) is the first line of `prompt`, else of `taskTitle`, `conversationName` and `lastAssistantMessage`, in this order, whatever the state. The activity (A-8), the second line of a row, is `{toolName}: {first line of toolInput}` (the name alone when the input is not text or is blank), else the first line of `lastAssistantMessage`, else empty, cut to 200 characters. The branch is the worktree's `displayName`, the repository its `repo` and the path its `path`. A row also carries the agent's `paneKey` (null when it has none), which finds its session for the history (A-7), and its `activity`, `status` and `projectKey` (A-8). The time is `stateStartedAt` for an agent that runs or waits ("2 分", the time since) and `updatedAt` for a done one ("18 分前"), sent as epoch milliseconds and formatted by the screen. The terminal handle is found by joining the agent's `paneKey` with the terminals' `"{tabId}:{leafId}"` (an orphaned terminal by its `recordedPaneKey`, as below). Rows are sorted by `updatedAt`, newest first. The launch targets are all worktrees, with their path, repository and `displayName`.

Just before it acts, Rust reads the list again (with the environment): a send goes only to a handle that belongs to a row of that list (a top-level agent of a live terminal; `writable` is not used, because a plain shell terminal is writable too; an orphaned terminal, one that lost its tab and still runs, belongs to the agent whose pane is its `recordedPaneKey` when its `agentIdentity` is `claude` and no other orphaned terminal recorded that pane, and a live terminal of that pane comes first), and a launch only into a worktree of it; otherwise the answer is a Japanese error and nothing is sent. Rust validates before it runs anything and answers in Japanese: the text is not blank and at most 100,000 characters; the handle begins with `term_` and holds only `[A-Za-z0-9_-]`; the path is absolute; the environment is one listed by `orca environment list --json` (`result.environments`, each a name or an object with a `name`, else an `id`).

The target is "このマシン" or a saved environment (a paired server). It is saved in `orca-settings.json` in the app config directory (`{"kind":"local"}` or `{"kind":"environment","name":"..."}`, written through a temporary file and a rename), and only when the file does not exist yet the first saved environment is used, else this machine. A saved environment that is no longer listed, or a file that cannot be used while an environment is saved, never switches the target by itself: the read is a failed one with 「保存した接続先が見つかりません」 (the label names the saved environment), the menu lists the environments and "このマシン", and the owner chooses again (with no environment saved there is nothing else to choose, so a file that cannot be used gives this machine). The status label shows it: green "{target} に接続中" after a read that worked, orange "{target} に接続できません" with the message in a notice when it failed (the rows of the last good read stay while the target is the same), and gray "未インストール" with a notice when no `orca` was found. The label is plain text until an environment is saved, and from then on a menu of "このマシン" and the environments; choosing one saves it, drops the selection and the rows of the old target, and reads again; until that first read of the new target returns, the label says 確認中 and the list 「読み込んでいます…」 (nothing is said about the target), and the menu stays. The environments are listed even when a read failed, so the target can still be changed. When `orca environment list` itself fails, the screen keeps the target, the environments and the rows it had, and shows the failure.

The list is read at startup (for the count), every 10 seconds while the Orca screen is shown and every 60 seconds otherwise, one read at a time, and no more by the clock once the command was found missing (the update button looks again). The count of the Orca button follows every read (the clock's read for the count alone included) through one function. A row has stopped when its group is 完了 or its status is `failed` or `interrupted` (Orca says an agent stopped with Esc as `state` `done` with `interrupted` true). A stopped row has a notice when, while the app runs, it went from not stopped to stopped between two reads, or it first appeared in a read after the first of the target and had already stopped (a pane the app has seen stopped is remembered, so it has no new notice when it leaves the list and comes back stopped, and the memory ends when it is seen running or the target changes). The rows of the first read of a target (at startup, and after the target is changed) are only the base and have no notice, so what had finished before is not counted; changing the target drops every notice, and so does a read that names another target than the one held. A notice goes when the session is shown on the Orca screen (the screen is shown, the window is not hidden, and the row is the selected tab; the session seen only in the side pane of A-9 does not clear it), when the row runs again (it is no longer stopped), or when it leaves the list; a row that stops while it is shown has no notice. A row with no pane key cannot be opened, so it has no notice (it is still counted while it waits). A failed read, and a read that did not find the rows while the command is there, leave the notices as they are; a missing command drops them. The notices are held in memory only. While one row or more is working (its group is 作業中 and its status is `working` or `monitoring`), the icon of `#nav-orca` (the `svg` only, not `.nav-count`) is yellow (`--agent-working`) and fades slowly (`opacity` between 1 and .55 over 2 seconds, `ease-in-out`, endless), by the class `working` on the button; under `prefers-reduced-motion: reduce` it stays yellow and does not fade. The number that work is not on the button: it is in the `aria-label` (read aloud, and in the tooltip on hover), after the count of the waiting ones (「Orca（確認待ち 1 件、作業中 2 件）」, 「Orca（作業中 2 件）」, 「Orca（確認待ち 1 件）」, else 「Orca」). The class and the label follow every read the count follows, so a read for the count alone moves them too; a failed read cannot say that a session works, so it takes the mark and that part of the label away and leaves the count of the waiting ones as it is, and a missing command or a change of the target removes them all.

The environments are read (`orca environment list`, and the target resolved, together with the SSH hosts of A-8) only at startup, when the screen is shown, by the update button, when the target changes and in a read after a failure; the clock reads the agents and terminals of the target held while the screen is shown, and only `orca worktree ps` (for the count, with no terminal list) while another screen is shown. A read in the background swaps the rows in place and keeps the selection (dropped only when its session is gone), the text in the textarea, the scroll position and the history on screen, and never calls `show()`.

Every destination is Claude, so a skill list completes commands as Claude Code's does. `orca skills installed --json` (`result.skills[]` with `name`, `description`, `providers`, `sourceKind`, `sourceLabel`) is read once when the screen is first shown with the command found (also while the target fails to read) and again by the update button, never per keystroke and never with `--environment`; a failure gives no list for now and never blocks a post, and the read is tried again by the list reads that follow, at most once a minute (so a list that failed while this machine's Orca was not running comes once it runs), until one succeeds. The list is that of the machine the app runs on, whatever the target, and it needs Orca running on that machine, so with a saved server as the target it can differ from that server's skills, and a change of the target does not read it again. A pure function keeps the skills whose `providers` include `claude` and turns each into the command `/{name}`, or `/{plugin}:{name}` for `sourceKind` `plugin` with a `sourceLabel` of the form `Claude plugin {plugin}` (its `name` has no plugin prefix); it drops a command listed twice, sorts by command and cuts the description to its first line. The output has no field for a skill that Claude Code does not offer to the user, so the `SKILL.md` of each skill is read (in the same read, off the UI thread) and the skill is left out when the front matter (from the first line `---` to the next `---`) has the top-level line `user-invocable: false`; the same text in the body, a nested key, `true` and a missing key leave it in, and CRLF and spaces around the value are tolerated. The file is `{home}/.claude/skills/{name}/SKILL.md` for `sourceKind` `home`, and, for a plugin, `{installPath}/skills/{name}/SKILL.md` for each `installPath` of the entries whose key starts with `{plugin}@` in `plugins` of `{home}/.claude/plugins/installed_plugins.json` (the skill is left out when any file it could read says `false`). The `name` is used as a path part only when it is one path element (not empty, not `.` or `..`, with no `/` or `\`). A skill whose file is not found or cannot be read stays in the list, as does every skill when there is no home folder or when `installed_plugins.json` is missing, unreadable or of another shape; none of these fails the read. The list opens when the text starts with `/` and the caret is still in that first word (no whitespace yet), and only while the textarea has the focus (a read in the background does not open it). It is a popup (`role="listbox"` with `aria-activedescendant`) directly above the composer, with the frame and shadow of `#account-popup`, the command in monospace and its description on one line with an ellipsis, 8 rows at most before it scrolls. It shows the commands that contain the text after `/`, case-insensitively, those that begin with it first. Up and Down move the highlight and wrap around, Tab or Enter put the command and one space in the place of the first word (the caret after the space, and nothing is posted), Escape closes it until the text changes, and a click on a row does what Tab does. Enter does not submit while the list is open. A read in the background does not close it or move the highlight.

Unit tests (`cargo test`) cover row building, the argument lists (the `--flag=value` form and the environment), the validation, the parsing of the output and the environments, the target setting and the skill list (including the front matter check of `SKILL.md`, the places of a home and a plugin skill, several places of one plugin, a file that cannot be read and a `name` that is not one path element, with the files given by a function so that no real home folder is read); none of them runs the real CLI. The E2E spec `orca.e2e.ts` covers the two panes and the divider, the drawing of the working view, the selection, the dialog of the worktrees, the arguments of a send and a launch, a failure keeping the text, the missing command, a failed read, the target menu, a read in the background, the count and its notices and the skill list.

## A-7 Orca session history

The work pane of A-6 shows the history of the selected session: what the user asked, what the agent answered and the tools it ran. The history is read from Orca's own runtime, not from the CLI (the CLI has no command for it), and nothing of it is stored by this app. It was written against Orca 1.4.248, whose runtime is not a public interface: an Orca update can change the calls, and then the history shows 「このセッションの履歴は読めません」 or a message of the read, while the list and the posts of A-6 keep working.

Selecting a row (with a pane key) opens its history: `orca_chat_open(environment, path, paneKey, channel)` is called with a `Channel` (`window.__TAURI__.core.Channel`), and Rust sends `OrcaChatEvent`s to it until `orca_chat_close` (the selection is cleared or its session is gone, the target changes, or the screen is left; the one-second tick of the screen sees it is no longer shown) or another `orca_chat_open`. Only one session is read at a time. An event of a channel that is no longer the current one is ignored. The history is not tied to the Orca screen (A-9): the read has one owner at a time, the work pane of the Orca screen or the side pane of a mail, a Slack thread or a Todo, and the history code (`ts/orca-chat.ts`) draws into the owner's view (the scroll box, its list, the button for older messages and the status line). Opening a read for one owner wipes what the owner before it drew, and an owner closes only its own read: the tick of the Orca screen that sees the screen is no longer shown calls `orca_chat_close` only while the screen still owns the read, and a side pane takes the read only while it shows a session in view. When the owner comes back into view (the Orca screen shown with a row still selected, or the item of a side pane open again) it opens its read again, also when another owner had it meanwhile. There is no second concurrent reader. While the window is hidden (`document.hidden`) the screen calls `orca_chat_pause(paused)` with `true` (also for a session opened then) and with `false` when it is shown again, and a paused session neither polls the transcript nor looks at the tabs again, keeping the connection, the older pages and what is drawn, and reads once at once on the resume. Rust validates the arguments (the path is absolute, the pane key is not empty, at most 256 characters of `[A-Za-z0-9:_-]`) and answers a Japanese error that the screen shows as the status.

What is read, with the pane key of the row and the worktree's path: `session.tabs.list` with `{worktree: "path:<path>"}`, whose `tabs[].agentStatus.paneKey` is matched and `agentStatus.providerSession.id` is the session id (none: 「このセッションの履歴は読めません」, and the tabs are looked at again every 30 seconds; a changed id, as after `/clear`, drops what was held and reads the new session); then the transcript, `nativeChat.readSession` for the first 40 messages and for each page of 100 older ones (`beforeOffset`), and, over a WebSocket, `nativeChat.subscribe` for what follows. This machine is read over the unix socket of `orca-runtime.json` in Orca's settings folder (`authToken`, and the transport of kind `unix` with its `endpoint`): one JSON line `{id, authToken, method, params}` and one line back, a connection for each call. That socket answers `method_not_supported` to `nativeChat.subscribe`, so on this machine the transcript is read again every 3 seconds and each answer is taken as the newest page. A saved environment (A-6) is read over its WebSocket (`ws://` only: the frames are encrypted end to end, with the pairing's key, and TLS is not built in) with the device token and the public key of `orca-environments.json`, using Orca's own framing, and the stream pushes the changes. Both files are read at each connect and never written. A token, a key or an authentication frame is in no log, no error text and no event. The unix socket exists on macOS and Linux; on another OS this machine has no history, with a message that says so.

An event is `items {start, items, hasMore}` (replace the timeline from index `start`; sent only when something changed) or `status {state, message}` with `state` `connecting`, `live`, `reconnecting` or `unavailable`. A failed or lost connection is `reconnecting` with the reason in Japanese, tried again after 1, 2, 5, 10 and then 30 seconds (the wait starts again once a page or a snapshot has been read, not when a call merely answered), and what is drawn stays on screen; a missing or rejected pairing is shown the same way with its own message. The messages are reduced in Rust (pure functions with unit tests): only user and assistant text and the agent's questions are drawn, a user message that the harness injected (known by its tag or its opening, as Orca's own screen hides it) and a message that starts an agent draw nothing, the lines of a user message that only name the file an image came from are cut, and a message left empty is not drawn. Tool calls in a row, with the results, reasoning and undrawn messages between them, become one `tools` item (a question, `question`, ends the run and is an item of its own) with a summary "ツールを 5 回実行" and the calls, each a name and the first line (at most 200 characters) of the first string among `file_path`, `path`, `notebook_path`, `command`, `pattern`, `query`, `url`, `description` and `prompt` of its input; when the run is the last item and a call has no result yet it also has a running summary "ツールを実行中". The outputs of the tools are not sent to the screen, except the answer to a question.

The history is drawn in `#orca-chat`: the user's messages as a right-aligned bubble of plain text (`--soft`; a message that handed a content over, A-9, holds the instruction and under it that content folded into one line, below), the agent's as Markdown in a white card with a thin border (the sanitizer of Todo's descriptions; a remote image is not loaded, its alt text is shown instead; a table has ruled cells), and a run of tools as a button with a chevron and the summary (`aria-expanded`), which opens the calls in monospace as "name  detail" in a white box with a thin border. The history stands on the ground colour `--bar`, which the status line above it shares, so a message reads as a card on it. The button of a run is small muted text with no border and no background, set close to the cards above and below it, and its text turns darker on hover. A call of `AskUserQuestion` is not folded and ends the run: it is a white box that shows each question, its choices with their descriptions, and 「回答: …」 once the result gives the answer (read from the output `Your questions have been answered: "{question}"="{answer}"`, the only output kept); until the call has a result the box says 「回答待ち」 and, when every question has choices, is answered in the box (A-11), and a call whose questions cannot be read stays an ordinary call of the run. A question has `multi` too, true when the call's `multiSelect` is true. The running summary replaces the summary while the selected row is in the 作業中 group. A user message that carries a handoff block (A-9) is reduced in Rust (`orca_handoff::fold`): the item has an optional `context` `{kind, title, text}` (`kind` is `mail`, `slack` or `todo`) and its `text` is only the instruction, the line that says the block is quoted data removed; a message with no well-formed block is unchanged (see A-9 for the format). The context is drawn inside the bubble as a one-line button with a chevron (`.orca-ctx-btn`, `aria-expanded`) that says the kind, the title cut to 12 characters (with "…") and the number of characters, e.g. `メール「請求書の金額が…」186 字`; pressing it opens the text (`.orca-ctx-text`, plain text, `textContent` only, never HTML or Markdown). This is drawn by the shared history code, so the Orca screen folds too. Which runs and which contents are open is kept by item id while the history is open, so a run that grows or an `items` event that draws it again keeps it open. While the screen is at the bottom (within 40 px) it stays at the bottom as items come; scrolled up, it does not move; opening a session scrolls to the bottom. While `hasMore` is true the button `#orca-older` (「以前の履歴を読む」) is at the top; it calls `orca_chat_older`, the older messages arrive as an `items` event from index 0, and the message that was in view stays where it was. A run of tools does not join across the edge of an older page, so it keeps its id and stays as it was; the calls of the older page are a run of their own. While disconnected the press is dropped and the button stays. The status is a line above the history: `connecting` shows 「読み込んでいます…」 while nothing is drawn, `reconnecting` and `unavailable` show their message in a `.pending` line, and `live` shows nothing; the end of the first read is `live` even with no messages.

Unit tests (`cargo test`) cover the reduction of a handoff block (the block found, the wrapper `<pasted_content id="…">…</pasted_content id="…">` of a long paste tolerated when it wraps the whole message, a malformed block left unchanged, the quoted-data line removed from the instruction), the framing and encryption of the paired connection against fixed vectors, the choice of the pairing and the endpoint, the merging of snapshots, appended messages and older pages, the noise filter, the tool runs and their summaries, the questions (also whether they allow several picks) and their answers, the changed index, the back-off, the pause and the events; none of them talks to a real Orca. The E2E spec `orca.e2e.ts` covers the opening and closing of the history by the selection, the drawing of the events, the Markdown, the questions, the folding of the tool runs and their state over a redraw, the older button and the scroll, the pause while the window is hidden, the status lines and the ignoring of a closed channel. The E2E spec `orca-handoff.e2e.ts` covers the folded content and the handing of the read between the Orca screen and a side pane.

## A-8 Orca terminal and project list

The Orca screen (A-6) shows the plain terminals of Orca, and its list pane is a list of projects with a switch to the working agents. It was written against Orca 1.4.248.

Projects. The list pane shows the projects first (the choice of view is kept in memory). A row (a button, `.orca-project`, `aria-pressed` for the selected one) has the status icon, the name and the number of sessions (nothing when it is 0). A pure function builds them from the two documents of A-6: one project for each `repoId` among the worktrees that are not archived (`isArchived` is not true), have a path, and whose `hostId` is `local` (a worktree with no `hostId` is this machine's); the name is the worktree's `repo`. The worktrees of an SSH host (any other `hostId`) are not projects: they make the row `ssh:{hostId}` of that host. The sessions of a project are its Claude rows (A-6) and its plain terminals. The list is newest first by the latest `lastActivityAt` of the project's worktrees. Below the projects, under the heading "SSH", are the SSH hosts, in Orca's order, drawn the same way: the name is the host's `label`, and the icon and the number are what the worktrees with its `hostId` show (idle and none when there are none). A host that the worktrees of the target have (`ssh:{hostId}`) but that this machine's Orca does not list is a row of that group too, named by its worktrees' host name, after the listed ones. There is no search, no filter and no group chevron.

Status icons, the same as Orca's. A pure function maps an Orca state word to one of seven: `waiting`, `blocked` and `permission` are `question` (the `message-circle-question-mark` icon, orange); `failed` is a small red dot; `working` is a yellow ring that turns (it stops under `prefers-reduced-motion`); `monitoring` is the `activity` icon; `interrupted` and `unconfirmed` are a small gray dot; `done` and `active` are a green dot ("完了", or "起動中" on the tab of a terminal); `inactive` is a faint gray dot ("動いていない"). The colors are variables in `:root`. A word not known yet is idle for a worktree and working for an agent, as in A-6, and an agent with `interrupted` true is interrupted unless it waits or failed. The status of a row is its agent's; the status of a project is the highest rank among its top-level agents with a live pty, its worktrees' `sidebarStatus` (else `status`), and its plain terminals (a green dot), in Orca's rank: question, failed, working, monitoring, interrupted, done, idle (`unconfirmed` is drawn as interrupted and ranks with it, one place above where Orca ranks it).

The bell (`#orca-bell`, `.icon-btn`, `aria-pressed`, `aria-label` "作業中を表示する", and "作業中の表示をやめる" while pressed) switches the list between the projects and the working view of A-6, and the heading stays. At its right shoulder it shows the question icon and the number of agents that wait; with none, the working mark and the number that work; with none, nothing.

The SSH hosts are read from this machine's Orca over its unix socket (`ssh.listEditableTargets`, `result.targets[]` with `id`, `label`, `configHost`; the socket of A-7, not a public interface), whatever the target is. Only `id` and `label` cross to the screen; the label is the first line of `label`, else the `configHost`, and a target with no `id` or no name is dropped. They are read with the environments (startup, the screen shown, the update button, a change of the target), never by the clock, and a read that does not say what the target is leaves the ones the screen holds. A failure gives no SSH group and no error line.

Tabs. Selecting a project shows its sessions as tabs in the work pane (`#orca-tabs`, `role="tablist"`, each tab a `role="tab"` button with `aria-selected`) and selects the one last selected there, else the first. A tab has the status icon, the title and "{branch} ・ {time}" (the time of A-6, only for a Claude session), and a close button (`.icon-btn`, `aria-label` "閉じる") beside it, which never selects the tab. The tabs are the project's Claude sessions (rows with a pane key), and its plain terminals, in the order they were first seen, so a read that reorders the sessions does not move them. A project with no session says 「セッションはありません」 in the work pane, with its name as the heading, and "Claude を起動" of the plus menu is the way to start one; no tab strip and no `#orca-work-title` shows while tabs do. The selection survives a read while its tab exists; when its session leaves Orca's list the project's last selected tab, else the first, is selected. Nothing closes by itself, a finished session included. A Claude session shows its history and its composer (A-6, A-7); a plain terminal fills the pane (below).

The plus menu. `#orca-new` opens a menu (`showMenu`, `role="menu"`) with one item, "Claude を起動", which selects no project, so that the work pane is the new-session pane of A-6.

Closing. The close button of a Claude session or a plain terminal of Orca calls `orca_close(handle, environment)`, which runs `orca terminal close --terminal <handle> --tab --json` (with `--environment=<name>` for a saved environment) with a timeout of 15 seconds; the handle is validated as in A-6, and the environment must be a saved one. The answer's `ptyKilled` is not looked at (it is false on a real machine although the process stops), and `error.code` `terminal_handle_stale`, which is what Orca answers when the terminal was closed first, is a success. On success the screen reads the list at once and the tab leaves with it; on a failure the message is shown (`#error`) and the tab stays. A tab whose session is gone from Orca's list leaves at the next read. A Claude session with no terminal handle cannot be closed.

Plain terminals of Orca. A terminal of `orca terminal list` that is not Claude's (`agentIdentity` is not `claude`: a shell, or another agent), still has its tab (not `orphaned`), and is in the worktree of a project is a tab of that project, titled by its `title`, with the green dot; the floating terminal has no worktree and is left out. Orca's runtime cannot stream the bytes of a terminal to this app (`terminal.subscribe` and `terminal.multiplex` answer `method_not_supported` over the unix socket), so the tab is a mirror, drawn by xterm.js (`src/vendor/xterm.js`, `xterm.css` and `addon-fit.js`, loaded as classic scripts and kept as distributed, with their version and license in a comment; the CSP is unchanged; scrollback 5000 lines; `ts/orca-terminal.ts`), sized to the pane when it is shown (`fit`, and a `ResizeObserver` whose fit waits until the size has rested for 50 ms): while it is shown, the screen reads `orca terminal read --terminal <handle> --screen --json` (`result.terminal.tail`, an array of lines with no colors, about 0.1 seconds each) every second, one at a time, and draws the frame again in xterm.js when it changed; the keys typed are sent with no `--enter`, so control bytes reach the terminal as typed, batched (at most 50,000 characters a send) and one send at a time, and the frame is read again soon after. What is typed can be a password, so it is kept out of the arguments of a process (`ps` shows them): with this machine as the target the keys go to its Orca over the unix socket of A-7 as `terminal.send` (`{terminal, text, enter: false, client: {id: "cookapps", type: "desktop"}}`, as the CLI sends them; the answer's `result.send.accepted` false is a failure). A saved environment has only the CLI's route, so there the keys go through `orca terminal send --terminal <handle> --text=<keys> --json --environment=<name>` and are in that process's arguments while it runs; type no password into the mirror of a saved environment. A key text is not checked for blank, but it may not be empty or hold a NUL or more than 100,000 characters. The handle must belong to a plain terminal of the list read just now, for a read as for keys; it is checked the first time a read or keys go to that handle (and target), and again after a read or a send of it failed. The mirror has no colors, a full-screen program is only approximate, and a size change is not sent. A terminal's screen and keys are in no log line, error text or event of the app. A failed send shows its message (`#error`); a failed read is tried again at the next second. The reads stop while another tab or screen is shown or the window is hidden (the shown terminal reads at once when the window is shown again), and the screen of a terminal is dropped when it leaves the list or the target changes.

Keys. While a terminal has the focus the app's own key handlers do not act: Escape only closes a menu, popup or hint that is open (none is while a terminal is clicked), and Cmd+Z of the inbox leaves a textarea's own, which is xterm.js's input. Cmd+C copies the selection and Cmd+V pastes, as in any field.

Unit tests (`cargo test`) cover the status mapping and rank, the activity line, the projects and their order, count and status, the plain terminals, the SSH targets, the screen lines, the stale answer, the arguments of close, read and send, the params of the keys sent over the socket, the validation of keys and handles, and the one-time check of a mirrored handle; none touches Orca or the settings folder. The E2E spec `orca.e2e.ts` covers the project list, the icons, the bell and its badge, the tabs and their selection and order, the plus menu, the close of an Orca tab (with its arguments, a failure and a tab that Orca closed first), and the mirror (the reads, the frames, the keys and the pause while the window is hidden).

## A-9 Hand to Orca

The open mail, Slack thread or Todo can be handed to Orca (A-6) from the screen it is on, in a pane on its right side. Nothing is sent by itself: the user checks the content (a card), writes an instruction, chooses where it goes and presses the button. The pane is `ts/orca-handoff.ts` (one class, `HandoffPane`, with a host for each screen); the content of each screen is built in `ts/orca-handoff-cards.ts`; the prompt is composed and the history folded in Rust (`src-tauri/src/orca_handoff.rs`). It was written against Orca 1.4.248, as A-6 to A-8.

Entry. The header of the open mail (`#mail-header`, after "Todo にする") and the header of a Todo's detail (`#todo-body > header`, before "その他") each have an icon button `#thread-orca` / `#todo-orca` (`.icon-btn`, `aria-label` "Orca に渡す", `aria-pressed`, the Orca icon of the sidebar) that opens the pane `#mail-handoff` / `#todo-handoff` (`aside.ho-pane.split-chat`, `aria-label` "Orca に渡す") on the right of the screen, with a divider (`#mail-split` / `#todo-split`, a `.split-bar` with `role="separator"`, `aria-label` "Orca の幅"), set by `ts/split.ts` as the Slack thread and the compose screen do and kept in memory. The mail's pane is 37% of the screen at first, at least 400px, and the divider sets it between a third and a half (`aria-valuemin` 33, `aria-valuemax` 50); the Todo's is 380px at first and at least that, and the divider widens it up to half (`aria-valuemin` 0, `aria-valuemax` 50). The pressed button, or the pane's close icon, closes it. In the Slack thread (S-6) the right pane of S-7 is tabs "Claude" and "Orca" (`#reply-tabs`, `role="tablist"`, `aria-label` "Claude と Orca", `role="tab"` buttons `#reply-tab-claude` / `#reply-tab-orca` with `aria-selected`; Claude first and selected at first; the selected tab has a 2px accent underline and bold accent text, over a line under the strip; while Orca is selected the pane is at least 400px wide, and its width is otherwise the shared divider's of S-7): Orca replaces the log and the request field of the Claude tab by the pane (`#st-orca`, which takes their rows of the grid) and hides "クリア"; S-7 is otherwise unchanged. The Orca tab has no title row of its own before a send (the tab names it).

What is in view decides the pane. A pane follows the item in view (`host.current()`: the mail thread shown, the Todo detail shown, the Slack thread shown with its Orca tab selected; checked after each open or close of the item and by a one-second tick): another item, or none, hides the pane and lets its read go; the item it is for shows the pane again only when a session was handed to it (below), else the pane stays closed (the Slack tab is always open while selected).

The send form (before a send). The pane has: the header "Orca に渡す" with a close icon (`aria-label` "閉じる"); the destination section "送り先" (with the name of the environment beside the heading when the target is a saved environment, as the status label of A-6 names it; nothing for this machine): a "新しいセッション" button (`aria-pressed`, selected at first) with the chip `.ho-chip` (`aria-haspopup` "dialog") that names the worktree chosen ("{repo} ・ {branch}", else "worktree を選ぶ" or "worktree がありません") and opens the dialog of A-6 (`openWorktreeDialog`: filter field, two-line rows; picking one closes it, chooses it and selects the new session), then the running sessions in the groups "入力待ち", "作業中" and "完了" (headings with the status icon and the number, as the working view of A-6), each a button `.ho-row` (`aria-pressed`, `data-handle`) with the title and the time, and under it "{repo} ・ {branch}"; only rows that have a terminal handle are listed (a row that can only be read cannot take a send). Under them, pinned: the card (`.ho-card`: the kind's icon, the title, the line under it, and a button `aria-label` "渡す内容を外す" that takes the card off), the textarea (`aria-label` "Orca への指示") and the button, "起動する" for a new session (disabled until a worktree is chosen) and "送る" for a running one; the button is also disabled while the instruction is blank or a post is on its way, and when the command is missing. The list of Orca (agents with their terminals, and the worktrees) is read once when the pane opens (`refreshOrca` of `ts/orca.ts`, the target the Orca screen holds; the first read and the read after a send start although another read is on its way) and the pane draws from it; a missing command or a failed read shows the notice of A-6 in the pane (`noticeOf`). The worktree chosen is kept in memory for the next handoff (dropped when it is no longer listed). Pressing the button once calls `orca_handoff`; a failure keeps the text and the card and shows the message above the card (`.pending.fail`), as A-6. A post on its way and its failure belong to the item: the pane held for another item neither waits for it nor shows its message, and when the failure came while another item was in view the instruction is put back in the field of its own item when that item is shown again, with its message.

The card. It is built when the pane opens (not for each item that is merely in view) and drawn as plain text (`textContent`): a mail is the open thread, oldest message first, each as `差出人: {from}`, `日時: {date}` and its text (the path of the summary, `mailText`), separated by `----`; the title is the subject and the line under it `{sender of the newest message} ・ 本文 {n} 字`. A Slack thread is its messages as the screen holds them, each `{name}  {time}` and the text (the text S-7 sends to Claude); the title is `#{channel} のスレッド` and the line `{first name} ほか ・ {n} 件` (the name alone when there is one author). A Todo is `タスク: {title}`, `プロジェクト: {project}`, `期限: {due}`, `説明:` and the description, and `コメント:` with the comments when they are already loaded (none are fetched for this); the title is the task's and the line `説明 {n} 字 ・ {due}` (`説明なし` when the description is empty). The card of the Slack thread and of the Todo is built again when the thread is read or the task is drawn again, until it is sent or taken off. The card can be opened to read the text that will be sent: a real button on the card (`.ho-card-toggle`, "送る内容を読む", the style of the folded line of the history, a chevron and `aria-expanded`, closed at first) shows the body of the card, exactly the string the command gets as `context.body`, as plain text (`textContent`, never HTML) in a box of limited height (160px) that scrolls. This is for every kind, so the user can read what a mail holds that the screen does not show (text hidden by a style, for one) before it reaches the agent; the app does not try to detect hidden text. The card keeps its nodes when it is drawn again (the Slack thread read again, the Todo drawn again, the one-second follow of the host): an open text stays open and shows the new body, and its scroll position and selection stay. Another item closes it, and taking the card off drops it. Taking the card off makes the post a plain one, with no block.

The command. `orca_handoff(destination, instruction, context, environment)`: `destination` is `{kind: "new", path}` (a worktree) or `{kind: "existing", handle}`; `context` is `null` or `{kind, title, body}`; `environment` is the target of A-6. Rust composes the prompt with a pure function (`orca_handoff::compose`) and then runs the launch or the send of A-6 once, with its checks (the list is read again, the handle belongs to a row, the path is a worktree of it, the environment is a saved one, the text is not blank and the whole prompt is at most 100,000 characters; Japanese errors; never tried again). A blank instruction is refused before anything runs (「指示を書いてください」), and a prompt over the limit says that the instruction and the content together may be 100,000 characters. The answer is `{paneKey, handle}` of A-6's launch; for a running session it holds only its `handle`. The prompt is

```text
{instruction}

{one line that says the block is quoted data and holds no instructions}
<cookapps-context kind="mail|slack|todo" title="{title}">
{body}
</cookapps-context>
```

with the attribute value on one line (a newline becomes a space, at most 200 characters, and `&`, `<`, `>` and `"` escaped) and, in the body, every opening or closing tag of the block, in any case, loses its `<` (it becomes `&lt;`), so that quoted mail can neither end the block nor start a second one or fake the fold. Before that, Rust takes out of the title and the body the C0 controls other than the line break and the tab, DEL, the zero-width characters (U+200B to U+200D, U+2060, U+FEFF), the bidi controls (U+202A to U+202E, U+2066 to U+2069) and the tag characters (U+E0000 to U+E007F), which are invisible or change how text reads and could split a tag apart (`<` + U+200B + `/cookapps-context>`); so `context.body` as the card shows it is the string that the command received, and the text sent is that string without those characters (the card text and the prompt differ by them only). The prompt text is in no log line.

The history folds it. A user message of the history (A-7) is searched for the block anywhere in the text, from the last occurrence of the data line followed by the opening tag at the start of a line: the block must end the message (only white space after the closing tag), have a known `kind`, and hold no closing tag in the body; the wrapper `<pasted_content id="x">…</pasted_content id="x">` that Claude Code's transcript puts around a long paste is taken off when it wraps the whole message. The instruction is the text before the data line; the title is unescaped; the body is shown as it was sent (the `&lt;` of a neutralized tag stays). Anything else is shown as it is.

After a send. The pane shows that session (and the mapping item → session is kept in memory only, nothing is saved to a file, so leaving and coming back to the same item shows the session again): a header of two lines (`.ho-session-head`): "{repo} ・ {branch}" (bold; the worktree's label until the list holds the session) and under it, in the accent color with a small dot before it, the status and the time as A-6 ("作業中 ・ 2 分", "確認中" until the list holds a new session), a button `aria-label` "Orca の画面で開く" that selects the session's project and tab on the Orca screen and shows the screen (`openInOrca`; the session of a launch that is not listed yet leaves the selection as it is), and the close icon `aria-label` "閉じる", which forgets the mapping of the item (the next open shows the send form; for the mail and the Todo it also closes the pane). Under it, the notice of A-6 when a read failed, the history of the session (the shared history code, in the pane's own scroll box, status line and older button; read only while the pane shows it in view) and the composer for more instructions (the textarea `aria-label` "Orca への指示" and "送る", sent with `orca_send` to the terminal of the session, to the target the session was started with; a failure keeps the text and shows the message). The list is read again every 10 seconds while a session is shown (not while the window is hidden, not while the command is missing, and not while a read is on its way). A session whose row has been in the list and is no longer in a ready list shows "終了" in place of its state. A session whose launch gave no pane key reads the pane key of its row once the row is in the list. When Orca's reply gave no pane key (`paneKey` null), the pane says the session was started (`.ho-note`) and has the button of the Orca screen, with no history. The skill list of A-6 is not offered in the pane (the Orca screen's completion is tied to its own field).

The read. The side pane takes the read of the history (A-7) from the Orca screen when it shows a session in view, and gives it up when the item is left, the tab is changed or the pane is closed; the Orca screen opens its own again when it is shown with a row selected. `orca_chat_open` is called again for each change of owner, and there is never more than one open session.

Unit tests (`cargo test`) cover the composition (the format, the escaping of the attributes, the neutralized tags, the limit over the whole prompt, a blank instruction), the reading of the launch reply, the destination, the validation that a handoff shares with a post, and the reduction (see A-7); none of them runs the real CLI. The E2E spec `orca-handoff.e2e.ts` covers the entry from the three screens, the destinations, the chip and its dialog, the card and its ×, the arguments of `orca_handoff` for a new and a running session and without a card, a failure keeping the text, the notice, the view after a send with the folded content and the composer, a launch with no pane key, leaving and returning to the item and the close icon, the handing of the read between the pane and the Orca screen, and the Slack tabs.

## A-10 Attach an image in Orca

The composer of the Orca screen (A-6) takes images by paste and by drop. Each is put in `.orca/drops/` of the worktree the post goes to, and its absolute path is in the text that is sent to Claude, which reads the image from that path. It works for a worktree of this machine and for one of a saved server (the target of A-6). The composer of A-9 (`ts/orca-handoff.ts`) takes no image. The image is kept in memory only, in no log line and in no file of this app. Rust is `src-tauri/src/orca_attach.rs` and the frontend is `ts/orca-attach.ts` (the post itself stays in `ts/orca.ts`). It was written against Orca 1.4.248, as A-6 to A-9.

Taking an image. A paste on the textarea takes the image files of `clipboardData`; the event is cancelled only when there is one, so pasting text (or a file that is not an image) works as before. A drop on the form `#orca-form` takes the files dropped; while a file is dragged over the form the composer has a dashed outline (`.dropping`). `dragDropEnabled` is `false` for the window (`tauri.conf.json` and `tauri.e2e.conf.json`), so a drop gives `File` objects to the page, and a document-level `dragover` and `drop` cancel a drag that holds files, wherever it is, so that a file dropped elsewhere does not make the webview navigate to it (a drag with no file is left alone, and the Todo list's row drag uses pointer events). A file whose type is not `image/*` is not added: the post error line (`#orca-error`) says 「画像だけを添付できます」, and the images among the dropped files are added. Nothing is added or removed while a post is on its way. A file over 20 MiB (the limit of Rust below) is refused before it is read, so that it is never held in memory, with 「画像は 20 MiB までです」 in `#orca-error`, and the other images among the files are added; the limit in `ts/orca-attach.ts` mirrors `MAX_IMAGE` in `orca_attach.rs`, which stays the authority. The file is read with `FileReader` into base64 and a `data:` URL, which is the thumbnail (the CSP allows `data:`, not `blob:`). The images of a read are added to the list as it is when the read ends, so two pastes in a row keep both images and an image removed meanwhile stays removed. While a read is on its way the button of the composer is disabled and `post()` does nothing; a read that ends while a post is on its way (`busy`) adds nothing and says 「送信中のため画像を追加できませんでした」 in `#orca-error`.

The strip `#orca-attachments` is above the composer (inside the form, after the destination row) and is hidden when there is no image. Each image is a 64 px thumbnail (`.orca-attachment`, `img` with `alt` the file name) with a remove button (`.icon-btn`, `aria-label` "{name} を外す"). The button of the composer is enabled with text or with an image (the other conditions of A-6 are unchanged).

The post. With images, `post()` first puts each one, in order, in the destination worktree (`row.path` of the selected row, or the worktree chosen for a launch) with `orca_attach_image(path, name, data, environment)`, which answers the text for Claude. The text sent (or the first prompt of a launch) is made by the synchronous command `orca_compose_text(text, paths)` (a pure function in `orca_attach.rs`, unit-tested; `ts/orca.ts` calls it only when there is an image): the text of the textarea without its trailing blanks, a blank line and one such path for each image on a line of its own; when the text is blank, only the paths; with no path, the text as it is. A failed upload shows its message in `#orca-error`, keeps the text and the images and sends nothing. The text for Claude of an upload is remembered for the image by worktree and target, so a post that is pressed again after a failed send or launch does not put the image there again; a worktree or target that differs puts it again. A success clears the textarea and the images. A selected row with no path and an image gives 「画像を置く worktree が分かりません」 and nothing is called. The send and the launch themselves are those of A-6: never tried twice, and checked against the list read just now.

`orca_attach_image` checks, in Rust and in Japanese: the path is absolute; the data is base64 of a file that is not empty and at most 20 MiB (an overlong string is refused before it is decoded); the bytes are an image by their magic bytes, PNG, JPEG, GIF or WebP (SVG and anything else is refused with 「画像（PNG、JPEG、GIF、WebP）だけを添付できます」); then it reads the worktree list of the target just now (as a launch does), requires the path to be in it and takes the `hostId` Orca names for it (none: 「Orca が worktree のホストを答えませんでした」), and refuses a worktree of an SSH host (`hostId` of the form `ssh:{id}`, which has no file calls) with 「SSH の接続先の worktree には画像を添付できません」. The extension is that of the kind found in the bytes (`png`, `jpg`, `gif`, `webp`), never the given name's. The file name is the stem of the given name (one path element, without its extension, only Unicode letters, digits, `-` and `_`, the others becoming `-`, trimmed of `-`, at most 40 characters, `image` when nothing is left) with that extension.

The upload is made over Orca's runtime, as A-7 reads it: this machine over its unix socket, a saved server over its WebSocket (one connection kept for the whole upload), with the pairing read from Orca's files at that moment; no token is in a return value, a log line or an error text. Every call takes `worktree` as `path:{absolute path}`, and a change also takes `expectedExecutionHostId`, the `hostId` above (without it, or with another value, Orca refuses it). The steps, in this order:
1. `files.stat` of `.orca/drops/.gitignore`; only when it answers `ENOENT`, `files.writeBase64Chunk` writes it with the content `*` and a newline, so the images do not show as changes of the repository. A failure of this write is ignored (as Orca does). Any other failure of the `stat` is the upload's.
2. One `files.stat` of `.orca/drops/{stem}.{ext}` decides the name: when it answers `ENOENT` (the message of Orca starts with it) the name is free and is `{stem}.{ext}`; when the file exists the name is `{stem}-{16 hex digits}.{ext}`, with the digits of the temporary name in step 3, and the name is not looked for again, because step 4 refuses an existing file. Any other failure of the `stat` is the upload's.
3. The bytes are written to `.orca/drops/.{name}.orca-upload-{16 hex digits}` with `files.writeBase64Chunk` in chunks of 384 KiB (a larger frame closes the host's socket): `append` is `false` for the first chunk (the file is created, and an existing one is refused) and `true` for the others; the folders are created by the call (`files.write` does not create them and is not used).
4. `files.commitUpload` copies the temporary file to `.orca/drops/{name}`, which fails when that exists, so a file is never overwritten.
5. `files.delete` (`recursive` false) removes the temporary file, after the commit and also after a failed chunk or commit; its result is ignored.
The answer is `{worktree path}/.orca/drops/{name}` made into the text for Claude: a blank, a double quote, a single quote, a backtick, a backslash and each of `$ ; & | < > ( ) { } [ ] * ? ! #` has a backslash before it (as Orca's own paste of an image path does, and Claude reads the image from such a path, a path with blanks included); a path with a control character is refused. The same route is used for this machine, although Orca itself passes the original path of a file there, so that a pasted image (which has no path) and a dropped one behave the same, and for a saved server. Nothing in `.orca/drops/` is deleted later: Orca has no clean-up of it either, and the `.gitignore` keeps it out of the repository.

Errors. The message of a failed call is Orca's code (「Orca がエラーを返しました（{code}）」), never Orca's own message, as A-7. A saved server whose pairing has only the `mobile` scope answers `forbidden` to these calls; the message then says the pairing has no permission to put files there, with the code. When Orca is not running on this machine, the message of A-7 for the unix socket is shown. `files.*` is not a public interface of Orca: an update can change it, and then an upload fails with a message while A-6 keeps working without images.

Unit tests (`cargo test`) cover the kind by the magic bytes (and what is refused), the base64 and the limit, the file name (path parts, unusual characters, a long name in characters and in bytes, the fallback), the name chosen with one `stat`, the escaping of the path and the refusal of a control character, the refusal of an SSH host, the message of `forbidden`, the `hostId` lookup, and the upload driven by a stand-in for Orca's calls (the order of the calls and the `hostId` in them, the chunk sizes and `append`, the `.gitignore` only when missing and its failure ignored, a taken name, a failed commit and a failed chunk with the temporary file deleted and the error passed, a failed delete not failing the upload, a `stat` that fails for another reason); none of them talks to a real Orca. The E2E spec `orca.e2e.ts` covers the paste and the drop, the thumbnail and its remove button, a file that is not an image, a file dropped elsewhere, the button enabled by an image alone, the arguments of `orca_attach_image` and the composed text of a send and of a launch (also with a blank text), a failed upload keeping the text and the images without sending, a send pressed again not uploading again, and a selected row with no path.

## A-11 Answer a question in the Orca history

A question of Claude (`AskUserQuestion`) that waits in the history of A-7 is answered where it is drawn: the user picks the choices and presses 「回答を送る」, and the picks are typed into the terminal of that session. It works on the Orca screen (A-6) and in the side pane of A-9, for a session of this machine and, by the same route, for one of a saved environment. Rust is `src-tauri/src/orca_answer.rs` (the command `orca_answer`), and the frontend is the history code `ts/orca-chat.ts`, which draws for both owners. It was written against Claude Code 2.1.318 and Orca 1.4.249, and the screens it waits for are the wording of Claude Code: an update of Claude Code can change them, and then nothing is sent and the question is answered in the terminal as before.

The box. A question item that waits (`waiting` true) and whose questions all have choices is drawn as a form (`.orca-question.orca-pick`, on `--bar`): for each question its text (`.orca-question-text`) and its choices, each a button (`.orca-pick-option`, `aria-pressed`, at least 44px high, 8px corners) with a mark, the label (`.orca-question-label`) and the description (`.orca-question-desc`). A question of one pick (`multi` false) has a circle for a mark and holds one pick, which another pick moves; a question of several (`multi` true) has a square that shows a check, and each press toggles one choice. At the foot, the note 「回答待ち」 (`.orca-question-waiting`) on the left and the primary button 「回答を送る」 (`.orca-pick-send`) on the right, disabled until every question has a pick. Nothing is sent before it is pressed. Any other question item (answered, or with a question that has no choices) is drawn as in A-7, with no buttons. The picks are held in memory by item id while the history is open, so an `items` event that draws the timeline again keeps them, and opening a session drops them. A press on a choice changes the buttons in place (no box is made again, so the focus stays).

The target. The view that draws the history says where an answer goes when the button is pressed: the Orca screen the handle of the selected row and the target it holds (the saved environment, or this machine), the side pane the handle of its session as its next send resolves it (`known.handle`, else the handle of its row) and the target the session was started with. When there is none (a row with no terminal handle) the box shows 「このセッションには送れません」 in a `.pending.fail` line and nothing is called.

The command. `orca_answer(handle, questions, environment)`, with `questions` a list of `{text, multi, options, picks}` (the texts of the question and of the choices as the history shows them, and the 0-based indexes of the picks). Rust checks, in Japanese and before anything is typed: there is at least one question and at most 10; a question has a text, 1 to 9 choices with a text each, at least one pick, every pick is a choice and none is twice, and a question of one pick has exactly one. The handle is a terminal handle as in A-6, `environment` is a saved one, and the handle must be a row of the list read just now (the session is gone otherwise). The keys are made by Rust from digits and Tab only (the digit is the choice's number, from 1); no text of the screen or of the history becomes a key, and the free-text choices of Claude Code ("Type something", "Chat about this") are not offered.

The steps, as measured on a real machine. Keys sent together at once break the form (the form took the second question's pick only and stopped), so the keys go one at a time, and before each key the screen of the terminal is read (`orca terminal read --screen --json`, `result.terminal.tail`) every 100 ms, for at most 5 seconds, until it shows what the key is for; a key typed while the question is not yet asked lands in the composer of the session. A key is typed with `orca terminal send --text=<key> --json` (no `--enter`), the route of the keys of the mirror of a saved environment in A-8; the key is a digit or a tab, so no secret is in the arguments, and the route is the same for this machine and for a saved environment. The picks are sorted in the order of the choices. For each question:
- A question of one pick waits for the question shown and types the choice's digit. With one question only, this digit sends the answer and there is no review. With more, it goes on to the next question.
- A question of several waits for the question shown (no box is checked yet) and types the digit of the first pick; then, for each next pick, it waits for the previous pick to be checked and types the next digit; at last it waits for the last pick to be checked and types Tab, which goes to the next question or, after the last one, to the review.
- After the last question, unless the only question is of one pick, it waits for the review and types 1 ("Submit answers").

A screen is compared by its characters only: every blank (including line breaks and the padding of the terminal) and the cursor `❯` are taken out of the screen's lines joined together and of the text it is compared with, so a line that wraps still matches and the cursor may stand on any line. The text of Claude is always above the interface, so a form is real only when it is at the end of the screen, and the text of Claude (which can carry the same question and numbered lines) or a permission prompt under it is not answered. The question is shown when all of this holds, as measured on Claude Code 2.1.318:
- The last line that is not blank starts with `Enter to select` and ends with `Esc to cancel`. The permission prompt of a tool ends in `Esc to cancel · Tab to amend`, and a working or waiting screen ends in its status line, so they are not taken for the form.
- After the last occurrence of the text of the question, the first choice follows at once (`1. Apple` for one pick, `1. [ ] Banana` with an empty box for several), and then the other choices in order (a line of description may lie between them).
- After the last choice come `{n+1}. Type something` (`{n+1}. [ ] Type something` for several), then, with only the full stop of the single choice or the `Submit` of the several and the rule between, `{n+2}. Chat about this`, and the footer line is the only thing after it.
- For several picks no box is checked.

The echo of the prompt that asked the question has the text but not the numbered choices, so it is not taken for the question, nor is a question whose box is already checked, nor an answered one, nor the text of Claude above another form. A pick is checked when its form is the same, with the boxes of the picks up to this one in the order of the choices checked (`2. [✔] Berry`) and no other box checked. The review is shown when the screen after the last `Review your answers` is exactly the answers, `● {question}` and `→ {the picked labels in the order of the choices, joined with ", "}` for each question in order, then `Ready to submit your answers?`, `1. Submit answers` and `2. Cancel`, and nothing after it (the review has no footer line): the answer "Banana" is not taken for "Banana, Bean".

Failures. A screen that is not the wanted one after 5 seconds stops the answer: before any key was typed the message is 「質問が画面に出ていません。ターミナルで答えてください」 and nothing was typed; after some key it is 「回答の途中で画面が変わりました。ターミナルで続けてください」, and what was typed stays in the terminal. A failed read or send gives the message of A-6 as it is, with 「（回答は途中までターミナルに入っています。ターミナルで続けてください）」 added when a key was already typed. The command is never tried again. The box shows the message in a `.pending.fail` line, keeps the picks, and enables the button again. While the answer is on its way the button reads 「送信中…」 and is disabled, with the choices; after a success it stays so until that item no longer waits (the history then shows 「回答: …」 and the choices go), so a question is not answered twice. When the command ends, the box alone is drawn again from the item as the timeline holds it, if the session shown is still the same one. The answer to a question is in no log line, and the keys are in no return value.

Not verified. The route for a saved environment is the same code with `--environment=<name>`, and it has not been run against a real saved environment. The wait of 5 seconds and the interval of 100 ms are first values. A session that asks while it is not at the question's screen (another dialog, the user typing) is not answered, by the screen check.

Unit tests (`cargo test`) cover the validation of the questions, the keys and their screens for one question of one pick, one of several, two of one pick, and one of one pick and one of several, the comparison of a screen (the three screens of Claude Code as measured, the echo of the prompt, a question with only some of its choices or with fewer than the form has, a checked box, a box checked that is not a pick, a pick still to come, an answered question, a wrapped line, a label cut in a word, blank lines after the footer, the text of Claude with the question and numbered lines above a permission prompt or above the input box and the status line, also with the footer line forged, the form of another question under the text, a review with another answer, in another order, with a longer answer, with a line after it and without the request to submit), and the typing of the keys against a stand-in terminal (the order of the keys, a screen that comes late, a screen that never comes before the first key and after it, a read and a send that fail before and after the first key); none of them runs the real CLI. The E2E spec `orca.e2e.ts` covers the form (the marks, one pick moved, several toggled, the button disabled until every question has a pick, nothing sent before the press), the arguments of `orca_answer` and the target (this machine, a saved environment, a row with no terminal), the button waiting until the question stops waiting and the answer shown then, the picks kept when the timeline is drawn again and dropped for another session, a failure keeping the picks, and a question that is answered or has no choices drawn without buttons; `orca-handoff.e2e.ts` covers the answer from the side pane.
