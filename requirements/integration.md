## A-1 Claude integration

A local MCP server (`cookapps-mcp`, stdio) lets Claude list, read, archive, mark read and trash inbox threads, and list events

## A-2 Claude model and effort

The Claude tab of the settings screen has a card "モデルと effort" (shown whether or not Claude can be used; the columns are headed "用途", "モデル" and "effort", and a note says the next call uses the choice and the default is Sonnet and medium, Sonnet and high for the Slack thread conversation, so the options carry no "(デフォルト)") with, for each of five purposes, a name, where it is used, and two narrow selects that choose its model and its effort: the Slack summary (S-2, "Slack の要約", used when a Todo is made from a Slack message), the mail summary (M-8, "メールの要約", the AI summary of the mail detail), the prompt conversation (S-3, "プロンプトの会話", editing the Todo summary prompt with Claude) the Slack text proofreading (S-4, "Slack に貼る文章の校正", the "Claude と校正" pane) and the Slack thread conversation (S-7, "Slack のスレッドの相談", the Claude pane of the thread detail). Each `claude -p` call uses the model and effort of its own purpose. The model is Haiku, Sonnet (the default) or Opus (Fable is not offered; a saved `"fable"` is an invalid value and gives Sonnet). The effort is low, medium (the default), high, xhigh or max, and `--effort` is always passed. Changing the model also switches the effort to the one the documentation recommends for it, saved in the same write: Haiku medium, Sonnet high, Opus medium (Rust `recommended_effort`, from https://platform.claude.com/docs/en/build-with-claude/effort, "Recommended effort levels"); the screen sends the model alone, and `claude_model_settings_save` takes an optional `effort` that defaults to the recommended one, while changing the effort sends both. The first default (nothing saved) stays Sonnet and medium, and Sonnet and high for `slackReply`. An effort select is colored by its value (`data-effort`, variables in `:root`): low gray, medium green, high yellow, xhigh orange, max red, following a change, a save and a failed save; the settings card colors the background and the text, and the frameless select of S-3 the text only. A change is saved at once, for that purpose only, in `claude-settings.json` in the app config directory (an object keyed by `slackSummary`, `mailSummary`, `promptChat`, `proofread` and `slackReply`, each `{model, effort}`; one save reads the file again, changes one purpose and writes all five through a temporary file and a rename), and the next call uses it. Rust checks the purpose, the model and the effort against their lists when saving (a refusal is a Japanese message), and a missing file, an unreadable file or an invalid value gives the default for that purpose, so only a listed value reaches `--model` and `--effort`. A file in the old form, one `{model, effort}` pair for every call, gives that pair to all five purposes until a purpose is saved, and a file without `slackReply` gives that purpose its default. From high up (high, xhigh, max) a call may run 300 seconds (`--effort max` took 61 seconds on a small input); below that it is 60 seconds for the summaries and 120 seconds for the prompt conversation and the proofreading. The `?` hint of the Claude card says that each of the five calls has its own model and effort. The thread detail of S-6 shows the selects of `slackReply` under its request field, as S-3 shows those of the prompt conversation. The screen of S-3 shows the selects of the prompt conversation too

## A-4 Claude connection

The `claude -p` calls of M-8, S-2, S-3, S-4 and S-7 go through the Claude Code CLI, which signs in either with the Claude subscription (the default) or with an Anthropic API key. The first card of the Claude tab ("Claude", with ↻ and `?`) has two rows with radios, "サブスクリプション" (email, plan, Claude Code version and state: ログイン中, 未ログイン with the `claude auth login` guidance, 未導入, 確認できません) and "API キー" (the workspace ID when Anthropic says it, the note that every call is billed, the state 未登録, 確認済み, 確認できません or 使えません, "貼り直す" and the disconnect button), so the state of the one not in use shows too. Pressing the radio of the API key row with no key stored, or with a key Anthropic refuses, only opens the key field ("確認して保存"); nothing is switched or logged out. If the keychain cannot be read, only the key row says 確認できません with the error; if asking for the connection itself fails, the card shows one failed row with the error and no radio, so nothing can be pressed, and Claude is in its failed state. At start only `claude_status` is called (so a start without the settings never asks Anthropic about a key); `claude_connection`, which answers the three parts of the card and the usable state `claude` with each state read once, is called when the Claude tab is first shown, by ↻ and after a change of the connection, and only the latest answer of the reads is used. While a change is on its way ↻ and the radios wait, and so does the button of the key field (also while the states are being read); sending the field while a change is on its way does nothing and does not empty it. A change of the connection redraws the connection card only, so the model selects and the prompt row keep their place and focus. Only the radio of a row switches the method (the radios are not grouped by name, so the arrow keys move none of them, and are disabled while a change is on its way); clicking or double-clicking the text of a row does nothing. The key is never shown, and the field is emptied as soon as it is read. The method is saved in `claude-auth.json` in the app config directory (`{"method":"subscription"|"apiKey"}`, written through a temporary file and a rename; a missing file, an unreadable one or an invalid value gives the subscription), and the key is in the OS keychain (service `jp.mysis.cookapps.claude`). Rust does not call the API for the work: the `claude -p` child process gets the key as `ANTHROPIC_API_KEY`, and `ANTHROPIC_AUTH_TOKEN` is taken out (the CLI prefers it) together with `ANTHROPIC_BASE_URL`, `CLAUDE_CODE_USE_BEDROCK`, `CLAUDE_CODE_USE_VERTEX` and `CLAUDE_CODE_USE_FOUNDRY` (they would send the key to another host or provider than the one it was checked against), while the subscription takes `ANTHROPIC_API_KEY`, `ANTHROPIC_AUTH_TOKEN` and `CLAUDE_CODE_OAUTH_TOKEN` out. The key is in no command-line argument, log line or error text. `claude auth status` answers `loggedIn: true` for a made-up key (measured), so it does not check a key. A pasted key is trimmed, must start with `sk-ant-` and must not be an Admin key (`sk-ant-admin`) (a refusal is a Japanese message), then `GET https://api.anthropic.com/v1/models?limit=1` with `Authorization: Bearer` and `anthropic-version: 2026-10-21` (a short timeout) asks Anthropic, and the response header `anthropic-workspace-id` is shown on the key row. 401 and 403 mean the key cannot be used; any other failure means it cannot be checked. At registration neither is saved. When `claude_status` asks again later, a key that cannot be checked stays usable (only the state says 確認できません), and a key Anthropic refuses is not usable. A key registered from the field that the radio of the API key row opened (`claude_key_save` with `switch`: after the check, the keychain write and the `claude-auth.json` write), and pressing the radio of a stored key (`claude_method_set` asks Anthropic first and refuses a rejected key; one that cannot be asked about is let through), switch to the API key and run `claude auth logout` for Claude Code, unless the API key is the method already (then nothing is logged out, so a login made again by hand is kept). The logout is checked by reading `claude auth status` again (that alone, no `--version`): only logged out or no Claude Code counts, and a login that remains, or a status that cannot be read, means the logout is not confirmed (the switch stays). `claude_method_set` then answers an error; `claude_key_save` answers that the key is stored, with `logoutError`, and the screen closes the field and shows that text as the error. A key pasted again with "貼り直す" (`switch` false) only replaces the key: the method does not change and nothing is logged out. Going back to the subscription only changes the method (the key is kept, and a logged-out row says 未ログイン with the `claude auth login` guidance). Deleting the key asks for confirmation, and when the key was in use the method goes back to the subscription (the logout is not undone). The usable state the whole screen follows (`Claude`: the sidebar, Todo, M-8, S-4, S-7, S-3) is `ready` for a logged-in subscription, or for an API key that is not refused (then email and plan are empty, the sidebar popup and the button's `aria-label` say "API キー" instead of the email); it is not `ready` while the key is refused or missing. The `?` hint explains the key (made in the Console, limited to a workspace, kept in the keychain, switching logs Claude Code out on this device). No cost is shown. Unit tests and E2E never run a real logout

## A-6 Orca

A screen of its own (`nav-orca`, `#orca`) shows which Claude agents run in Orca, a desktop agent orchestrator with a CLI (`orca`), posts to them, shows the history of the selected one (A-7) and starts new ones. It stores nothing about a session: every read asks the CLI again. Only agents of type `claude` are listed and started; an agent of another type (Codex) has no row, and a launch always starts Claude.

The screen is two panes side by side (`#orca` is a `.split-main`): the list pane `#orca-list` on the left, the divider `#orca-split` (a `.split-bar` with `role="separator"`, `aria-orientation="vertical"`, `aria-label` "一覧の幅", `aria-valuemin` 20, `aria-valuemax` 50 and `tabindex` 0), and the work pane `#orca-work`. The list is 30% of the screen at first and the user sets it between 20% and 50% by dragging the divider, or with the arrow keys (Right widens, Left narrows, 2% a step); the ratio is kept in memory (as the divider of S-1 and S-6, `ts/split.ts` serves both). The list pane has a header bar (as `#slack-header`) with the heading "プロジェクト" (`#orca-heading`) and, at its right, in this order, the bell `#orca-bell` (A-8), the update button (`↻`, `aria-label` "更新") and the new button `#orca-new` (`+`, `.icon-btn`, `aria-label` "新しく起動する", `aria-haspopup` "menu": it opens the menu of A-8). The status label with a dot (`#orca-status`, or `#orca-target`) is in a footer (`#orca-foot`) at the bottom of the list pane, under the list. The list shows the projects (A-8) first; with the bell pressed it shows the working view: three groups with a heading that has the status icon of A-8, the name and the number at the right end: "入力待ち" (above the others, because the user has to act), "作業中" and "完了"; a group with no rows has no heading, and with no rows at all the list says "動いているエージェントはありません". A row (a button) has three lines: the status icon, the title (the first line of the prompt) and the time at the right; the latest action of the agent (A-8); and Claude's mark with "{repo} ・ {branch}". There is no repository heading, no filter and no agent chip. `nav-count` of the Orca button shows the number of agents that wait or work (入力待ち plus 作業中, not 完了), with the label "Orca（作業中 n 件）"; it does not enter the Dock badge.

The work pane has a header that is the tab strip of the selected project (A-8), or, while no tab shows, `#orca-work-title` ("新しいセッション" when no project is selected, else the project's name); the history `#orca-chat` that scrolls (A-7); and under it, pinned, the composer: a textarea and a primary button. A row of the working view is selected by clicking it (`aria-pressed`, the `--soft` background), which also selects its project and its tab (A-8); a row with no pane key cannot be selected. With a row selected, the button is "送る" and the placeholder is "追加の指示を書く（/ でスキル）", and the button is disabled when that row has no terminal handle (its history can still be read). In the new-session pane (no project selected: the first state, and "Claude を起動" of the plus menu), a row above the composer has the label "起動先" and the chip `#orca-dest-pick`, which opens a dialog (`showMenu`, `role="dialog"`) with a filter field (`aria-label` "worktree を絞り込む", case-insensitive on "{repo} ・ {branch}") and two-line rows (the repository, then the branch) of every worktree; picking one closes it and the chip names it. The button is "起動する" and it is disabled until a worktree is chosen; the placeholder is "起動するエージェントへの指示を書く（/ でスキル）". The button is also disabled while the text is blank or a post is on its way, and when the command is missing. While a post is on its way the textarea is disabled, and it has the focus again afterwards. A post that works clears the textarea and reads the list at once; one that fails keeps the text and shows the CLI's message (`error.message`) above the composer. A send whose answer says `result.send.accepted` is false is a failure too (Japanese message), so the text stays. Selecting a row clears the worktree chosen for a launch, so the next launch chooses it again. A post is never tried again, because after a lost reply a second one would post twice (the CLI forbids a fresh retry of a launch). The side pane of A-9 launches and sends through the same checks (`orca_handoff` composes the prompt and then runs the same launch or send once).

The CLI is found among the absolute places `/usr/local/bin/orca` and `/Applications/Orca.app/Contents/Resources/bin/orca` (a GUI app has no shell PATH), and run with an argument list, never through a shell, in the temporary folder, with stderr dropped and a timeout (15 seconds for a read, 60 seconds for a launch and a send) after which the child is killed, off the UI thread. The commands are `orca worktree ps --limit 200 --json` and `orca terminal list --json` (the list), `orca terminal send --terminal <handle> --text=<text> --enter --json` (send), `orca agent launch --agent claude --worktree path:<path> --surface terminal --prompt=<text> --json` (launch; its reply holds `result.outcome` `{kind: "terminal", handle, paneKey}`, which `orca_launch` returns as `{paneKey, handle}`, each `null` when the reply lacks it or holds it in a shape that is not a pane key (at most 256 characters of `[A-Za-z0-9:_-]`) or a terminal handle (A-9 uses it to read the history of the session it started)), `orca environment list --json` and `orca skills installed --json`; the text of the user is joined to its flag (`--text=--json` is accepted, while `--text --json` is refused as "requires a value"), and `--environment=<name>` is added to every one of them but the list of environments and the list of skills when a target is chosen (`orca skills installed` refuses `--environment` with `invalid_environment`, because it lists the skills of the machine it runs on). The output is JSON, `{ok, result, error: {code, message}}`, also on failure, so stdout is read whatever the exit code and `error.message` is shown (the code when there is no message); an empty output or one that is no JSON gives a Japanese message. The prompt text is in no log line.

Rows are built by a pure function from the two documents (`result.worktrees[].agents[]` and `result.terminals[]`), tolerant of absent fields. An agent is kept when its `agentType` is `claude`, it is top-level (`parentPaneKey` null) and `hasLivePty` is true. Its group follows `state`: `waiting`, `blocked` and `permission` are 入力待ち, `done` is 完了, and every other state (`working`, and a state not known yet) is 作業中. The line (the title of the row and of its tab) is the first line of `prompt`, else of `taskTitle`, `conversationName` and `lastAssistantMessage`, in this order, whatever the state. The activity (A-8), the second line of a row, is `{toolName}: {first line of toolInput}` (the name alone when the input is not text or is blank), else the first line of `lastAssistantMessage`, else empty, cut to 200 characters. The branch is the worktree's `displayName`, the repository its `repo` and the path its `path`. A row also carries the agent's `paneKey` (null when it has none), which finds its session for the history (A-7), and its `activity`, `status` and `projectKey` (A-8). The time is `stateStartedAt` for an agent that runs or waits ("2 分", the time since) and `updatedAt` for a done one ("18 分前"), sent as epoch milliseconds and formatted by the screen. The terminal handle is found by joining the agent's `paneKey` with the terminals' `"{tabId}:{leafId}"` (an orphaned terminal by its `recordedPaneKey`, as below). Rows are sorted by `updatedAt`, newest first. The launch targets are all worktrees, with their path, repository and `displayName`.

Just before it acts, Rust reads the list again (with the environment): a send goes only to a handle that belongs to a row of that list (a top-level agent of a live terminal; `writable` is not used, because a plain shell terminal is writable too; an orphaned terminal, one that lost its tab and still runs, belongs to the agent whose pane is its `recordedPaneKey` when its `agentIdentity` is `claude` and no other orphaned terminal recorded that pane, and a live terminal of that pane comes first), and a launch only into a worktree of it; otherwise the answer is a Japanese error and nothing is sent. Rust validates before it runs anything and answers in Japanese: the text is not blank and at most 100,000 characters; the handle begins with `term_` and holds only `[A-Za-z0-9_-]`; the path is absolute; the environment is one listed by `orca environment list --json` (`result.environments`, each a name or an object with a `name`, else an `id`).

The target is "このマシン" or a saved environment (a paired server). It is saved in `orca-settings.json` in the app config directory (`{"kind":"local"}` or `{"kind":"environment","name":"..."}`, written through a temporary file and a rename), and only when the file does not exist yet the first saved environment is used, else this machine. A saved environment that is no longer listed, or a file that cannot be used while an environment is saved, never switches the target by itself: the read is a failed one with 「保存した接続先が見つかりません」 (the label names the saved environment), the menu lists the environments and "このマシン", and the owner chooses again (with no environment saved there is nothing else to choose, so a file that cannot be used gives this machine). The status label shows it: green "{target} に接続中" after a read that worked, orange "{target} に接続できません" with the message in a notice when it failed (the rows of the last good read stay while the target is the same), and gray "未インストール" with a notice when no `orca` was found. The label is plain text until an environment is saved, and from then on a menu of "このマシン" and the environments; choosing one saves it, drops the selection and the rows of the old target, and reads again; until that first read of the new target returns, the label says 確認中 and the list 「読み込んでいます…」 (nothing is said about the target), and the menu stays. The environments are listed even when a read failed, so the target can still be changed. When `orca environment list` itself fails, the screen keeps the target, the environments and the rows it had, and shows the failure.

The list is read at startup (for the count), every 10 seconds while the Orca screen is shown and every 60 seconds otherwise, one read at a time, and no more by the clock once the command was found missing (the update button looks again). The environments are read (`orca environment list`, and the target resolved, together with the SSH hosts of A-8) only at startup, when the screen is shown, by the update button, when the target changes and in a read after a failure; the clock reads the agents and terminals of the target held while the screen is shown, and only `orca worktree ps` (for the count, with no terminal list) while another screen is shown. A read in the background swaps the rows in place and keeps the selection (dropped only when its session is gone), the text in the textarea, the scroll position and the history on screen, and never calls `show()`.

Every destination is Claude, so a skill list completes commands as Claude Code's does. `orca skills installed --json` (`result.skills[]` with `name`, `description`, `providers`, `sourceKind`, `sourceLabel`) is read once when the screen is first shown with the command found (also while the target fails to read) and again by the update button, never per keystroke and never with `--environment`; a failure gives no list for now and never blocks a post, and the read is tried again by the list reads that follow, at most once a minute (so a list that failed while this machine's Orca was not running comes once it runs), until one succeeds. The list is that of the machine the app runs on, whatever the target, and it needs Orca running on that machine, so with a saved server as the target it can differ from that server's skills, and a change of the target does not read it again. A pure function keeps the skills whose `providers` include `claude` and turns each into the command `/{name}`, or `/{plugin}:{name}` for `sourceKind` `plugin` with a `sourceLabel` of the form `Claude plugin {plugin}` (its `name` has no plugin prefix); it drops a command listed twice, sorts by command and cuts the description to its first line. The list opens when the text starts with `/` and the caret is still in that first word (no whitespace yet), and only while the textarea has the focus (a read in the background does not open it). It is a popup (`role="listbox"` with `aria-activedescendant`) directly above the composer, with the frame and shadow of `#account-popup`, the command in monospace and its description on one line with an ellipsis, 8 rows at most before it scrolls. It shows the commands that contain the text after `/`, case-insensitively, those that begin with it first. Up and Down move the highlight and wrap around, Tab or Enter put the command and one space in the place of the first word (the caret after the space, and nothing is posted), Escape closes it until the text changes, and a click on a row does what Tab does. Enter does not submit while the list is open. A read in the background does not close it or move the highlight.

Unit tests (`cargo test`) cover row building, the argument lists (the `--flag=value` form and the environment), the validation, the parsing of the output and the environments, the target setting and the skill list; none of them runs the real CLI. The E2E spec `orca.e2e.ts` covers the two panes and the divider, the drawing of the working view, the selection, the dialog of the worktrees, the arguments of a send and a launch, a failure keeping the text, the missing command, a failed read, the target menu, a read in the background and the skill list.


## A-7 Orca session history

The work pane of A-6 shows the history of the selected session: what the user asked, what the agent answered and the tools it ran. The history is read from Orca's own runtime, not from the CLI (the CLI has no command for it), and nothing of it is stored by this app. It was written against Orca 1.4.248, whose runtime is not a public interface: an Orca update can change the calls, and then the history shows 「このセッションの履歴は読めません」 or a message of the read, while the list and the posts of A-6 keep working.

Selecting a row (with a pane key) opens its history: `orca_chat_open(environment, path, paneKey, channel)` is called with a `Channel` (`window.__TAURI__.core.Channel`), and Rust sends `OrcaChatEvent`s to it until `orca_chat_close` (the selection is cleared or its session is gone, the target changes, or the screen is left; the one-second tick of the screen sees it is no longer shown) or another `orca_chat_open`. Only one session is read at a time. An event of a channel that is no longer the current one is ignored. The history is not tied to the Orca screen (A-9): the read has one owner at a time, the work pane of the Orca screen or the side pane of a mail, a Slack thread or a Todo, and the history code (`ts/orca-chat.ts`) draws into the owner's view (the scroll box, its list, the button for older messages and the status line). Opening a read for one owner wipes what the owner before it drew, and an owner closes only its own read: the tick of the Orca screen that sees the screen is no longer shown calls `orca_chat_close` only while the screen still owns the read, and a side pane takes the read only while it shows a session in view. When the owner comes back into view (the Orca screen shown with a row still selected, or the item of a side pane open again) it opens its read again, also when another owner had it meanwhile. There is no second concurrent reader. While the window is hidden (`document.hidden`) the screen calls `orca_chat_pause(paused)` with `true` (also for a session opened then) and with `false` when it is shown again, and a paused session neither polls the transcript nor looks at the tabs again, keeping the connection, the older pages and what is drawn, and reads once at once on the resume. Rust validates the arguments (the path is absolute, the pane key is not empty, at most 256 characters of `[A-Za-z0-9:_-]`) and answers a Japanese error that the screen shows as the status.

What is read, with the pane key of the row and the worktree's path: `session.tabs.list` with `{worktree: "path:<path>"}`, whose `tabs[].agentStatus.paneKey` is matched and `agentStatus.providerSession.id` is the session id (none: 「このセッションの履歴は読めません」, and the tabs are looked at again every 30 seconds; a changed id, as after `/clear`, drops what was held and reads the new session); then the transcript, `nativeChat.readSession` for the first 40 messages and for each page of 100 older ones (`beforeOffset`), and, over a WebSocket, `nativeChat.subscribe` for what follows. This machine is read over the unix socket of `orca-runtime.json` in Orca's settings folder (`authToken`, and the transport of kind `unix` with its `endpoint`): one JSON line `{id, authToken, method, params}` and one line back, a connection for each call. That socket answers `method_not_supported` to `nativeChat.subscribe`, so on this machine the transcript is read again every 3 seconds and each answer is taken as the newest page. A saved environment (A-6) is read over its WebSocket (`ws://` only: the frames are encrypted end to end, with the pairing's key, and TLS is not built in) with the device token and the public key of `orca-environments.json`, using Orca's own framing, and the stream pushes the changes. Both files are read at each connect and never written. A token, a key or an authentication frame is in no log, no error text and no event. The unix socket exists on macOS and Linux; on another OS this machine has no history, with a message that says so.

An event is `items {start, items, hasMore}` (replace the timeline from index `start`; sent only when something changed) or `status {state, message}` with `state` `connecting`, `live`, `reconnecting` or `unavailable`. A failed or lost connection is `reconnecting` with the reason in Japanese, tried again after 1, 2, 5, 10 and then 30 seconds (the wait starts again once a page or a snapshot has been read, not when a call merely answered), and what is drawn stays on screen; a missing or rejected pairing is shown the same way with its own message. The messages are reduced in Rust (pure functions with unit tests): only user and assistant text and the agent's questions are drawn, a user message that the harness injected (known by its tag or its opening, as Orca's own screen hides it) and a message that starts an agent draw nothing, the lines of a user message that only name the file an image came from are cut, and a message left empty is not drawn. Tool calls in a row, with the results, reasoning and undrawn messages between them, become one `tools` item (a question, `question`, ends the run and is an item of its own) with a summary "ツールを 5 回実行（Read 2、Edit 2、Bash 1）" (in order of first use) and the calls, each a name and the first line (at most 200 characters) of the first string among `file_path`, `path`, `notebook_path`, `command`, `pattern`, `query`, `url`, `description` and `prompt` of its input; when the run is the last item and a call has no result yet it also has a running summary "ツールを実行中（Edit 1）". The outputs of the tools are not sent to the screen, except the answer to a question.

The history is drawn in `#orca-chat`: the user's messages as a right-aligned bubble of plain text (`--soft`; a message that handed a content over, A-9, holds the instruction and under it that content folded into one line, below), the agent's as Markdown (the sanitizer of Todo's descriptions; a remote image is not loaded, its alt text is shown instead; a table has ruled cells), and a run of tools as a button with a chevron and the summary (`aria-expanded`), which opens the calls in monospace as "name  detail". A call of `AskUserQuestion` is not folded and ends the run: it is a box that shows each question, its choices with their descriptions, and 「回答: …」 once the result gives the answer (read from the output `Your questions have been answered: "{question}"="{answer}"`, the only output kept); until the call has a result the box says 「回答待ち」, and a call whose questions cannot be read stays an ordinary call of the run. The running summary replaces the summary while the selected row is in the 作業中 group. A user message that carries a handoff block (A-9) is reduced in Rust (`orca_handoff::fold`): the item has an optional `context` `{kind, title, text}` (`kind` is `mail`, `slack` or `todo`) and its `text` is only the instruction, the line that says the block is quoted data removed; a message with no well-formed block is unchanged (see A-9 for the format). The context is drawn inside the bubble as a one-line button with a chevron (`.orca-ctx-btn`, `aria-expanded`) that says the kind, the title cut to 12 characters (with "…") and the number of characters, e.g. `メール「請求書の金額が…」186 字`; pressing it opens the text (`.orca-ctx-text`, plain text, `textContent` only, never HTML or Markdown). This is drawn by the shared history code, so the Orca screen folds too. Which runs and which contents are open is kept by item id while the history is open, so a run that grows or an `items` event that draws it again keeps it open. While the screen is at the bottom (within 40 px) it stays at the bottom as items come; scrolled up, it does not move; opening a session scrolls to the bottom. While `hasMore` is true the button `#orca-older` (「以前の履歴を読む」) is at the top; it calls `orca_chat_older`, the older messages arrive as an `items` event from index 0, and the message that was in view stays where it was. A run of tools does not join across the edge of an older page, so it keeps its id and stays as it was; the calls of the older page are a run of their own. While disconnected the press is dropped and the button stays. The status is a line above the history: `connecting` shows 「読み込んでいます…」 while nothing is drawn, `reconnecting` and `unavailable` show their message in a `.pending` line, and `live` shows nothing; the end of the first read is `live` even with no messages.

Unit tests (`cargo test`) cover the reduction of a handoff block (the block found, the wrapper `<pasted_content id="…">…</pasted_content id="…">` of a long paste tolerated when it wraps the whole message, a malformed block left unchanged, the quoted-data line removed from the instruction), the framing and encryption of the paired connection against fixed vectors, the choice of the pairing and the endpoint, the merging of snapshots, appended messages and older pages, the noise filter, the tool runs and their summaries, the questions and their answers, the changed index, the back-off, the pause and the events; none of them talks to a real Orca. The E2E spec `orca.e2e.ts` covers the opening and closing of the history by the selection, the drawing of the events, the Markdown, the questions, the folding of the tool runs and their state over a redraw, the older button and the scroll, the pause while the window is hidden, the status lines and the ignoring of a closed channel. The E2E spec `orca-handoff.e2e.ts` covers the folded content and the handing of the read between the Orca screen and a side pane.

## A-8 Orca terminal and project list

The Orca screen (A-6) has a terminal, and its list pane is a list of projects with a switch to the working agents. It was written against Orca 1.4.248.

Projects. The list pane shows the projects first (the choice of view is kept in memory). A row (a button, `.orca-project`, `aria-pressed` for the selected one) has the status icon, the name and the number of sessions (nothing when it is 0). A pure function builds them from the two documents of A-6: one project for each `repoId` among the worktrees that are not archived (`isArchived` is not true), have a path, and whose `hostId` is `local` (a worktree with no `hostId` is this machine's); the name is the worktree's `repo`. The worktrees of an SSH host (any other `hostId`) are not projects: they make the row `ssh:{hostId}` of that host. The sessions of a project are its Claude rows (A-6) and its plain terminals, and the screen adds the terminals of the app. The list is newest first by the latest `lastActivityAt` of the project's worktrees. Below the projects, under the heading "SSH", are the SSH hosts, in Orca's order, drawn the same way: the name is the host's `label`, and the icon and the number are what the worktrees with its `hostId` show (idle and none when there are none). A host that the worktrees of the target have (`ssh:{hostId}`) but that this machine's Orca does not list is a row of that group too, named by its worktrees' host name, after the listed ones. There is no search, no filter and no group chevron.

Status icons, the same as Orca's. A pure function maps an Orca state word to one of seven: `waiting`, `blocked` and `permission` are `question` (the `message-circle-question-mark` icon, orange); `failed` is a small red dot; `working` is a yellow ring that turns (it stops under `prefers-reduced-motion`); `monitoring` is the `activity` icon; `interrupted` and `unconfirmed` are a small gray dot; `done` and `active` are a green dot ("完了", or "起動中" on the tab of a terminal); `inactive` is a faint gray dot ("動いていない"). The colors are variables in `:root`. A word not known yet is idle for a worktree and working for an agent, as in A-6, and an agent with `interrupted` true is interrupted unless it waits or failed. The status of a row is its agent's; the status of a project is the highest rank among its top-level agents with a live pty, its worktrees' `sidebarStatus` (else `status`), its plain terminals (a green dot) and, added by the screen, the terminals of the app that have not ended (a green dot too; Orca does not know them, so a project or an SSH host row that Orca calls idle shows the green dot while one of them runs, and the gray one again when the last has ended), in Orca's rank: question, failed, working, monitoring, interrupted, done, idle (`unconfirmed` is drawn as interrupted and ranks with it, one place above where Orca ranks it).

The bell (`#orca-bell`, `.icon-btn`, `aria-pressed`, `aria-label` "作業中を表示する", and "作業中の表示をやめる" while pressed) switches the list between the projects and the working view of A-6, and the heading stays. At its right shoulder it shows the question icon and the number of agents that wait; with none, the working mark and the number that work; with none, nothing.

The SSH hosts are read from this machine's Orca over its unix socket (`ssh.listEditableTargets`, `result.targets[]` with `id`, `label`, `configHost`, `connected`; the socket of A-7, not a public interface), whatever the target is. Only `id`, `label` and `connected` cross to the screen; `configHost` stays in Rust, and a target whose `configHost` does not match `[A-Za-z0-9][A-Za-z0-9._-]*` (at most 255 characters) or has no `id` is dropped. They are read with the environments (startup, the screen shown, the update button, a change of the target), never by the clock, and a read that does not say what the target is leaves the ones the screen holds. A failure gives no SSH group and no error line.

Tabs. Selecting a project shows its sessions as tabs in the work pane (`#orca-tabs`, `role="tablist"`, each tab a `role="tab"` button with `aria-selected`) and selects the one last selected there, else the first. A tab has the status icon, the title and "{branch} ・ {time}" (the time of A-6, only for a Claude session), and a close button (`.icon-btn`, `aria-label` "閉じる") beside it, which never selects the tab. The tabs are the project's Claude sessions (rows with a pane key), its plain terminals and the terminals of the app, in the order they were first seen, so a read that reorders the sessions does not move them. A project with no session says 「セッションはありません」 in the work pane, with its name as the heading, and "Claude を起動" of the plus menu is the way to start one; no tab strip and no `#orca-work-title` shows while tabs do. The selection survives a read while its tab exists; when its session leaves Orca's list the project's last selected tab, else the first, is selected. Nothing closes by itself, a finished session included. A Claude session shows its history and its composer (A-6, A-7); a terminal fills the pane (below).

The plus menu. `#orca-new` opens a menu (`showMenu`, `role="menu"`) with "Claude を起動", which selects no project, so that the work pane is the new-session pane of A-6, and "ターミナルを開く", which opens a dialog (`role="dialog"`, `aria-label` "起動先") with a filter field (`aria-label` "起動先を絞り込む", case-insensitive), the group "このマシン" with the worktrees of this machine as two-line rows (the repository, then the branch) and the group "SSH" with the hosts (the label, then 「未接続」 when `connected` is false, which does not stop it). `orca_terminal_targets` reads them just now: `orca worktree ps` without `--environment` (the worktrees as for projects, not archived, of this machine) and the SSH hosts. A failure of the former is a Japanese message in the dialog, and the hosts still show.

Closing. The close button of a Claude session or a plain terminal of Orca calls `orca_close(handle, environment)`, which runs `orca terminal close --terminal <handle> --tab --json` (with `--environment=<name>` for a saved environment) with a timeout of 15 seconds; the handle is validated as in A-6, and the environment must be a saved one. The answer's `ptyKilled` is not looked at (it is false on a real machine although the process stops), and `error.code` `terminal_handle_stale`, which is what Orca answers when the terminal was closed first, is a success. On success the screen reads the list at once and the tab leaves with it; on a failure the message is shown (`#error`) and the tab stays. A tab whose session is gone from Orca's list leaves at the next read. A Claude session with no terminal handle cannot be closed. The close button of a terminal of the app ends its process and forgets it.

Terminals of the app. A terminal runs in a real PTY (`portable-pty`, in `terminal.rs`), so a full-screen program such as `claude` works, and is drawn by xterm.js (`src/vendor/xterm.js`, `xterm.css` and `addon-fit.js`, loaded as classic scripts and kept as distributed, with their version and license in a comment; the CSP is unchanged; scrollback 5000 lines; `ts/orca-terminal.ts`). Commands: `terminal_open(target, cols, rows, channel)` answers an id Rust generated, `terminal_write(id, data)`, `terminal_resize(id, cols, rows)`, `terminal_ack(id, bytes)` and `terminal_close(id)`. Only `terminal_open` waits for something outside (Orca's list); the others never wait for a PTY, so none of them holds a worker of the app, and a stuck terminal cannot stop another terminal, the close of any terminal or the quit. The target is `{kind: "worktree", path}` or `{kind: "ssh", id}`, and the screen never passes a program, an argument or a host name: just before it acts, Rust reads this machine's list again (never with `--environment`), and the path must be a worktree of it that is not archived, or the id one of `ssh.listEditableTargets`, else the answer is a Japanese error and nothing runs. A worktree opens the shell of the user (`$SHELL` when it is an executable, else the password database), in the path. An SSH host runs `/usr/bin/ssh -- {configHost}` with no shell and no other argument, so the host name is read from `~/.ssh/config`. `TERM` is `xterm-256color`, `COLORTERM` is `truecolor`, and `LANG` is `en_US.UTF-8` when the app has none. The id must be known; `cols` and `rows` are 1 to 1000 and nothing is clamped; an input is at most 1 MiB; each is a Japanese error otherwise. Each terminal has a reader thread, a sender thread and a write thread, and the sender sends events through a Tauri channel: `data` (base64 of the bytes read, at most 16 KiB each, so a burst is split; the bytes may end inside a UTF-8 character, so the screen hands xterm.js a `Uint8Array`) and `exit` (the exit code). Output is held back by the screen's confirmations: the screen calls `terminal_ack(id, bytes)` with the bytes xterm.js has drawn (the callback of `write`, in steps of 32 KiB, and the rest when the id arrives), also for a terminal whose tab is not shown; the reader stops reading while the output read but not confirmed is 1 MiB or more, so the program is held by the PTY, and goes on when `terminal_ack` brings it below, or stops for good when the terminal is closed or the app quits. A `terminal_ack` for a terminal that is gone is a success. Reads of a few hundred bytes are joined: the sender sends at once what is read after a pause of 1 ms or more, and otherwise waits up to 1 ms for a full 16 KiB, so a program that prints without end makes events of 16 KiB, not one event for each read. Input is queued, never written in the call: `terminal_write` only puts it in the queue of the terminal and answers, the write thread writes the queue in the order the calls came (the calls are not `async`, so Tauri runs them in the order the screen made them), and a program that does not read blocks that write thread only. The queue holds 4 MiB; a write that would go over it is a Japanese error (「入力が詰まっています。動いているプログラムが入力を読んでいません」) and the input is dropped, and once a write to the PTY has failed (the process is gone) every write is an error. Input behind a write that is stuck, a Ctrl-C included, waits for it: the PTY is not written out of order, so the way out of a stuck terminal is its close button, which kills the process, drops the queue and does not wait for the write thread. A terminal's output and input are in no log line, error text or event of the app. The screen sizes the terminal to the pane when it is shown (`fit`, and a `ResizeObserver` whose fit waits until the size has rested for 50 ms) and sends a new size only when it changed; the terminals keep running while another tab, project or screen is shown, and a finished one stays as a tab with a gray dot (and the green dot while it runs) and the line 「[終了しました]」 until it is closed, and nothing is written to it. When the app quits, the shells end with it (the state is dropped on `RunEvent::Exit`, which kills the children and waits for no read or write); nothing is kept or restored at the next start. A child that has been waited for (it ended) is never signalled by the close or the quit, because its process id may be another process's by then. After a close the reader thread ends at the next output or at the end of the output: a process that ignores the hangup and still holds the terminal keeps that thread and its file descriptor until it prints or ends. A terminal belongs to the project of the worktree it was opened in on this machine, or to the SSH host's row. With a saved environment as the target the project list is that server's, and a read may fail, so a project or an SSH host that the list does not show but that has a terminal of the app gets a row of its own (a project of this machine under the heading "このマシン" above "SSH", an SSH host in the "SSH" group), with the name it was opened with, so that the terminal can always be reached and closed; the row goes with its last terminal, and the work pane then returns to the new-session pane. A terminal that cannot be opened leaves the selection where it was.

Plain terminals of Orca. A terminal of `orca terminal list` that is not Claude's (`agentIdentity` is not `claude`: a shell, or another agent), still has its tab (not `orphaned`), and is in the worktree of a project is a tab of that project, titled by its `title`, with the green dot; the floating terminal has no worktree and is left out. Orca's runtime cannot stream the bytes of a terminal to this app (`terminal.subscribe` and `terminal.multiplex` answer `method_not_supported` over the unix socket), so the tab is a mirror: while it is shown, the screen reads `orca terminal read --terminal <handle> --screen --json` (`result.terminal.tail`, an array of lines with no colors, about 0.1 seconds each) every second, one at a time, and draws the frame again in xterm.js when it changed; the keys typed are sent with no `--enter`, so control bytes reach the terminal as typed, batched (at most 50,000 characters a send) and one send at a time, and the frame is read again soon after. What is typed can be a password, so it is kept out of the arguments of a process (`ps` shows them): with this machine as the target the keys go to its Orca over the unix socket of A-7 as `terminal.send` (`{terminal, text, enter: false, client: {id: "cookapps", type: "desktop"}}`, as the CLI sends them; the answer's `result.send.accepted` false is a failure). A saved environment has only the CLI's route, so there the keys go through `orca terminal send --terminal <handle> --text=<keys> --json --environment=<name>` and are in that process's arguments while it runs; type no password into the mirror of a saved environment. A key text is not checked for blank, but it may not be empty or hold a NUL or more than 100,000 characters. The handle must belong to a plain terminal of the list read just now, for a read as for keys; it is checked the first time a read or keys go to that handle (and target), and again after a read or a send of it failed. The mirror has no colors, a full-screen program is only approximate, and a size change is not sent. A failed send shows its message (`#error`); a failed read is tried again at the next second. The reads stop while another tab or screen is shown or the window is hidden (the shown terminal reads at once when the window is shown again), and the screen of a terminal is dropped when it leaves the list or the target changes.

Keys. While a terminal has the focus the app's own key handlers do not act: Escape only closes a menu, popup or hint that is open (none is while a terminal is clicked), and Cmd+Z of the inbox leaves a textarea's own, which is xterm.js's input. Cmd+C copies the selection and Cmd+V pastes, as in any field.

Unit tests (`cargo test`) cover the status mapping and rank, the activity line, the projects and their order, count and status, the plain terminals, the destinations, the SSH targets (and that the host name does not leave Rust), the screen lines, the stale answer, the arguments of close, read and send, the params of the keys sent over the socket, the validation of keys, handles and host names, the one-time check of a mirrored handle, the launch of a shell and of `ssh`, the environment, the size and input limits, the joining of short reads, and, with a real local PTY running `/bin/sh -c`, the events of output and exit, the write and its order, the resize, the close and the end at quit, that the reader stops without confirmations and goes on with them, that close and quit free a stopped reader, that output after a close ends the reader, that a child that was waited for is not signalled, and that after a large write to a program that does not read the close, the quit, the resize and the writes of another terminal return at once and the queue refuses input at its limit; none touches ssh, Orca or the settings folder. The E2E spec `orca.e2e.ts` covers the project list, the icons, the bell and its badge, the tabs and their selection and order, the plus menu and the dialog, the arguments of `terminal_open`, `terminal_write`, `terminal_resize`, `terminal_ack` and `terminal_close`, the output, the green dot of an idle project or SSH host row while a terminal of the app runs there, a finished terminal, a failed open, the close of an Orca tab (with its arguments, a failure and a tab that Orca closed first) the mirror (the reads, the frames, the keys and the pause while the window is hidden), the row of a project or an SSH host the list does not show, and the selection that stays when a terminal cannot be opened.

## A-9 Hand to Orca

The open mail, Slack thread or Todo can be handed to Orca (A-6) from the screen it is on, in a pane on its right side. Nothing is sent by itself: the user checks the content (a card), writes an instruction, chooses where it goes and presses the button. The pane is `ts/orca-handoff.ts` (one class, `HandoffPane`, with a host for each screen); the content of each screen is built in `ts/orca-handoff-cards.ts`; the prompt is composed and the history folded in Rust (`src-tauri/src/orca_handoff.rs`). It was written against Orca 1.4.248, as A-6 to A-8.

Entry. The header of the open mail (`#mail-header`, after "Todo にする") and the header of a Todo's detail (`#todo-body > header`, before "その他") each have an icon button `#thread-orca` / `#todo-orca` (`.icon-btn`, `aria-label` "Orca に渡す", `aria-pressed`, the Orca icon of the sidebar) that opens the pane `#mail-handoff` / `#todo-handoff` (`aside.ho-pane.split-chat`, `aria-label` "Orca に渡す") on the right of the screen, with a divider (`#mail-split` / `#todo-split`, a `.split-bar` with `role="separator"`, `aria-label` "Orca の幅"), set by `ts/split.ts` as the Slack thread and the compose screen do and kept in memory. The mail's pane is 37% of the screen at first, at least 400px, and the divider sets it between a third and a half (`aria-valuemin` 33, `aria-valuemax` 50); the Todo's is 380px at first and at least that, and the divider widens it up to half (`aria-valuemin` 0, `aria-valuemax` 50). The pressed button, or the pane's close icon, closes it. In the Slack thread (S-6) the right pane of S-7 is tabs "Claude" and "Orca" (`#reply-tabs`, `role="tablist"`, `aria-label` "Claude と Orca", `role="tab"` buttons `#reply-tab-claude` / `#reply-tab-orca` with `aria-selected`; Claude first and selected at first; the selected tab has a 2px accent underline and bold accent text, over a line under the strip; while Orca is selected the pane is at least 400px wide, and its width is otherwise the shared divider's of S-7): Orca replaces the log and the request field of the Claude tab by the pane (`#st-orca`, which takes their rows of the grid) and hides "クリア"; S-7 is otherwise unchanged. The Orca tab has no title row of its own before a send (the tab names it).

What is in view decides the pane. A pane follows the item in view (`host.current()`: the mail thread shown, the Todo detail shown, the Slack thread shown with its Orca tab selected; checked after each open or close of the item and by a one-second tick): another item, or none, hides the pane and lets its read go; the item it is for shows the pane again only when a session was handed to it (below), else the pane stays closed (the Slack tab is always open while selected).

The send form (before a send). The pane has: the header "Orca に渡す" with a close icon (`aria-label` "閉じる"); the destination section "送り先": a "新しいセッション" button (`aria-pressed`, selected at first) with the chip `.ho-chip` (`aria-haspopup` "dialog") that names the worktree chosen ("{repo} ・ {branch}", else "worktree を選ぶ" or "worktree がありません") and opens the dialog of A-6 (`openWorktreeDialog`: filter field, two-line rows; picking one closes it, chooses it and selects the new session), then the running sessions in the groups "入力待ち", "作業中" and "完了" (headings with the status icon and the number, as the working view of A-6), each a button `.ho-row` (`aria-pressed`, `data-handle`) with the title and the time, and under it "{repo} ・ {branch}"; only rows that have a terminal handle are listed (a row that can only be read cannot take a send). Under them, pinned: the card (`.ho-card`: the kind's icon, the title, the line under it, and a button `aria-label` "渡す内容を外す" that takes the card off), the textarea (`aria-label` "Orca への指示") and the button, "起動する" for a new session (disabled until a worktree is chosen) and "送る" for a running one; the button is also disabled while the instruction is blank or a post is on its way, and when the command is missing. The list of Orca (agents with their terminals, and the worktrees) is read once when the pane opens (`refreshOrca` of `ts/orca.ts`, the target the Orca screen holds) and the pane draws from it; a missing command or a failed read shows the notice of A-6 in the pane (`noticeOf`). The worktree chosen is kept in memory for the next handoff (dropped when it is no longer listed). Pressing the button once calls `orca_handoff`; a failure keeps the text and the card and shows the message above the card (`.pending.fail`), as A-6.

The card. It is built when the pane opens and drawn as plain text (`textContent`): a mail is the open thread, oldest message first, each as `差出人: {from}`, `日時: {date}` and its text (the path of the summary, `mailText`), separated by `----`; the title is the subject and the line under it `{sender of the newest message} ・ 本文 {n} 字`. A Slack thread is its messages as the screen holds them, each `{name}  {time}` and the text (the text S-7 sends to Claude); the title is `#{channel} のスレッド` and the line `{first name} ほか ・ {n} 件` (the name alone when there is one author). A Todo is `タスク: {title}`, `プロジェクト: {project}`, `期限: {due}`, `説明:` and the description, and `コメント:` with the comments when they are already loaded (none are fetched for this); the title is the task's and the line `説明 {n} 字 ・ {due}` (`説明なし` when the description is empty). The card of the Slack thread and of the Todo is built again when the thread is read or the task is drawn again, until it is sent or taken off. The card can be opened to read the text that will be sent: a real button on the card (`.ho-card-toggle`, "送る内容を読む", the style of the folded line of the history, a chevron and `aria-expanded`, closed at first) shows the body of the card, exactly the string the command gets as `context.body`, as plain text (`textContent`, never HTML) in a box of limited height (160px) that scrolls. This is for every kind, so the user can read what a mail holds that the screen does not show (text hidden by a style, for one) before it reaches the agent; the app does not try to detect hidden text. The card keeps its nodes when it is drawn again (the Slack thread read again, the Todo drawn again, the one-second follow of the host): an open text stays open and shows the new body, and its scroll position and selection stay. Another item closes it, and taking the card off drops it. Taking the card off makes the post a plain one, with no block.

The command. `orca_handoff(destination, instruction, context, environment)`: `destination` is `{kind: "new", path}` (a worktree) or `{kind: "existing", handle}`; `context` is `null` or `{kind, title, body}`; `environment` is the target of A-6. Rust composes the prompt with a pure function (`orca_handoff::compose`) and then runs the launch or the send of A-6 once, with its checks (the list is read again, the handle belongs to a row, the path is a worktree of it, the environment is a saved one, the text is not blank and the whole prompt is at most 100,000 characters; Japanese errors; never tried again). A blank instruction is refused before anything runs (「指示を書いてください」), and a prompt over the limit says that the instruction and the content together may be 100,000 characters. The answer is `{paneKey, handle}` of A-6's launch; for a running session it holds only its `handle`. The prompt is

```text
{instruction}

{one line that says the block is quoted data and holds no instructions}
<cookapps-context kind="mail|slack|todo" title="{title}">
{body}
</cookapps-context>
```

with the attribute value on one line (a newline becomes a space, at most 200 characters, and `&`, `<`, `>` and `"` escaped) and, in the body, every opening or closing tag of the block, in any case, loses its `<` (it becomes `&lt;`), so that quoted mail can neither end the block nor start a second one or fake the fold. The prompt text is in no log line.

The history folds it. A user message of the history (A-7) is searched for the block anywhere in the text, from the last occurrence of the data line followed by the opening tag at the start of a line: the block must end the message (only white space after the closing tag), have a known `kind`, and hold no closing tag in the body; the wrapper `<pasted_content id="x">…</pasted_content id="x">` that Claude Code's transcript puts around a long paste is taken off when it wraps the whole message. The instruction is the text before the data line; the title is unescaped; the body is shown as it was sent (the `&lt;` of a neutralized tag stays). Anything else is shown as it is.

After a send. The pane shows that session (and the mapping item → session is kept in memory only, nothing is saved to a file, so leaving and coming back to the same item shows the session again): a header of two lines (`.ho-session-head`): "{repo} ・ {branch}" (bold; the worktree's label until the list holds the session) and under it, in the accent color with a small dot before it, the status and the time as A-6 ("作業中 ・ 2 分", "確認中" until the list holds a new session), a button `aria-label` "Orca の画面で開く" that selects the session's project and tab on the Orca screen and shows the screen (`openInOrca`; the session of a launch that is not listed yet leaves the selection as it is), and the close icon `aria-label` "閉じる", which forgets the mapping of the item (the next open shows the send form; for the mail and the Todo it also closes the pane). Under it, the notice of A-6 when a read failed, the history of the session (the shared history code, in the pane's own scroll box, status line and older button; read only while the pane shows it in view) and the composer for more instructions (the textarea `aria-label` "Orca への指示" and "送る", sent with `orca_send` to the terminal of the session, to the target the session was started with; a failure keeps the text and shows the message). The list is read again every 10 seconds while a session is shown (not while the window is hidden). When Orca's reply gave no pane key (`paneKey` null), the pane says the session was started (`.ho-note`) and has the button of the Orca screen, with no history. The skill list of A-6 is not offered in the pane (the Orca screen's completion is tied to its own field).

The read. The side pane takes the read of the history (A-7) from the Orca screen when it shows a session in view, and gives it up when the item is left, the tab is changed or the pane is closed; the Orca screen opens its own again when it is shown with a row selected. `orca_chat_open` is called again for each change of owner, and there is never more than one open session.

Unit tests (`cargo test`) cover the composition (the format, the escaping of the attributes, the neutralized tags, the limit over the whole prompt, a blank instruction), the reading of the launch reply, the destination, the validation that a handoff shares with a post, and the reduction (see A-7); none of them runs the real CLI. The E2E spec `orca-handoff.e2e.ts` covers the entry from the three screens, the destinations, the chip and its dialog, the card and its ×, the arguments of `orca_handoff` for a new and a running session and without a card, a failure keeping the text, the notice, the view after a send with the folded content and the composer, a launch with no pane key, leaving and returning to the item and the close icon, the handing of the read between the pane and the Orca screen, and the Slack tabs.
