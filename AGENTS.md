# cookapps

cookapps is a personal desktop client for Gmail.
It also shows Google Calendar, Todoist, Slack and Orca, and it has a local MCP server.
It is built with Tauri v2 and Rust.

This file is the developer guide.
User-facing text is in `README.md` and `docs/`.

## Scope

- The only user is the owner.
- Only Gmail accounts are supported.
- Other mail providers (generic IMAP, Outlook and so on) are out of scope.
- Calendar, Todoist, Slack and Orca are integrations around the mail client.
- The app updates itself on macOS (Apple Silicon) only.
- Notion is a planned integration.

### Out of scope

- Saving drafts of mail (a mail is written and sent in one go)
- Creating, editing and deleting events
- Any other feature of a full-featured mail client

## Technical constraints

- Gmail and Google Calendar are accessed with OAuth 2.0, using the desktop-app flow: loopback redirect with PKCE.
- The Gmail scope is `gmail.modify`.
  - It is enough to trash and archive.
  - A permanent delete (one that skips the trash) needs `https://mail.google.com/`.
- The Calendar scope is `calendar.readonly`.
- A mail is sent with `users.messages.send` (`mail_send.rs`; a new mail and a reply), which `gmail.modify` is enough for: Google's reference for the method lists `https://mail.google.com/`, `gmail.modify`, `gmail.compose` and `gmail.send` as the scopes it accepts (https://developers.google.com/workspace/gmail/api/reference/rest/v1/users.messages/send, read 2026-11-14), so no new scope is asked for and no account must log in again. The request is `{raw, threadId}`, with `raw` the RFC 5322 message in base64url (https://developers.google.com/workspace/gmail/api/guides/sending). A reply is put in its thread only when `threadId` is given, `In-Reply-To` and `References` are set as RFC 2822 says and the subject matches (https://developers.google.com/workspace/gmail/api/guides/threads), so Rust reads the Message-ID and References of the thread's last message that is not a draft (`threads.get`, `format=metadata`) and refuses a Message-ID that is not one well-formed `<id>`. Before anything is sent Rust checks each recipient as one plain ASCII `addr` or `Name <addr>`, and refuses a CR, LF or other control character in a recipient, the subject or the sender, so that no header can be injected. A subject or a name that is not ASCII is sent as RFC 2047 encoded-words, and the plain-text body as UTF-8 base64 with CRLF line ends. A rate-limited or 401 send is sent again (Gmail did not process it), and an answer that is lost is not, so a mail is never sent twice by the app. Nothing of the mail (recipients, subject, body) is kept or logged.
- A Slack workspace may also have an App-Level Token (`xapp-`, scope `connections:write`, S-16), kept in the OS keychain (service `jp.mysis.cookapps.slack-app`, user name the workspace's `team_id`) and never shown or logged. With it the app keeps a WebSocket open to Slack's Socket Mode (`apps.connections.open`, then the `wss` address of slack.com it answers) for as long as the app runs, and reads the channels whose message events arrive; the list is still read on a timer (every 5 minutes while every workspace is connected, else every 2 minutes).
- The custom emoji of a Slack workspace (S-26) are read with `emoji.list` (`emoji:read`, an optional scope) when a thread or a channel's history has a reaction, or when the emoji picker of S-25 opens, kept in memory only for an hour (`TimelineCache`) and never saved; their images are fetched by `fetch_images` as the users' icons are, only from the hosts of `icon_host_ok`.
- A reaction of a Slack message is added or taken off (S-25) with `reactions.add` and `reactions.remove` (`reactions:write`, an optional scope) by the workspace's token, only when the user presses it, or chooses an emoji in the picker, in the thread or in a channel's history; the people who gave a reaction (`users`) are read for `mine` and kept in memory only.
- Updates use `tauri-plugin-updater`. Pushing the annotated tag `v{version}`, or merging the Release PR (which makes that tag, `release.yml`), starts the `release` job, which makes `cookapps.app.tar.gz`, its `.sig` and `latest.json` (`scripts/make-latest-json.sh`) and puts them in a GitHub Release.
  The app reads `releases/latest/download/latest.json` (`plugins.updater.endpoints` in `tauri.conf.json`) and verifies the download with the public key `plugins.updater.pubkey`.
  `bundle.createUpdaterArtifacts` is not in `tauri.conf.json`; the `release` job passes it with `--config`, so a local build needs no signing key.
  The version is the tag's alone (at the owner's instruction, 2026-11-09; Discussion #293): `version` in `src-tauri/Cargo.toml` and `Cargo.lock` is fixed at `0.0.0` and `tauri.conf.json` has none, and the `release` job passes the version of the tag with `--config` too, which Info.plist, `app.package_info()` (U-2) and the updater's comparison take. A build without it (`tauri dev`, E2E) reports `0.0.0`, and `scripts/install-app.sh` passes the latest tag.
- The refresh token is stored locally so the user does not log in at every start.
- Tokens go in the OS keychain (macOS Keychain, Windows Credential Manager), never in a plain file.
- The list of accounts (email addresses only) is saved in `accounts.json` in the app config directory.
- The last weeks of the calendar, with the details of their events (place, description, Meet link and so on), are saved in `calendar-cache.json` in the same place; the first day of the week is in `calendar-settings.json`, the calendars the owner chose to show (for each account, the calendar IDs with whether each is shown; a calendar never chosen follows `selected` at Google, which is never written) are in `calendar-selection.json`, the model and effort of the eight purposes of the Claude calls are in `claude-settings.json`, the workspaces that the Slack side menu folds (S-19; team IDs only) are in `slack-side.json`, and the Orca to talk to (this machine or a saved environment) is in `orca-settings.json`. The method the Claude calls sign in with is in `claude-auth.json` there, and the Anthropic API key is in the OS keychain (service `jp.mysis.cookapps.claude`).

It was written against Orca 1.4.248 and an Orca update can change it.

- A file pasted or dropped on an Orca terminal or in the pane of A-9 (A-10) is put in `.orca/drops/` of the worktree, under its own name (a name taken gets `name copy.ext`, `name copy 2.ext`, as Orca 1.4.253 does; a name with a path separator, a control or bidirectional formatting character, or over 255 bytes, is refused), through `files.stat`, `files.readDir`, `files.writeBase64Chunk`, `files.commitUpload` and `files.delete` of Orca's runtime (this machine's unix socket, a paired server's WebSocket), which are not a public interface. It was written against Orca 1.4.248 (the names and the typed text follow Orca 1.4.253), and an Orca update can change it. The file is held in memory only, and the window's own file drop is off (`dragDropEnabled` false) so that the page gets the dropped files.
- A plain terminal started from the plus of the Orca work pane (A-16) is made by Orca's CLI, `orca terminal create --worktree path:<path> --json` (`--environment=<name>` for a saved environment), run once, in a worktree of the list read just before, with an argument list and a timeout; its reply `result.terminal.handle` names the terminal. It was checked on Orca 1.4.250 (its help and its CLI source), and an Orca update can change it.
- A new worktree for the hand-over of A-9 is made by Orca's CLI, `orca worktree create --repo=id:<repository id> --name=<name> [--branch=<branch>] [--base-branch=<ref>] --no-parent --json` (`--environment=<name>` for a saved environment; `--branch` and `--base-branch` only when `orca_worktree_create` was given a branch or a base), run once, in the temporary folder, with an argument list and a timeout of 60 seconds; its reply `result.worktree.path` is the new worktree's absolute path. Just before, Rust checks that the environment is a saved one, that the repository id is a project of the list read just now (an `ssh:` host and an archived-only repository are not), and that the name, trimmed, is not empty, does not start with `-`, is not `.` or `..` and has no control character, `/` or `\`, and that the branch and the base, when given, are, trimmed (a blank one is none), a name git accepts as a ref (`git check-ref-format`: they do not start with `-`, hold no space, control character, zero-width, bidirectional or tag character (the ones `orca_handoff` takes out of a card) or `~ ^ : ? * [ \`, no `..` or `@{`, are not `@`, and have no component that is empty, starts with `.` or ends with `.lock`, nor a `/` or `.` at the end); nothing is made otherwise. The repository id is `OrcaProject.key` (`repoId` of `orca worktree ps`), so `--repo=id:` is used and not `--project`, which takes a project id or a display name. `--no-parent` is passed because the CLI otherwise records the context it can infer (`ORCA_TERMINAL_HANDLE` of the environment) as the parent. It was checked on Orca 1.4.255 by its help and its CLI source in `app.asar` (`handlers/worktree.js`, `worktree-project-target.js`) and by the shape of `orca worktree show --json`; the command itself was never run, so the exact reply of `worktree create` (`result.worktree.path`), its behavior on a saved environment, what it does with `--branch` when the branch already exists (reading the `app.asar` of Orca 1.4.256 suggests that it checks that branch out and makes no numbered new one; it was never run) and with `--base-branch`, the time it takes on a large repository and the answer of a repository whose setup policy is undecided (the CLI asks for `--setup`) were not checked, and an Orca update can change them.
- How the Orca work pane is split into panes (A-17) is saved for each project of each target in `orca-panes.json` in the app config directory: a tree of panes and splits that holds only tab ids (`claude:{pane key}`, `orca:{handle}`, `file:{n}` for a file open in the editor of A-18) and project keys of Orca, mended against the tabs Orca lists at each read, never holding what a terminal printed or was typed.
- The files of a worktree on the Orca screen (A-18) are read and saved through `files.readDir`, `files.read`, `files.writeIfUnchanged` and `git.checkIgnored` of Orca's runtime (this machine's unix socket, a paired server's WebSocket, the connection of A-10), which are not a public interface. They were read in the `app.asar` of Orca 1.4.253 and tried on this machine's Orca (a saved environment was not tried), and an Orca update can change them. A file is written only when the disk still holds the text that was read, by Orca's own signature of it, so a file changed elsewhere is never overwritten; only text of at most 384 KiB that is UTF-8 and has one kind of line end is opened. The text of a file is held in memory only and is in no log or file of the app. The reads of a folder, of its ignore marks (`git.checkIgnored`, asked after the list is drawn) and of a file believe a worktree that was confirmed against `orca worktree ps` for 60 seconds, in memory only and for the exact path of one target, so a folder read starts no CLI; a save and a download ask the list each time. The time of the automatic save is in `editor-settings.json` in the app config directory.
- The difference of a file from HEAD on the Orca screen (A-24) is read through `git.diff` of Orca's runtime (this machine's unix socket, a paired server's WebSocket, the connection of A-10), with `staged` false and `compareAgainstHead` true, which is not a public interface. It was read in the `app.asar` of Orca 1.4.255 (`git-params.js`, the handler of `git.diff`) and not yet tried on a saved environment, and an Orca update can change it. Rust compares the two texts by lines (`orca_diff.rs`, Myers' algorithm of the `similar` crate, with a deadline of 2 seconds), only for text of at most 384 KiB a side that is UTF-8; a binary file, a diff Orca marks as too large, and over a paired server a diff over about 4 MiB (`diff_too_large`) are refused with a reason. The texts are held in memory only and are in no log and no file of the app.
- The branches of a worktree on the Orca screen are read through `git.localBranches` (`{worktree}`, answered `{current, branches, committedAt, worktreePaths}`) and `repo.searchRefs` (`{repo, query, limit: 50, namespace: "remote"}`, answered `{refDetails: [{refName, localBranchName}], refs, truncated}`) of Orca's runtime (this machine's unix socket, a paired server's WebSocket, the connection of A-10), which are not a public interface. They are the calls of the branch picker of Orca 1.4.255's renderer, were read again in the `app.asar` of Orca 1.4.256 and tried on this machine's Orca 1.4.256 over its unix socket (a saved environment was not tried, and the old shape of `repo.searchRefs` with `refs` alone was not seen on a real Orca), and an Orca update can change them. The worktree is believed as for the files above (`orca worktree ps`, 60 seconds, an SSH host refused), `repo` is the `OrcaProject.key` of the worktree and is sent as `id:{key}`, and the branch names are held in memory only and are in no log and no file of the app. The branch of a worktree is switched through `git.switchBranch` (`{worktree, target: {kind, name}, expectedExecutionHostId}`, `kind` `local` or `remote` only, never `new`, which makes a branch; answered `{ok, branch, head}` with `warning` when the switch worked but a later step failed, as a success; a refusal comes as an error whose message is Orca's own words and is shown as it is, cut at 200 characters). Its handler was read in the `app.asar` of Orca 1.4.256 (`out/main/index.js`, `agent-session-operation-ledger-*.js` of `app.asar.unpacked`) and the call was never run on a real Orca, because it changes a worktree. Orca refuses it for changes not committed, a merge or rebase in progress, a running git action or an agent at work, and an Orca without the method answers `method_not_found` (then the owner is asked to update Orca). Being a write, it reads the target's list each time, as a save does, and throws away what was believed of the worktree after it, whatever it answered.
- The history of a worktree on the Orca screen (A-27) is read through `git.history` (`{worktree, refs: "head", limit, skip, historyToken}`, `limit` 1 to 200, answered `{items: [{id, displayId, subject, message, author, timestamp, parentIds}], hasMore, historyToken, historyChanged}`, the commits reachable from HEAD, the newest first; the first read has no `historyToken` and Orca answers one, a UUID it keeps for 15 minutes of idleness, and the next reads send it back with `skip`, so that they read the history the first page began even if HEAD moved (`historyChanged` true and no item when Orca no longer holds it, then the list is read again from the start); Orca still walks `skip` commits for each page, as the token is no cursor; read in the `shared/git/history/` and `rpc-contract/git-params.js` of Orca 1.4.258's `app.asar`, and the token was not tried on a real Orca), `git.commitCompare` (`{worktree, commitId}`, answered `{summary: {status, parentOid, changedFiles, errorMessage}, entries: [{path, status, oldPath, added, removed}]}`, the files a commit changed against its first parent) and `git.commitDiff` (`{worktree, commitOid, filePath, parentOid, oldPath}`, answered in the shape of `git.diff`: the text at the parent and at the commit) of Orca's runtime (this machine's unix socket, a paired server's WebSocket, the connection of A-10), which are not a public interface. The three reads were called on this machine's Orca 1.4.258 over its unix socket and the shape of each answer was checked there; a saved environment was not tried, and an Orca update can change them. `git.commitDiff` can answer a failure of git on Orca's side with empty texts and no error, so Rust cannot tell a commit Orca could not read from an empty file. The worktree is believed as for the files above (`orca worktree ps`, 60 seconds, an SSH host refused), and the commit ids sent are full object ids that Rust checked. The subjects, authors, paths and texts are held in memory only and are in no log and no file of the app, and nothing here writes to the worktree. The choice between the files and the history is held in memory only (no file).
- A file of a worktree on the Orca screen is copied to this PC (A-22) through `files.stat`, `files.readChunk` (and, on a host that lacks either, `files.readPreview`, by which a text file comes back as a UTF-8 string, so a text that is not UTF-8 is not the same bytes) of Orca's runtime (this machine's unix socket, a paired server's WebSocket, the connection of A-10), which are not a public interface. They were tried on Orca 1.4.254 on this machine's unix socket (a saved environment was not tried), and an Orca update can change them. The file is read 384 KiB at a time, never past the size `files.stat` gave, and written to a new temporary file beside the destination (`create_new`, a taken name is not used), which is renamed onto it when every byte has come; the copy has no `com.apple.quarantine` attribute. The destination is only the place picked in the save dialog (`tauri-plugin-dialog`, opened by Rust; the page sends no path and has no permission of the plugin). The bytes of the file are in no log and no file of the app other than the copy.
- The editor of A-18 colors a file by its language (A-21) with highlight.js, vendored in `src/vendor/` and loading nothing from outside.   - The login is PKCE S256 with a loopback redirect, served by the listener that Google's login uses (`auth.rs`). Notion takes any port on `127.0.0.1` for the registered redirect and the path must be the registered one (tried on 2026-11-14 by `GET /authorize`); the code is exchanged at `/token`, which also revokes (RFC 7009; a revoke of a made-up token answered 200).
  - The tokens are in the OS keychain, service `jp.mysis.cookapps.notion`, user name the workspace's id, as one JSON entry (access token, refresh token, expiry) so that a new pair replaces the old in one write. They are never shown, logged or kept in a file, and `cookapps-mcp` does not read them, so nothing else refreshes them. One token is one workspace, so each workspace is connected on its own.
  - The access token lasts 8 hours; it is refreshed 5 minutes before its end and when a call is refused with 401. The refresh token changes at every refresh and an old one used again ends the connection, so a workspace refreshes one at a time and the new pair is written to the keychain before the access token is used. A refresh answered `invalid_grant` (180 days after the first consent at the latest, or 30 days unused) deletes the keychain entry and leaves the workspace in the list with `reconnect` true; any other failure keeps the tokens.
  - A call is Streamable HTTP: `initialize`, the `notifications/initialized` notice, then `tools/call`; the reply is JSON or a server-sent event stream. The token holds the user's full rights (77 tools, deletion included), so `ALLOWED_TOOLS` in `notion.rs` is the only list of tools the app calls, and it holds `notion-get-self` alone for now. Notion's limit is 180 requests a minute (600 on Business and above).
  - Not tried against a real login by this code, so a Notion update or the first real connection can show a difference: the `workspace_id` and `workspace_name` of the token reply, the shape of the text of `notion-get-self` (`user_of` reads `name` and `email` or `person.email`, at the top or under `user`), and the session id header of the reply to `initialize`.
- If the OAuth consent screen is "External" and in "Testing", refresh tokens expire after 7 days.
  - Use an "Internal" consent screen, or publish an "External" one.

## Stack and layout

```text
ts/            TypeScript, compiled by tsc to src/js/ (gitignored). No framework, no bundler
ts/bindings/   Rust struct types written by ts-rs (generated, committed)
src/           index.html, CSS, vendored libraries (src/vendor/)
src-tauri/     Rust backend (Tauri v2); src/bin/cookapps-mcp.rs is the MCP server
e2e/           WebdriverIO specs, fixtures and mocks
scripts/       check-version.sh, install-app.sh, make-latest-json.sh, build-milkdown.mjs and milkdown-entry.js (bundle src/vendor/milkdown.js)
docs/          public documentation (GitHub Pages)
requirements/  the requirements, one file per area
tmp/           scratch files, gitignored except .keep
```

- The frontend is plain TypeScript, HTML and CSS.
  `ts/` is split into one module per screen.
  The screens show no help text: no placeholder or line of text that explains what to type or what a button does (at the owner's instruction, 2026-11-08). The rule is in `.claude/rules/frontend.md`.
- The backend is Rust.
  Each service has its own module: `gmail.rs`, `calendar.rs`, `todoist.rs`, `notion.rs` (Notion's MCP server: the OAuth connection and the tokens), `slack.rs` (with `slack_markdown.rs`, which turns Markdown into Slack's mrkdwn, S-6 and S-21, `slack_mrkdwn.rs`, which reads Slack's mrkdwn as the structure the thread draws, S-12, `slack_blocks.rs`, which reads a message's blocks and attachments, S-11, `slack_emoji.rs`, the table of Slack emoji names that the `emojis` crate lacks, and `slack/socket.rs`, the Socket Mode connection, S-16), `claude.rs` (with `claude_auth.rs`, how `claude -p` is signed in, A-4), `orca.rs` (with `orca_link.rs` and `orca_e2ee.rs` for the connection to Orca's runtime, `orca_handoff.rs` for the prompt of A-9, `orca_attach.rs` for the files of A-10, and `orca_stream.rs` for the stream of A-12, `orca_panes.rs` for the split panes of A-17, `orca_files.rs` for the file pane and the editor of A-18, the download of A-22, the reading of the diff of A-24, the reading and the switch of the branches of a worktree, and the commits of a worktree, the files of a commit and the diff of one of them (A-27), `orca_diff.rs` for the comparison of A-24, `orca_language.rs` for the language of an open file, A-21), `fonts.rs` (the fonts by screen, A-20), `app_log.rs` (the app's log, A-28), `skills.rs` (the skills of the Claude calls, saved as `SKILL.md` files in `claude-plugin/` of the config directory), `ghostty.rs` (Ghostty's settings for the Orca terminals, A-13), `orca_theme.rs` (the colors of the Orca terminals, A-14, with the table `orca_themes.json`).
  The modules shared by the services are `accounts.rs` (the list of accounts in `accounts.json`, and the atomic write of a settings file), `auth.rs` (the OAuth login, the tokens and the keychain), `mail_address.rs` (splits a From or To header into a name and an address), `mail_send.rs` (builds the message of a new mail or a reply and sends it with `users.messages.send`, the command `send_mail`), `images.rs` (the images in HTML mail, with `images/macos.rs`, which fetches an external image with NSURLSession) with `image_senders.rs` (the senders whose external images are shown without asking), `disk_cache.rs` (the kept copies of the last mail list, calendar weeks and Todo that the screen draws first at startup), `markdown_patch.rs` (puts an edit of the rich Markdown editor into the original text by lines, A-26) and `update.rs` (the self-update and its settings, U-1 and U-2).
  The modules are in the library crate (`src-tauri/src/lib.rs`), and `main.rs` only calls `cookapps_lib::run()`.
- Internal functions take the config directory (`&Path`), not an `AppHandle`, so `cookapps-mcp` can share them.
- The Rust version is pinned in `rust-toolchain.toml` and in the CI workflows (`release.yml` and `rust-cache.yml`, by the ref of `dtolnay/rust-toolchain`). Keep them equal.
- `.cargo/config.toml` sets `MACOSX_DEPLOYMENT_TARGET` to the value `tauri build` takes from `bundle.macOS.minimumSystemVersion` (default 10.13), so `tauri dev`, clippy and `cargo test` share the dependency builds of the E2E and release builds instead of rebuilding them. Keep the two equal.

## Run

Install the Rust version in `rust-toolchain.toml`.

```sh
npm install
npx tauri dev
```

At the first start, press "Log in with Google" and the default browser opens.
Add more accounts from "Add account" in the Google tab of the settings screen.

### OAuth client JSON

1. In a Google Cloud project, enable the Gmail API and the Google Calendar API.
2. Configure the OAuth consent screen.
3. Create an OAuth client of type "Desktop app".
4. Download its JSON and save it as `client_secret.json` in the Tauri `app_config_dir`.
   - The format is `{"installed":{"client_id":"...","client_secret":"..."}}`.
   - If the file is missing, the login screen shows an error with the absolute path to put it in.

### MCP server

`cookapps-mcp` reads the same `client_secret.json`, `accounts.json` and keychain entries as the app, and it never logs in.
Install it with `cargo install --path src-tauri --bin cookapps-mcp --locked`.
The setup is in `docs/mcp.md`.
The tools are `list_inbox`, `get_thread` and `list_events` (read), and `archive`, `set_read` and `trash` (write).

## Tests

There are three layers: static, unit and E2E.
No check is repeated in two layers.

| Layer | What it checks | Tools | What it does not check |
|-------|----------------|-------|------------------------|
| Static | Format, lint, types, Rust-TS type match, fixed source version | cargo fmt, clippy, Biome (lint only), tsc, bindings diff, `scripts/check-version.sh` | Behavior |
| Unit | Pure Rust logic (parsing API responses, validating input, computing dates, IDs and URLs, converting errors) | cargo test | Screens, WebView |
| E2E | Screen behavior (how command results are drawn, the commands and arguments an operation calls, how errors show) | WebdriverIO (real WKWebView, commands mocked) | Processing inside Rust |

- Frontend TS holds only drawing and operation. Logic that needs a test is a pure Rust function.
- Tests never touch a real external service, the keychain or the real config folder.
  E2E builds use a separate identifier and an in-memory keyring.
- E2E mocks live only in `e2e/`.
- Each E2E run starts one app for each of its capabilities and gives each a free WebDriver port, so runs from the main checkout and from the worktree can overlap.

```sh
npm run lint        # Biome (lint only)
npm run build:ts    # tsc (ts)
npm run e2e:check   # tsc (e2e)
npx tsc --noEmit -p .claude/skills/readme-product/shots/tsconfig.json   # tsc (the spec of the README photos)
cd src-tauri && cargo fmt --check
cd src-tauri && cargo clippy --all-targets --all-features -- -D warnings
cd src-tauri && cargo test --all-features    # also writes the ts-rs types to ts/bindings/
npm run e2e:build   # build the app for E2E (feature e2e)
npm run e2e         # WebdriverIO
scripts/check-version.sh   # the source version is the fixed one: 0.0.0 in Cargo.toml and Cargo.lock, none in tauri.conf.json
```

`.claude/tools/run-ci.sh` runs the static checks and unit tests above (all but the E2E two) on a clean working tree and writes a record for HEAD, and `.claude/tools/run-e2e.sh` does the same for E2E, and runs `run-ci.sh` beside its wdio run after `e2e:build` when HEAD has no passing CI record.
Before a push, `pre-git.sh` only checks that both records exist for HEAD.

## CI

The release is `.github/workflows/release.yml`, and only a pushed tag `v*` and the owner's merge of the Release PR (a closed pull request from `release/next` into main, merged by the repository's owner) start it (at the owner's instruction, 2026-11-09; #303).
Static, unit and E2E checks run on the developer's machine before a push (`run-ci.sh` and `run-e2e.sh`, with a record for each HEAD that `pre-git.sh` checks), not in GitHub Actions, so a pull request runs no check of this repository: closing one starts `release.yml`, which does nothing unless it is the merged Release PR.
A push to main that changes the dependencies, the Rust version or `docs/` runs two workflows, and neither checks anything: `rust-cache.yml` builds the Rust dependencies of the release to fill the cache that `release` restores (at the owner's instruction, 2026-11-08; #248), and `pages.yml` builds `docs/` with Jekyll and deploys it to GitHub Pages.
A change reaches main through a pull request, and the machine that ran the checks sends their results as the commit statuses `e2e` and `review`.
A release is the owner's merge of the Release PR, the pull request that writes the new version at the top of `CHANGELOG.md` (an agent prepares it, `.claude/rules/issues.md`), which `release.yml` tags and releases at once, in the run that the merge starts; the next agent to act watches that run through (an agent tags by hand only when the workflow did not, `.claude/rules/issues.md`).

| Job | Environment | What it does |
|-----|-------------|--------------|
| `tag` | ubuntu-latest | on a pushed tag `v*`, and on a pull request from `release/next` of this repository that was merged into main (any other closed pull request and every fork ends here), reads the tag (the pushed one, or the first `## v{version}` heading of `CHANGELOG.md` at the merge commit), checks that the source version is still the fixed one, that the tag has the form `v0.{minor}.{patch}` and is that heading, and that the commit is on main, then for a merge pushes the annotated tag on the merge commit with `GITHUB_TOKEN` (`contents: write`, and `actions: read` to list the runs). A tag that already has a run of a push (made by hand) is not tagged again and the merge run builds nothing; a tag already on the merge commit with no such run is the job's own from an earlier attempt, and the build goes on. A tag pushed with `GITHUB_TOKEN` starts no workflow, so the next job follows in the same run |
| `release` | macos-latest | needs `tag`; restores the Rust cache (`Swatinem/rust-cache`, `shared-key: release`, `prefix-key: v1-rust`, never saves), then builds the app with the version of the tag (`--config`) and puts the signed `.app`, its updater files and `latest.json` in a GitHub Release. The secrets are `APPLE_CERTIFICATE`, `APPLE_CERTIFICATE_PASSWORD`, `APPLE_SIGNING_IDENTITY`, `TAURI_SIGNING_PRIVATE_KEY` and `TAURI_SIGNING_PRIVATE_KEY_PASSWORD` |
| `cache` (`rust-cache.yml`) | macos-latest | on a push to main that changes `src-tauri/Cargo.toml`, `src-tauri/Cargo.lock`, `rust-toolchain.toml`, `.cargo/config.toml` (part of the cache key) or one of the two workflow files, on a schedule (Monday and Thursday 18:17 UTC) and by hand, restores the cache with the same toolchain, toolchain clean-up and `rust-cache` settings as `release`; unless that is an exact hit it runs `npx tauri build --no-bundle` and saves the cache. It holds no secret |
| `build` and `deploy` (`pages.yml`) | ubuntu-24.04 | on a push to main that changes `docs/`, builds it with `actions/jekyll-build-pages` and deploys it with `actions/deploy-pages`. It needs the Pages source set to "GitHub Actions" (`build_type: workflow`) |

A tag run or a merge run reads only the caches of its own ref and of the default branch, and a tag's own cache cannot be read by the next tag, so the cache is made on main and `release` only restores it.
GitHub evicts a cache that no run has used for 7 days, so `rust-cache.yml` also runs on a schedule; it restores the cache for real (not `lookup-only`), because GitHub's documentation does not say that a lookup counts as use.
The cache is restored into the signed release, so when a dependency or action that ran on main is found compromised and reverted, delete the caches of main (`gh cache delete --all`) and raise `prefix-key` in both workflows, because a restored cache would carry its output into the build.

## Known limitations

- The access token expiry is not tracked. On a 401, the token is refreshed and the request is retried (also in the middle of `threads.get`).
- On a rate limit (429 or 403 `rateLimitExceeded`), interactive operations retry up to 2 times (they follow `Retry-After`, capped at 30 seconds).
  Auto sync does not retry. It backs off per account (`SyncState`).
- There is no coverage tool.
- CI releases macOS only. Windows is not built or released, and it has not been checked on a real Windows machine.
